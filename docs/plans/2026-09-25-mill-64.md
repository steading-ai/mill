# A drain stops claiming and releases each run at its next step boundary, with no aborted attempt

## Approach

Today `SIGTERM` reaches a run through `internal/run/heartbeat.go`'s select
loop: the `<-s.stopping` case fires `h.fail(errShutdown)` the instant the
worker is asked to stop, which cancels the step's context mid-attempt exactly
like a kill does. `walk.go`'s `stopped()` then routes that into
`shutdownStep`, which calls `AbortOpenStepRuns` — the current attempt is
always left `aborted`, whether it was one line into a session or one commit
from closing. That is the bug: a graceful stop and a kill are the same code
path, and the "no aborted attempt" half of this work order's title is false
of every stop today.

The fix has two independent halves that must land together:

1. **Stop no longer aborts.** The heartbeat's job becomes renewing the lease
   and reading `cancel_requested`, nothing else; `<-s.stopping` is dropped
   from its select entirely. Nothing in the heartbeat cancels a step because
   the process was asked to stop.
2. **The walk loop itself decides when to leave.** `walk()` already re-derives
   `current_step` from the ledger every pass (Invariant 10) before deciding
   whether to run it. A drain adds one more check at that same point, before
   `stepUnderBoundary` is called: if the worker is draining *and* the step
   about to run has no `StepRun` of its own yet in `detail.GetSteps()`,
   release the lease and return instead of starting it. This is a per-step
   check, not a per-session one: the repository's own workflows
   (`workflows/feature/workflow.yaml`, `workflows/quick-fix/workflow.yaml`)
   give the same `session` name to many distinct steps (`session: implement`
   names seven separate steps in `feature`), so a check phrased as "has this
   session started" — which scans every step sharing that session id — would
   report "started" for all seven the moment the first of them opens, and a
   drain gated on it would sit through the rest of the run instead of
   releasing at the very next boundary. Whether *this* step
   (`step.GetName()`), specifically, has a row in `detail` already is what
   "boundary" actually has to mean.

This is what makes a stop a boundary release rather than a poll of "am I
between steps": a step already attempted at least once (a retry continuing
the same session, or a revise that has moved `current_step` backward onto a
step with a prior `StepRun` row) is never interrupted, because that row
already exists in `detail` and the drain check does not fire for it — the
run's own retry and revise semantics are untouched, and so is the feedback
`walk()` threads between attempts only in memory (`feedback`/`feedbackFrom`,
carried across the loop's own iterations, never re-derived from the ledger):
a drain landing between a failed attempt and its retry, or between a revise
decision and its target's new attempt, would otherwise drop that feedback
silently, and the per-step check rules it out because a retry or revise
target always has a prior row. A step with no `StepRun` of its own yet —
including the very next step after the one that just closed — is exactly
where "no attempt aborted" and "released at the boundary" both hold at once:
nothing has been written for it yet, so there is nothing to abort, only a
lease to give back.

Removing the heartbeat's abort-on-stop case exposes one gap the work order's
own framing does not mention: today, a step's context reaching
`stepCtx.Done()` with no reason ever set cannot happen, because the
`<-s.stopping` case always primes `h.reason` first. Once that case is gone,
a *kill* (a second signal, or the grace window elapsing, cancelling the
process's outer context, which is `stepCtx`'s parent) still needs to resolve
to `errShutdown` — that is what `walk.go`'s `stopped()` reads to call
`shutdownStep` and abort the in-flight attempt, and what `run.go`'s
`r.stop()` reads as the reason to release with, instead of falling through to
its `RELEASE_REASON_CRASH` fallback for a bare `context.Canceled`. Left
unfixed, "a second SIGTERM during a drain aborts the run... reason
shutdown" (an acceptance criterion this node keeps) would silently break the
moment the `stopping` case is removed. The fix is a `clean atomic.Bool` on
`heartbeat`, set before `stop()` cancels its context; the `stepCtx.Done()`
case now calls `h.fail(errShutdown)` itself, but only when `!clean` — a
clean `stop()` leaves `h.err()` nil as it does today, and an unclean
cancellation (a kill) still resolves to shutdown.

The remaining deliverables build on those two: worker-level drain state and
an enriched in-flight list for `Probe`; a `Drain` RPC and `mill drain` CLI/MCP
surface so an operator can ask a *remote* worker to drain, not only send it a
signal; the reclaim criterion widened to admit *either* shape a worker can
leave a run in — "last attempt aborted" (a kill; unchanged, since neither
`AbortOpenStepRuns` nor `shutdownStep` clears `runs.lease_id`, only the skift
lease) *or* "this worker's own run with no lease" (a boundary release, which
aborts nothing) — so mill#44's kill-path reclaim keeps working exactly as it
does today and a drain-left run reclaims the same way; and a real fix for
`serve.go` feeding `supervise` the same physical signal by two independent
paths at once — its own `signal.NotifyContext`-derived `ctx` (cancelled by
`SIGTERM`/`SIGINT`) *and* a second, separate `signals` channel from
`stopSignals()` (registered for the same two signals) — which lets one
`SIGTERM` reach `supervise` as both `ctx.Done()` and a channel receive and
skip straight to the kill path on the first signal a human sends. The fix is
to give `supervise` only one of the two: `cmd.Context()` — a plain context,
never wrapped in `signal.NotifyContext` — in place of `ctx`, the same call
`mill work`'s own, already-correct call to `supervise` already makes today.

**Rejected: poll `s.stopping` inside `stepUnderBoundary`'s per-step-slice
callback (`docs/sandbox.md`'s "step boundary" — the file-write boundary the
workspace already batches around) instead of in `walk()`.** The workspace's
step boundary is about file writes settling into promotable slices; it fires
*inside* a running step's evidence collection and has no notion of "has this
step been attempted before," which is the actual thing that must gate a
drain. Reusing it would mean re-deriving that per-step check at a second call
site, or teaching the workspace boundary about ledger step-run state it has
no other reason to know. `walk()` already has `detail` and the step in hand
at exactly the point that decides whether to call `stepUnderBoundary` at
all; adding the check there is one predicate at one existing call site, not
two.

**Rejected: track worker state (claiming/draining/idle) and in-flight
step/time-in-step live on the `Worker` struct.** The worker today knows only
that a node is in flight (`inFlight sync.Map`, keyed by node id, storing
`struct{}`); giving it a live view of "current step, time in it" would mean
either polling the ledger from inside the worker on a timer (duplicate work
the store already tracks) or pushing per-step events up from `internal/run`
into `internal/cli`/`internal/server`, a layering `internal/run` does not
otherwise have (it drives one run and reports its outcome, nothing about a
worker's whole fleet). `Probe`'s answer instead enriches `inFlight`'s stored
value with just enough to look the rest up on demand — `RunID` and
`NodeRef` — and `WorkerService.Probe`'s handler resolves "current step, time
in it" with one `Store.Status`/`Inspect` call per in-flight run at
probe-time, the same read `mill status` already does. This trades a little
per-probe latency (bounded by concurrency, which is small by design — mill
runs a handful of nodes per worker, not thousands) for zero new bookkeeping
inside the claim loop.

6. **`internal/run/reclaim.go`: widen `Resumable` to admit both shapes a
   worker can leave a run in.**
   A graceful stop no longer leaves an `aborted` step run — step 4 made sure
   of that — so `Resumable`'s current filter
   (`summary.GetLastStepStatus() == STEP_RUN_STATUS_ABORTED`) alone would find
   nothing after a drain, defeating the "own next start reclaims before
   `ClaimNext`" half of `docs/architecture.md` §"Failure and stop" for the new
   case. But the old shape still exists and must keep working: neither
   `AbortOpenStepRuns` (the kill path) nor `shutdownStep`
   (`internal/run/shutdown.go`) clears `runs.lease_id` — only the skift lease
   is released — so a kill-aborted run is left with its step run `aborted`
   *and* `lease_id` still set. Replacing the criterion instead of widening it
   would silently stop reclaiming that shape, regressing mill#44. The
   criterion becomes an OR of both left-behind shapes, still scoped to this
   worker's own run and to `RUN_STATUS_RUNNING`/`RUN_STATUS_SELECTING` via the

   `RunSummary.Run.GetUpdatedAt()` is already on the one `Status` response

   Files: `internal/run/reclaim.go`, `internal/run/worker.go` (the one call

   Test: `internal/run/reclaim_test.go`, updated cases — a run left `aborted`

## Risks

- **`serve.go`'s other uses of `ctx` (migrations, workflow push,
  `WorkerService` construction, and the line-271 shutdown goroutine) must
  keep seeing a context that cancels on `SIGTERM`/`SIGINT`, even though
  `supervise` no longer does.** Step 8's fix touches only what `supervise`
  itself receives — `cmd.Context()` in place of `ctx` at the one call site,
  line 265 — leaving `ctx` and every other place it is read untouched.
  Confirmed by reading `serve.go` in full: no other call passes `ctx` (or
  `signals`) into `supervise`, and `supervise`'s own signature and body do
  not change, so this is a one-line, single-call-site fix with nothing else
  to keep in sync.
- **The new drain-boundary check in `walk()` must never fire for a step that
  has already been attempted, or a mid-retry step or a revise target would be
  cut off — the opposite of "no aborted attempt."** A session-based check
  (`sessionStarted`/`SessionID`, matching `execute.go`'s own `Start`/`Resume`
  decision) was considered and rejected here: this repository's own
  workflows share one `session` name across many distinct steps
  (`workflows/feature/workflow.yaml`'s `session: implement` names seven of
  them), so "has this session started" is true for the whole group the
  moment the first of them opens, not just for the step about to run — a
  drain gated on it would wait through most of a run instead of releasing at
  the next boundary. Step 4's check instead asks whether *this* step, by
  name, already has a `StepRun` row in `detail` — true for a retry or a
  revise target, false for a step never yet attempted, regardless of which
  session it or its neighbors use — and the mid-retry and shared-session
  cases in step 4's test are what prove this rather than asserting it.
- **`Probe`'s enriched in-flight list costs one `Store` lookup per in-flight
  run, per probe.** Bounded by `Concurrency`, which is small by design
  (`docs/architecture.md` §"The daemon is the loop, not a scheduler" — one
  worker drives a handful of runs, not thousands); accepted rather than
  cached, since a cached view would need its own invalidation and the whole
  point of `Probe` is answering for the worker's *current* state.
  `WorkerServiceConfig` gaining a `Store`/client dependency it does not have
  today (step 9) is the one piece of new plumbing this risks surfacing wrong
  at implementation time — the exact shape (`Store` interface subset vs. the
  concrete client `internal/cli/serve.go` already builds) is deferred to
  implementation and flagged rather than guessed here.
- **`mill drain --timeout`'s default (5 minutes, step 10) is this plan's
  choice, not the work order's.** If a workflow's steps commonly run longer
  than that between session-boundaries, an operator relying on `--wait`'s
  default would see a timeout on an otherwise-healthy drain. Mitigated by
  making it a flag, not a constant, and named as a explicit choice under
  Decisions rather than left implicit.
- **Step 1's proto additions are a wire-compatible change** (new fields, new
  RPCs, no field renumbering or removal) so `make lint-contract` /`buf
  breaking` is expected to pass with no exception needed; if implementation
  finds otherwise (e.g., `ProbeResponse`'s field numbers collide with
  something this research did not see), that is this node's cue to renumber
  before merging, not to suppress the check.

## Decisions

- **The boundary check lives in `walk()`, not in the heartbeat or in a new
  goroutine.** The heartbeat's whole job is lease renewal; folding "should
  this run leave now" into it is what causes today's bug (stop and kill
  sharing one path). `walk()` already owns the decision of what runs next
  and already re-derives it from the ledger every pass, so the drain check
  is one more condition on a decision that already exists, not a new one.
- **"Does this step already have a `StepRun` row" — not "has this step's
  session started," not "is a step attempt open," not "did the last step
  close cleanly" — is the boundary a drain respects.** A session-based check
  looked equivalent at first (`execute.go`'s own `Start`/`Resume` choice uses
  one) but is not: this repository's workflows give the same `session` name
  to several distinct steps, so "session started" is true for all of them
  once any one has opened, while "this step has a row" is true only for the
  step actually attempted. The per-step form is what lets a step's own
  retries and an `on_failure: revise` target continue uninterrupted through a
  drain (both always have a prior row) while still releasing between two
  steps that merely happen to share a session name.
- **A drained run stays `running` with `lease_id` empty, not `waiting` or
  `parked`.** Those states mean something else (a filed gate; a tripped
  circuit breaker) and both are read by other code paths (`ClearRunGate`,
  `Park`) this node has no reason to touch. `running` with no lease is a
  state nothing in the store writes today; step 2 adds the one query that
  produces it, and reclaim (step 6) is the one place that reads it looking
  for candidates — `ClaimNext`'s own `run.status in (running, selecting)`
  branch (`docs/ledger.md` §Resume) already admits it as an ordinary,
  unremarkable case for a *different* worker's `ClaimNext` to pick up, if
  this worker's own reclaim does not get to it first.
- **`Resumable`'s sort key becomes the run's own `updated_at` for both
  branches, not a step run's `ended_at`.** Now that `Resumable` admits two
  shapes at once (step 6: aborted, or no lease), the two need one shared
  ordering to interleave fairly rather than two separate ones; the run's own
  `updated_at` already advances on every write either shape makes to it (a
  kill's `AbortOpenStepRuns`, or a drain's `ReleaseLease`), so it is available
  for both without the per-candidate `Inspect` call the old `ended_at`-based
  sort needed. This preserves the existing "oldest first" fairness (whichever
  run has been waiting longest gets reclaimed first) with a different,
  still-monotonic, and now shared source.
- **`Drain` is fire-and-forget over the wire; waiting is `mill drain`'s job,
  not the RPC's.** A blocking RPC would need its own timeout and cancellation
  story on top of connect's; `--wait` polling `Probe` reuses a read path this
  node is building anyway and keeps `Drain` itself a one-line "ask nicely,"
  matching how `Worker.Drain()` (step 7) already returns immediately and
  lets `Worker.Run` report when the last run is actually done.
- **Where the work order was silent on `mill drain --timeout`'s default**:
  five minutes, chosen as long enough for one in-flight step under an
  ordinary workflow's per-step time budgets to reach a boundary, short enough
  that a terminal command does not hang indefinitely on a stuck run. Flagged
  under Risks as this plan's own choice, not a value taken from the node.
- **`ReleaseLease` requires the caller's own current lease, fenced the same
  way `AbortOpenStepRuns` is**, rather than being an unconditional
  operator-style override. It is a worker releasing its own hold, called
  from inside `drainStep` under the run's own lease, not a remote "force
  release" operation — `mill restart`'s existing `preempted`/`restart` path
  already covers the "take it away from a worker that will not give it up"
  case, and duplicating that here was rejected as out of scope.
