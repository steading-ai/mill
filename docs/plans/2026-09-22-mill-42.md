# The merge gate spends a retry on the forge's mergeability lag after a catch-up push

## Approach

Approach B from the think step: a proactive bounded wait in each forge
adapter's `Merge`, mirroring `OpenPR`'s `awaitBranch`, plus a bounded
in-attempt retry loop in the merge gate (`internal/run/gate.go`'s `approve`)
that consumes a structured signal on `forge.MergeRefusedError` through
`forge.Retryable` — the seam the acceptance criteria names.

Rejected: a reactive-only fix (retry the merge call itself with no proactive
poll) satisfies the outcome but not the literal ask in criterion 1, which
explicitly compares to `pr`'s dedicated pre-check, and it would spend a real
405 against the forge on every catch-up merge instead of a cheap read.
Rejected: a proactive-wait-only fix, because it drops criteria 2 and 3
outright — mill#42's complaint was specifically that *any* second transient
parks the run, so the residual race after the wait's deadline still has to be
absorbed without cost. Rejected: bumping the `merge` step's `retries` in the
workflow config — it satisfies no acceptance criterion and hides the real
condition (a state that clears by itself) behind a wider budget for
conditions that should not clear (a real, durable refusal).

`HeadMovedError` is deliberately left untouched: it is already `Retryable`,
but nothing in `internal/run` consumes that today (confirmed by grep — every
existing caller of `forge.Retryable` is a package test), so a `HeadMovedError`
today already just fails the step and costs an ordinary, charged retry. That
is out of scope for mill#42, which is about `MergeRefusedError` specifically;
changing `HeadMovedError`'s cost would be an untested, uncalled-for behavior
change riding on this fix.

## Steps

1. **`internal/forge/forge.go`: give `MergeRefusedError` a structured, adapter-set
   signal for "worth another attempt inside this one."**
   Add two fields, `Pending bool` ("the forge has not finished computing
   mergeability yet — GitHub's `mergeable_state: unknown`, GitLab's
   `detailed_merge_status: checking/unchecked/preparing`") and `Conflict bool`
   ("the forge sees a real conflict — GitHub's `dirty`, GitLab's `conflict` —
   which catch-up did not see because the target moved again after it ran").
   Change `Retryable` so the `MergeRefusedError` branch returns
   `refused.Pending || refused.Conflict` instead of the current unconditional
   `false`. Update the package doc comment (`forge.go:21-26`) and
   `MergeRefusedError`'s doc comment, which currently say a refusal is never
   retried — that claim becomes "never retried as a fresh step attempt; a
   refusal that names its own transience is retried in place instead."
   *Proof:* extend `internal/forge/forge_test.go`'s existing `Retryable` table
   (`forge_test.go:132`, the table already exercised by
   `Expect(forge.Retryable(err)).To(Equal(retryable))`) with two new rows: a
   `MergeRefusedError{Pending: true}` → `true`, and a
   `MergeRefusedError{}` (today's shape, e.g. `Detail: "blocked"`) → `false`
   (regression guard: this must not flip). `go test ./internal/forge/...`
   passes; the existing `Detail: "blocked"` → `Retryable() == false` assertions
   in `github_test.go`/`gitlab_test.go` continue to pass unchanged, since
   `Pending`/`Conflict` default false.

2. **`internal/forge/github/github.go`: wait for mergeability before merging,
   and classify a refusal that still lands.**
   Add `mergeableWait`/`mergeablePoll` fields on `Client` (same shape as
   `branchWait`/`branchPoll`), `defaultMergeableWait = 15 * time.Second`,
   `defaultMergeablePoll = time.Second`, and a `WithMergeableWait(wait, poll
   time.Duration) Option` mirroring `WithBranchWait`. Add
   `awaitMergeable(ctx, number int) (string, error)`, modelled on
   `awaitBranch` (github.go:618-648): reads `c.pull(ctx, number).MergeableState`
   in a loop, returns as soon as it is not `"unknown"`, and — unlike
   `awaitBranch` — returns the last-seen state rather than an error when the
   deadline passes, since criterion 2 is what absorbs an unsettled state past
   this point, not a hard failure here. Call it from `Merge` (github.go:475)
   right before building the merge body, and use its returned state instead of
   `pr.Detail` when constructing a `*forge.MergeRefusedError` on a 405/403/422,
   setting `Pending: state == "unknown"` and `Conflict: state == "dirty"`.
   *Proof:* new specs in `internal/forge/github/github_test.go` under
   "merging": (a) a PR whose single-GET reports `mergeable_state: unknown`
   then `clean` on the next poll merges without the gate ever seeing a
   refusal — `client.Merge` stubbed with `WithMergeableWait` set short (as
   `WithBranchWait` already is in the branch-wait specs) and two sequential
   `GET .../pulls/7` responses; (b) a merge that still gets a 405 after the
   wait's deadline, with the last-polled state `unknown`, returns a
   `*forge.MergeRefusedError` with `Pending: true` and
   `forge.Retryable(err) == true`; (c) the same, but state `dirty`, returns
   `Conflict: true` and `forge.Retryable(err) == true`; (d) the existing
   "returns a typed refusal naming GitHub's reason" spec (github_test.go:264)
   is updated to stub the fresh `GET .../pulls/7` the new `awaitMergeable`
   call now makes (returning `mergeable_state: "blocked"` via a new or reused
   testdata fixture) and keeps asserting `Pending`/`Conflict` both false and
   `Retryable() == false`. `go test ./internal/forge/github/...` passes.

3. **`internal/forge/gitlab/gitlab.go`: the same wait and classification, in
   GitLab's vocabulary.**
   Same shape as step 2: `mergeableWait`/`mergeablePoll` fields,
   `WithMergeableWait` option, `awaitMergeable` polling
   `detailed_merge_status` until it is outside `{"checking", "unchecked",
   "preparing"}`, called from `Merge` (gitlab.go:375) before the PUT.
   `Pending` is true when the fresh status is still one of those three;
   `Conflict` is true when it is `"conflict"`.
   *Proof:* mirror step 2's four specs in `internal/forge/gitlab/gitlab_test.go`
   against GitLab's fixtures and status strings; update the existing
   `Retryable() == false` refusal spec (gitlab_test.go:300) to stub the fresh
   read the new wait introduces. `go test ./internal/forge/gitlab/...` passes.

4. **`internal/run/run.go`: a configurable pause for the gate's in-attempt
   merge retry.**
   Add `Options.MergeRetryWait time.Duration` ("how long the merge gate
   pauses between merge attempts it retries in place, for a refusal that
   names its own transience. Zero takes `defaultMergeRetryWait`."), and a
   `defaultMergeRetryWait = 2 * time.Second` constant beside
   `defaultActivityCeiling`. Resolve it in `New` (run.go:330-348) alongside
   the other zero-value defaults:
   `if options.MergeRetryWait <= 0 { options.MergeRetryWait = defaultMergeRetryWait }`.
   *Proof:* covered by step 5's specs, which set this field small to keep the
   suite fast; no standalone test needed for a plain default-assignment line,
   consistent with how `ActivityCeiling`'s default is proven only through the
   specs that exercise it.

5. **`internal/run/gate.go`: absorb a `Pending` or `Conflict` refusal inside
   `approve`, without charging the step's retries.**
   Extract the existing catch-up subsequence (gate.go:84-109: `CatchUp` →
   overlap check → re-read PR → `checkCaughtUp`) into a helper,
   `catchUp(ctx, s, f, pr) (forge.PullRequest, error)`, so it can be called
   both from `approve`'s first pass and from the new retry loop without
   duplicating the mill#52 cross-check. Add
   `mergeRetrying(ctx, s, f, pr) (forge.PullRequest, error)`: a loop, bounded
   by an unexported `const mergeRetryBudget = 5`, that calls `f.Merge`; on
   success returns; on an error, uses `errors.As` for `*forge.MergeRefusedError`
   guarded by `forge.Retryable(err)` — the named seam — and only then branches:
   `Conflict` reruns `catchUp` (mill#42's criterion 3) and loops back to merge
   again; plain `Pending` sleeps `r.options.MergeRetryWait` (respecting
   `ctx.Done()`) and loops back to merge again; anything else, or the budget
   exhausted, returns the error unchanged so it propagates as an ordinary
   step failure exactly as today. Rewire `approve` to call `catchUp` then
   `mergeRetrying` in place of the inline block and the bare `f.Merge` call.
   Add a doc line to `docs/architecture.md` beside the existing catch-up/check
   paragraph (`docs/architecture.md:150-152`) naming this third pass.
   *Proof:* new specs in `internal/run/gate_test.go`, under a new "The merge
   gate absorbs the forge's own transients" describe block, using an extended
   `fixtureForge` (step 6): (a) the forge refuses once with `Pending: true`
   then succeeds — the run finishes `DONE`, `f.forge.mergeCalls() == 2`, and
   `stepRuns(detail, "merge")` has length 1 (one step attempt, not charged);
   (b) the forge refuses once with `Conflict: true` then succeeds — same
   assertions, proving the retry went through `catchUp` again rather than
   failing to `implement`; (c) the forge refuses `mergeRetryBudget` times with
   `Pending: true` and never recovers — the step *does* fail/retry through the
   ordinary path (this is the bound: a durably stuck merge must still surface,
   not loop forever); (d) a plain `MergeRefusedError{}` (today's durable-refusal
   shape, `Pending`/`Conflict` both false) still fails the step in one call,
   `mergeCalls() == 1` — regression guard matching the existing "returns a
   typed refusal" behavior. All existing specs in the "Catching up with a
   moved target" describe block (gate_test.go:319-408) keep their exact
   `mergeCalls()`/`stepRuns()` counts unchanged, since the fixture never
   refuses in those paths. `go test ./internal/run/...` (or
   `ginkgo -p --randomize-all --fail-on-pending --keep-going ./internal/run/...`)
   passes.

6. **`internal/run/support_test.go`: let `fixtureForge` script a sequence of
   merge refusals.**
   Replace the single `refuse error` field's *use* with a FIFO queue,
   `refuseQueue []error`, consumed one error per `Merge` call before falling
   through to today's success path; keep the field named `refuse` as an
   alias/append-on-construct convenience if that reads better, but the
   underlying storage must support more than one scripted failure — today's
   field is unused by any spec (confirmed by grep), so this is a pure
   extension, not a behavior change to any existing test. `mergeCalls()`
   keeps counting every call, scripted or not.
   *Proof:* exercised directly by step 5's new specs; no separate test file,
   since `support_test.go` is test infrastructure and its contract is proven
   by the specs that use it.

## Risks

- **GitHub/GitLab's actual status vocabulary differs from what the existing
  testdata fixtures encode.** The plan takes GitHub `mergeable_state:
  "unknown"`/`"dirty"` and GitLab `detailed_merge_status:
  "checking"/"unchecked"/"preparing"`/`"conflict"` from the adapters' own doc
  comments and existing fixtures (`pull_opened.json`'s `"clean"`,
  `pull_merged.json`'s `"unknown"`, `merge_request_opened.json`'s
  `"mergeable"`). If real-world behavior differs, the fix would still compile
  and pass its own (self-consistent) tests but classify the wrong forge
  responses as `Pending`/`Conflict` in production. Mitigation: the
  classification is centralized in one `awaitMergeable`/one classification
  site per adapter, so correcting the string set later is a small, isolated
  change, not a redesign.
- **The list-pulls endpoint (`GET /pulls`) already carries `mergeable_state`
  in this codebase's own fixtures (`pulls_open.json`), which real GitHub does
  not populate on that endpoint.** This plan does not touch that existing
  modeling choice — `awaitMergeable` always does its own fresh single-PR read
  rather than trusting `pr.Detail` from a list call — so the fix is correct
  regardless of whether that pre-existing fixture inaccuracy is ever
  corrected. Worth flagging to a reviewer, but out of scope for mill#42.
  Flagged in this plan's final message rather than fixed here.
  (Both adapters already accept a `Detail` on the `PullRequest` the caller
  passes in; this plan simply stops trusting it for the merge decision.)
- **Extracting `catchUp` out of `approve` changes control flow around
  mill#33/mill#52's already-tested behavior.** Mitigated by step 5's proof
  requiring the existing "Catching up with a moved target" specs to keep
  their exact `mergeCalls()`/`stepRuns()` counts — any regression there is a
  hard test failure, not a silent behavior change.
  the extraction is mechanical (move the block, same order of operations),
  which keeps the diff reviewable against the original.
- **`mergeRetryBudget = 5` combined with two forges' worth of proactive wait
  (up to 15s each) could make a durably-stuck merge take a while to surface.**
  This is the intended bound (bounded, not unbounded), and criterion 2/3's
  own scenario only needs the *first* residual race absorbed — five in-attempt
  attempts at `MergeRetryWait` (default 2s) is ~10s on top of the adapter's
  15s wait, well under the kind of step timeout the workflow already budgets
  for a `skill` step (hours, per `feature_test.go`'s "implement is three
  hours"). If a reviewer wants a shorter bound, both constants are named and
  isolated for a one-line change.
- **This plan assumes `internal/run/gate.go` importing `internal/forge`
  directly (for `forge.Retryable`/`forge.MergeRefusedError`) does not create
  an import cycle.** `internal/run/run.go` already imports `internal/forge`
  for the `Forge` type on `repo`, so `gate.go` (same package) gains nothing
  new at the package-dependency level — only a new import line in one file.

## Decisions

- **`Pending`/`Conflict` as two booleans on `MergeRefusedError`, not a new
  error type or an enum.** The work order's own error taxonomy in
  `forge.go` already uses typed booleans-by-implication (`Merged()`,
  `Open()` on `PullRequest`); two independent booleans on the existing type
  is the smallest change that lets `gate.go` branch on either without a type
  switch, and keeps `errors.As(err, &refused)` the one call site needs.
- **The proactive wait lives inside each adapter's `Merge`, not as a new
  `forge.Forge` interface method.** Keeps the interface unchanged, matches
  `awaitBranch`'s existing precedent (adapter-internal to `OpenPR`), and lets
  each adapter keep its own vocabulary private.
- **`HeadMovedError` is left exactly as it behaves today** (a charged, ordinary
  step retry) — not folded into the new in-attempt loop, since mill#42 is
  scoped to `MergeRefusedError` and changing `HeadMovedError`'s cost has no
  acceptance criterion behind it.
- **Default wait/retry magnitudes**: adapter proactive wait 15s/1s (matches
  `defaultBranchWait`/`defaultBranchPoll` exactly, since it is the same class
  of forge-catch-up lag); in-attempt merge retry 2s pause, 5-attempt budget
  (no number is given in the work order; chosen to comfortably cover "some
  seconds," per mill#21's own incident description, without materially
  lengthening a stuck run before it surfaces).
- **`fixtureForge.refuse` becomes a queue rather than adding a second field.**
  The existing field is unused by any spec today, so widening its type is
  free; a second field alongside it would leave two ways to script the same
  thing.
- **No acceptance-suite (`tests/acceptance`) changes.** The fix is provable
  at the unit level in both affected packages; nothing here changes what a
  real deployment's sandbox, credentials, or reconciliation sweep do.
