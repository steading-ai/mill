# The local workspace ends an attempt's process tree and its scratch when the attempt ends

## Approach

`internal/workspace/workspace.go` already has the mechanism this node wants:
`StepBoundary`, built for the machine backend, whose doc comment names this
exact gap — "the local backend has no such boundary and does not implement
it, so the loop asks nothing of it" (`workspace.go:703-710`) — and whose
call site, `internal/run/walk.go:150-166` (`underBoundary`), already begins
the boundary before an attempt, ends it after the attempt however it went,
waits for the end to complete before the next attempt starts, and logs
rather than fails the run when the end itself errs. `docs/sandbox.md`'s
"Step boundary" section documents the same contract for the machine's own
`mill-step-<ordinal>.slice`, including the one thing a slice does **not**
reach — a container created through podman's API socket, `docs/sandbox.md:241`
— which is answered there by machine teardown and, for the spec database
specifically, by testcontainers' own reaper, Ryuk (`internal/testsupport/postgres.go`'s
`patientReaper`). Neither backstop exists for `local`: there is no machine to
tear down, and Ryuk's removal of the spec container has not been removing
its volume (491 orphaned volumes since 2026-09-20, one per `go test
./internal/store/` run).

So this plan gives `internal/workspace/local.Workspace` its own
implementation of `workspace.StepBoundary`, reusing the existing call site
and contract unchanged, plus one independent fix in
`internal/testsupport/postgres.go` for the volume deliverable 4 asks about
directly. Concretely, per step (`BeginStep`/`EndStep`, keyed by the ordinal
the run loop already hands them, combined with the workspace's own run id
for a name unique across the whole host — `mill-<runID>-<ordinal>`):

`local.Workspace.Exec` is *not* the one chokepoint every session, check and
preparatory-step process goes through — only checks and preparatory steps
call it (`check.Run(ctx, s.workspace, ...)` at `execute.go:714`, `gate.go:353`,
`preparatory.go:61`). A skill step's session sidecar is spawned by
`internal/harness/claude.Adapter`, whose own default execer is a bare
`workspace.Spawner{}` (`adapter.go:140`); `internal/cli/run.go`'s
`claudeAdapter` hands it the run's workspace as that execer only for
`workspace.KindMachine` (`run.go:833-840`) — the local backend's branch
constructs the adapter with no `WithExecer` at all, so a scope, a `TMPDIR`
entry or a `PATH` shim placed only inside `Workspace.Exec` would reach a
check or a preparatory command and never the session-spawned e2e stacks,
browsers and `go build` runs the node's own evidence is about.

The fix is one shared attempt-scoping `workspace.Execer` that both paths run
through, not two copies of the same logic. `local.Workspace` builds it once
(`open`, alongside the socket server it already starts) as a decorator
around the `w.execer` it already holds, and stores it on a new unexported
field. `Workspace.Exec`'s existing implementation changes in exactly one
place — its final call, `w.execer.Exec(ctx, workspace.Command{...})`, becomes
`w.attemptExec.Exec(ctx, workspace.Command{...})` — so a check or
preparatory-step process is scoped exactly as before, just through the
shared decorator instead of inline logic. `local.Workspace` also implements
a new optional interface, `workspace.SessionExecer` (`SessionExec()
workspace.Execer`, doc-commented and placed beside `StepBoundary` in
`workspace.go`, the same "asked only if implemented" pattern as
`ActivitySink`/`CacheCandidate`), returning that same decorator directly —
not wrapped in `Workspace.Exec`'s own env-building, since the harness
adapter already computes a session's full environment itself
(`adapter.go`'s `a.environment(session)`, `EnvInherit`/`EnvStrict`) and calls
its execer with `ClearEnv: true`; the decorator only adds to whatever
`Command.Env` a caller already built, so it composes with that instead of
discarding it. `internal/cli/run.go`'s `claudeAdapter`, for the non-machine
case, type-asserts `ws` against `workspace.SessionExecer` and passes
`claude.WithExecer(se.SessionExec())` when it implements it — the same shape
the machine branch already uses, so a caller that used to close over a
process-only view of "the workspace's execer" now sees the same object a
check step's command runs through, and the mechanism below reaches both.

- **Process tree** (deliverable 1, AC1). `BeginStep` probes once, cached on
  the workspace, whether `systemd-run --user` is usable in this account's
  session. The shared decorator wraps the spawned command in `systemd-run
  --user --scope --unit=<name>-<n> --collect
  --property=TimeoutStopSec=<grace> -- ...` when a scope is usable, or keeps
  today's `Setpgid` process group otherwise, and records the scope name (or
  the `*workspace.Process`) against the current step — for every command it
  spawns, whether the caller is `Workspace.Exec` (a check, a preparatory
  step) or the harness adapter through `SessionExec` (a skill step's
  session, and whatever it starts under it: an e2e stack, a browser, a
  `go build`). `EndStep` stops every scope this step created (`systemctl
  --user stop`, waited to inactive) or signals every tracked process group
  (SIGTERM, the grace window, then SIGKILL for stragglers) — whichever mode
  `BeginStep` chose. A cgroup scope is the only one of the two that reaches
  a grandchild that detached into its own session (`setsid`, `nohup … &`,
  the shape a backgrounded e2e stack or a launched browser takes) — a pgid
  kill does not, which is the gap the node's own evidence describes.
- **Scratch** (deliverable 2, AC2). `BeginStep` creates `<rundir>/tmp/<ordinal>`
  (removing any stale directory of the same name first — see Decisions) and
  the shared decorator sets it as `TMPDIR` on every command it spawns —
  merged into whatever `Command.Env` the caller already built, so it reaches
  a session the same way it reaches a check or preparatory command's own
  `WORKSPACE_SOCKET`/`STEP_TOKEN` entries (`local.go:526-529`).
  `GOTMPDIR`/`GOCACHE` are never touched, so the build cache stays warm.
  `EndStep` removes it.
- **Containers** (deliverable 3, AC3). `BeginStep` also builds a small `bin/`
  directory, and the shared decorator prepends it to `PATH` on every command
  it spawns — reaching a session-spawned `podman`/`docker` invocation (an
  e2e script's own compose-up) the same way it reaches TMPDIR above, not
  only a check or preparatory command's — holding wrapper scripts for
  `podman`, `docker`, `podman-compose` and `docker-compose` (whichever of
  these the guest's e2e scripts actually invoke — see Risks) that inject
  `--label mill.attempt=<name>` (and, for
  `podman run`/`create`, `--cgroups=split`, which `docs/sandbox.md:244`
  documents as the flag that makes a container land under the invoking
  cgroup at all) ahead of the real command's own arguments, then exec the
  real binary. `EndStep` sweeps by that label regardless of which mode
  reaped the process tree: `podman ps -a --filter label=mill.attempt=<name>
  -q | xargs -r podman rm -f -v`, then the same filter against `podman
  volume ls -q | xargs -r podman volume rm`, so a container the label
  missed but whose creator process the scope/group kill already removed
  still has its volume swept.

Deliverable 4 is unrelated to the above — it is postgres's own container,
started by `internal/testsupport/postgres.go` for mill's own spec suite, not
by an attempt at all — and is fixed independently: mount the postgres image's
declared data directory on tmpfs in the `ContainerRequest`, so `CREATE
DATABASE`'s file copies never touch a real volume and there is nothing for
`podman volume ls` to ever list, rather than trying to make removal of an
already-created anonymous volume more reliable than Ryuk already tries to
make it.

**Rejected alternatives.**

- A new interface and a new wrap point, e.g. around `Runner.execute()`'s
  single call site (`walk.go:254`) or around the eight `endActivity`/
  `abortActivity` call sites across `select.go`, `walk.go`, `gate.go`,
  `revise.go` and `upstream.go` — rejected because `workspace.StepBoundary`
  already exists, is already wired through exactly the call site with
  exactly the needed semantics, and is explicitly documented as the local
  backend's one missing piece. A second mechanism would duplicate that
  plumbing and leave two "attempt ended" hooks that must be kept in sync by
  hand.
- Relying on process-tree reaping alone for deliverable 3 (i.e., trusting
  that a systemd scope's cgroup kill also takes a `podman run` the step
  started) — rejected on `docs/sandbox.md:241,244`'s own evidence: even the
  machine backend's slice, a real cgroup boundary, does not reach a
  container created through the podman API socket, and reaches a `podman
  run` from the shell only with `--cgroups=split` set. A container is not a
  descendant process at all; it needs its own removal path no matter how
  good the process-tree reaping gets.
- Fixing deliverable 4 by asking `container.Terminate()`/Ryuk to remove
  volumes more aggressively — rejected because the volume is created the
  moment the container starts (the postgres image declares `VOLUME` on its
  data directory), so removal-time fixes are chasing a resource that never
  needed to exist; mounting tmpfs at that exact path prevents it outright
  and is a smaller, more local change.

## Steps

1. **The shared attempt-scoped `Execer`, wired to both paths, scratch
   only.** New file `internal/workspace/local/boundary.go`: a `stepState`
   struct (tmp dir, ordinal, name) held on `Workspace` under its existing
   mutex, and an unexported `attemptExecer` type — `Exec(ctx, command)`
   reads the current step's state under lock, merges `TMPDIR` into
   `command.Env` (appending a `TMPDIR=` entry; it never removes or reorders
   whatever the caller already put in `Env`), and calls through to an inner
   `workspace.Execer`. `Workspace` gains an unexported field holding one,
   built once in `open` around the `w.execer` it already has.
   `BeginStep(ctx, ordinal)` computes `name := "mill-" + handle.RunID + "-" +
   strconv.Itoa(ordinal)`, removes then creates `<rundir>/tmp/<ordinal>`
   (0700), and stores the state; `EndStep(ctx, ordinal, _)` removes the
   directory and clears the state, ignoring `ordinal` mismatches only by
   logging (best-effort, matches `StepBoundary`'s existing "logged, does not
   fail the run" contract). `local.go`'s `Exec` (`local.go:514-544`) changes
   in exactly one line: its final `w.execer.Exec(ctx, workspace.Command{...})`
   becomes `w.attemptExec.Exec(ctx, workspace.Command{...})`, so a check or
   preparatory-step process is scoped exactly as it always was, only through
   the shared decorator now. `internal/workspace/workspace.go` gains a new
   optional interface next to `StepBoundary`:
   ```go
   type SessionExecer interface {
       SessionExec() Execer
   }
   ```
   doc-commented as what a workspace implements when a skill step's session
   is not already spawned through its own `Exec` — the machine backend is
   not, since `harnessesFor` already hands the workspace itself to the
   adapter as its execer (`run.go:833-840`) — and `local.Workspace`
   implements it, returning `w.attemptExec` itself, unwrapped by
   `Workspace.Exec`'s own env construction (the caller — the harness
   adapter — already builds a session's full environment and calls its
   execer with `ClearEnv: true`; the decorator only adds to `Command.Env`,
   never discards it, so this composes rather than conflicts).
   `internal/cli/run.go`'s `claudeAdapter`, in its non-machine branch, type
   asserts `ws` against `workspace.SessionExecer` and adds
   `claude.WithExecer(se.SessionExec())` when it succeeds — closing the gap
   the review found: before this step, only `Workspace.Exec`'s callers
   (checks, preparatory steps) ever saw a workspace-scoped execer on the
   local backend; a skill step's session sidecar, and everything it spawns
   underneath it, ran through a bare `workspace.Spawner{}` that `BeginStep`
   never touched.
   *Proven by* a new `internal/workspace/local/boundary_test.go`: `BeginStep`
   followed by `Exec` of a command that prints `$TMPDIR` shows the new
   directory; the same directory shows through `SessionExec().Exec` called
   directly with the caller's own `Env` already set (proving the merge
   composes rather than replaces, the way the harness adapter relies on);
   `EndStep` removes it; a second `BeginStep` at the same ordinal
   (simulating a resumed worker finding a crashed attempt's leftovers) does
   not fail and leaves a fresh, empty directory. `go test
   ./internal/workspace/local/...`.

2. **Process-group and systemd-scope reaping.** Same file: a `killMode`
   probed once per `Workspace` (cached, not per step) by checking whether
   `systemd-run --user true` succeeds; `Options` gains `Grace
   time.Duration` (default `5 * time.Second`, matching `run.DefaultGrace`'s
   value — `internal/workspace/local` cannot import `internal/run`, so this
   is a sibling constant, not a shared one). In scope mode, `attemptExecer.Exec`
   wraps `command.Path`/`Args` in `systemd-run --user --scope
   --unit=<name>-<n>.scope --collect --property=TimeoutStopSec=<grace> --
   <path> <args...>` (n a per-step counter) before handing it to the
   existing `w.execer`, and appends the scope's unit name to the step
   state; in group mode, the command is unchanged (`Setpgid` already happens
   in `Spawner.Exec`) but the returned `*workspace.Process` is appended to
   the step state instead. Both apply equally whether the caller reached
   `attemptExecer` through `Workspace.Exec` or through `SessionExec`, since
   it is the same value either way. `EndStep` walks whichever list is
   populated: scope mode calls `systemctl --user stop <unit>` for each and
   polls `ActiveState` until inactive or a timeout; group mode calls
   `Process.Signal(SIGTERM)` on each, waits up to `Grace`, then
   `Process.Signal(SIGKILL)` on any still running, waiting for `Wait()` to
   return.
   *Proven by* `boundary_test.go`: with a fake or forced group-mode probe
   (deterministic in CI, which may not have a usable `systemd --user`), a
   spec starts a background process through `SessionExec().Exec` after
   `BeginStep` — the same entry point the harness adapter now uses, so the
   spec exercises the path a real session's processes actually take rather
   than only the check/preparatory one (e.g. `sh -c 'sleep 30 & wait'`, or
   better, a child that itself calls `setsid` before backgrounding, to prove
   the fallback's known limit honestly rather than hiding it) — calls
   `EndStep`, and asserts — by PID liveness (`syscall.Kill(pid, 0)`) — that
   the direct child's group is gone; a second spec, skipped unless the
   systemd-user probe succeeds in the spec environment (`Skip` with a clear
   reason, not a hard failure), proves the scope mode additionally reaches a
   `setsid`'d grandchild. This is acceptance criterion 1's spec coverage.

3. **Podman labeling and sweep.** New file
   `internal/workspace/local/podman.go`: `BeginStep` writes a `bin/`
   directory under the step's own scratch area holding four small shell
   wrappers (`podman`, `docker`, `podman-compose`, `docker-compose`) that
   prepend `--label mill.attempt=<name>` (and, for a `podman`/`docker`
   subcommand of `run` or `create`, `--cgroups=split` for `podman` only —
   `docker` has no such flag) before `exec`-ing the real binary found
   further down `PATH`; `attemptExecer.Exec` prepends this directory ahead
   of any `PATH` entry already in `command.Env`, for the current step,
   whichever caller reached it. `EndStep` runs (best-effort,
   errors logged not failed) `podman ps -a --filter label=mill.attempt=<name>
   -q | xargs -r podman rm -f -v` then `podman volume ls --filter
   label=mill.attempt=<name> -q | xargs -r podman volume rm`, through the
   same `workspace.Execer` the workspace already has, not a new one.
   *Proven by* no new automated spec — acceptance criterion 4 asks only for
   coverage of 1 and 2, and gating a unit spec on the host actually having
   rootless podman would make `go test ./internal/workspace/local/...` flaky
   where it is not available. Verified by hand per the Proof section below,
   matching acceptance criterion 3's own wording exactly.

4. **`internal/testsupport/postgres.go`: no volume for mill's own spec
   database.** In `Start`'s `ContainerRequest` (`postgres.go:79-93`), add a
   tmpfs mount at the postgres image's declared data directory (confirm the
   exact path against the pinned `postgresImage` digest rather than assumed
   — `podman image inspect --format '{{json .Config.Volumes}}'
   docker.io/library/postgres:18@sha256:4ef4...`; expected
   `/var/lib/postgresql/data`, sized generously — spec databases are many
   small clones, not one big one, but the template plus every concurrent
   spec process's clone must fit) via `HostConfigModifier`'s `Tmpfs` map.
   No other behavioural change: `awaitConnections`, `createTemplate`, `clone`
   and `drop` are untouched.
   *Proven by* the existing `internal/testsupport` consumers (every `db`-
   labelled suite) staying green under `make test-db`, plus the manual
   verification in Proof below matching acceptance criterion 3.

5. **Update the two doc comments this plan makes false.**
   `internal/workspace/workspace.go:709-710`'s "the local backend has no
   such boundary and does not implement it" and `docs/sandbox.md:239`'s "a
   backend with no slice — the local one — is asked neither" both need a
   sentence naming what `local` does instead (a systemd `--user` scope or a
   process group, not a slice, and no cache-candidate snapshot since
   `local` still does not implement `CacheCandidate`/lineages). No code
   changes.
   *Proven by* review only — doc comments have no test.

## Risks

- **Which container CLI the guest's e2e scripts actually invoke is not
  knowable from this repository** — "steading-e2e-*" is a project run
  *through* mill, not mill's own fixture, so its scripts are outside this
  checkout. The plan covers `podman`, `docker`, `podman-compose` and
  `docker-compose` as the realistic set; if the actual invocation is
  something else (a Python/Go test harness talking to the socket directly,
  the way `internal/testsupport/postgres.go` itself does), the PATH shim
  cannot label it and only the systemd-scope/group reaping of step 2 would
  apply to it — which, per the Approach's rejected-alternatives note, does
  not reach a container at all. If this turns out to be the case, the fix
  is the same shape as step 4: whatever created the container needs to pass
  the label itself, discovered and named during implementation rather than
  guessed here.
- **No systemd `--user` session in the guest's account** would leave every
  step in group mode, which is what exists today and does not close AC1's
  detached-process case. Step 2's probe already degrades to this
  automatically rather than failing, so the feature ships either way; only
  the `setsid`-escape case stays open until (or unless) a systemd user
  session is provisioned for the account, a fact worth confirming against
  the guest directly (`systemctl --user status`) before or during
  implementation, since it changes how much of AC1 is actually closed on
  day one.
- **The postgres image's data-directory path could differ from
  `/var/lib/postgresql/data`** for the pinned `postgres:18` digest — step 4
  names the exact command to confirm it before writing the mount, rather
  than assuming.
- **A `systemd-run --user --scope` invocation changes the process's
  immediate parent** from mill's own worker to `systemd-run`/`conmon`-style
  supervision, which could change what `Process.Pid()`/`Wait()` observe
  (`local.go`'s `Exec` return value is a `*workspace.Process` built around
  `exec.Cmd`, and the caller — `check.Run`, the harness adapter — reads
  `Stdout`/`Stderr`/`Wait()` off it directly). `systemd-run --scope`
  (without `--pty`, foreground, not `--unit`-only) keeps the invoked command
  as `systemd-run`'s own child with its stdio inherited, so the pipes
  `Exec` already wires up should behave unchanged — but this needs a spec
  in step 2 that actually reads stdout/stderr through a scope-mode `Exec`
  before trusting it, not just a liveness check on the PID.
- **`SessionExec`'s caller already builds a full environment and passes
  `ClearEnv: true`** (`adapter.go`'s `begin`, `EnvInherit`/`EnvStrict`); the
  shared decorator must only add to `command.Env` (`TMPDIR`, the `PATH`
  prefix) and never touch `ClearEnv` or rebuild the map, or it would either
  silently drop capability-scoped variables the adapter deliberately left
  out (`EnvStrict`) or reintroduce host floor entries the adapter
  deliberately excluded — the opposite of what routing the session through
  the workspace is for. Step 1's spec calling `SessionExec().Exec` directly
  with the caller's own `Env` already set is what catches a regression here
  before it reaches a real session.

## Decisions

- **Attempt identity is `mill-<runID>-<ordinal>`**, not the store's
  `StepRun.Id` the work order's wording ("labelled with the step run id")
  suggests literally — `workspace.StepBoundary`'s existing contract only
  carries the ordinal, and `local.Workspace` already knows its own run id,
  so combining the two is globally unique across the host without changing
  an interface the machine backend also implements. Recorded here since a
  reviewer comparing this against the work order's literal words should see
  why it does not match verbatim.
- **`BeginStep` at an already-used name tears down and recreates rather
  than refusing.** `local.Workspace` does not implement `StepResumer`, so a
  worker that crashed mid-step and resumes starts its ordinal count over at
  1 (`internal/run/run.go:884-889`'s `ok` guard simply does not fire for
  `local`), which can collide with a still-present leftover from the
  crashed attempt under the very same name. Treating `BeginStep` as
  idempotent — clean up anything already there, then start fresh — turns
  that collision into exactly the resume-safety net a real `StepResumer`
  would have provided, without implementing one. If ordinal-continuity
  across restarts is wanted for `local` later, it is a separate,
  independently useful change (`StepResumer`), not a prerequisite for this
  node's four deliverables.
- **The grace window is a `local`-package constant (`5 * time.Second`),
  not threaded from `internal/run`.** `internal/workspace/local` sits below
  `internal/run` in the dependency graph (the reverse import would cycle),
  so it cannot reuse `run.DefaultGrace` directly; matching its value keeps
  the two behaviours consistent without an import. `Options.Grace` is
  exposed so a caller that wants a different window can still set one, the
  same shape `harness/claude/adapter.go`'s `WithGrace` already takes.
- **No automated spec for the podman sweep (deliverable 3).** Acceptance
  criterion 4 names only 1 and 2 for `internal/workspace/local` specs;
  gating a suite on rootless podman being present would make it flaky
  wherever it is not, so criterion 3 is proven by the manual sequence in
  Proof, matching its own wording exactly rather than approximating it in
  Go.
