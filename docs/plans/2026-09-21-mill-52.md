# The caught-up tree is never tested before it merges

## Approach

The merge gate's clean catch-up path (`catchUp.Merged` in
`internal/run/gate.go`'s `approve`) merges, signs and pushes a target branch's
new commits into the run's branch and then asks the forge to merge — no step
runs in between. That is the one structural hole mill#2/mill#26 fell through:
two migrations with the same version number, on branches that never touched
the same file, so catch-up saw nothing to review. The overlap path does not
have this hole today: a conflict already fails the merge step as a judgment
(`catchUpOverlapError`), which revises the run back through `implement`, and
the ordinary step sequence that follows — `commit`, `clean-tree`, and, on
`mill`'s own project workflow, `live-tier` — reruns before `merge` is
attempted again, against the resolved tree. So the overlap path already tests
the caught-up tree, provided the workflow defines a check worth running; the
clean path is the one that tests nothing at all.

The fix: when `approve` sees `catchUp.Merged`, run the workflow's own
`check`-kind steps between `commit` and `merge` — the checks that would have
run had a step actually executed after catch-up — against the tree catch-up
just produced, before calling `f.Merge`. A failure becomes a new judgment
error, `catchUpCheckError`, handled by `runGate` exactly the way
`catchUpOverlapError` already is: a finding, not a park, routed to
`implement` by the merge step's own `on_failure: revise implement`. This
reuses every piece of existing machinery — `internal/check.Run`, the
`judgment`/`revise` plumbing, the workflow's own step definitions — and adds
no new schema, no new step kind, and no new per-repository configuration
concept.

**Rejected: a new "repository check command" config surface.** AC1 says "the
repository's check command," but no such concept exists today — every check
is a named step in a workflow, and the generic `quick-fix`/`feature`
workflows define exactly one (`clean-tree`, which only asserts the tree has
no uncommitted diff — it would have passed trivially on the mill#2/mill#26
tree, since catch-up leaves a clean, fully-committed tree by construction).
Introducing a new config field (e.g. a repository-level test command in
`mill.toml`) so every generic workflow gets a real check would actually make
this node's fix meaningful for non-`mill` projects, but it is a materially
bigger change — new schema, new config surface, a decision about what a
project without one gets — and not something this node's title asks for. It
is a real gap, worth its own node; this plan does not attempt it. `mill`'s
own project workflow (`mill-quick-fix`/`mill-feature`) already has a
`live-tier` step that runs `make test`, so the fix here does fully close the
incident class for `mill` itself, which is what actually crash-looped.

**Rejected: always rerunning checks after every catch-up, overlap included.**
Running the check span unconditionally, regardless of path, would make AC1's
"clean or overlapping" guarantee structural instead of relying on the
overlap path's existing step replay. It was rejected because it duplicates
work that already happened moments earlier in the ordinary step sequence —
`live-tier` alone is budgeted up to 1h30m, and running it twice per overlap
resolution is a real cost, not a theoretical one. The new spec (`Steps 3`
below) and the doc update both call out explicitly that the overlap path's
coverage is the existing replay, not new code, so the guarantee is documented
even though it isn't re-triggered.

**Rejected: revising to a check step instead of `implement`.** A rerun that
only needs to prove the tree passes, not fix anything, could in principle
supersede straight to the pre-merge check step and skip a wasted `implement`
pass. Rejected because `catchUpCheckError`'s failure *is* real work most of
the time (mill#2/mill#26 needed an actual renumber) — routing to `implement`
like the overlap case already does is the correct default, and inventing a
second revise target for the rare "the check was flaky" case is more
machinery than this node's acceptance criteria ask for.

## Steps

1. **Generalize `runGate`'s error-to-finding handling.**
   `internal/run/gate.go`: replace the `errors.As(err, &overlap)` check in
   `runGate` (currently naming `*catchUpOverlapError` specifically) with a
   small unexported interface, e.g.:
   ```go
   type mergeFinding interface {
       error
       finding() string
   }
   ```
   and `errors.As(err, &target)` against it, so any error `approve` returns
   that implements `finding()` becomes a judgment with that text — the seam
   the next step's new error type plugs into. `*catchUpOverlapError` keeps
   its existing `finding()` method unchanged.
   Proof: existing `gate_test.go` catch-up specs (both `It`s in "Catching up
   with a moved target before merging") still pass unmodified — this step
   changes no behavior, only how the error is matched.

2. **Add `catchUpCheckError` and the check-span helper.**
   `internal/run/gate.go`: add `catchUpCheckError{step, reason, stderr
   string}` beside `catchUpOverlapError`, with `Error()` and `finding()`
   methods in the same style (`finding()` names the failing check, its
   reason, and its stderr, and says the merge is already staged — mirroring
   `catchUpOverlapError.finding()`'s framing but for "a check failed," not
   "resolve a conflict"). Add `checksBetween(workflow *millv1.Workflow,
   after, before string) []*millv1.Step`, walking `workflow.GetSteps()` and
   collecting the `STEP_KIND_CHECK` steps strictly between the two named
   steps, in order (`stepNamed` in `internal/run/walk.go:439` is the existing
   precedent for this kind of lookup by name). Add `(r *Runner)
   checkCaughtUp(ctx context.Context, s *state) error`, which calls
   `checksBetween(s.workflow, "commit", "merge")` and, for each step, runs it
   through `internal/check.Run(ctx, s.workspace, check.Request{Name:
   step.GetName(), Check: step.GetCheck(), WorkflowDir:
   r.options.WorkflowDir})` under a context bounded by that step's own
   timeout (`stepContext`, `internal/run/execute.go:86`, already used by the
   ordinary step-execution path — reused here rather than duplicated).
   The first check that does not pass returns `*catchUpCheckError`; all
   passing returns `nil`.
   Proof: this step is additive (new, unexported, uncalled code) and is
   proven together with step 3 by the new spec — no separate unit test
   is added for `checksBetween` alone, since its only caller and only
   meaningful behavior is exercised end-to-end there. `go build ./...`
   confirms it compiles and the interface is satisfied
   (`s.workspace` already implements `workspace.Execer` via `Exec`,
   the same way `runCheck` in `execute.go:697-703` uses it).

3. **Call `checkCaughtUp` from `approve`'s clean catch-up path.**
   `internal/run/gate.go`, in `approve` (around the existing `if
   catchUp.Merged` block): after re-reading the PR (the existing
   `f.PR(ctx, s.run.GetBranch())` call, needed because the self-merge moved
   the head), call `r.checkCaughtUp(ctx, s)` and return its error if any,
   before falling through to `f.Merge`. No change to the overlap branch or
   to the `pr.Merged()`/`UpToDate` fallthrough.
   Proof (new spec, in `internal/run/gate_test.go`, inside the existing
   `Describe("Catching up with a moved target before merging", ...)`
   block, alongside the two existing `It`s): use `f.variant` (already used
   elsewhere in this test file) to push a workflow copy with one extra
   `check`-kind step inserted between `clean-tree` and `pr` via
   `insertAfter` — a small script/command that fails when a specific marker
   file is present (kept out of the fixture's real `clean-tree`, whose
   meaning — "no uncommitted diff" — should not be repurposed). Script
   `duringImplement`-style, as the existing overlap spec does: seed the
   marker file onto the target branch during the first `implement` turn
   (`f.seedTarget`), on a path the run's own commits never touch, so catch-up
   finds no overlap and merges cleanly. Assert:
   - `f.forge.mergeCalls()` is `0` after the merge step's first attempt —
     the forge is never asked to merge the tree the new check failed against
     (this is AC2's own assertion, verbatim).
   - `stepRuns(detail, "merge")[0].GetStatus()` is `FAILED`, and the
     revised prompt (`calls[...].Prompt.Text`, the pattern the existing
     overlap spec already reads) names the failing check and its reason —
     the finding, not a park.
   - script the second `implement` turn to remove the marker file and
     commit, so the run completes normally on its next pass (mirroring the
     existing overlap `It`'s shape exactly) — `f.runOf(ctx).GetStatus()` is
     `RUN_STATUS_DONE` and `f.forge.mergeCalls()` is `1` by the end, so the
     spec proves both "never merges the bad tree" and "recovers once fixed,"
     not just the failure half.

4. **Document catch-up's coverage in `docs/architecture.md`.**
   Insert a new `### Catch-up` subsection between `### Check steps`
   (`docs/architecture.md:144-146`) and `### Gate steps` (`:148`), stating:
   catch-up runs inside the merge gate's own act, before the forge is asked
   to merge (`internal/workspace.CatchUp`, mill#33); when it finds an overlap
   the merge fails as a finding and the ordinary step sequence — including
   whatever `check`-kind steps the workflow defines between `commit` and
   `merge` — reruns against the resolved tree on its way back to `merge`;
   when it merges cleanly with no review needed, nothing else would
   otherwise run, so those same check steps run once, directly, against the
   tree catch-up produced, and a failure is the same kind of finding an
   overlap is (mill#52 — two independently-fine changes that combined into a
   broken tree with no textual conflict). No proof beyond review: this is
   documentation, not behavior.

## Risks

- **`checksBetween` hardcodes the step names `"commit"` and `"merge"`.**
  Every workflow read while planning this (`quick-fix`, `feature`,
  `mill-quick-fix`, `mill-feature`) uses those exact names, so this holds
  today. A workflow that renamed either step would silently run zero extra
  checks rather than failing loudly. Accepted: the existing `revise commit`/
  `revise implement` `on_failure` targets in every workflow YAML already
  hardcode these same names as strings with no validation, so this matches
  the codebase's existing convention rather than introducing a new
  fragility.
- **Running a check outside the normal step-execution wrapper misses
  something that wrapper does.** Mitigated by reusing `stepContext` for the
  timeout and `internal/check.Run` for the command itself — the two things
  that matter for correctness. Not reused: per-step ledger/activity rows
  (`mill inspect`/`mill logs` won't show a distinct "check ran here" entry
  for this rerun the way a normal step attempt would) and `Sink`-based
  incremental output streaming. Accepted for this fix: the failure's
  `finding()` text still carries the check's name, reason and stderr into
  the merge step's own failed-attempt record, which is where an operator
  already looks first; adding a dedicated ledger row for a check that isn't
  a step is a bigger change than this node asks for.
- **The new spec's marker-file check must be carefully distinguished from
  the fixture's real `clean-tree`.** Mutating `clean-tree` itself to make
  it content-sensitive would conflate two different checks' meanings and
  risk masking a real "dirty tree" bug in future changes to this test.
  Mitigated by inserting a *new* check step via `f.variant`/`insertAfter`
  instead of mutating `clean-tree`'s existing command.
- **This does not fix the incident class for any non-`mill` project.**
  Named explicitly in *Approach* above as a rejected larger scope, not
  hidden — `clean-tree` alone, re-run by this fix, would not have caught
  mill#2/mill#26 on a project without something like `live-tier`. If this is
  the wrong call, the answer is a follow-up node for a repository-level
  check-command concept, not reopening this one.

## Decisions

- **"The repository's check command" (AC1) reads as "the workflow's own
  `check`-kind steps between `commit` and `merge`,"** not a new
  per-repository config concept — see *Approach*, rejected alternative one.
- **Only the clean catch-up path gets the new inline check run;** the
  overlap path's existing step replay is asserted (via the doc update) to
  already satisfy AC1 for that path, and is not given a second, redundant
  check run — see *Approach*, rejected alternative two.
- **A check failure always revises to `implement`,** reusing the merge
  step's existing `on_failure: revise implement` and never introducing a
  second revise target — see *Approach*, rejected alternative three.
- **No ledger/activity row is added for the inline check rerun** beyond what
  the merge step's own failed attempt already records via `finding()` — see
  *Risks*, second bullet.
