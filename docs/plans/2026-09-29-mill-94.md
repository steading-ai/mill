# A run no worker holds says so: a stopped status for cancel, drain, shutdown and a fenced heartbeat

## Approach

`RUN_STATUS_RUNNING`'s doc comment is a promise the store does not keep:
"a lease is held and a step is executing or about to." Four paths leave a
run `running` with `lease_id` cleared or stale — cancel and shutdown
(`internal/run/cancel.go`, `internal/run/shutdown.go`, neither of which
calls `ReleaseLease` at all today, so the row's `lease_id` is left pointing
at a lease skift has already released), drain (`ReleaseLease` clears the
lease but the query's own comment says "the run stays running"), and a
fenced heartbeat whose reclaim fails (`internal/run/heartbeat.go`'s
`beat()`, which returns `errors.Join(ErrFenced, reclaimErr)` and today
writes nothing). A fifth case is structural rather than a bug in one call
site: an `OPEN` node whose lease skift no longer shows at all (the worker
that held it is simply gone, with no heartbeat left to fail) is invisible
to `sweepOne`, which returns immediately on `node.GetStatus() ==
STATUS_OPEN` before ever asking whether the run is still actually held.

The fix is one new terminal-looking-but-resumable status,
`RUN_STATUS_STOPPED`, that means exactly what the leaseless-`running` shape
already means today by convention: no worker holds this, the next claim
resumes it. Once the enum value and its CHECK-constraint migration exist,
the work is mechanical and small, because most of the surface that has to
recognize "resumable, unheld" already does so structurally rather than by
an explicit status check:

- `internal/domain/transitions.go`'s `runTransitions` needs one new state
  reachable from `RUNNING`, itself able to reach `FAILED`/`ABANDONED`
  (mirroring `WAITING`/`PARKED`'s existing reachability, per the file's own
  comment on why those two are terminal-reachable).
- `internal/store/queries/runs.sql`'s `ReleaseRunLease` needs its `SET`
  changed to also write `status = 'stopped'`, and its `WHERE` broadened
  from `status = 'running'` to `status IN ('running', 'selecting')` — a
  cancel or shutdown can interrupt a run before it has chosen a workflow
  (`docs/ledger.md` §Resume's own "a selecting run never refuses a claim"),
  and this is the write `cancelStep`/`shutdownStep` need to start calling.
- The same file's `ReopenRun` — `Rerun`'s reopen of a `failed` run — needs
  its `SET status = 'running'` changed to `SET status = 'stopped'` too. It
  writes `lease_id = NULL` in the same statement, which is precisely the
  `RUNNING`-with-no-lease shape the new invariant forbids; today nothing
  catches this because no invariant test exists yet. Once one does, this
  query has to change or the invariant fails on the very first `mill
  rerun` of a failed run. Semantically this is not a new behavior, only a
  new, correct name for one that already existed: a reopened run holds no
  lease and waits for the next claim, exactly what `stopped` means.
- `store.go`'s `claimableStatuses` and `Status()`'s default list need
  `"stopped"` added, by name, since both are explicit maps/slices rather
  than derived.
- `internal/run/reclaim.go`'s `Resumable` filters `Status` to `RUNNING,
  SELECTING` specifically to find "a run left running with no lease" (a
  drain's boundary release); once `ReleaseLease` writes `stopped` instead,
  that shape no longer has status `RUNNING` and `Resumable` needs
  `RUN_STATUS_STOPPED` added to its own filter to keep finding it — a
  direct, necessary consequence of the `ReleaseLease` change, not a
  separate concern, so it lands in the same step.
- Nothing else in the store needs to change: `held()` already excludes
  `STOPPED` for free (`selectingOrRunning` does not match it),
  `AbortOpenStepRuns`'s claimable-admission check is the same map as
  `SetLease`'s, and `internal/cli/read.go`'s generic `enumWord`-based
  status name renders `"stopped"` with no new code.

Two things are genuinely new behavior, not just plumbing, and both are
named as deliverables: the fenced-heartbeat-reclaim-failure path
(`heartbeat.go`/`walk.go`) and the sweep's new branch for an `OPEN` node
skift no longer shows a lease for (`sweep.go`, using `Node.claimed`, which
is already vendored at
`vendor/github.com/steading-ai/skift/gen/skift/v1/skift.pb.go:778`). Both
are in scope in this one plan — the work order's deliverables name both
explicitly ("a failed reclaim... and the sweep... also write stopped"),
so splitting them into a second node would leave a stated deliverable
undone without a reason.

**Rejected: sweep-only, deferring the reclaim-failure fix.** The `Think`
step considered this as "the smallest thing," reasoning that AC2's "after
the sweep or the next claim" makes the sweep independently sufficient to
satisfy the acceptance criterion. Rejected on rereading the deliverables
list, which names the reclaim-failure path as its own bullet, not as an
alternative to the sweep — and because leaving it unfixed means a run whose
own worker is still alive and ticking (just fenced) stays wrongly
`running` with a dead `lease_id` until the *next* worker's sweep notices,
rather than the moment its own heartbeat already knows.

**Rejected: a shared `stopStep` helper unifying `cancelStep`,
`shutdownStep`, `drainStep`, and the new reclaim-failure step.** The four
call sites differ in exactly one thing each needs to get right: whether
there is an open attempt to abort (drain: no), the `Reason` string
recorded, and whether a `skift.Release` (an active call this worker makes)
or nothing on the skift side (the reclaim-failure case, where skift has
already fenced this worker out) follows. Three of four already exist as
separate small functions with this shape; forcing a fourth into one
parametrized helper trades four short, readable functions for one with a
branchy signature, for a body that is two calls long. Not worth it at this
size.

**Rejected: teaching the sweep to distinguish "reclaim genuinely failed"
from "another worker already has it."** The store's own fencing already
does this for free: the sweep's new branch presents the *stale* lease id
it read off the run row to `AbortOpenStepRuns`/`ReleaseLease`; if another
worker's `SetLease` already claimed the node, the fence comparison fails
and the write is refused with no effect, leaving the new worker's state
untouched (Invariant 9). No separate check is needed or would be more
correct than what fencing already guarantees.

   constraint.** `proto/mill/v1/mill.proto`: add
   `RUN_STATUS_STOPPED = 8;` after `RUN_STATUS_ABANDONED = 7`, documented

   leaseless running run." `internal/store/migrations/00027_run_status_stopped.sql`
   (new; `00026` is the current newest): `ALTER TABLE runs DROP CONSTRAINT
   runs_status_check; ALTER TABLE runs ADD CONSTRAINT runs_status_check
   CHECK (status IN (..., 'stopped'));` with the matching `-- +goose Down`
   dropping `'stopped'` back out. Run `make generate` to regenerate
   `gen/mill/v1/mill.pb.go`.
   - **Proof:** `make check-generated` reports nothing stale; `go build
     ./...` succeeds; `make test-db` still passes (the migration suite in

  Invariant 13 against the actual code changed, to catch drift between the
  two, the way every prior plan in this repo does before closing.

## Risks

- **`internal/cli/workspace.go`'s `retainedText` and `internal/server/logs.go`'s
  `runEnds`/`internal/cli/logs.go`'s `endLogs` are not touched.** Neither
  is named in the work order's deliverables (which scope the CLI surface to
  `status`/`explain`/`rerun`). `retainedText`'s `default: "unknown"` case
  will describe a stopped run's workspace as "unknown" rather than
  correctly — cosmetic, and `terminalStatuses` (which actually governs
  `workspace clean`'s deletion) does not include `stopped`, so a stopped
  run's workspace is never wrongly removed. `runEnds` not knowing about
  `stopped` means `mill logs -f` on a run that becomes `stopped` keeps
  waiting for activity that will not resume until a new worker claims it,
  rather than ending the stream the way it does for `waiting`/`parked`.
  Both are real gaps but outside this plan's named scope; flagged here
  rather than silently left for a future reader to rediscover.
- **The reclaim-failure step (5) touches heartbeat/fencing logic, the
  highest-stakes code in `internal/run`.** A mistake here (e.g. releasing a
  lease that a legitimately-reclaimed heartbeat still holds) could
  double-stop a run that is actually fine. Mitigated by relying on the
  store's own fencing rather than any local judgment call — the release is
  attempted unconditionally and the store's compare-and-swap decides,
  exactly as Invariant 9 already guarantees for every other fenced write.
- **`sqlc` must regenerate cleanly against the migration in step 1 before
  step 3's query change compiles.** If `sqlc vet`/`make generate` is not
  run between steps 1 and 3, the `runs.sql` change in step 3 will not be
  caught by the CHECK constraint at the DB level until `make test-db`
  actually runs a case that hits `stopped` — ordering the steps as written
  (constraint first) avoids writing a value the schema would reject.
- **`make generate` needs `buf` (and its plugins) on `PATH`.** If the
  sandbox this runs in lacks it, step 1 cannot regenerate and must say so
  rather than hand-write `gen/mill/v1/mill.pb.go`.

## Decisions

- **Both the mechanical core (proto/migration/store/domain/CLI) and the two
  named "also write stopped" cases (reclaim failure, sweep) are one plan,**
  not split into a follow-up node. The work order's deliverables name both
  explicitly; see *Approach*'s first rejected alternative for why
  sweep-only was considered and rejected.
- **`waitingOn()` gains `STOPPED` as an additional match on the existing
  `RUNNING` case, not a new `case` with hand-written text.** The deliverable
  asks for wording to the effect of "waiting for a worker to claim it,"
  which is exactly what the existing leaseless-running branch already
  produces; duplicating it as a literal string risks the two drifting
  apart the next time one is edited.
- **The sweep's new branch returns before `reconcileClosed`, never calling
  it.** `reconcileClosed`'s entire body assumes a node skift has closed
  (`DONE`/`DROPPED`); an `OPEN`-but-unclaimed node is a different shape
  (the node is still workable, just not by anyone right now) and reusing
  that function's branches would misdescribe it as done or dropped.
- **`errReclaimFailed` is joined together with `ErrFenced`, not used to
  replace it.** Every existing `errors.Is(err, ErrFenced)` call site
  (`walk.go`'s own fallback case, `run.go`'s `stop()`, `worker.go`'s
  `drive()`) must keep matching a reclaim failure, since it is still, in
  every sense those callers care about, a fencing event; only `walk.go`'s
  `stopped()` needs the finer distinction, and it is given first refusal on
  the switch so it can act before the generic case would.
- **`ReopenRun` writes `status = 'stopped'`, not `'running'`.** It already
  wrote `lease_id = NULL` in the same statement, so the shape it produces
  has always been "leaseless, resumable by the next claim" — this is not a
  new behaviour, only the correct name for one `Store.Rerun` already had.
  Leaving it as `'running'` once Invariant 13 exists would make `Rerun`
  the one write path in `internal/store` that still violates it.
- **`ReleaseRunLease`'s `WHERE` admits `status IN ('running', 'selecting')`,
  and `STOPPED` is added to the `SELECTING` entry of `runTransitions` too,
  not just `RUNNING`.** `CreateRun` leaves a fresh run `selecting` while it
  already holds the claiming lease, so a cancel or shutdown can legitimately
  land on a run that never reached `running`; restricting the release to
  `running` alone would leave the store lease stuck (and the transition
  check would refuse the write before the skift-side release was even
  attempted), for a shape `internal/run/reclaim_test.go`'s `abortedRun`
  fixture already exercises today.
