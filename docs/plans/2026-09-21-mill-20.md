# One worker claims everything by default

## Approach

Collapse `mill work`'s runner-per-project model into one runner and one `skift.Client`, whose `ClaimNext`/`Ready` calls carry the configured project list as a `NodeFilter` — empty meaning every project, exactly as skift's own filter already defines it (`proto/skift/v1/service.proto:527-533`). Everything the run loop does *after* a claim — every graph write and every gate read `internal/run` makes once a node is held — runs against a client scoped to that claim's own project, not the worker's fixed (possibly empty) one: `Client.Scoped(project string) *Client` returns a shallow copy pinned to the claimed project's slug, and `state` (the run loop's per-claim context) carries one, set once right after the claim from `claimed.Project`.

This is deliberately not resting on a blanket reading of which request fields tolerate an empty or qualified-only project — that reading does not hold uniformly. `GetNodeRequest.project` and `ReportUsageRequest.project` are documented as "optional when the node reference carries its own project" (`service.proto:439-441,999-1001`), but `ApplyPatchRequest.project` is documented only as "the project the patch applies to... a node reference without a project half resolves here" (`service.proto:145-148`) — no stated optionality — and `Client.Gates` builds `NodeFilter{Projects: []string{c.project}}` (`internal/skift/patch.go:259`), which for an unconfigured client sends a one-element filter naming the *empty string* as a project, not the empty list that means "every project": a filter that cannot match anything, reached from the worker's gate-dedup path (`internal/run/gate.go:272,296`). Scoping every post-claim call to the claim's own project sidesteps this proto-reading question entirely: nothing downstream of a claim ever runs against a project-less client, so every call is exactly as correct as today's already-proven single-project runner, for every request shape, without an audit of which fields skift happens to make optional. Calls that carry no project on the wire at all (`Release`, `Heartbeat`) and calls that run before or outside a claim's state (`Node`/`Claim` for `mill run`'s own single-node path, `ProjectNamed`, `GetProject`'s fallback, the sweep's read of an already-qualified stored node ref) are unaffected and stay on the worker's own client.

Rejected, from the prior step's note:

1. **Keep `[]*Runner`, add a zero-project entry only for the empty case.** Smallest possible diff, but for `project: [a, b]` it still runs two runners/two clients round-robined, which contradicts the work order's own stated end state ("with one runner there is one skift client, which is what it wanted") and does not give `mill status`/`doctor` one filter to name — they'd have to describe N runners instead of one. Rejected as not actually answering what was asked.
2. **Drop `Client.project` entirely and thread an explicit project parameter through every method in `internal/skift`.** Would be as correct as `Scoped`, but churns every call site's signature in the package for the same outcome `Scoped` gets from one new method and one field on `state`. Rejected as more invasive than the problem requires.
3. **Fix only `Client.Gates`'s filter-building bug (`nil` instead of `[]string{c.project}` when `c.project == ""`) and leave every other post-claim call on the worker's unscoped client, trusting the proto's "optional" wording where it applies.** Smaller diff, but it asks every future reader of `internal/skift` to remember by hand which of a dozen request types are genuinely project-optional and which merely look like they might be — exactly the confusion that produced the `Gates` bug in the first place. Rejected: `Scoped` makes the whole post-claim path uniformly correct instead of auditing each proto field one at a time.

## Risks

- **`mill#5`'s "worker says what it holds" line has no code or scaffolding in this checkout to build against.** Step 4 answers the literal acceptance criterion ("`mill status` prints the worker's filter") with a config-derived, not live-process-derived, line, so it does not depend on mill#5 landing first — but if mill#5 turns out to define a specific wire shape or RPC for this, step 4's line may need to move or be superseded once that lands. Flagged rather than guessed at.
- **The scratch-namespace-with-no-project case (step 3) is a narrow, probably-rare combination** (machine backend + scratch registry + a worker configured with no project filter) that the work order doesn't mention. Erroring clearly at startup is the smallest safe default; if it turns out operators commonly want both, a follow-up would need a separate config key naming which project the scratch registry belongs to.
- **Rewriting `internal/cli/work_test.go`'s "refuses to start" spec (step 2) changes an existing, currently-passing acceptance spec's meaning, not just its assertion.** This is intentional and named in the work order's own acceptance criteria, not a fence being quietly broken — but it's the one existing test in the tree this plan deliberately inverts, worth a reviewer's particular attention.
- **This reverses a specific, recent, deliberate choice** (`f0b2ba9`, "fix(skift): scope claims, ready and gate reads with skift's NodeFilter") that pinned every filter to `c.project` specifically because an unfiltered filter had just started meaning "every org project" as an *unintended* side effect of a contract upgrade. This plan reintroduces that behavior on purpose, opt-in by the absence of configured projects. Worth citing `f0b2ba9` in the implementation commit so it reads as a deliberate widening, not a regression of that fix.

## Decisions

- **The worker's own (base) `skift.Client` is built with the sole configured project's slug when exactly one is named, or `""` when the filter is empty or has more than one.** After step 1, that base client's fixed project is only load-bearing for `mill run`-style bare-ref resolution and `GetProject`'s fallback (used when `claimed.Project` is nil, i.e. an old skift); every post-claim call instead runs against a client scoped per-claim via `Client.Scoped`. Neither the base client nor a scoped one needs to represent a *list*, so there is no need to change `Client.project`'s type from a single string. The work order is silent on this; smallest option that satisfies "one runner, one client" without widening `Client`'s shape.
- **Every skift call the run loop makes after a claim is scoped to that claim's own project via `Client.Scoped`, rather than trusting a per-field reading of the proto's "optional project" wording.** The alternative — leaving the base client unscoped and relying on each request type's own optionality — turned out not to hold uniformly (`ApplyPatchRequest` isn't documented as optional the way `GetNodeRequest`/`ReportUsageRequest` are, and `Client.Gates`'s filter is provably broken for an empty project). Scoping is the smaller, uniformly-correct fix: one new method, one field on `state`, no per-call proto audit.
- **A worker configured with a machine-backend scratch namespace and no project filter fails fast at startup**, rather than silently picking an arbitrary project or disabling scratch cleanup. The work order doesn't mention this interaction; failing clearly is the smallest safe default given there's no principled way to guess which project's forge a scratch registry belongs to.
- **A node whose project has no repository is failed and held (`failRun`/`Skift.Hold`), not merely released.** `Hold` removes the node from every ready set, which is what actually prevents the hot claim/open-run/release loop the deleted startup check existed to stop; a released-only lease does not, since the node is claimable again the instant it's released. This replaces the earlier idea of releasing with `RELEASE_REASON_PREEMPTED`/`"no repository"`: `failRun` never calls `Release` at all (matching its existing lost-sandbox use), so there is no `ReleaseReason` to choose — the acceptance criterion's "released with reason `no repository`" is read as "the node stops being held against this refusal, with the reason recorded on it," which `Hold`'s free-text `reason` satisfies directly.
- **The once-per-project dedup for the "no repository" log lives on `Worker` as a `sync.Map`**, matching the existing `inFlight sync.Map` field, rather than a new shared helper — the codebase has no generic "log once per key" utility today, and one isn't warranted for a single call site. This log is now a courtesy on top of `Hold`'s loop-breaking, not the mechanism the acceptance criterion depends on.
- **`mill status`'s new header line reads the same config file `mill work` would, not a live worker's state.** There is no existing channel from a running `serve --work` process to the `status` CLI's store-socket-only read path, and building one is `mill#5`'s stated territory, not this node's.
