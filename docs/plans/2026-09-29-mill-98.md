# mill's suite fails by timing: the drain-at-boundary spec, the read tools fixture's socket, and step-run order under a repeating clock

## Approach

Three independent, small fixes, each confined to the file(s) the work order names:

1. **`internal/run/worker_test.go`'s "a drain releases at the boundary"** is rewritten to assert what `docs/architecture.md`'s §Stop already promises and what mill#70 (`6363525`) implemented — every run the worker held is released with no `ABORTED` step run and no lease, whatever boundary it reached — instead of counting `implement` attempts. Rejected: forcing determinism by dropping to one in-flight run, since the spec's own point (a freed slot claims nothing more) needs at least one run in flight and one pending node, i.e. concurrency ≥ 2; "fixing" the worker to make the boundary deterministic, since mill#70's nondeterminism here is correct behavior, not a bug — the work order is explicit that the defect is the spec, not the code.

2. **`ListStepRuns`** (`internal/store/queries/step_runs.sql`) gains a DB-generated monotonic tiebreak column, via a new migration, ordered on after `started_at`, replacing `id`. `id` (a ULID) is monotonic only within one `newULID()` process clock (`internal/store/ulid.go`) — correct for everything this test suite exercises today, but not a schema-level guarantee, and not true across a resume by a second worker process (`docs/architecture.md`'s crash-recovery path). The column is a `GENERATED BY DEFAULT AS IDENTITY` column, not `bigserial`: an identity column's generated sequence is accessed through the table's own privileges, so the application role's existing `INSERT` grant on `step_runs` (`00012_grants.sql`) is enough; a `bigserial` column creates a separate sequence object that role has no `USAGE` on, which would make every `InsertStepRun` under the application role fail with `permission denied for sequence`. Rejected: leaving `id` as the tiebreak and only adding a spec that happens to pass today, since that doesn't address what the work order calls out ("not by a random-suffixed id") and just re-confirms present, process-scoped luck; replacing the ULID `id` with a serial primary key, which would touch the `id_ulid` CHECK constraint, the `feedback_from` self-FK, and every other reader of `step_runs.id` — disproportionate for this node.

3. **`internal/cli/workflow_test.go`'s `servingWith`** (the one fixture behind `serving()`, used by every `db`-labelled CLI spec, not only "The read tools") swaps its `os.Stat(socket)` readiness poll for a short-retry `net.Dial("unix", socket)` probe, closing each attempt. `bind()` (which creates the socket's filesystem inode) and `listen()` (which makes it acceptable) are separate steps inside `net.Listen`; `os.Stat` can observe the inode before the kernel is accepting on it, which is exactly the `connect: connection refused` the work order describes — not something specific to the guest's virtualization. Rejected: scanning captured stderr for `Server.Listen()`'s "listening" log line, more fragile (coupled to log text) for no correctness gain over a direct dial; threading a readiness channel out of `internal/cli/serve.go` into the test, which adds test-only instrumentation to production code for a fixture-level race — disproportionate, and not what the work order asks for ("dial with a short retry inside the fixture").

## Risks

- **The new store spec (step 2) would pass even against the unfixed query if it only forced `started_at` equal**, since two step runs inserted the ordinary way (through `l.start`/`l.close`) already get correctly (monotonically) ordered ULIDs today — the in-process monotonic clock `internal/store/ulid.go` guarantees — which would make an id-order-agreeing spec a false proof. Mitigation: as step 2 now specifies, the spec inserts the two rows directly with explicitly chosen `id`s that sort *opposite* to their insertion (attempt) order, so it fails against `ORDER BY started_at, id` and only passes against `ORDER BY started_at, seq`.
- **A `bigserial`/sequence-backed column would have broken every `InsertStepRun` under the application role**, since the application role (`mill_app`) has no `GRANT USAGE` on a separately-owned sequence (`00012_grants.sql` grants only `SELECT, INSERT, UPDATE` on the tables themselves) — and no spec in the repo would have caught it, since store specs insert as the owning connection (`l.db`), not through the application role. Mitigated by using `GENERATED BY DEFAULT AS IDENTITY` instead of `bigserial` (step 2), whose generated sequence's privilege checks route through the table's own grants. Worth the implementer double-checking against a real `mill_app`-authenticated connection (or at minimum reading `00012_grants.sql` alongside the new migration) rather than trusting this reasoning alone, since it's exactly the class of gap the owning-connection specs can't surface.
- **No backfill for existing rows' `seq` values** — an identity column added via `ALTER TABLE` back-fills existing rows with sequential values in an unspecified but internally consistent order; nothing depends on old rows' relative `seq` matching their true historical insertion order, only new rows inserted after this migration need it, which is what acceptance criterion 2 asks for. If a reviewer wants old rows' `seq` to reflect true `id`/`started_at` order too, a data backfill would need adding to the migration's Up — not done here since nothing in the acceptance criteria asks for it and the work order's own reasoning is forward-looking ("a clock that repeats a timestamp").
- **Rewriting the drain spec's assertions (step 1) narrows what it checks** — losing the exact "one implement attempt, closed" pin means a real future regression that always aborted (rather than always cleanly closing) an in-flight attempt on drain would still be caught (the new `NotTo(ABORTED)` assertion), but a regression that somehow made a *second* implement attempt start when it shouldn't would not be, since the new spec no longer counts attempts. This is the intended trade the work order asks for ("it no longer counts implement attempts"), but worth a reviewer's attention as a real, if narrow, coverage loss.
- **`net.Dial`-and-close inside `Eventually`'s polling function (step 3) runs on every retry tick (up to 50ms apart for up to 60s)** — negligible connection churn for a test fixture, but if the dial ever blocked instead of failing fast (it won't for a refused unix connection, which returns immediately), it could slow the poll; no mitigation needed given unix-domain connect semantics.

## Decisions

- **`seq` is `GENERATED BY DEFAULT AS IDENTITY`, not `bigserial`.** The work order doesn't specify a mechanism; identity avoids granting the application role `USAGE` on a new, separately-owned sequence object, which `bigserial` would require and `00012_grants.sql` does not currently give — `BY DEFAULT` (rather than `ALWAYS`) is chosen over `ALWAYS` only so a future caller could still supply an explicit value if ever needed, matching how `id` is caller-supplied; nothing in this plan actually does that today.
- **The new store spec inserts step runs directly with explicitly chosen `id`s, rather than through `l.start`/`l.close`.** Going through the store's own API would mint real, monotonic `newULID()` values that already sort correctly today, making the spec pass regardless of whether `seq` exists — it would prove nothing about the fix. Choosing `id`s that deliberately sort backwards from insertion order is what makes the spec fail on the old query and pass only on the new one.
- **New column name: `seq`.** The work order says "a sequence or the attempt's insertion order" without naming one; `seq` is the smallest, most locally readable choice, even though `activity.seq` is a different (app-assigned, per-parent) concept — the two are in different tables and neither query ever joins on the name, so the collision is cosmetic. If a reviewer prefers a name that avoids any visual echo of `activity.seq` (e.g. `ordinal`, `insert_seq`), that's a one-line rename with no other consequence.
- **`seq` stays internal to the store layer** — not added to `millv1.StepRun` or any other proto message, since no acceptance criterion asks for it to be visible outside `ListStepRuns`'s own ordering.
- **No backfill for existing rows' `seq` values** (see Risks) — the acceptance criteria only require correct ordering going forward from two step runs the test itself creates with a forced tie.
- **The drain spec's replacement assertion iterates every step name the quick-fix workflow can reach, not just `implement`/`commit`**, to match the "whatever boundary it reached" wording in the work order's Deliverables exactly, rather than guessing which single step boundary is relevant.
