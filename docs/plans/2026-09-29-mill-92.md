# A restart whose forge half fails leaves the old branch in place, and the next generation can never push

## Approach

Four independent gaps, one root incident. Each gets the smallest fix that
satisfies its own deliverable, and none require a new stored field or a
proto message beyond one additive RPC.

1. **Restart's forge cleanup, run where the credential lives.** `mill
   restart`'s CLI process resolves a forge credential the same way `mill run`
   does — from `$MILL_FORGE_TOKEN` / `$CREDENTIALS_DIRECTORY/forge-token` in
   its own environment — which an operator's interactive shell usually does
   not have; only `mill.service`'s environment does. `WorkerService` already
   exists for exactly this shape of problem ("things only the credentialed
   worker process can answer honestly" — `docs/architecture.md` §"One
   binary, two faces", precedented by `Probe`'s forge check). Add one RPC,
   `RetireBranch`, that runs the close-PR-then-delete-branch sequence inside
   the worker process, and have `internal/cli/restart.go` call it instead of
   building its own local `forge.Forge`. This is the smallest option that
   satisfies "not in the CLI process": a single additive RPC reusing the
   existing socket, transport, and config-resolution pattern, rather than a
   broader credential-distribution redesign.

2. **Restart reports failure, not success with a note.** Two sub-bugs, one
   fix each, both in `internal/run/restart.go`: (a) the `old == nil` branch
   (added by `1fa4bc6` for a different bug) never retries the forge cleanup
   at all — it just prints a note and proceeds to open the next generation;
   (b) once (a) is fixed, an error from the retried cleanup must propagate
   as `Restart`'s own error rather than being swallowed. Both are fixed by
   the same small change: make the `old == nil` branch call `closeBranch`
   the same way the `default:` branch already does, and return its error
   wrapped with the generation it belongs to.

3. **The `pr` step must not reuse a foreign-head pull request.** The
   decision point is `internal/run/execute.go`'s `pullRequest`, the one
   place that both knows the run's own local head (`r.head`) and holds
   whatever `forge.Forge.OpenPR` answered. Comparing the two there is
   sufficient by itself (a mismatch is caught however it arose) and is the
   only version of this check `internal/run`'s own specs can exercise,
   since `internal/run` tests run against `fixtureForge`, a fake that never
   reaches `internal/forge/github` or `internal/forge/gitlab` — AC4 asks
   for a test "in internal/run" covering this, which fixes the layer the
   check has to live at. Paired with it: `OpenPR`'s existing-pull-request
   path in both adapters currently returns the forge's answer unchecked,
   the one place the real incident's "reuse" happened and the one place a
   healthy push's own indexing lag could otherwise make the new
   `internal/run` check flap. The adapters already solve exactly this
   problem on the *create* path (`awaitBranch`, guarding mill#46); applying
   the same wait to the *reuse* path is "bring the run's branch to its own
   head" from the deliverable's own wording, and reuses tested machinery
   instead of growing new fixture surface no production code exercises.

4. **The merge gate must not read a foreign-head pull request.** Same
   shape as (3), same helper: `internal/run/gate.go`'s `approve` reads
   `f.PR(ctx, s.run.GetBranch())` once, before any catch-up; comparing that
   read's `HeadSHA` against `r.head(ctx, s)` at that point is deliverable
   4's whole ask (mill#71's catch-up-moved case is a *later* head change,
   inside `catchUp`, and is explicitly out of scope — this check runs
   before catch-up ever touches the branch).

**Approaches not taken:**
- A CLI-local fallback that tries the socket's `WorkerService` and falls
  back to resolving its own credential when none is mounted. Rejected: the
  incident was a *silent* partial success: a fallback that sometimes
  succeeds locally and sometimes routes through the worker is the same
  shape of surprise with a different trigger. The RPC is now the only path;
  no worker reachable is a named, non-zero failure.
- Making the head-mismatch check live inside `forge.Forge.OpenPR`/`PR`
  itself (one implementation per adapter, no `internal/run` change).
  Rejected: unreachable from `internal/run`'s own specs, so it cannot
  satisfy AC4's "tests in internal/run cover 1 and 2" on its own.
- A new stored field recording the `pr` step's pushed head, read back by
  the merge gate instead of the workspace's live local head. Rejected:
  nothing commits between `pr` and `merge` in the workflow, so the
  workspace's own `r.head(ctx, s)` already answers the same question with
  no schema change.

## Risks

- **`make test-acceptance` cannot run in this environment.** Steps 1, 2,
  3, 4, 6, 7, 8 are fully proven by `make test`; step 5 (the CLI's RPC
  call) is thin enough — one closure, one wrapped error — that its
  correctness mostly rides on steps 3-4's own tests, but the wiring itself
  (does `mill restart` actually reach a running `mill serve --work` over
  the right socket) is only proven live. Mitigation: if the live tier is
  unavailable, say so in the node's result instead of asserting it passed,
  and note that step 5's `restart.go` change is small and reviewable by
  reading, the same way `drain.go`'s identical pattern already is.
- **The reuse-path `awaitBranch` fix (step 7) changes real adapter
  behavior other things may depend on.** Every `pr`-step caller already
  tolerates `OpenPR` taking as long as `BranchWait` (the create path has
  always could); the reuse path gains the same bound, not a new one.
  Mitigation: `internal/run/pr_test.go` and the adapter suites both cover
  it; if `BranchWait`'s default proves too short for a forge under load in
  practice, that is a config change (`WithBranchWait`), not a design
  change.
- **Two generations' pull requests can legitimately share a branch name
  mid-flight** (a restart's forge cleanup is still running when the new
  generation's `pr` step reaches the forge). This node does not add
  locking between them — `mill restart`'s own doc comment already says
  restart is "never automatic," so the two are not expected to race in
  practice. If review disagrees, the smallest addition is ordering (CLI
  waits for `RetireBranch` before returning from `restart`, which it
  already does — it is synchronous) rather than new coordination.
- **`foreignHeadError` duplicated logic between `execute.go` and
  `gate.go`.** Mitigated by factoring the comparison and the type into one
  new small file (`internal/run/forge_head.go`) in step 6, used by both.

## Decisions

- **`RetireBranch` is one RPC, not three.** The work order frames restart's
  forge cleanup as one unit ("both halves"); `internal/forge.Retire`
  already exists as one function once extracted (step 1), so the RPC
  mirrors it rather than exposing `PR`/`ClosePR`/`DeleteBranch`
  individually — fewer round trips, and nothing else needs the finer
  granularity.
- **No local fallback when no worker is reachable at the socket.** The
  incident was a silent partial success; a command that sometimes resolves
  its own credential and sometimes routes through a worker reintroduces the
  same ambiguity under a different trigger. `mill restart` now always goes
  through `WorkerService.RetireBranch`, and a socket with nothing mounted
  is a named, non-zero failure ("no worker runs in this process").
- **`RetireBranchRequest` carries `project` explicitly**, rather than
  reusing `workerForgeResolver`'s "the first configured project" shortcut.
  `Probe`'s shortcut is fine because it answers about the worker itself;
  `RetireBranch` acts on a specific node's repository, which need not be
  `projects[0]` for a worker configured to claim several.
- **The `old == nil` restart path does not retry `discardWorkspace`.**
  Correctly finding the abandoned run's workspace needs its real run ID,
  which `runByNode` does not return for an abandoned run (`old == nil` is
  exactly that "no live run" signal) — fetching it would need a new store
  lookup outside this node's four deliverables, all of which are about the
  forge half specifically. Left as today's behavior; not claimed as fixed.
- **The foreign-head check is a hard failure, not a `mergeFinding`.** Both
  the `pr` step and the `merge` step already park on an unhandled error
  (`on_failure: park` in `docs/domain-model.md`'s workflow tables for both);
  routing this through `implement` via a judgment finding would suggest a
  code fix resolves it, but nothing in the tree is wrong — the fix is a
  restart. A plain error, naming the mismatch, is the smallest correct
  shape.
- **The reuse-path adapter fix (step 7) re-reads the pull request after
  `awaitBranch` succeeds**, rather than trusting the object read before the
  wait. `awaitBranch` confirms the branch *ref*; the pull request object's
  own `head_sha` field is a second, separately-cached value on both forges'
  APIs and is not guaranteed to have updated in the same round trip.
