# A branch that fell behind main parks at merge instead of catching up

## Approach

Give the `merge` gate its own catch-up act, run before it asks the forge to
merge, and let the existing revise machinery carry a conflict back to
`implement` unchanged.

`internal/run/gate.go`'s `approve` already reaches the forge directly
(`s.repo.Forge`) to read the pull request, merge it, and read the merge
commit — this is the precedent `internal/workspace/workspace.go`'s
`ForgeVerbs` doc comment names: "a merge is the mill's own act at the end of
a run... reached through forge.Forge directly and has no verb." Catch-up is
the same kind of act — host-side, engine-only, never something a session
asks for — so it is added the same way: a new host-side operation, called
from `approve` before `f.Merge`, never registered as a socket verb in
`internal/workspace/socket/socket.go`.

Concretely:

1. `approve` always fetches the pull request's target branch (`pr.Target`)
   first, with the same credential pattern `Push` already uses
   (`Verbs.OriginAuth`, `checkout.Signer.GitConfig()`). A fetch is a read; it
   needs the credential once, host-side, and afterwards the target's commits
   sit in the checkout's own object database, reachable by an ordinary local
   `git merge` that needs no credential at all — which is what lets a later
   `implement` attempt finish this without the sandbox ever holding a forge
   token (`docs/sandbox.md`'s boundary is about mutating the remote, not
   about reading refs the host already fetched).
2. If the branch already contains the target's head, catch-up is a no-op and
   `approve` proceeds to `f.Merge` as before.
3. Otherwise catch-up decides whether it may finish this itself by comparing
   two file sets since the branches' merge-base: the files *this PR's own
   commits* changed (what a reviewer's diff covers) and the files the
   *target's new commits* changed. If the two sets do not overlap, no file a
   reviewer looked at is touched by catching up, so catch-up performs the
   merge itself (`git merge --no-ff`, signed, pushed — reusing `Push`'s
   signing and push path) and `approve` proceeds to `f.Merge`. `--no-ff`, not
   rebase, because the ledger's evidence already points at SHAs on this
   branch; rebasing would rewrite them out from under evidence that has
   already closed steps, which is exactly what the `commit` skill's own
   "never rebase" constraint (`workflows/quick-fix/skills/commit/SKILL.md`)
   exists to prevent.
4. If the two sets overlap — the ordinary case a stale branch runs into,
   and the only case that can conflict — catch-up runs the merge to the
   point of staging it and stops: `git merge --no-commit --no-ff
   <fetched-ref>`, host-side, then *no commit*. Whatever that leaves in the
   working tree — conflict markers on unmerged paths, or a clean merge
   already staged — stays uncommitted. `runGate` turns the overlap into
   `result{judgment: true, feedback: <finding naming the overlapping files>}`
   with a non-nil error — the same shape `evidence.go`'s reviewer-verdict
   findings take (`{criterion, severity, summary, location}` in
   `workflows/feature/skills/review/verdict.schema.json`), so the note that
   reaches `implement` reads like a reviewer's blocking finding, not like a
   merge failure. `implement`'s session, on the same checkout, resolves any
   conflict markers the merge left by editing files — the ordinary edits it
   already makes — and explicitly does **not** commit: its own skill already
   says so ("Do not commit; the next step does",
   `workflows/quick-fix/skills/implement/SKILL.md`), and a commit a session
   made itself would carry no signature, because the signing key is never
   bound into the sandbox a session runs in
   (`internal/workspace/machine/machine.go`) — `pr`'s push refuses an
   unsigned commit outright (`ErrUnsigned`,
   `internal/workspace/verbs/verbs.go`). The merge is finished, and signed,
   by the ordinary `commit` step exactly as it finishes any other change:
   `git commit` with `MERGE_HEAD` already set (because catch-up stopped
   short of clearing it) commits as a merge, through the same host-side,
   signed `Commit` verb every other commit in the run already goes through
   — `commit`'s skill needs no change, because from its side this looks
   like any other dirty tree it stages and commits. This is what makes the
   result "go back through commit, clean-tree, pr and review" true for
   every case that touched anything a reviewer saw, not only the cases that
   fail to auto-merge: overlap, not conflict, is the signal, because a
   reviewer's approval of a file is stale the moment that file's content
   changes under it, whether or not git needed help combining it — and
   commit, not implement or catch-up, is still the only place a commit on
   this run's branch is made.
5. `merge`'s workflow declaration in both `workflows/feature/workflow.yaml`
   and `workflows/quick-fix/workflow.yaml` gains `on_failure: revise
   implement`. `internal/run/revise.go`'s existing `judgment` bypass
   (`failStep`, lines 72-77) already skips a judgment failure's own
   retry-and-reask loop and goes straight to `on_failure`, and `revise`
   already supersedes every step from `implement` through `merge`
   (`SupersedeSteps(FromStep, ThroughStep)`), which is what re-runs
   `commit`, `clean-tree`, `pr` and `review` on the caught-up branch. None
   of `revise.go` changes.

Two alternatives considered and rejected:

- **Do nothing beyond the merge gate itself; let `f.Merge`'s conflict
  surface as today.** This is the status quo the work order is closing:
  `f.Merge`'s conflict is a `MergeRefusedError`, non-retryable, and the gate
  has nowhere to send it — the run parks with a human holding the bag on a
  routine rebase. Rejected because it satisfies none of the three
  acceptance criteria.
- **A new `check` step (e.g. `catch-up`) plus a new session-reachable socket
  verb, sitting between `pr` and `merge`.** This was the working leaning
  after the think step, but it does not fit the codebase's own boundary: a
  check step's command runs inside the sandboxed machine, which by design
  (`docs/sandbox.md` — "a session's own `git push` inside the machine has no
  credential and fails; that is the design, not a bug") never holds a forge
  credential. Catch-up needs one, for the same reason `Push` does. Rejected
  because it would require inventing a new session-reachable verb for an act
  the codebase has already decided sessions never perform, when the merge
  gate already has direct, credentialed forge access sitting one call above
  where the conflict would otherwise surface.

## Steps

1. **Add the catch-up operation, reachable only by the engine.**
   New `CatchUpRequest`/`CatchUpResult` types in
   `internal/workspace/workspace.go` (mirroring `PushRequest`/`PushResult`'s
   doc-comment style, but declared as plain types, not as a method on the
   session-facing `ForgeVerbs` interface): `Target` empty means the
   repository's default branch; the result carries `UpToDate bool`,
   `Merged bool`, `SHA string` (the new head, when merged and pushed by
   catch-up itself), and `Overlap []string` (the files both sides touched,
   when catch-up instead left a merge staged, uncommitted, in the working
   tree for `implement` and `commit` to finish).
   Implement the operation as a plain method on `verbs.Verbs` in
   `internal/workspace/verbs/verbs.go`, alongside `OriginAuth` rather than
   on `forgeVerbs` — it is not part of the gated, session-facing verb set —
   reusing `f.v.Checkout()`, `OriginAuth`, `checkout.Signer.GitConfig()` and
   the `signed` check `Push` already applies. Expose it on the concrete
   `local.Workspace` / `machine.Workspace` types
   (`internal/workspace/local/local.go`, `internal/workspace/machine/machine.go`)
   the same way `GitRunner()` already is, and add it to the `run.Workspace`
   interface `internal/run/run.go` declares for the loop's own use (line 70)
   — that interface, not `workspace.Workspace`, is what `s.workspace` is
   typed as in `internal/run`, and is the actual chokepoint that makes the
   operation callable from `approve`. It is added to none of
   `workspace.Workspace`, `workspace.ForgeVerbs`, or
   `internal/workspace/socket/socket.go`'s verb table, so no session and no
   socket call can reach it.
   Files touched: `internal/workspace/workspace.go`,
   `internal/workspace/verbs/verbs.go`, `internal/workspace/local/local.go`,
   `internal/workspace/machine/machine.go`, `internal/run/run.go`.
   Proof: `go test ./internal/workspace/...` passes, including new cases
   covering: already up to date (no-op); target advanced in files this
   branch never touched (merges, signs, pushes, reports the SHA); target and
   branch both touched the same file, whether or not git could auto-merge it
   (runs `git merge --no-commit --no-ff`, leaves the result — staged
   cleanly, or with conflict markers on unmerged paths — uncommitted in the
   working tree, and reports the overlapping files; makes no commit and no
   push).

2. **Wire it into the merge gate.** `internal/run/gate.go`'s `approve` calls
   the new catch-up operation before reading `pr.Merged()` / calling
   `f.Merge`. `runGate` is changed so that a non-empty-`Overlap` result
   produces `result{judgment: true, feedback: <finding text>}` and a
   non-nil error, instead of the generic error `approve` would otherwise
   return; an `UpToDate` or `Merged` result falls through to `f.Merge`
   exactly as today.
   Files touched: `internal/run/gate.go`.
   Proof: `go test ./internal/run/...` passes, including new cases in
   `gate_test.go` (or the existing gate test file) covering: catch-up is a
   no-op when the branch is current and `f.Merge` is still called; a
   non-overlapping catch-up merges, pushes, and `f.Merge` is still called;
   an overlapping catch-up returns `judgment: true` with feedback naming the
   overlapping files, leaves the merge staged uncommitted in the checkout
   for `implement` and `commit` to finish, and never calls `f.Merge` at
   all — this is what makes criterion 3 hold structurally, not by
   convention.

3. **Send a caught-up conflict back to `implement`.** Add
   `on_failure: revise implement` to the `merge` step in
   `workflows/feature/workflow.yaml` and `workflows/quick-fix/workflow.yaml`.
   No other field on `merge` changes; `retries: 1` stays as it is, now
   governing rounds of catch-up-conflict findings the same way it already
   governs any other judgment on this step.
   Files touched: `workflows/feature/workflow.yaml`,
   `workflows/quick-fix/workflow.yaml`.
   Proof: `go test ./internal/workflow/...` passes unchanged (`Validate`'s
   "revise targets an earlier step" rule holds: `implement` precedes
   `merge` in both workflows), plus a new assertion in
   `internal/workflow/feature_test.go` (and the quick-fix equivalent) that
   `merge`'s `on_failure` is `revise implement`.

Steps are ordered so the tree builds and every existing test still passes
after each one: step 1 adds an operation nothing calls yet, step 2 calls it
from a codepath already covered by `internal/run`'s own tests, and step 3
only changes workflow declarations that step 2's behavior already justifies.

## Risks

- **GitHub and GitLab differ in how cleanly "fetch + merge --no-ff + push"
  maps onto their permissions model.** A branch protection rule that
  forbids merge commits, or requires the push to go through the forge's own
  API, would make a locally-built merge commit unpushable even though it
  merged cleanly. Mitigated by reusing `Push`'s existing signed-push path
  exactly, so a repo that already accepts the run's ordinary commits accepts
  this one; a repo that would refuse it refuses today's `Push` too, and the
  refusal is not new behavior this change introduces.
- **A catch-up that needs the target branch's full history costs a fetch on
  every merge-gate attempt**, including auto-approved ones that were already
  current. Bounded by the operation being a no-op (ancestry check only)
  when the branch already contains the target's head, so the cost is one
  cheap fetch per attempt, not a merge on every attempt.
- **The overlap finding's shape must actually match what `implement`'s
  skill expects to receive as feedback**, or the revise loses information a
  human would need to resolve it by hand. Mitigated by shaping it like
  `workflows/feature/skills/review/verdict.schema.json`'s finding
  (criterion, severity, summary, location), which `implement` already knows
  how to read from `review`'s revises. The finding needs no separate pointer
  to what to merge — catch-up already left the merge staged in the working
  tree `implement` starts in, so `git status` shows the same files the
  finding names.
- **A file-level overlap check is coarser than a real conflict.** Two
  commits can touch the same file in unrelated hunks and merge cleanly, so
  some of what this routes to `implement` would have merged with no human
  or model attention at all. Accepted rather than mitigated: the criterion
  is "if the catch-up touched anything a reviewer saw," and a file a
  reviewer saw changing at all is exactly that, whether or not git needed
  help combining it — the cost is an occasional implement attempt that
  turns out to be `git merge` with no conflicts to resolve, not a wrong
  result.
- **A refusal at `f.Merge` itself is still not classified** (`internal/forge`'s
  `Retryable` has no caller in `internal/run` before or after this change).
  Because catch-up runs fresh on every attempt, a race — the target moving
  again in the gap between catch-up's push and `f.Merge` — is absorbed by
  the merge step's existing retry, which re-enters `approve` and re-runs
  catch-up from the top. A refusal that is not a race (a protected-branch or
  required-review rule) still spends that one retry before parking, but it
  is not the conflict this node is about, and GitHub and GitLab both return
  the same ambiguous status for a conflict and for those refusals
  (confirmed in `internal/forge/github/github.go` and
  `internal/forge/gitlab/gitlab.go`'s `Merge`), so `f.Merge`'s own failure
  cannot reliably tell the two apart. Left as-is; not part of this change.

## Decisions

- **Merge, not rebase**, for catch-up. Rebasing would rewrite the SHAs the
  ledger's evidence already closed on; `--no-ff` preserves every commit this
  run has made, matching the `commit` skill's own constraint against
  rewriting history.
- **File overlap with the PR's own diff, not "git could not auto-merge," is
  what decides whether catch-up may finish the merge itself.** A reviewer's
  approval is of a diff against the target branch; anything that changes a
  file inside that diff invalidates it whether or not the merge needed
  manual resolution, so the plan sends both cases — a real conflict and a
  clean three-way merge of a shared file — back through `implement`,
  `commit`, `clean-tree`, `pr` and `review`, and reserves the silent,
  no-review-needed path for the case where the two sides touched no file in
  common at all.
- **Catch-up is engine-only, reached the same way `f.Merge` already is** —
  directly from `internal/run/gate.go`, never as a session-reachable check
  step or socket verb — because the sandbox's credential boundary
  (`docs/sandbox.md`) means a session-side implementation would need a new
  kind of credentialed verb the codebase has deliberately avoided giving
  sessions for merging, and the merge gate already has everything catch-up
  needs one call above where the conflict would otherwise surface. Only the
  fetch is credentialed; the `git merge --no-commit` catch-up runs
  afterward is a local object-database operation needing no credential at
  all, so doing it host-side costs nothing extra, and it is what leaves
  `implement`'s session something to resolve by editing rather than a bare
  list of filenames and no way to reproduce the state itself.
- **The stale-branch conflict path never reaches `f.Merge`.** Catch-up runs
  first, on every attempt, so the ordinary case this node is about — a
  branch and its base touching the same file — is caught and routed to
  `implement` before it could ever cause `f.Merge` to fail with
  `MergeRefusedError`. `f.Merge`'s own residual ambiguity between a
  protected-branch refusal and a race is called out under Risks and left to
  the step's existing single retry, not solved here.
- **Reuse the existing `judgment` bypass and `revise implement` rather than
  changing `internal/run/revise.go`.** The mechanism a reviewer's blocking
  finding already uses is the same shape a catch-up overlap needs: not the
  step's own failure, addressed to the implementer, bounded by the step's
  own retries. No changes to `revise.go` are needed or made.
- **Where the work order was silent on which branch to catch up against**:
  the pull request's own `Target` field (`forge.PullRequest.Target`), not a
  hardcoded `main` — the same field `pr`'s skill leaves empty to mean "the
  repository's default branch," so catch-up follows whatever the PR was
  actually opened against.
