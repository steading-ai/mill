# Activity records with invalid UTF-8 are dropped with a warning

## Approach

Add an additive `sanitized` bool to `Activity` and, right before `proto.Marshal` writes a record, walk the whole message with a proto-reflection recursion — every `string`-kind field, including list elements, map values, and nested messages such as `ToolCall.arguments` (`google.protobuf.Struct`) — replacing any value that is not valid UTF-8 with the same bytes run through `strings.ToValidUTF8`, and set `sanitized` when anything changed. This mirrors `internal/workspace/redact/redact.go`'s existing `Redactor.Message`/`redactMessage` walk, which already solves "touch every string field of an `Activity` uniformly" for redaction; sanitization is the same shape of problem and should not invent a second one. Running the walk after the ceiling's own truncation (`applyCeiling`/`summarize`) also closes a second, previously unnoticed source of the same failure: `summarize`'s byte-slice cutoff can itself split a multi-byte rune and produce invalid UTF-8 independent of the original tool output.

Rejected:
- **Retyping the vulnerable fields (`ToolResult.content`, `Text.text`, etc.) to `bytes`** — the work order's other allowed option. It is not blocked by policy (`proto/README.md` allows a breaking change pre-1.0 as a deliberate decision), but it ripples into every current string-based reader (`RenderActivity`'s formatting, `seal.go` coalescing, `store/convert.go`) and does not actually remove the underlying problem: `mill logs` still prints to a terminal, so invalid bytes still need sanitizing at render time even if the wire type is lossless. It only wins if a byte-exact tool result is a hard requirement, and nothing in `docs/activity.md` or the incident asks for that.
- **Sanitizing only `ToolResult.content`** — the field actually seen breaking. Cheaper, but the acceptance criteria explicitly name "tool result *or session text*", so `Text`/`Thinking`/`Prompt`/`HarnessStderr` would stay exposed to the identical bug, and a generic walk costs little more than an enumerated one while covering the `Struct` case too.
- **Sanitizing in the log line only, no new proto field** — the smallest possible change, but it fails criterion 1 outright: the criterion requires the persisted *record* to say it was sanitised, not just the operational warning.

## Steps

1. **Add the `sanitized` field to the contract.** Add `bool sanitized = 28;` to `message Activity` in `proto/mill/v1/mill.proto`, with a doc comment saying what it means (a string field of this body held invalid UTF-8 and was rewritten with the replacement character). Regenerate with `buf generate`. Proof: `make check-generated` (or the equivalent manual diff against a scratch `buf generate` output) reports no drift, and `go build ./...` still compiles with the new field unused.

2. **Sanitize before marshal.** In `internal/run/activity.go`, add `sanitizeUTF8(m protoreflect.Message) bool`, the reflection walk described above, and call it in `activityWriter.append` immediately before `proto.Marshal(a)` (after `applyCeiling`, so a ceiling-truncated body is also covered), setting `a.Sanitized = true` when it returns true. Proof: the existing suite in `internal/run/activity_test.go` — in particular the two ceiling tests, which assert exact `Content` equality for pure-ASCII input — must still pass unchanged, proving the walk is a no-op on valid UTF-8.

3. **Prove the acceptance criterion.** Add a spec to `internal/run/activity_test.go`: record a `ToolResult` whose `Content` contains `\xff`, assert `Record` succeeds (not dropped), the stored record has `GetSanitized() == true`, `GetToolResult().GetContent()` is valid UTF-8 (`unicode/utf8.ValidString`) and equals the expected replacement-character rewrite, and that `RenderedLog` (what `mill logs` reads) returns the sanitized text. Proof: `go test ./internal/run/...` — this spec is the proof `mill#54`'s acceptance criteria ask for directly.

4. **Name the record kind and the tool call in the warning.** Add `activityLogFields(a *millv1.Activity) []any` to `internal/run/activity.go`: returns `"source"`, and, when the body's oneof is set, `"kind"` (the oneof field's name, e.g. `"tool_result"`), plus `"call_id"` when the body is a `ToolResult`. Wire it into `internal/run/execute.go`'s `recordActivity`, appending these fields to the existing `Warn` call alongside `run`/`step_run`/`error`. Proof: a direct unit test of `activityLogFields` in `internal/run/activity_test.go` (or a small Go `Test...` function) asserting it returns `kind=tool_result` and `call_id=<id>` for a `ToolResult` activity, and just `kind` (no `call_id`) for e.g. a `Text` activity. Testing the pure helper is the right-sized proof; the one-line call-site change in `execute.go` needs no separate integration test.

## Risks

- **Field number collision.** If another change lands a field at `28` on `Activity` first, re-check the message before editing and use the next free number.
- **Toolchain absence.** `buf`/`go`/sidecar deps are pinned in `mise.toml` and resolve via `mise exec` in this checkout; if a different execution environment lacks them, `make sidecar-deps` documents how to fetch what `buf generate --template buf.gen.ts.yaml` needs.
- **Under-proving criterion 3.** Testing `activityLogFields` in isolation, rather than forcing a real write failure through the full `Runner`/`state` machinery, is a judgment call about proportionality. If review disagrees, the fallback is a heavier integration test that closes the activity file out from under a live `Runner` and asserts the captured `slog` output (there is precedent for capturing `slog.NewTextHandler` output to a `strings.Builder` in `internal/run/retention_sweep_test.go`).
- **Tagged release.** `mill.v1` has a tag (`v0.1.0`), and `proto/README.md` treats a breaking change to a tagged contract as needing a new package version. This plan's field addition is non-breaking, so it does not trigger that; `buf breaking` in Proof is the check that would catch it if the change accidentally became breaking.

## Decisions

- **New field, not a retyped one.** `sanitized` is added as a new `bool` on `Activity` rather than turning the affected `string` fields into `bytes`; the work order allowed either, and the additive route touches nothing downstream that already assumes `string` (`RenderActivity`, `seal.go`, `store/convert.go`).
- **No index/store propagation.** `sanitized` is not added to `ActivityIndexRow`, the `activity` SQL table, or `sqlc` queries — `docs/activity.md` states index columns are added only once a query needs one, and none does yet.
- **Whole-message walk, not a per-field patch.** Sanitization covers every `string`-kind field reachable from `Activity`, not just `ToolResult.content`, so `Text`/`Thinking`/`Prompt`/`HarnessStderr` and `ToolCall.arguments` (a `Struct`) are covered by the same code path the acceptance criteria's "tool result or session text" wording implies.
- **Sanitize after truncation.** The walk runs after `applyCeiling`, so a ceiling-truncated `tool_result` summary — which can itself contain a byte-sliced, invalid UTF-8 fragment — is also covered, not just the pre-truncation body.
- **`docs/activity.md` left unedited.** It is marked draft-for-review and already lags the shipped schema; keeping it current is out of scope for this fix.
