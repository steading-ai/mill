# WatchRuns: the ledger's change stream from a cursor

## Approach

Add `WatchRuns` as a server-streaming RPC that reads the `events` table
through a new global `(occurred_at, id)` index, reusing the `Observer`
wake primitive `Logs`' every-run follow (`internal/server/logs.go`
`logsFollowEveryRun`) already established, plus a keepalive ticker `Logs`
does not need. This was chosen over two alternatives:

- **A dedicated outbox table**, which the work order floats as the
  alternative if `events` "cannot carry a cursor index without
  partitioning." It can: the table is small (append-only, "tens of runs a
  day" per `docs/ledger.md`'s own argument against partitioning), and a
  second, differently-ordered index costs one migration. An outbox would
  dual-write every one of the ~10 call sites that already write `events`
  and duplicate data the audit table already holds, for no benefit at this
  volume. Rejected as disproportionate.
- **A standalone poll loop with no `Observer` reuse**, the smallest
  possible diff. Rejected because it would give `WatchRuns` different
  latency and reconnect characteristics from its nearest sibling (`Logs`)
  for no stated reason — the kind of divergence a reviewer following
  Chesterton's Fence would flag, since the codebase has exactly one wake
  primitive for exactly this shape of problem.

Message shape mirrors skift's `WatchEventsResponse` (an optional event
submessage plus an always-present cursor) rather than reusing `mill.v1`'s
existing `Event` message (`proto/mill/v1/mill.proto:960`), because `Event`
carries `before`/`after` `Struct` fields the work order explicitly says to
leave out ("Keep the response small... do not attach the run"). A new,
narrower `RunEvent` message is defined instead.

`WatchRuns` inherits the same latency floor `Logs`' every-run follow has
today: only `CreateRun` pushes an eager `Observer.Signal("")`; every other
event-producing write is picked up on the `Observer`'s existing 5s fallback
timer. This satisfies the acceptance criteria ("prints a line... as it
happens") at the same cadence `Logs --follow` already ships, and widening
every write's signalling is a separate, additive change if a future node
asks for tighter latency — not attempted here.

## Steps

1. **Proto contract: `WatchRuns` RPC and messages, generated.**
   `proto/mill/v1/store.proto`: add `WatchRunsRequest` (`cursor` string,
   `project` string), `WatchRunsResponse` (`cursor` string, `RunEvent`
   event), `RunEvent` (`run_id`, `node_ref`, `step_run_id`, `op`,
   `occurred_at`), and `rpc WatchRuns(WatchRunsRequest) returns (stream
   WatchRunsResponse)` on `StoreService`, doc-commented in the same style
   as the RPC list's existing entries (see `Logs`'s comment at
   `store.proto:203-207` for the model). Run `make generate` to regenerate
   `gen/mill/v1` and `gen/mill/v1/millv1connect`.
   `internal/server/store_service.go`: implement a minimal `WatchRuns`
   handler that validates the request and sends only the opening-position
   message (cursor, no event) — the smallest body that satisfies the
   `StoreServiceHandler` interface `var _ millv1connect.StoreServiceHandler
   = (*StoreService)(nil)` (`store_service.go:59`) already asserts, so the
   tree keeps compiling. No event reading yet.
   `internal/server/permissions.go`: add
   `millv1connect.StoreServiceWatchRunsProcedure: interceptor.PermissionRead`
   to the `permissions` map (`:22-33`), alongside `Status`, `Inspect`,
   `Logs`. Without this the interceptor's documented default
   (`:18-20`, "an RPC added without a decision about who may call it is one
   only the service's own uid reaches") applies, and the console — a
   reader-role caller, per the node's own Context — could never reach the
   RPC this step exists to give it.
   *Proof:* `buf lint`, `make generate` (no diff beyond what's committed),
   `go build ./...`; a new Ginkgo spec in `internal/server/watch_runs_test.go`
   asserting a fresh subscription with no cursor receives exactly one
   message carrying a cursor and no event; and a new
   `DescribeTable`/`Entry("WatchRuns", ...)` row alongside the existing
   `Status`/`Logs` entries in `internal/server/permissions_test.go`'s "the
   read verbs need only read" table (`:15-26`), asserting `WatchRuns`
   resolves to `PermissionRead` rather than falling to the unclassified-RPC
   default `permissions_test.go:61` covers.

2. **Migration: a global cursor index on `events`, and the decision recorded.**
   `internal/store/migrations/00023_events_watch_index.sql`: `CREATE INDEX
   events_occurred_at_id_idx ON events (occurred_at, id)`, `+goose Up`/`Down`
   in the style of `00011_events.sql`. `docs/ledger.md` §events
   (`:190-194`): amend "it is not a change stream for consumers; nothing
   subscribes to it" to say `WatchRuns` reads the table from a cursor of
   `(occurred_at, id)`, name the new index, and record the index-over-outbox
   decision and its reasoning (the argument already in the doc against
   partitioning applies to this index too) — this is also the acceptance
   criterion "`docs/ledger.md` §events no longer says nothing subscribes to
   it."
   *Proof:* `make db-migrate` applies cleanly against a fresh database;
   `internal/store/migrations/migrations_test.go`'s existing up/down-round-trip
   spec passes unmodified against the new migration; `go test
   ./internal/store/migrations/...`.

3. **Store query: events across runs, joined for `node_ref`, ordered and windowed.**
   `internal/store/queries/events.sql`: a new sqlc query (e.g.
   `WatchableEvents`) selecting `events` joined to `runs` for `node_ref`,
   filtered by `occurred_at, id > cursor` and, when given, `runs.node_ref
   LIKE $project || '#%'` (matching the existing project-filter convention
   at `internal/store/queries/runs.sql:104`), ordered `occurred_at, id`.
   Run `make generate` (sqlc) to produce `internal/store/events.sql.gen.go`.
   A small domain/store-level helper wraps it with the stale-cursor check:
   refuse a cursor older than the configured window before running the
   query.
   *Proof:* a db-labelled Ginkgo spec (`Label(testsupport.DBLabel)`, the
   pattern `internal/store/store_test.go` and `internal/server/logs_test.go`
   already use) asserting events from two different runs interleave in
   `(occurred_at, id)` order, and that a `project` filter excludes the
   other project's events.

4. **Wire the read into `WatchRuns`: catch-up, follow via `Observer`, keepalive.**
   `internal/server/store_service.go` (or a new `internal/server/watch_runs.go`
   alongside `logs.go`, mirroring its `logsFollowEveryRun` shape): on open,
   validate/decode the cursor (empty means start from now — encode as
   `occurred_at` at call time with no prior `id`), refuse one older than the
   window with `connect.NewError(connect.CodeFailedPrecondition, ...)`
   naming the window in the message text; then loop: `Observer.Subscribe("")`,
   read events since cursor (step 3's query), send each as a `RunEvent`,
   advance the cursor, `Observer.Wait` — with an added `time.Ticker`
   (interval configurable, 30s default per the deliverable) in the same
   `select` so an otherwise-idle wait still emits a cursor-only keepalive
   message at least that often. The replay window and keepalive interval are
   new `StoreServiceOption`s (mirroring `WithMcpServers`,
   `store_service.go:32-36`), defaulting to 24h and 30s, wired from a new
   `serve` flag in `internal/cli/serve.go` alongside where
   `server.NewObserver(server.DefaultObserverFallback)` is already
   constructed (`serve.go:165`).
   *Proof:* Ginkgo specs in `internal/server/watch_runs_test.go` (db-labelled)
   for the four scenarios the work order names: an event written during a
   live subscription arrives exactly once; a subscriber that reconnects with
   its last received cursor sees no gap and no duplicate across the
   reconnect; a cursor older than the window is refused with
   `CodeFailedPrecondition` and a message naming the window's length; and
   the Gherkin scenario verbatim — a subscriber holding the opening cursor
   before calling `Status` sees a step close that happens in between arrive
   as an event after that cursor. A keepalive spec with a short configured
   interval asserting a cursor-only message arrives within it when nothing
   else has happened.

5. **CLI: `mill status --follow`, the stream's proof from the outside.**
   `internal/cli/read.go`'s `newStatusCommand`/`runStatus` (`:148-183`)
   gains a `--follow` (`-f`) flag. When set, instead of one `Status` call it
   opens `WatchRuns` and prints one line per event as it arrives (op,
   node_ref, run/step, timestamp) — the CLI's proof of the stream, in the
   spirit of `mill logs --follow`'s rendering in `internal/cli/logs.go`. On
   a broken stream it reconnects with the last cursor it held, so a restart
   of `mill serve` mid-follow resumes without a duplicate or a gap
   (acceptance criterion). Ctrl-C exits cleanly via
   `signal.NotifyContext`, matching `logs.go:149-153`'s pattern for a stream
   with no natural end.
   *Proof:* a CLI-level Ginkgo/table test (alongside `internal/cli/logs_test.go`'s
   pattern) driving `runStatus`/the new follow path against a fake or
   in-process `StoreService`, asserting: events print as they arrive, and a
   simulated stream break followed by reconnect emits no duplicate line for
   an event already printed.

6. **Docs: the CLI entry, and full-suite pass.**
   `docs/tools.md`: add `mill status --follow` next to the existing
   `mill logs --follow` documentation (`:241-254`), with an example
   transcript in the file's existing style. Confirm `docs/ledger.md`'s
   §events edit from step 2 and this entry are consistent with each other
   and with `docs/roadmap.md` O5 — left untouched deliberately (see
   Decisions).
   *Proof:* `make lint` (includes `docs_test.go`'s citation/deferral-language
   checks over any doc this step touched) and a full `make test`.

## Risks

- **The new index doesn't get used, or write-amplifies more than
  expected.** `EXPLAIN` the step-3 query against a seeded multi-run
  `events` table during that step, before wiring the handler around it; if
  the planner doesn't pick the index, the index definition (not the
  approach) is what's wrong.
- **`Observer`'s `""`-key signalling is sparser than `WatchRuns` needs**
  (only `CreateRun` pushes eagerly today, per Approach). If the acceptance
  criterion "prints a line... as it happens" is read strictly rather than
  as "within the existing ~5s fallback," the fix is additive — have
  `StartStepRun`/`CloseStepRun`/etc. also `Signal("")` — and does not change
  this plan's shape, only adds a step. Not done here on the assumption that
  `Logs`' existing cadence is the accepted bar.
- **CLI reconnect-with-cursor is the least-precedented piece** — nothing in
  `internal/cli` today reconnects a broken stream. If step 5 turns out
  larger than estimated, it can land as its own follow-up commit within
  this same node without changing steps 1-4, since the RPC and server side
  are complete and independently testable before the CLI exists.
- **`docs/roadmap.md` O5 goes stale** ("deferred until a consumer asks") the
  moment this ships, but it is not a named deliverable and AGENTS.md says a
  work order is the only reason to touch a design document. Left alone;
  named here so a reviewer doesn't read the omission as an oversight.
- **A second `mill serve` instance would break `Observer`-based delivery**
  (in-process only). Nothing found in `docs/architecture.md` or
  `docs/roadmap.md` suggests more than one instance runs today; `Logs`
  already carries this same assumption. If that changes, both RPCs need
  revisiting together — not a risk unique to this change.

## Decisions

- **Index over outbox** for reading `events`: one new global index, not a
  second table. Reasoning in Approach.
- **`RunEvent` is a new, narrow message**, not the existing `Event`
  (`mill.proto:960`): the work order asks the response stay small and
  never carry `before`/`after`; `Event` carries both.
- **`op` stays a free-text `string`**, matching how `events.op` is already
  stored and how skift's own `WatchEventsRequest.ops` is typed — no new
  enum minted for it.
- **CLI surface: `mill status --follow`**, not a new `mill watch` verb —
  matches the already-documented `mill logs --follow` convention.
- **Replay window: configurable, default 24h**, as literally stated by the
  work order.
- **Keepalive: 30s default**, implemented as a `time.Ticker` arm alongside
  `Observer.Wait` — new relative to `Logs`, which needs none since its
  transport is a local unix socket with no intervening proxy; `WatchRuns`
  is written to the same expectation `Logs` has today (no public network
  exposure built by this node) but ships the keepalive anyway since the
  work order asks for it unconditionally.
- **`WatchRunsRequest` carries no `lease_id`**, matching every other
  read-only RPC (`Status`, `Inspect`, `History`, `Cost`, `Logs`, `WhoAmI`,
  `Health`).
- **Cursor encoding**: opaque to the client per the proto's own contract;
  implemented server-side as `occurred_at` (RFC3339) and `id` joined in a
  single string, matching `docs/ledger.md`'s "a cursor of `(occurred_at,
  id)`" language directly.
- **`docs/roadmap.md` is not touched**, per AGENTS.md's rule that a work
  order is the only reason to edit a design document; only `docs/ledger.md`
  and `docs/tools.md`, the two the work order names, are amended.
