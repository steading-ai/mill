# A red merge gate returns the failing check's log to the implementer

## Approach

Enrich at the evidence layer, not the gate layer: `internal/evidence/evidence.go`'s
`verifyStatus` is the one place that already decides what `status` evidence
means and what it says when it does not hold, and every workflow
(`workflows/*/workflow.yaml`) uses `status` evidence in exactly one place —
the merge gate — so enriching there reaches the merge gate's revise and,
through `checksFailedError.finding()` (`internal/run/gate.go:258-261`) and
`parkBody` (`internal/run/breaker.go:211-225`), the park gate's body, with no
changes needed in either of those two files. The rejected alternative — have
`internal/run/gate.go`'s `checksFailedError` call `forge.FailingChecks`
itself — would work today (nothing else consumes `status` evidence) but puts
forge-log knowledge in a layer that currently treats evidence failures as
opaque strings, and buys nothing over doing it once in `evidence.go`.

The log fetch is a **second method**, not a new field `FailingChecks`
always populates. `FailingChecks` already has one existing caller,
`internal/run/healing.go`'s `RedMainFindings`, which runs on the worker's
15-minute sweep (`DefaultSweepInterval = DefaultTTL`, `internal/run/run.go:55`)
against every configured project's default branch and only ever reads a
failing check's `Name`/`URL` (`internal/run/healing.go:271-291`) — never a
log. Making every `FailingChecks` call also fetch and filter a log would
tax that sweep, for every red repository, every 15 minutes, for a use it
never makes. So `CheckResult` gains `Conclusion` and an opaque `LogID` (both
free — no extra request, read off the same response `FailingChecks` already
decodes), and `Forge` gains a second method, `CheckLog(ctx, CheckResult)
(string, error)`, that `verifyStatus` calls once per failing check, only when
it is building the failure message a revise or a park needs. The smallest
alternative — do nothing beyond `checksFailedError`, and skip the
`evidence.Forge` interface change — was rejected because it does not
generalise: any future `status`-evidence caller would have to grow its own
copy of the same three lines gate.go would otherwise have needed. The
one-call-does-everything alternative (fold the log straight into
`FailingChecks`) was rejected for the sweep-cost reason above.

Filtering to failure lines and capping at 8 KiB is one function, shared by
both adapters (`internal/forge`), rather than written twice: GitHub and
GitLab already both import `internal/forge` for `CheckResult` itself, so a
third file there costs nothing new to reach and gives one place to fix the
filter's rules later.

## Steps

1. **Shared log-excerpt filter, package `internal/forge`.**
   New file `internal/forge/logexcerpt.go`: a function that takes raw log
   bytes and returns the lines containing any of the work order's failure
   keywords (`Error`, `FAIL`, `✘`, `expected`, `Received`, `exit code`),
   joined, then capped to 8 KiB by keeping the **tail** when the filtered
   text still does not fit — the same "the useful part is last" rule
   `internal/run/breaker.go`'s own `trimTail` already uses, restated here
   since `internal/forge` cannot import `internal/run` (the dependency runs
   the other way). No adapter, no network: this step is pure logic.
   *Proven by* a new `internal/forge/logexcerpt_test.go`: a log with no
   matching lines returns empty; a small log under 8 KiB passes through
   whole; a log whose matching lines still exceed 8 KiB is cut to its tail,
   on a rune boundary; a log with matches scattered through noise keeps only
   the matching lines. `go test ./internal/forge/...`.

2. **Widen the `Forge` contract.** `internal/forge/forge.go`: `CheckResult`
   gains `Conclusion string` (the forge's own word: GitHub's check-run
   `conclusion` or commit-status `state`; GitLab's job `status`) and `LogID
   string` (opaque; empty means this check has no log a forge can be asked
   for — a GitHub commit status has none). `Forge` gains `CheckLog(ctx
   context.Context, check CheckResult) (string, error)`, documented as
   fetching, filtering and capping that check's log, and refusing with a
   named reason — not a panic, not a zero value — when `check.LogID == ""`
   or the forge cannot serve the log (expired, forbidden). Every existing
   stub implementing `forge.Forge` needs the new method so the tree keeps
   building: `internal/forge/forge_test.go`'s `stubForge`,
   `internal/run/support_test.go`'s `fixtureForge`, and
   `internal/workspace/verbs/verbs_test.go`'s `catchUpForge` (which already
   refuses `FailingChecks` on principle — `CheckLog` gets the same
   "not catch-up's to call" refusal).
   *Proven by* `make build` and the full existing suite still green
   (`make test-unit`) — this step changes no behaviour, only the shape
   everything after it fills in.

3. **GitHub: `Conclusion`/`LogID` and `CheckLog`.**
   `internal/forge/github/github.go`: `checkRuns.Runs` gains `ID int64`
   (GitHub's check-run id, which is the Actions job id when Actions created
   the run — https://docs.github.com/rest/actions/workflow-jobs); `FailingChecks`
   sets `Conclusion: run.Conclusion` and `LogID: strconv.FormatInt(run.ID,
   10)` for check-run failures, and `Conclusion: status.State` with
   `LogID: ""` for commit-status failures (there is no job to ask GitHub
   for a log of). `CheckLog` refuses immediately with a named reason when
   `check.LogID == ""` ("reports through a commit status, not a check run:
   there is no log to read"); otherwise it does a raw (non-JSON, following
   redirects — `GET .../actions/jobs/{id}/logs` 302s to blob storage) fetch
   through a new small helper (`c.raw(ctx, path)`, alongside `c.call`, since
   `call` always JSON-decodes and the log body is plain text), strips the
   minted credential's own token out of the raw bytes before anything else
   touches them (defense in depth: nothing found under §Constraints wires a
   redactor into this path, so the adapter that knows the token is where it
   gets scrubbed), then hands the result to `forge.FilterLog` from step 1.
   A 404/403/410 from GitHub becomes the AC3 case: `CheckLog` returns an
   error naming the status GitHub gave, not a panic and not a silently empty
   excerpt.
   *Proven by* new cases in `internal/forge/github/github_test.go`
   (`httptest`-backed, matching the file's existing pattern): a check run's
   `FailingChecks` entry carries `Conclusion`/`LogID`; `CheckLog` against a
   fixture job-log body returns the filtered, capped excerpt; a token
   embedded in the fixture response never survives into the result;
   `CheckLog` against a 404 and a 403 names why, rather than erroring
   opaquely; `CheckLog` against a commit-status-only failure (empty
   `LogID`) refuses without a network call.

4. **GitLab: `Conclusion`/`LogID` and `CheckLog`.**
   `internal/forge/gitlab/gitlab.go`: `job` gains `ID int` and `Status
   string`; `FailingChecks` sets `Conclusion: j.Status` and `LogID:
   strconv.Itoa(j.ID)`. `CheckLog` fetches `GET
   /projects/:id/jobs/:job_id/trace` (plain text, no redirect dance GitHub's
   endpoint needs), scrubs the token, filters through `forge.FilterLog`. A
   trace GitLab refuses (expired job, forbidden) becomes the same AC3 shape
   as GitHub's.
   *Proven by* new cases in `internal/forge/gitlab/gitlab_test.go`,
   mirroring step 3's list one-for-one (GitLab has no commit-status
   equivalent, so every `FailingChecks` entry here always carries a
   `LogID`; there is no "no log to read" case to cover for GitLab, only the
   forge-refuses cases).

5. **Wire the excerpt into `status` evidence.**
   `internal/evidence/evidence.go`: the `Forge` interface (`evidence.go:78-84`)
   gains `FailingChecks(ctx, sha) ([]forge.CheckResult, error)` and
   `CheckLog(ctx, forge.CheckResult) (string, error)`. `verifyStatus`, on
   `forge.Failed`, calls `FailingChecks`; for each result it calls
   `CheckLog` and writes one block per check — the check's name and
   conclusion as a header, then the excerpt, or (AC3) the reason `CheckLog`
   gave when it errored, in its place. This composed text becomes
   `NotVerifiedError.Reason`, replacing today's one-line
   `"the forge reports the checks on %s as failed"`. A `FailingChecks` call
   that itself errors, or that returns nothing (status is `Failed` but no
   check names itself, which today's code already tolerates in
   `internal/run/healing.go`'s `redMainFinding`), falls back to the
   existing bare sentence rather than producing an empty or malformed
   message.
   *Proven by* new cases in `internal/evidence/evidence_test.go`: a failed
   status with one failing check produces a `NotVerifiedError.Reason`
   containing the check's name and its excerpt; a `CheckLog` error is named
   rather than swallowed; a `FailingChecks` error, or an empty result,
   falls back to the current one-line message so nothing regresses when a
   forge cannot say more.

6. **Update the pinned merge-gate spec and add the work order's own
   scenario.** `internal/run/gate_test.go`'s existing assertions at
   `gate_test.go:516-518` (`ContainSubstring("the forge reports the checks
   on")`, `"as failed"`, `"Nothing was merged"`) still hold — the header
   sentence is unchanged, only what follows it grows — so no existing
   assertion breaks, but `internal/run/support_test.go`'s `fixtureForge`
   needs a way to script `FailingChecks`/`CheckLog` return values for a
   scenario to drive. Add the acceptance criterion 1 scenario itself:
   given a fixture forge whose `FailingChecks` names one check and whose
   `CheckLog` returns a body containing `run-verbs.spec.ts:67` and
   `expect(locator).toBeDisabled() failed` (filtered through the real
   `forge.FilterLog`, not hand-trimmed, so the spec proves the whole path),
   the revise `implement` receives names both.
   *Proven by* the new spec in `internal/run/gate_test.go`, run under
   `Describe("The merge gate reads the forge's checks before it merges")`
   alongside the existing ones.

7. **Live tier.** `internal/forge/github/live_test.go` and
   `internal/forge/gitlab/live_test.go` each get one case exercising
   `FailingChecks` + `CheckLog` against a real red commit in the guest's
   configured scratch repository (docs/runbook.md's existing live-tier
   pattern — these files already gate on a live credential being present).
   *Proven by* `make test-acceptance` (or the live-tagged subset the two
   files already use) passing in the guest.

## Risks

- **GitHub's check-run id is not always the Actions job id.** True only for
  check runs a third-party GitHub App created rather than Actions itself;
  handled by treating a `CheckLog` call against such an id as any other
  forge refusal (404) — AC3's "log cannot be read" path already covers it,
  so no special detection is needed, only the existing refusal handling.
- **The failure-keyword filter fragments a multi-line assertion** (e.g. a
  Jest `expected`/`Received` pair on separate lines with an unmatched line
  between them). Step 1's spec is written against exactly the scenario named
  in the work order (steading#9's run) to catch this before it reaches the
  adapters; if the plain per-line filter fragments it, the fallback inside
  step 1 is to keep a fixed window of context lines around each match
  rather than only the matching line itself — decided in that step, not
  guessed here.
- **Rate limiting from the live-tier or a red repository's repeated sweep.**
  Only `verifyStatus` calls `CheckLog`, and only when a `status`-evidence
  step's check is actually being verified (bounded by the merge gate's own
  retry cadence) — `RedMainFindings`'s sweep never calls it, by design (see
  Approach). No new risk beyond what `FailingChecks` already costs today.
- **`CheckResult`'s new fields are additive**, so nothing already decoding
  or constructing one breaks; the only breaking surface is the `Forge`
  interface gaining `CheckLog`, contained to the stub list in Files above.

## Decisions

- `FailingChecks` stays log-free; the log fetch is a separate `CheckLog`
  call the evidence layer makes per failing check, not a field
  `FailingChecks` always populates — see Approach.
- The filter-and-cap function lives in `internal/forge` (not duplicated per
  adapter, not in `internal/evidence`), since both adapters already depend
  on that package for `CheckResult`.
- Redaction of the mill's own forge token out of a fetched log is done by
  the adapter that minted the credential, at fetch time — no existing
  cross-cutting redactor reaches gate or comment bodies, so this is the
  narrowest place that can guarantee it.
- A check with no log to offer (`LogID == ""`, GitHub's commit-status case)
  refuses from `CheckLog` with a named reason rather than being silently
  skipped, satisfying AC3 uniformly for both "no log exists" and "log
  exists but the forge refused it."
- `verifyStatus` falls back to today's one-line message when `FailingChecks`
  itself errors or returns nothing, rather than inventing a message with no
  check to point at — this keeps the change additive for the case nothing
  changed about.
