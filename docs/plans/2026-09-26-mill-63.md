# A usage cap parks every run and then every ready node

## Approach

Build the work order's own design: the gateway is the detector, because it is
the only place that sees every upstream response — including the 429 and its
headers that a session's own sidecar classification (`sidecar/src/exit.ts`)
never gets to look at. Three pieces, in order of how far they reach:

1. **The gateway observes every forwarded response**, not just the `200`s it
   already counts usage from. A `429` or `5xx` — or an upstream it could not
   reach at all — is recorded per step and process-wide, with whatever reset
   time the response named. A `200` clears both.
2. **The run loop consults the gateway before the sidecar's own exit reason.**
   A step the gateway saw refused is routed into mill#57's existing
   `upstreamRefusal` path the same as a sidecar-classified one — reusing, not
   duplicating, mill#57's streak/wait/give-up machinery — except that when a
   reset is known, the run waits until it instead of escalating and giving up
   at thirty minutes.
3. **The worker stops claiming while the account is capped.** A process-wide
   breaker in `Worker.claim()` — a new name, not `internal/run/breaker.go`'s
   park path — trips on the gateway's own process-wide observation and clears
   on a successful probe, so a worker holding no ready node still stops
   asking skift for one it cannot serve.

The reset is carried as a new field on `harness.v1.ProcessExit` rather than
gateway-local memory or a parsed string. `proto/mill/v1/mill.proto`'s
`StepRun.exit` is literally `harness.v1.ProcessExit` (confirmed by reading the
message: `harness.v1.ProcessExit exit = 10;`), so a field added to
`ProcessExit` reaches the ledger with no other schema change, is written by
the ordinary `FailStepRun` call `upstreamRefusal` already makes, and is
read back by `UpstreamStreak` the same way a fresh worker or `mill explain`
already reads the reason (Invariant 10). `internal/store/convert.go`'s
`stepRunProto` decodes `StepRun.exit` with `protojson.Unmarshal` from a JSON
blob column, so this needs no SQL migration either — a new proto field simply
appears in that JSON the next time it is written.

**Rejected: widen the sidecar's own classification instead.** `exit.ts`'s
`upstreamRefused` could be changed to also treat a `4xx` `api_error_status` of
`429` as an outage, with no gateway change at all. Rejected because the
sidecar sees only `api_error_status`, and the gateway's own budget refusal
*is* a `429` (`internal/gateway/gateway.go`'s `overBudget`, answered at
`ServeHTTP` with `rate_limit_error`) — a session that spent its budget would
be reclassified as an outage and retried forever rather than failing the way
the workflow's `on_failure` expects. The work order's own decision — "the
gateway is the detector" — exists exactly to avoid this: only the gateway
knows which `429` is whose. (In fact, reading `ServeHTTP` and `modifyResponse`
together shows the two never even reach the same code: `overBudget`'s refusal
returns before `g.proxy.ServeHTTP` is called at all, so a budget `429` never
reaches `modifyResponse`. The two 429s are already structurally apart; this
plan's job is to have the gateway also look at the ones that do reach it.)

**Rejected: gateway-detection with in-memory-only reset state.** Keep the
reset as a field on `*gateway.Gateway` alone, read by `internal/run` through
a new `Gateway.Refused` call but never written to the ledger. Rejected
because a worker restart mid-outage — the acceptance criteria's own
scenario — would lose it: the resumed run would recompute `UpstreamStreak`
from the ledger and find no reset, falling back to escalating-and-giving-up
even though the cap's reset is unchanged. Invariant 10 ("nothing is carried
in the worker's head") is exactly the reason mill#57 made `UpstreamWait`,
`UpstreamStreak` and `UpstreamGiveUp` pure functions over the ledger in the
first place; the reset has to live in the same place.

**Rejected (smallest possible): only add the worker-wide breaker, leave
retry/wait unchanged.** Stop `Worker.claim()` on any observed `429`/`5xx`,
without touching `upstream.go` or the exit classification at all. This alone
would satisfy AC2 (no more claims while capped) but not AC1, AC3 or AC4: the
two runs already in flight when the cap hits would still fail-and-retry on
mill#57's old 4xx-is-not-an-outage rule, exhausting real retries and parking
on a `429` the human can do nothing about, while the worker sits idle next to
them refusing to claim more work. Named as the baseline the work order asks
for, and rejected because it leaves the exact failure mode mill#63 exists to
fix.

## Risks

- **Whether the subscription's weekly cap refuses `count_tokens` the same as `messages` is not verifiable in this sandbox** (no live subscription-backed upstream to test against; the work order's own Notes flag the same gap). If it does not — the cap only ever refuses `messages` — `internal/gateway/probe.go`'s existing probe would report healthy while the account is still capped, and the worker breaker would clear early on a probe that never actually tested the capped path. Mitigation: before this node merges, run `mill doctor` (or `Gateway.Probe` directly) against a real capped account once and confirm it also answers `429`; if it does not, the fix is a one-line change to `Probe`'s request (from a `count_tokens` call to a minimal real `messages` call), named here so it is the plan's problem and not a surprise mid-implementation.
- **The exact header name for the subscription's own weekly/five-hour reset is not confirmed.** `https://platform.claude.com/docs/en/api/rate-limits` documents `anthropic-ratelimit-{requests,tokens,input-tokens,output-tokens}-reset` for the *organization* API's per-minute limits, and `retry-after` for both; a captured SDK transcript in this repo (`spikes/mcp/transcripts/mcp-only.jsonl`) shows the Claude Agent SDK surfacing a `rate_limit_event` with `resetsAt`/`rateLimitType: "five_hour"`/`"seven_day"` fields that do not match those header names, which is the *subscription* plan's own shape and is not documented as raw HTTP headers anywhere this plan could find. Mitigation: `observeUpstreamRefusal`'s header parsing is deliberately defensive — `retry-after` alone (always documented, always present on an ordinary rate limit) is enough to make AC1/AC3 work even if the subscription-specific header is never identified; a wrong or missing header name degrades to `Reset` staying zero, which falls back to mill#57's existing escalating-wait-then-park behavior, not a crash or a wrong wait. Confirm the real header by capturing one live `429` from a capped subscription account before or shortly after this ships, and add it to the parse list — this does not block the rest of the plan.
- **The worker breaker's interaction with `Concurrency > 1`.** Two runs already in flight when the cap trips each wait independently inside their own goroutine (mill#57's existing per-attempt `r.wait`), holding their own slots the whole time; the new worker-wide check in `claim()` only stops a *new* slot from being taken. This is the intended behavior (AC3: "no new work is claimed... while... two runs already in flight... wait"), not a bug, but it does mean a long-lived reset (the weekly cap can be days away) ties up up to `Concurrency` slots for that whole span, same as mill#57's escalating wait already does today for shorter outages — no new exposure, just a longer version of an accepted one.
- **A doubled observation path.** After step 3, a turn the sidecar itself classifies as an outage (a real `5xx`, `exit.ts`'s existing fallback) and one the gateway also saw refused are the same request; `gatewayUpstreamRefusal`'s mutation only *overwrites* `Reason`/`Reset` on the exit the sidecar already produced, never conflicts with it — confirmed by construction in step 3's design, not left as an open question, but called out here because a change to either side later must preserve this "gateway wins when it has an opinion, sidecar's own classification stands otherwise" ordering.
- **`internal/server/worker_service.go`'s exact location and shape (step 6) was not confirmed by this plan's own research** — only `proto/mill/v1/worker.proto` and mill#64's plan narrative were read, not the handler file mill#64 must have added. Named here rather than assumed: the implementer confirms the file first; the change itself (adding one field to a response the handler already builds from `Worker.State()`) is additive and low-risk regardless of which file it turns out to be.

## Decisions

- **The reset lives on `harness.v1.ProcessExit` as a new `google.protobuf.Timestamp reset` field**, not as a parsed string appended to a reason, and not as gateway-local memory. Chosen because `StepRun.exit` already *is* `ProcessExit`, so this is a zero-new-schema addition that Invariant 10 and `UpstreamStreak`'s existing ledger-only read pattern both already assume is how facts like this travel.
- **`UpstreamResetMargin = 30 * time.Second`** is added past a named reset before retrying (the work order says "plus a small margin" without a number). Thirty seconds was chosen to match the order of magnitude of `upstreamBaseWait` (15s) — enough to absorb clock skew and the cap's own propagation delay without meaningfully lengthening the wait.
- **A reset already in the past is treated as if none were known**, falling through to the existing escalating-wait-then-give-up policy, rather than retrying immediately in a tight loop or waiting forever on stale information. The work order says a known reset is "waited for, not given up on" but does not say what happens once it has passed and the upstream is still refusing; this plan chooses to keep mill#57's thirty-minute safety net for that case, counted from the streak's original `since` as it already is today.
- **The worker breaker is named `waitOutUpstream`/lives in `worker.go`, not `internal/run/breaker.go`**, per the work order's own instruction that `breaker.go` is the park path and this is a different thing.
- **No new `WorkerOptions.Gateway` field.** The worker reaches the shared `run.Gateway` through `w.options.Runner.options.Gateway` — the same value `internal/cli`'s `gatewayRunOptions` already wires into the runner from the process's one `*gateway.Server` — rather than plumbing a second copy through `internal/cli/work.go`. `Worker` and `Runner` are the same package, so the unexported field is already reachable; this avoids a redundant constructor argument for a value that only ever has one source.
- **The worker breaker's clearing probe is `Gateway.Probe`'s existing `count_tokens` request, reused rather than duplicated** — a successful probe is an ordinary `200` through `ServeHTTP`, which already clears the gateway's outage state via step 2's `clearUpstream`, so the worker never needs its own separate "tell the gateway it's healthy again" call. This is provisional on the Risks section's open verification of whether `count_tokens` is actually gated the same as `messages`.
- **`internal/run/select.go`'s assessment path is left untouched.** The work order's scope (the "Where" section, and every acceptance criterion) is the main run loop's step retries; extending the same treatment to tier assessment would be a second, unscoped feature.
