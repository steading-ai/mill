# A revise target resumed after a drain, cancel or restart starts without the findings that sent it back

## Approach

`internal/run/walk.go`'s `walk` holds a revise's findings in two locals,
`feedback`/`feedbackFrom`, set once from an `outcome` and handed to the next
step's prompt (`walk.go:72-73,119`). Nothing else carries them, which is
exactly the shape Invariant 10 (docs/ledger.md §"Resume in Go") forbids for
everything else the loop needs: `current_step` itself is re-derived from
`Inspect` on every pass, and the loop already has one precedent for feedback
specifically — `anySessionStarted`/`r.findings` (`walk.go:111-113`,
`preparatory.go:133-171`) rebuild a run's first-session findings from the
ledger every time, gated only on whether a session has already begun, so a
drain between "findings computed" and "session started" loses nothing. This
node gives a revise's or a retry's findings the same footing: derive them
from the ledger when nothing is already carried in memory, rather than only
carrying them.

Doing that needs two things the ledger does not yet reliably hold, checked
directly rather than assumed (Gather Context's task flagged this as a
disagreement with the work order's premise):

1. **The findings text itself, for a plain check/skill failure.** Today
   `internal/run/revise.go`'s `failStep` only attaches `Evidence` to a failed
   attempt when `res.judgment` is true — a reviewer's revise verdict
   (`revise.go:43-46`, added by mill#78). A check or skill step that fails
   and revises leaves `Evidence` unset; only `Exit` is recorded. `findings`
   (`revise.go:55-58`) is computed immediately after, from `res.feedback`
   (itself `check.Feedback(check, result)` — `internal/check/check.go:223-228`
   — for a check step, or a gate's own deny reason) or `cause.Error()`. That
   string is exactly what a resumed attempt needs back; it is simply not
   persisted yet for this case.
2. **A way to find, from the ledger alone, which attempt the current step's
   feedback answers**, and to do it correctly when more than one workflow
   step can revise the same target. `internal/run/verify.go` has
   `latestClosed` (closed attempts only) and `stepRunByID` (by id), but
   nothing that returns "the latest attempt of a step, whatever its status"
   — needed for a step whose latest row is `SUPERSEDED` (a revise target) or
   `FAILED` (a retry not yet retried). And `workflows/feature/workflow.yaml`
   has two steps naming `implement` as their revise target — `review`
   (`workflow.yaml:322`) and `merge` (`workflow.yaml:345`) — so "the step
   that revised this one" is not always a single named step; it has to be
   found by which candidate's attempt is actually the latest, not by name
   alone.

The plan adds both, plus one small derivation function wired into `walk`
exactly where `r.findings` already is, composed with it via the existing
`withFindings` rather than gated on an all-or-nothing "is feedback already
non-empty" check — a retried skill step whose session never started can
legitimately owe both the run's provisioning findings and its own revise
feedback at once, and the two must not silently replace each other.

**Rejected alternative: derive `feedback`/`feedbackFrom` unconditionally on
every pass, removing the in-memory fields entirely** (Think's Approach 3).
This is the more "pure" reading of Invariant 10 and was the initial leaning,
but it is a larger diff for no behavioral gain: the in-memory path and the
ledger-derived path would have to agree byte-for-byte on every non-interrupted
pass anyway (same functions read the same rows), and rejecting it keeps
`outcome.feedback`/`feedbackFrom` — and every existing caller of
`stepUnderBoundary` — untouched. If step 3 below turns out to need
substantially the same restructuring to fit the guard in, this is the
fallback, but it does not.

**Rejected alternative: a baseline that only covers the reviewer-verdict
case** (Think's Approach 1, "already half-true today"). It fails deliverable
2 verbatim ("The same derivation covers a retry of a failed check or skill
step") and Scenario 2 (a failed live-tier check that revises). Point 1 above
exists specifically to close that gap.

## Steps

1. **Persist what a plain check/skill failure found, not only a reviewer's
   verdict.** `internal/run/revise.go`'s `failStep`: move the `findings`
   computation (currently lines 55-58) above the `FailStepRun` call, and
   widen `failEvidence`'s construction (lines 43-46) to set it on the
   non-judgment path too, when there is something to say:
   ```go
   var failEvidence *millv1.Evidence
   switch {
   case res.judgment:
       failEvidence = verified.Value
   case findings != "":
       failEvidence = &millv1.Evidence{
           Kind:   millv1.EvidenceKind_EVIDENCE_KIND_EXIT,
           Value:  &millv1.Evidence_Exit{Exit: exit},
           Output: findings,
       }
   }
   ```
   `internal/domain/evidence.go`'s `ValidateFailureEvidence` (called from
   `FailStepRun`, `internal/domain/steps.go:117-120`) only shape-checks —
   `EVIDENCE_KIND_EXIT` needs a non-nil `Exit`, which is already guaranteed
   above — and does not run `checkDeclaredKind`, so this is accepted
   whatever evidence kind the step's own definition declares. No other
   reader of a `FailStepRunRequest` or `StepRun.Evidence` changes shape or
   meaning; this only adds a value where none was written before.
   *Proven by* the existing revise/retry specs (`aborted_test.go`,
   `breaker_test.go`, `commit_test.go`, `gate_test.go`) passing unmodified —
   none assert `Evidence` is absent on a failed non-judgment attempt — plus
   one new assertion added to an existing self-retry spec (e.g.
   `breaker_test.go`'s retry case) that `f.inspect(ctx)`'s failed row now
   carries `Evidence.GetOutput()` equal to the check's own feedback text.
   `make test`.

2. **A ledger lookup for "the latest attempt of a step, any status."**
   `internal/run/verify.go`, next to `latestClosed`:
   ```go
   // latestAttempt is the attempt at a step with the highest attempt
   // number, whatever its status, or nil: unlike latestClosed, this also
   // returns a superseded or failed row, which is what a resumed revise
   // target or retry needs to look at.
   func latestAttempt(detail *millv1.InspectResponse, step string) *millv1.StepRunDetail {
       var found *millv1.StepRunDetail
       for _, d := range detail.GetSteps() {
           sr := d.GetStepRun()
           if sr.GetStepName() != step {
               continue
           }
           if found == nil || sr.GetAttempt() > found.GetStepRun().GetAttempt() {
               found = d
           }
       }
       return found
   }
   ```
   Unused until step 3 wires it in; the tree builds and every existing spec
   stays green.
   *Proven by* `make lint && make test` (no behavior change yet).

3. **Derive a revise's or a retry's feedback from the ledger when nothing is
   carried in memory.** New functions in `internal/run/revise.go`, beside
   `revise`:
   ```go
   // resumedFeedback rebuilds what a revise target or a step's own retry
   // owes its next attempt from the ledger alone, for a worker resuming
   // with nothing carried from the pass that found it (Invariant 10).
   // own's status says which case applies, checked in this order because a
   // superseded row can also carry a stale feedback_from of its own (a
   // second or later revise round preserves the field a first StartStepRun
   // set, which is not the round that just superseded it):
   //   - superseded: this step is a revise target, revised again just now
   //     — read the freshest attempt among every step whose on_failure
   //     names it, not the row's own stale feedback_from.
   //   - feedback_from already set, row not superseded: an attempt that was
   //     itself interrupted mid-answer (aborted, not superseded) — reuse
   //     what it was already told to answer.
   //   - failed, nothing later: an unspent retry of this step's own last
   //     failure.
   //   - anything else — closed, running, or a first-ever aborted attempt
   //     with nothing to answer — owes nothing.
   func (r *Runner) resumedFeedback(s *state, detail *millv1.InspectResponse, name string) (string, string) {
       own := latestAttempt(detail, name)
       if own == nil {
           return "", ""
       }
       var source *millv1.StepRunDetail
       switch {
       case own.GetStepRun().GetStatus() == millv1.StepRunStatus_STEP_RUN_STATUS_SUPERSEDED:
           source = sourceOfSupersede(s.workflow, detail, name)
       case own.GetStepRun().GetFeedbackFrom() != "":
           source = stepRunByID(detail, own.GetStepRun().GetFeedbackFrom())
       case own.GetStepRun().GetStatus() == millv1.StepRunStatus_STEP_RUN_STATUS_FAILED:
           source = own
       }
       if source == nil || source.GetEvidence() == nil {
           return "", ""
       }
       feedback := feedbackOf(source.GetEvidence())
       if feedback == "" {
           return "", ""
       }
       return feedback, source.GetStepRun().GetId()
   }

   // sourceOfSupersede is the latest attempt, among every step whose
   // on_failure names target, that could have sent it back: the one
   // Inspect's start-time ordering puts last among the candidates
   // (latestClosed's own comment already documents that ordering), since
   // SupersedeSteps runs immediately after the revising step's own failure
   // closes. More than one step can name the same revise target — feature's
   // own workflow has both review and merge revise implement
   // (workflow.yaml:322,345) — so this cannot be answered by name alone.
   func sourceOfSupersede(workflow *millv1.Workflow, detail *millv1.InspectResponse, target string) *millv1.StepRunDetail {
       revising := map[string]bool{}
       for _, step := range workflow.GetSteps() {
           if step.GetOnFailure().GetKind() == millv1.OnFailureKind_ON_FAILURE_KIND_REVISE &&
               step.GetOnFailure().GetReviseTarget() == target {
               revising[step.GetName()] = true
           }
       }
       var found *millv1.StepRunDetail
       for _, d := range detail.GetSteps() {
           if revising[d.GetStepRun().GetStepName()] {
               found = d
           }
       }
       return found
   }

   // feedbackOf is evidence rendered the way a resumed attempt is owed it:
   // a revise verdict as verdictFeedback already renders it for the live
   // path, an exit's recorded output verbatim — the same string failStep
   // computed and a live retry already carries in memory. Evidence closes a
   // step too (an approving verdict, CloseStepRun's own value at
   // walk.go:462-467), and a superseded row can be one of those — a
   // downstream revise's span covers every step from its target through
   // itself, which can include an earlier step that had already closed on
   // approval — so only a revise decision is rendered; anything else is
   // treated as no feedback, not as approval text mislabeled as findings.
   func feedbackOf(evidence *millv1.Evidence) string {
       switch verdict := evidence.GetVerdict(); {
       case verdict != nil && verdict.GetDecision() == millv1.VerdictDecision_VERDICT_DECISION_REVISE:
           return verdictFeedback(verdict)
       case verdict != nil:
           return ""
       default:
           return evidence.GetOutput()
       }
   }
   ```
   Wire it into `internal/run/walk.go`'s loop, right after the existing
   preparatory-findings block (`walk.go:111-113`), composed rather than
   gated on `feedback` alone — `feedbackFrom` is untouched by the
   preparatory-findings block, so it alone says whether anything has
   already been carried into this pass from a real attempt:
   ```go
   if feedbackFrom == "" {
       derived, from := r.resumedFeedback(s, detail, step.GetName())
       feedback = withFindings(feedback, derived)
       feedbackFrom = from
   }
   ```
   When `derived` is `""` (not a revise target, no unspent retry),
   `withFindings(feedback, "")` returns `feedback` unchanged, matching
   acceptance criterion 3 exactly. When both preparatory findings and a
   genuine revise/retry apply — a retried skill step whose session never
   started — the two compose, run findings first and the step's own answer
   last, the same order `withFindings`'s doc comment already establishes for
   a check's feedback.
   *Proven by* the new specs in step 4.

## Risks

- **Two steps can name the same revise target** (`review` and `merge` both
  `revise implement` in `workflows/feature/workflow.yaml`), which the first
  draft of this plan missed by assuming "the revising step" was unique by
  name. `sourceOfSupersede` resolves it by Inspect's documented start-time
  ordering across candidates rather than by name, which is correct for
  every *automatic* on_failure revise, since `SupersedeSteps` for one always
  runs immediately after that step's own failure closes. It is not
  guaranteed correct for a manual `mill rerun --from implement`, which can
  supersede an earlier step's already-*approved*, closed attempt without any
  revising step having failed at all — `feedbackOf`'s explicit
  decision-must-be-REVISE check is what keeps that case from rendering an
  approval as if it were a finding; without it, this would still be wrong
  even with the ordering fix.
- **Evidence with a `Verdict` is not always a revise's** — `closeStep`
  writes an approving verdict as evidence too (`walk.go:462-467`), and a
  later, unrelated supersede can leave that approved row `SUPERSEDED`
  without changing its evidence. `feedbackOf` checks the decision
  explicitly rather than assuming any recorded `Verdict` came from a revise;
  the first draft of this plan made that assumption and it does not hold.
- **Widening `failEvidence` changes what every plain check/skill failure
  writes to the ledger**, not only the revise-target case. Checked directly:
  `ValidateFailureEvidence` has no declared-kind restriction
  (`domain/steps.go:117-120`), and no existing spec asserts `Evidence` is
  unset on such a row, so this is additive rather than a behavior change for
  anything reading the ledger today.
- **The three release-mechanism specs (step 4) are near-duplicates of each
  other and of an existing spec.** If `cancel_test.go`'s existing fixture
  for a mid-run release doesn't expose a clean equivalent to
  `worker.Drain()`'s mid-script hook, or `cancelledTurn` needs adapting to
  cancel a step's *second* attempt rather than its first, adapting this
  plan's drain spec to each file's idiom is mechanical but not zero-effort;
  budget for reading each fixture's existing pattern before writing its new
  spec, same as this plan did for `worker_test.go` and `reclaim_test.go`.

## Decisions

- **The literal `findings` string is persisted and read back verbatim**,
  not re-rendered through a new formatting function — it is already the
  exact text `check.Feedback` produces and the live in-memory path already
  shows an implementer, so storing anything else would make a resumed
  prompt differ from an uninterrupted one.
- **`Evidence.output`'s doc-comment change is not a breaking or contract
  change.** `proto/README.md` defines a breaking change as a removed or
  renumbered field; this only broadens use of an existing field (13) and
  corrects a comment that would otherwise be inaccurate once step 1 lands.
- **Test placement**: the drain and cancel variants go in the files that
  already own each mechanism's fixtures (`worker_test.go`, `cancel_test.go`)
  rather than a new file, so each stays next to the fixture helpers and
  existing sibling specs it reuses. The worker-shutdown variant and
  acceptance criterion 3's negative case both go in `resume_test.go`, which
  already owns the `cancelledTurn`/mid-turn-abort idiom that shape needs —
  `restart_test.go` was rejected for this (it is a run restart, a different
  mechanism, not a worker shutdown).
- **No new unit-level tests for `latestAttempt`, `sourceOfSupersede` or
  `feedbackOf` in isolation** — consistent with how `latestClosed` and
  `stepRunByID` are exercised only through the black-box `fixture`/`runner`
  specs elsewhere in this package, not called directly from a test.
