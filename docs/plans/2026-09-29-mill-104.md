# The live tier runs the run loop's database specs instead of skipping them

## Approach

Approach 2 from the Think note ("full deliverable as scoped"), run in the
order: plumbing first, then one real run of the acceptance command to learn
whether the seven named specs share a root cause, then triage. Approach 1
(env wiring only) was rejected because it provably fails the node's own
acceptance criteria 1 and 2 — the guest's skift checkout is untrusted by
`mise`, so `requireAvailable` would still either skip (fixture "available"
but broken) or the `BeforeEach` would fail with a `mise` trust error rather
than the missing-prerequisite message criterion 2 asks for. Approach 3
(defer the seven specs to a follow-on) was rejected as the default because
the deliverable text is explicit ("each either fixed or shown to have
failed only for the measuring shell's environment, with the reason recorded
in the commit") and the node's own acceptance criteria only close once that
command passes end to end; I fall back to it — landing the plumbing and
reporting the seven as a follow-on with reproduction evidence — only if
triage turns up unrelated, deep bugs whose fixes would outgrow this node,
and say so plainly if that happens rather than force them in.

Confirmed against the guest directly before writing this plan: `goose` is a
mise shim from this project's own (trusted) `mise.toml`
(`aqua:pressly/goose`), already resolves and runs from both the repo root
and `internal/testsupport`; the skift checkout at
`/mnt/lima-stead-data/skift/checkout` has its own untrusted `mise.toml`
that pins the same tool and carries a `[env]` side effect, which is what
trips the trust check when `goose` is invoked with the checkout as its
working directory (`internal/testsupport/skift.go`'s `startSkift`, `Dir:
repo`). The `skift` binary is already on `PATH` at `/usr/local/bin/skift`,
so nothing about the binary lookup needs to change.

## Risks

- **The seven specs are not one bug.** Step 4's opening diagnostic run is
  designed to surface this early; if they are unrelated and any is deep
  (a real concurrency or gate-logic bug rather than an environment
  artefact), the fix for that one spec may need its own investigation
  beyond what this plan can size in advance. Answer: treat it as its own
  sub-problem, fix it if it is small, and if it is not, stop, document
  the finding precisely (what fails, why, under what conditions), and say
  in the commit that it is being left for a follow-on node rather than
  silently shipped half-fixed.
- **`goose`'s cwd-independent invocation might still resolve the wrong
  tool version.** Moving `Dir` off the checkout means `goose` resolves
  against mill's own `mise.toml` pin (`3.28.0`) rather than skift's own
  (also `3.28.0` today, confirmed by reading both files) — if skift's pin
  ever drifts from mill's, the fixture would silently use mill's version
  instead of skift's. Answer: this is accepted as intentional per the
  work order's own instruction ("runs `goose` from the run's own
  toolchain"); not fixed here, but worth a comment in the code explaining
  the tradeoff so a future reader does not "fix" it back.
- **The `MILL_REQUIRE_FIXTURES` variable name is the work order's own
  example ("for example `MILL_REQUIRE_FIXTURES`"), not a mandate.** Taking
  it as the actual name (see Decisions) is a small bet; if wrong, it is a
  one-string rename across `skift.go` and the two workflow YAMLs.
- **The doc edit to `docs/sandbox.md:550` risks re-asserting the
  pre-existing, unverified claim that a nested machine's `MILL_SKIFT_REPO`
  already works end to end.** Reading the machine backend's code
  (`internal/workspace/machine/machine.go`, `lifecycle.go`) during
  research turned up no code path that actually exports `MILL_SKIFT_REPO`
  as an environment variable there — only the read-only bind at a fixed
  path. `docs/sandbox.md:618` already flags a related gap ("no `skift`
  binary is inside a machine"). Answer: the doc edit in step 5 describes
  only what this node changes (the local backend) and does not claim the
  machine backend's existing behaviour was verified or changed; it is
  named here so a reviewer does not read the new sentence as asserting
  more than was checked.

## Decisions

- **Variable name:** `MILL_REQUIRE_FIXTURES`, the work order's own
  example, taken literally since nothing else was named.
- **Where the variable is set:** only inside the `live-tier` check step's
  own command line in both workflow YAMLs, not in the Makefile or any CI
  config — the deliverable's "outside the tier it still skips" is
  otherwise unenforceable.
- **`attachOnlyWorkspaces` does not get `SkiftCheckout`:** it never runs a
  check step or session (only `Attach`, for reconciliation and the
  sweep), so there is nothing there for the variable to reach.
- **No new unit test for `requireAvailable`'s Skip-vs-Fail dispatch:**
  `ginkgo.Skip`/`ginkgo.Fail` are control-flow primitives tied to the
  currently running spec; no existing test in this codebase exercises a
  Skip or Fail call site directly (`SkipUnlessSandboxReady`,
  `HostOnlySkip`'s caller, are both untested the same way). Acceptance
  criteria 1 and 2 are themselves written as manual command proofs for
  exactly this behaviour, so the plan uses those rather than adding an
  artificial nested-Ginkgo-run test.
- **The machine backend's own `MILL_SKIFT_REPO` export is left
  untouched:** the node's deliverables name the local backend
  specifically ("the local backend gives... the way the machine backend
  does"), and the guest itself runs on the local backend, which is what
  makes this node matter here. Fixing the machine backend's apparent gap
  (if it is one) is a separate node's work.
