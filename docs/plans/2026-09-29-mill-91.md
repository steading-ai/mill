# The merge gate's status wait is cumulative across a run's attempts, so a fresh head's checks time out at once

## Approach

Move the fold that decides "how long has this been waited on" out of
`internal/run/execute.go`'s `elapsed()` — which today answers "how long has
this *step* existed" by taking the earliest `started_at` across every
`StepRun` attempt at the step, ever, regardless of what commit each one was
reading checks for — and into `internal/evidence` itself, as a function of
the *head* rather than the step. `evidence.Step` gains a small history
(`StatusHistory []StatusRead`, each a head and when it was read) in place of
the single `Elapsed time.Duration` field; `verifyStatus`'s pending branch
folds that history down to "how long has *this* head (`Claim`) been waited
on" by finding the earliest entry whose `Head` matches, and compares that
against the cap.

`internal/run/verify.go` supplies the history from `StepRun.base_commit`,
the same field `firstBase`/`earliestBase` already read for `commit`
evidence — but only after fixing what it actually records for a merge
gate's attempts. As written today, `internal/run/execute.go`'s
`baseCommit()` inherits `base_commit` from the previous attempt whenever
that attempt was aborted (`abortedBase`), unconditionally, for every step
kind. That is correct for `commit` evidence — an aborted attempt's span is
still open work, and its base must not move out from under it — but wrong
for a merge gate: the whole point of that abort-and-retry cycle is a fresh
read of wherever the branch's head is *now*, which catch-up may have moved
since the attempt that was just aborted started. Left as is, `base_commit`
for a gate step would stay pinned to the very first head this run's merge
ever saw, however many times catch-up has since moved it, which would make
the new per-head history exactly as blind to a moved head as `Elapsed` is
today. `baseCommit()` is changed to read a fresh head on every new attempt
for a step declaring `status` evidence, and to keep the existing
carry-forward behaviour for every other kind.

Two alternatives were considered and rejected (see the prior *Think* note
for the fuller comparison):

- **Fix only `internal/run/execute.go`'s `elapsed()`** — keep
  `evidence.Step.Elapsed time.Duration` as-is, and have `elapsed()` filter
  by the current attempt's `base_commit` instead of matching on step name
  alone. Smaller diff, and consistent with the `Base`/`EarliestBase`
  single-value convention. Rejected because acceptance criterion 3 asks for
  "a test in `internal/evidence`" that proves the reset-on-head-change
  behaviour, and under this approach that behaviour lives entirely in
  `internal/run`'s ledger scan — a test placed in `internal/evidence` could
  only assert what is already true today (the verifier is stateless per
  call), proving nothing about the actual fix. Moving the fold into
  `evidence` makes the acceptance criterion literally satisfiable with a
  real test, not a tautological one.
- **Give `StepRun` a new field for the exact sha a status read checked**,
  written wherever `checkBeforeMerge` runs, instead of reusing
  `base_commit`. More precise — it would not depend on `base_commit` and
  workspace HEAD agreeing — but a pending read that gets aborted
  (`AbortOpenStepRuns`) never reaches a write path that could set it: the
  attempt ends before anything about that read is durably recorded except
  the `StepRun` row `StartStepRun` already wrote. Recording it would mean a
  new store RPC call on the abort path, purely to serve this one read,
  which is a bigger and riskier change than fixing the one place
  `base_commit` is already wrong for this step kind.

## Steps

1. **Move the per-head clock into `internal/evidence`.**
   Files: `internal/evidence/evidence.go`, `internal/evidence/evidence_test.go`.
   Add a `StatusRead` type (`Head string`; `At time.Time`) and replace the
   `Elapsed time.Duration` field on `Step` (evidence.go:186–189) with
   `StatusHistory []StatusRead`, documented as: every past attempt's read,
   for the `status` verifier alone, to measure how long the *current* head
   has itself been waited on rather than how long the step has existed
   (mill#91). Add a method `func (s Step) headWait(head string) time.Duration`
   that takes `now := s.now()`, folds `StatusHistory` down to the earliest
   `At` among entries whose `Head == head`, and returns `now` minus that (or
   `0` when nothing matches — a head read for the first time has waited
   nothing). In `verifyStatus`'s `forge.Pending` case (evidence.go:687–696),
   replace `if step.Elapsed >= limit` with `if wait :=
   step.headWait(sha); wait >= limit`; the refusal message is unchanged (it
   already names `limit`, the configured cap, not the raw elapsed value).
   In `evidence_test.go`'s "The status verifier" block: update the existing
   "gives up once the checks have not settled within the workflow's cap"
   test (lines 533–541) to inject `s.Now` and set
   `s.StatusHistory = []evidence.StatusRead{{Head: sha, At: now.Add(-3 *
   time.Minute)}, {Head: sha, At: now.Add(-11 * time.Minute)}}` — two entries
   for the same head, so the same test also proves the fold picks the
   *earliest* matching one, not just any. Add a new test, "gives a freshly
   read head its own window, however long an earlier head waited": history
   containing only an entry for a *different* sha at `now.Add(-61 *
   time.Minute)` (past the 10-minute cap the `step()` helper's workflow
   already sets), `Claim` set to the (different) `sha` the helper uses, and
   assert `evidence.Pending(err)` is `true` — the earlier head's wait does
   not count against this one. This is the test acceptance criterion 3
   names.
   **Proof:** `go test ./internal/evidence/...` (or `ginkgo
   ./internal/evidence/...`) green, including the two status-verifier
   tests above.

2. **Stop carrying a merge gate's `base_commit` forward across an aborted,
   still-pending attempt.**
   File: `internal/run/execute.go`.
   Change `baseCommit()` (execute.go:650–655): only consult `abortedBase`
   when `step.GetEvidence() != millv1.EvidenceKind_EVIDENCE_KIND_STATUS`;
   a status-evidence step always takes the fresh `r.head(ctx, s)`, on every
   attempt, aborted predecessor or not. Update the doc comments on
   `baseCommit` and `abortedBase` to say why the exemption exists: unlike a
   `commit` step, whose aborted attempt is unfinished work that must not
   look like a fresh start, a merge gate's aborted attempt is a pending
   check that timed out its poll — the next attempt is meant to ask about
   wherever the branch's head is *now*, catch-up included, and inheriting
   the old base would hide exactly the head movement this node exists to
   notice.
   **Proof:** `go build ./...`; no test in this repository currently
   exercises `baseCommit` in isolation, so this step's own correctness is
   carried by step 3's test (below), which fails without it — verified by
   temporarily reverting this step alone and re-running that test.

3. **Wire the ledger into the new history, and retire `elapsed()`.**
   Files: `internal/run/verify.go`, `internal/run/execute.go`.
   In `verify.go`'s `(r *Runner) verify` (line 40), replace `Elapsed:
   elapsed(detail, step.GetName(), r.options.Now())` with `StatusHistory:
   statusHistory(detail, step.GetName())`. Add `statusHistory` beside
   `firstBase`/`earliestBase` (verify.go:417–437): for every
   `StepRunDetail` whose `StepRun.StepName` matches, append
   `evidence.StatusRead{Head: sr.GetBaseCommit(), At:
   sr.GetStartedAt().AsTime()}`. Document, at this function, that it only
   produces a trustworthy history because step 2 made `base_commit` track
   the actual head on every attempt of a status-evidence step; a
   `commit`-evidence step's `base_commit` would not mean the same thing,
   which is fine, since no `commit` step calls the `status` verifier.
   Delete `elapsed()` from `internal/run/execute.go` (execute.go:922–940) —
   its only caller was the line just changed.
   **Proof:** `go build ./...` succeeds (confirms nothing else called
   `elapsed()`).

4. **Make the forge fixture's pull request head track the branch's actual
   commits.**
   File: `internal/run/support_test.go`.
   `fixtureForge.PR()` (support_test.go:531–541) returns a `HeadSHA` fixed
   at a constant 40 `a`s forever, set once and never updated — the forge
   fixture has never had to distinguish one head from another, because
   every existing spec that cares about a moved head (mill#62's "re-checks
   the head a conflict's own catch-up produces") does so through
   `checksQueue`'s call order, not through the sha. This node's fix makes
   `Claim` (the sha the run loop hands `verifyStatus`, read from
   `pr.HeadSHA`) and `base_commit` (what `statusHistory` now folds on)
   actual, correlated values, and no spec can exercise that correlation
   against a forge that always reports the same sha regardless of what
   `f.commits` just committed. Add a `headSHA string` field to
   `fixtureForge`, a `setHead(sha string)` method that sets it under the
   existing mutex, and have `PR()` override `f.pr.HeadSHA` with `f.headSHA`
   whenever it is set. Call `f.forge.setHead(info.SHA)` from `fixture.commits`
   (support_test.go:120–138) right after it records the commit in `f.made`,
   so every scripted session's commit becomes, from here on, what the forge
   reports as the pull request's head — the same thing a real forge does on
   its own once a push reaches it.
   **Proof:** `go build ./...` for the test package; the existing gate
   specs that read `f.forge`'s state (mill#62's checks-call-count specs,
   the pending-timeout spec below) still pass unchanged — none of them
   assert the literal constant sha, only call counts and queue order.

5. **Prove the wiring end to end: an exhausted head's wait does not follow
   the run to the head a revise moves it to.**
   File: `internal/run/gate_test.go`.
   Add one spec to the "The merge gate reads the forge's checks before it
   merges" describe block, alongside the existing pending-timeout spec
   (gate_test.go:520–541, which this change must leave passing unchanged —
   see note below). Reuse its `short-status-timeout` workflow variant and
   `f.forge.checksAt = forge.Pending`, so the first merge attempt-group
   exhausts the workflow's cap on the original head exactly as that spec
   does, and revises back to `implement`. Additionally script the second
   `implement` call — the one the revise causes, the fifth entry appended
   to `f.quickFixScripts()` since scripts are consumed by call index and
   the fourth (`pr`) entry is otherwise reused — with a `Do` that commits
   (`f.commits`) and then sets `f.forge.checksQueue =
   []forge.Status{forge.Pending}` (falling through to `checksAt =
   forge.Success` once the queue is spent), so the new head (a genuinely
   different, later commit, now correctly reported by the fixture forge
   after step 4) is read as pending exactly once — putting it through the
   same `headWait` comparison the exhausted head went through — before
   settling green on the next poll. Assert `f.runOf(ctx).GetStatus()` is
   `RUN_STATUS_DONE`, not `RUN_STATUS_PARKED`, and `stepRuns(detail,
   "implement")` has length 2 (one revise, matching the sibling spec's
   shape). This is acceptance criterion 1's scenario, at the level nearest
   the incident reports: under the current code (or with only step 1 done
   and steps 2 or 4 skipped) this spec fails, either because the second
   head is refused within its first pending read (cumulative clock already
   past cap) or because `Claim` and `base_commit` never agree on what "the
   same head" means; it passes once steps 1–4 all land.

   Note on the existing pending-timeout spec (gate_test.go:520–541): with
   steps 2 and 4 applied, the run's *second* head — the one `implement`'s
   revise produces — now gets its own full window before being refused
   too, rather than being refused near-instantly on the old cumulative
   clock. `f.forge.checksAt` stays `forge.Pending` forever in that spec, so
   the second head times out on its own after its own ~30ms cap; the
   number of revise cycles is unchanged (the merge step's own retry budget,
   not the pending-clock, bounds it to one), so `stepRuns(detail,
   "implement")` is still length 2 and the run still parks — the spec's
   assertions hold, it simply takes on the order of one more `Timeout`'s
   worth of wall-clock time than before.
   **Proof:** `ginkgo internal/run/gate_test.go` green: the existing
   pending-timeout and catch-up-conflict specs unchanged, and the new
   spec passing.

## Risks

- **`base_commit`, even after step 2, is still captured once at the start
  of an attempt, before that attempt's own `catchUp` runs.** A single
  attempt in which catch-up moves the head *mid-attempt* (the scenario
  mill#71, held, owns) will see `headWait` grant that moved-to head a
  fresh window rather than any accumulated one, because no history entry
  yet names it. That is the same direction of error step 2's fix aims
  for — never a wrongly-extended stale wait — and mill#71's own scope is
  precisely to give that case a real answer; this node does not attempt
  it.
- **Step 5's timing constants (borrowed from the existing sibling spec:
  10ms interval, 30ms timeout) are wall-clock-based and could be flaky
  under load**, exactly as the existing spec they're modelled on already
  is, and the new spec now waits out two such windows rather than one
  (see the note in step 5). Mitigation: same as that spec already accepts
  — if it flakes in CI, widen the margins rather than dropping the
  assertion.
- **Renaming `Step.Elapsed` to `Step.StatusHistory` is a breaking change to
  `evidence.Step`'s public shape.** The only caller is
  `internal/run/verify.go` (confirmed by grep), so this is contained to
  the files steps 1 and 3 touch; no other package or test constructs a
  `Step` literal naming `Elapsed`.
- **Narrowing `baseCommit`'s carry-forward to exclude status-evidence
  steps changes ledger data (`StepRun.base_commit`) other code paths also
  read** — `firstBase`/`earliestBase`, used by `reviewBrief`/
  `revisionBrief` for a `verdict` step's diff, and by `commit` evidence
  itself. Both are scoped to the step *name* they are asked about; a
  workflow's merge/gate step is never itself a `commit`-evidence step or a
  revise target in the shipped `quick-fix` definition, so this change
  touches no step those functions are ever called for. A workflow that
  did put `status` evidence on a step also used as a revise target's diff
  base would see a different `base_commit` history than before; nothing
  in this repository's workflows does that today.
- **The fixture change in step 4 makes `fixtureForge.PR()` report a
  `HeadSHA` that used to be a fixed constant.** Grepped for any spec
  asserting that literal value (`strings.Repeat("a", 40)`) directly; none
  found, but the implementer should re-check after adding the field, since
  a spec relying on it by coincidence rather than by name would not show
  up in that grep if it compares against a variable holding the same
  constant.

## Decisions

- **The fold moves into `internal/evidence`, not `internal/run`.** The
  work order is explicit that the test proving this lives in
  `internal/evidence`; the smaller, `internal/run`-only fix (filtering
  `elapsed()` by `base_commit`) cannot support that test non-trivially,
  so the slightly larger diff is the one taken.
- **`base_commit` is reused as the head-history key, once `baseCommit()`
  is fixed to keep it accurate for a status-evidence step, rather than
  adding a new ledger column for "the sha this attempt actually checked."**
  The work order does not ask for a schema change; the abort path has no
  write of its own to attach a new field to without adding one, and
  `base_commit` already carries the right fact for every step kind once
  its one wrong case (status evidence, carried forward like commit
  evidence) is corrected.
- **The fixture forge's `HeadSHA` is made to track real commits (step 4)
  rather than keeping the constant and testing only through call order,
  the way mill#62's specs do.** This node's whole deliverable is that a
  *different* head gets its own window, which is not expressible through
  call order alone — the spec has to be able to say "this is a different
  sha" and have the run loop agree.
- **The new `internal/run` regression test (step 5) drives the head
  change through an ordinary revise's new commit, not through
  `workspace.CatchUp`/`seedTarget`.** mill#71 (held) owns catch-up's own
  behaviour and the work order says not to fold the two together; a head
  change is a head change regardless of which mechanism produced it, so
  testing it the plainer way keeps this node's test independent of
  mill#71 landing or not.
- **No change to the refusal message's wording.** The deliverable's
  "elapsed is that head's, not the run's" is satisfied by `headWait`
  measuring the right thing; the message already names the configured
  cap (`limit`), not a raw elapsed duration, and the work order does not
  ask for that format to change.
- **No filtering of ledger history by generation/restart.** `elapsed()`,
  `firstBase`, and `earliestBase` all already scan every `StepRunDetail`
  for a step name across the run's whole history, restart or not;
  `statusHistory` keeps that same scope rather than introducing a new,
  narrower one as part of an unrelated fix.
