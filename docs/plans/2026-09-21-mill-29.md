# Concurrent verbs share one output chunker per stream, and records carry no verb id

## Approach

Mint a per-invocation `verb_id` (`int64`, a package-level `sync/atomic` counter in `internal/workspace/verbs`, incremented once per `Host.Run` call — the single chokepoint every git verb funnels through; confirmed by grep that `forgeVerbs.PR`/`Push`/`Checks` never call `Sink` themselves) and thread it through `workspace.Sink`'s three methods as a new parameter (`Started(verb string, verbID int64, args ...)`, `Output(verb string, verbID int64, stream string, data []byte)`, `Ended(verb string, verbID int64, err error)`). Carry it on the wire on all three verb-shaped records — `VerbStarted`, `Output` (the message `verb_output` and `check_output` share), and `Verb` — as a new `verb_id` field. In `internal/run/activity.go`, key `verbChunks` and the verb half of `truncatedStreams` by `(verb_id, stream)` instead of `stream` alone, reading the id back off the record body the writer was handed rather than re-deriving it.

This is Approach 1 from the prior Think step, chosen over two rejected alternatives:

- **A recorder-object redesign** (`Sink.Started` returns a per-call object owning `Output`/`Ended` and its own private `Chunker` pair) would remove the map-keying question by construction, but it changes `Sink`'s method *shape*, not just its parameter list, across the same three implementers this plan already touches, for a marginal robustness gain — and it still needs `activityWriter`'s mutex for the actual file write, so it doesn't actually remove `activityWriter`'s involvement, just relocates where two `Chunker` fields live. It also contradicts the deliverable's own phrasing, "a per-verb **key** for the chunker," which presumes a keyed lookup survives, correctly keyed.
- **Minting the id inside `activityWriter`, off its existing `seq` counter** (a dedicated `StartVerb(...) (int64, error)` method) would reuse a value that's already meaningful to a reader (the `verb_started` record's own seq), but it breaks the one convention every other write method in the file shares — `Record`, `EndVerbOutput`, `EndCheckOutput`, `End`, `Close` all return only `error` — for a saving that doesn't materialize: the id still has to flow back through `verbSink.Started`'s return value into `Host.Run`'s local scope and forward into `Output`/`Ended`, exactly the same plumbing shape as minting it in `verbs.Host.Run` directly. Not worth the inconsistency.

The deliverable's literal wording names `verb_id` only on `Verb` and `Output`, but the Problem section it sits under requires attributing `verb_output` *to its `verb_started`* — unsatisfiable unless `VerbStarted` carries the same id, otherwise attribution falls back to positional/ordering inference, which is the exact hazard under concurrency this node exists to close. `VerbStarted` gets the field too; recorded under Decisions.

## Risks

- **`Sink`'s signature change is a three-way simultaneous edit** (interface, `SinkVar`, `verbSink`, `fakeSink`) — a missed call site is a compile error, not a silent bug, so this is low-risk but must be done as one atomic step (Step 2) rather than left partially threaded.
- **Field-number choice on `Output`** (`verb_id = 3`) is shared between `verb_output` and `check_output`; if a later change gives `check_output` its own reason to carry a per-check identity, it would reuse the same field number for an unrelated meaning. Mitigated by the doc comment stating explicitly that it's verb-only and zero/unset on `check_output`; a future divergent need would add a differently-named field rather than repurposing this one.
- **The interleaving spec's assertions are only as strong as what it constructs.** Two verbs, one stream, hand-built records prove the keying is correct for the exact corruption pattern described in the node ("Verb A's unterminated tail... glued onto verb B's first line"); it does not exercise the real concurrent-goroutine path through `verbs.Host.Run` end-to-end. That path is exercised by existing acceptance-style specs (`logs_test.go`) only for the single-verb case — a genuinely concurrent two-goroutine acceptance spec is not added here as it would be nondeterministic to write reliably and the deliverable specifically asks for the interleaving to be asserted at the record level, which the hand-built spec does directly and deterministically.

## Decisions

- **`VerbStarted` gets `verb_id` too, though the deliverable's literal text names only `Verb` and `Output`.** The deliverable's own Problem section requires attributing `verb_output` to its `verb_started`, which needs a matching id on both ends; omitting it from `VerbStarted` would leave that requirement unmet. Taken as the work order's actual intent over its narrower enumeration.
- **The id is minted in `internal/workspace/verbs` (a package-level atomic counter in `Host.Run`), not in `activityWriter` off the existing `seq` counter.** See Approach — avoids breaking the uniform `error`-only return convention every other `activityWriter` write method shares, for no plumbing savings (the id has to flow back through `Host.Run`'s local scope either way).
- **The id is process-global, not scoped per attempt or per workspace.** No requirement found in `docs/activity.md` for narrower scope; a monotonically increasing `int64` unique for the life of the worker process is strictly sufficient to disambiguate concurrent records within one activity file, and simpler than resetting a counter per attempt.
- **`truncatedStreams`'s verb-side keying is folded into this change** rather than filed as a separate node, since it's the identical shared-by-stream-only defect and the "no line crosses" acceptance bar implicitly covers a verb's output being wrongly silenced by a concurrent verb's ceiling marker.
- **`check_output`/`checkChunks` are left untouched.** Checks run one at a time per attempt (no concurrent `check.Sink` callers), so they have no analogous bug, and the deliverable doesn't name them.
