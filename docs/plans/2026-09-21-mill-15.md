# The harness and the workspace report everything they see

## Approach

Run a spike against the real, pinned SDK (`0.3.263`) before touching any
contract or code, then wire the two flags it needs
(`includePartialMessages`, `forwardSubagentText`) straight through from
`stream_event` to the wire, letting the already-built `internal/run`
activity writer (`mill#13`) do the folding it was already built and tested
to do.

The SDK's own `.d.ts` documents both flags, but not their edge behavior:
what a partial text block looks like next to its completed sibling, whether
`forwardSubagentText` changes the shape of tool-call/tool-result events for
a subagent (not just text), and what `parent_tool_use_id` reads as on a
top-level (non-subagent) event. `docs/spikes/sdk-sessions.md` exists
precisely so this kind of question gets answered by running the SDK and
reading what comes back, not by reading its types and guessing. Spiking
first means the proto fields this node adds (`block_id`, `delta`, `final`
on `Text`, the new `Thinking` message, `parent_call_id` on `Event`) are
shaped by an observed stream, not a plausible one — and it means a
surprise here is caught before it is load-bearing in the contract, the
sidecar, and `execute.go` all at once.

Two alternatives were considered and rejected:

- **Whole-block-only, no deltas.** Keep `includePartialMessages` off, and
  treat every completed content block as one final `Text`/`Thinking`
  event, dropping the `delta`/`block_id` fields entirely. This is simpler
  and would pass `buf breaking` more trivially, but it fails the acceptance
  criteria outright — `mill logs -f` is required to show text arriving in
  pieces, and the work order is explicit that "no live deltas" is exactly
  the gap this node closes. Rejected: it does not do the assigned work.

- **Synthesize `block_id` in the Go writer instead of the sidecar.** The
  writer already tracks call/turn state; it could infer block boundaries
  from ordering and timing instead of the sidecar assigning an id. This
  was rejected because the SDK's `stream_event` carries a message-scoped
  `index` that is the only reliable seam between one content block and the
  next — the sidecar sees it directly, in order, with no reconstruction.
  Pushing that inference downstream would mean the writer guessing at
  boundaries from a flattened stream that has already lost the one signal
  that marked them, and would leave `harness.proto` without the fields the
  work order explicitly lists as deliverables.

3. **`sidecar/src/session.ts`: turn the flags on and forward what they
   produce.**
   Files touched: `sidecar/src/session.ts` (`buildOptions`,
   `handleMessage`), `sidecar/spec/fake_sdk.ts` (new scenarios),
   `sidecar/sidecar_test.go` or a new `sidecar/streaming_test.go` (new
   Ginkgo specs).
   What happens: `buildOptions()` sets `includePartialMessages: true` and
   `forwardSubagentText: true` on the `Options` it returns.
   `handleMessage()` gains a `"stream_event"` branch: a
   `content_block_delta` with a text/thinking delta is forwarded as a
   `text`/`thinking` event with `delta: true`, `final: false`, a
   `block_id` synthesized from the message id and block `index` (the pair
   the spike confirmed is the seam), and text equal to *that increment
   only* — never the block's accumulated text so far. This is the point
   the previous draft got wrong: it re-sent the whole block once more on
   completion, which is not what the deliverable asks for ("the block's
   last delta carries `final: true`", docs/activity.md:121) and duplicates
   every byte already written, because `internal/run/activity.go`'s
   `DeltaHoldback.Add` treats every call's text as an increment to append
   regardless of `final` (activity.go:434-437,
   internal/workspace/redact/redact.go:285-301) — a resent whole block is
   added on top of the deltas already held or released, not in place of
   them. Instead, the block's close (`content_block_stop`) is forwarded as
   one more record for the same `block_id`, `delta: false`, `final:
   true`; whether that closing record ever carries trailing text or is
   always empty is exactly what step 1's spike must observe (the
   Anthropic streaming API's `content_block_stop` event carries no delta
   of its own, so the closing record is very likely empty) — this is
   read from the spike's captured output, not assumed here, and either
   way `Add` only ever sees each byte once. No block is ever forwarded
   whole. The completed assistant message keeps carrying `usage` and tool
   calls exactly as today. Every event `handleMessage` produces carries
   `parent_call_id` set from the SDK message's `parent_tool_use_id` when
   non-null. `TOOL_RESULT_LIMIT` and `truncate()` are deleted; a tool
   result is forwarded whole.
   Test that proves it: new `fake_sdk.ts` scenarios that script a
   multi-delta text block, a thinking block, a subagent tool call/result
   pair, and an oversized (several-hundred-KB) tool result; new Ginkgo
   specs assert the emitted `harnessv1.Event` stream has the right
   `block_id`/`delta`/`final` sequence per block — critically, that
   concatenating every event's text for one `block_id` in order equals
   the block's full text exactly once, with no record repeating bytes
   another record in the same block already carried — `parent_call_id`
   set on the subagent's events and unset on the top level's, and the
   large result's `Text`/`ToolResult` byte length matches the source with
   no truncation.

4. **`internal/run/execute.go`: complete `activityFromEvent`.**
   Files touched: `internal/run/execute.go`.
   What happens: the `Event_Text` case carries `BlockId`/`Delta`/`Final`
   through instead of hardcoding `Final: true`; a new `Event_Thinking`
   case does the same for `Activity_Thinking`; every case sets
   `ParentCallId` from `event.GetParentCallId()`. The stale doc comment
   above the function (which currently says block id/delta/parent_call_id
   are "deferred to activity-fidelity") is corrected to describe what the
   function now does.
   Test that proves it: existing/extended tests in `internal/run/*_test.go`
   feed a synthetic `harnessv1.Event` stream (delta text, thinking,
   subagent-tagged events, a several-hundred-KB tool result) through
   `sessionEvents`/the writer and assert on the resulting `Activity`
   records — confirming (not modifying) the writer's turn assignment,
   `parent_call_id` folding, delta hold-back, and the 64MB ceiling against
   this real shape of input, per the work order's explicit instruction not
   to touch that logic.

5. **`internal/run/activity.go`: accumulate deltas on read, render
   thinking; `internal/cli/logs.go` and `mcp_tools.go` split `-f` from
   static rendering.**
   Files touched: `internal/run/activity.go` (new `ActivityRenderer`
   type; `RenderedLog`), `internal/cli/logs.go` (`renderActivities`,
   `drainActivities`, `follow`), `internal/cli/mcp_tools.go` (`logs`).

   The previous draft had `mill logs` without `-f` call the existing,
   stateless `RenderActivity(a)` per record and rely on a `final` record
   holding the block's whole text. After step 3's fix that is no longer
   true: with real deltas, a `final` `Text`/`Thinking` record carries only
   its own (likely empty) closing increment, and nothing in the read path
   accumulated the deltas that came before it — the one-line-per-block
   promise (the deliverable's own words) and the `thinking <n> words`
   acceptance criterion both need the *whole* block's text, which now
   only exists as the sum of several records. The mill's own design
   (docs/activity.md §Lifecycle point 4, "Seal") does this coalescing once,
   at attempt close, into a frame — but Seal is rollout item 3
   (docs/activity.md §Rollout) and has not landed in this tree (no
   frame/zstd writer exists, and `Activity.ended_at` is set nowhere); this
   node is rollout item 4, and per §Rollout each rollout item "is
   independently shippable and leaves `mill logs` working" on its own,
   which this node cannot claim if it depends on Seal already existing.
   So this step does the minimum equivalent coalescing itself, directly
   against the live file, rather than either building Seal or silently
   assuming it: a new `ActivityRenderer` in `internal/run/activity.go`
   holds, per `block_id`, the `Text`/`Thinking` bytes of a block still in
   progress; its `Render(a *millv1.Activity) string` method appends a
   non-final delta's text to that hold and returns `""`, and on a `final`
   record concatenates the hold with the closing record's own text,
   clears the hold, and renders one line from the whole (`text ...`
   summarized, or the new `thinking <n> words` case) — every other body
   kind is unchanged, delegated to the existing stateless
   `RenderActivity`. `RenderedLog` and `logs.go`'s non-follow
   `renderActivities` and `mcp_tools.go`'s `logs` — the three callers that
   render a whole attempt's worth of records — each construct one
   `ActivityRenderer` for their run and call it per record instead of the
   bare `RenderActivity`. `mill logs -f` does not use the accumulator at
   all: `drainActivities`/`follow` write a `Text`/`Thinking` record's own
   text straight to stdout as it arrives, delta or final, with no summary
   line and no held-back accumulation, so the model is watched typing —
   exactly "deltas printed raw" (docs/activity.md's `mill logs` table);
   every other body kind on that path still renders through the existing
   stateless `RenderActivity`.

   This closes the acceptance criterion's first half ("a live `mill logs
   -f` shows text appearing in pieces") and the `thinking <n> words`
   criterion, against the live file. Its second half — "the sealed frame
   holds one `text` per block with `ended_at`" — names an artifact (the
   frame, and `Activity.ended_at`) that only Seal produces; this node
   supplies exactly the delta/`final` records Seal's own coalescing step
   is specified to consume, but building Seal itself is out of this
   node's scope (docs/activity.md §Rollout scopes it to "Deltas, thinking,
   subagent lineage, the sidecar's cap removed, streamed check and verb
   output, the attempt cap" — no frame, index or twin). Recorded under
   *Risks* and *Decisions* below: that half of the criterion is Seal's to
   close, not this node's.

   Test that proves it: `internal/run/activity_test.go` gains cases
   feeding an `ActivityRenderer` a delta/delta/final sequence for one
   `block_id` and asserting exactly one rendered line, holding the full
   concatenated text (and, for thinking, the correct total word count),
   plus a case with two interleaved block ids asserting each accumulates
   independently and neither line appears before its own `final`.
   `internal/cli/logs_test.go` (or wherever the existing follow tests
   live) gains a case that feeds the same delta/final pair through
   `--follow` and asserts the raw pieces appear on stdout as each record
   arrives, versus the single accumulated summary line the non-follow
   path prints for identical input. `internal/cli/mcp_tools_test.go` (or
   sibling) gains an equivalent case for the `logs` MCP tool.

## Risks

- **The spike shows partial-message behavior different from what the work
  order assumes** (e.g., no clean `content_block_stop`, or `index` not
  stable across a message). Answer: step 1 runs before any contract or
  code change, specifically so this is caught while only a doc section is
  at stake, not a merged proto.
- **Removing `TOOL_RESULT_LIMIT` makes the Go adapter's `maxLine = 8 << 20`
  wire cap a real, reachable ceiling** rather than a comment that's
  already true. Answer: `docs/activity.md` assumes the harness bounds
  results to "a few hundred KB" upstream of the sidecar, which stays well
  under 8MB; this node fixes the stale comment (step 4) and flags the cap
  in the result, but does not raise it — a result that actually
  approaches 8MB is a separate problem this node does not need to solve.
- **`buf breaking` reports a break the additive fields don't intend.**
  Answer: read the report before calling the node done; per
  `proto/README.md`, pre-1.0 breaks are allowed but must be named
  explicitly in the result — silence, not the break itself, is the
  failure mode to avoid.
- **The writer's turn rule (usage arrives before the tool results
  answering that turn's calls) looks wrong once real delta/parent data
  flows through it, tempting a "fix."** Answer: the work order explicitly
  forbids this; step 4's tests confirm the existing rule against the new
  input shape and change nothing about `assignTurn`.
- **`mill logs -f`'s raw-delta path diverges from the static path in a way
  that breaks an existing consumer of `RenderActivity`.** Answer:
  `RenderActivity` itself keeps its current per-record behavior for every
  body kind except gaining the thinking case; the accumulation is new
  code (`ActivityRenderer`) that its three whole-attempt callers
  (`RenderedLog`, `logs.go`'s static path, `mcp_tools.go`) opt into, and
  the `-f` path is additive and only engages under `--follow`, so nothing
  that calls bare `RenderActivity` today changes behavior.
- **The acceptance criterion "the sealed frame holds one `text` per block
  with `ended_at`" cannot literally be met**, because Seal
  (docs/activity.md §Rollout item 3: frames, the index, the twin,
  recovery) has not landed in this tree — there is no frame writer and
  nothing sets `Activity.ended_at` anywhere in `internal/run` or
  `internal/store`. Answer: this is named here rather than left silent,
  per the reviewer's finding. This node supplies the delta/`final`
  records Seal's own coalescing step (§Lifecycle point 4) is specified to
  consume, and step 5 gives `mill logs` the equivalent, observable
  behavior — one line per block — directly against the live file in the
  meantime. The literal frame and `ended_at` are Seal's to produce; if the
  mill still holds this node to the literal wording, that is a dependency
  on rollout item 3 landing first, which this plan cannot manufacture
  without building Seal itself (frame format, zstd, the index, the twin
  capture) — explicitly out of scope for "the only node that touches
  `proto/harness/v1`."

## Decisions

- `block_id` is synthesized by the sidecar from the SDK message id plus
  the content block `index`, and is scoped to one session attempt — not a
  global id — matching how every other id in the activity record
  (`call_id`, `turn`) is scoped.
- The spike's findings are recorded as a new dated addendum in the
  existing `docs/spikes/sdk-sessions.md`, in the same "Script / Observed /
  Verdict" style as the file's other entries, rather than a new file.
- `internal/run/activity.go`'s writer logic (`assignTurn`, `redactBody`,
  `applyCeiling`) is not modified by this node — the work order's
  "confirm, not modify" instruction is read as covering exactly that
  write-time logic. The file does grow two additive, read-side pieces the
  acceptance criteria call for by name and that the writer never had a
  reason to do itself: the `Activity_Thinking` case in `RenderActivity`,
  and the new `ActivityRenderer` that accumulates a block's deltas for
  whichever caller wants one line per block instead of one per record.
- The literal "sealed frame" half of the streaming-text acceptance
  criterion is Seal's (rollout item 3) to close, not this node's; this
  node's `ActivityRenderer` is a stand-in against the live file, not a
  reimplementation of seal-time coalescing, and is expected to be
  superseded (or reused) when Seal lands and writes `Activity.ended_at`
  into the frame directly.
- The `Thinking` proto message mirrors `Text`'s shape exactly
  (`block_id`, `delta`, `final`, plus its own text field) rather than
  reusing `Text` with a kind flag, so a consumer can `switch` on the
  `Event` oneof the same way it already does for the existing cases.
- `parent_call_id` is added as a field on `Event` itself (applying to
  every event the flight forwards) rather than duplicated per body
  variant, since `internal/harness/claude/adapter.go`'s `flight.deliver()`
  forwards the whole event with no per-case logic — a single field keeps
  that pass-through untouched.
