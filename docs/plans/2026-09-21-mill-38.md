# A session's test suite reaches the production dagger and mill through the default sockets

## Approach

Give every process a workspace spawns — a check step, a session's sidecar,
and everything the session's own shell spawns under it — an explicit
`DG_SOCKET`/`MILL_SOCKET` that names a path under the run's own directory,
one nothing ever binds. This closes the hole at the one place both the
local and machine backends already funnel a spawned process's environment
through: `Workspace.Environment()`. That map is merged into a sidecar's and
a check step's environment *after* the harness adapter's deny-list filter
and in both `strict` and `inherit` (`internal/harness/claude/environment.go`
lines 174-191: "The workspace's own variables go on with them, in both
modes and after the deny filter"), the same place the run's git identity and
egress/proxy variables already cross both environment floors
(`mill#50`, `mill#54`, `ab2b659`). No change to the deny list itself is
needed or correct: `deniedPrefixes` already strips `DG_`/`MILL_` from
whatever the mill's own process happens to have set (mill#24), which is why
the incident's sessions had *no* socket variable at all rather than a leaked
real one. Stripping to nothing was mistaken for safety; the gap is that
absence makes `defaultSocketPath()` and `envOr(daggerSocketEnv,
defaultDaggerSocket)` (`internal/cli/serve.go:42-49`,
`internal/cli/run.go:62-70`) fall back to the compiled-in production paths,
which the local backend's shared filesystem and uid make reachable. Handing
every child a real, non-empty, dead path instead of no path at all is what
makes that fallback never trigger.

The exact same fix already reaches specs and check steps as well as
sessions: `local.Workspace.Exec` (`internal/workspace/local/local.go:508-538`)
merges `environmentFor(token)` into every command it spawns — git, a check
step's `mise exec`, and a spec that calls `w.Exec` directly — before the
harness even enters the picture, and the machine backend's own `Exec`
(`internal/workspace/machine/exec.go`) does the same through
`execEnvironment`. One function, called from both workspace types'
`Environment()`, fixes the whole surface the incident actually hit (a
`ginkgo` run inside a session's checkout), not only the harness adapter's
sidecar spawn.

That still leaves one hop unfixed, found by the first review of this plan:
a session's own tools (its Bash calls) do not read the sidecar's process
environment directly. `sidecar/src/session.ts`'s `sessionEnv` builds the
SDK's `options.env` from a small, explicit set of copy-lists —
`ENVIRONMENT_PASSTHROUGH`, `WORKSPACE_GIT_ENVIRONMENT`,
`WORKSPACE_EGRESS_ENVIRONMENT` — and "what is not listed here is not
present" by the file's own doc comment. `DG_SOCKET`/`MILL_SOCKET` are on
neither list, so even once the sidecar's own process environment carries
the dead paths (via `session.Workspace.Env`, above), the session's shell
still sees no socket variable at all and the incident's actual failure mode
— a spec's `ginkgo` run falling through to the compiled-in default — is
unchanged. `WORKSPACE_EGRESS_ENVIRONMENT` is the right list to extend,
not a new one: its own doc comment already states the principle these two
names fall under — "a step may not choose its own way out" — and the
proxy and gateway variables already there are copied past a step's
carve-out for exactly that reason.

Two things not done, and why:

- **No change to `internal/cli`'s socket-defaulting logic.** Removing the
  hardcoded `/run/dagger/dg.sock` / `/run/mill/mill.sock` fallback, or
  requiring the flag, would fix the symptom by breaking the caller the
  default exists for: `defaultSocketPath()`'s own comment says it is "the
  runtime directory... which is where a systemd RuntimeDirectory= puts it,"
  i.e. the actual worker unit relies on exactly this fallback when it is
  started with no `--socket` and no `$MILL_SOCKET`. The bug is not that the
  default exists; it is that a session or check step's environment doesn't
  override it. Touching the CLI defaults would be a bigger, riskier change
  for no criterion this node states.
- **No attempt to sandbox the local backend properly** (a mount namespace or
  a bind of emptiness over `/run/dagger` and `/run/mill`) so the paths are
  unreachable regardless of environment. The local backend's own package doc
  states its isolation is "the account and the tool policy, and nothing
  more," with the machine backend named as the implementation with "a real
  boundary" — this is a settled architectural line, not an oversight, and
  redoing it would also break the backend on macOS, where `ab2b659`'s own
  commit message records it being exercised ("on this Mac"). Out of
  proportion for this node; the acceptance criteria ask for the environment
  to lie about the socket, not for the filesystem to hide it.

## Steps

1. **Add the shared "dead socket" helper.**
   `internal/workspace/exec.go` gains a function — alongside `FloorNames`,
   `Floor`, `OnFloor`, which already state the local-backend-and-sidecar
   shared vocabulary this belongs next to — that takes a run's own directory
   and returns the two variables:
   ```go
   func DeadSockets(dir string) map[string]string {
       return map[string]string{
           "DG_SOCKET":   filepath.Join(dir, "no-dagger.sock"),
           "MILL_SOCKET": filepath.Join(dir, "no-mill.sock"),
       }
   }
   ```
   with a doc comment naming why: real, absolute, non-empty paths (so
   `envOr`/`defaultSocketPath`'s "empty means unset" never re-triggers the
   fallback this fix closes), scoped to the run's own directory (so two runs
   never collide and cleanup is automatic — `Destroy` already removes the
   whole directory), and never created or bound by anything, so a dial
   fails rather than reaching a worker. The comment is careful to say
   "scoped to," not "visible inside": for the local backend `dir` is a
   directory a session's own processes can see, but for the machine backend
   (step 3) it is a host-side accounting path the machine's namespace never
   mounts — the dead value still lands in the session's environment, it is
   just never resolvable from either side, which is stronger, not weaker.
   Files touched: `internal/workspace/exec.go`.
   Proof: new cases in `internal/workspace/exec_test.go` asserting
   `DeadSockets(dir)` returns two distinct, non-empty, absolute paths under
   `dir` that are neither `/run/dagger/dg.sock` nor `/run/mill/mill.sock`
   nor `/run/user/*/mill/mill.sock`-shaped, and that nothing is listening at
   either (a short `net.Dial("unix", path)` fails).

2. **Wire it into the local workspace's environment.**
   `internal/workspace/local/local.go`'s `environmentFor` (currently lines
   422-437) reads `w.handle` under the existing lock (the way
   `GitEnvironment` and `Environment` already do) and, when it is non-nil,
   merges `workspace.DeadSockets(filepath.Dir(handle.Socket))` into the
   returned map — `filepath.Dir(handle.Socket)` is the run's own directory,
   the same one holding `checkout/`, `ws.sock`, `browser/` and `gitconfig`
   (`local.go:280-292`). Nil handle (before `Create`/`Attach`) returns the
   map unchanged, matching `GitEnvironment`'s existing nil handling.
   Files touched: `internal/workspace/local/local.go`.
   Proof: a new case in `internal/workspace/local/local_test.go` (or
   `support_test.go`) that, after `Create`, asserts `w.Environment()`
   (and, separately, the environment a real `w.Exec` child actually sees —
   the suite already has a pattern for reading a spawned child's own env,
   used by the `ab2b659` floor spec) carries `DG_SOCKET`/`MILL_SOCKET` set
   to paths under the run's directory that do not exist on disk and are not
   `/run/dagger/dg.sock` / `/run/mill/mill.sock`.

3. **Wire it into the machine workspace's environment, and document why it
   was already closed.**
   `internal/workspace/machine/machine.go`'s `Environment()` (lines 696-711)
   gets the same treatment: read `w.handle` under lock, and when non-nil,
   merge `workspace.DeadSockets(filepath.Dir(handle.Socket))` — `handle.Socket`
   here is `filepath.Join(w.config.socketDir(record.ID), SocketName)`
   (`machine.go:559`), a **host-side** path under the worker's own runtime
   directory that the machine's namespace never mounts anywhere, so a
   session inside the machine cannot resolve it either way — the value
   still reaches the session's environment (a session's env is assembled on
   the host, before the process is placed in the machine), it is just never
   dereferenceable from either side of the boundary. This is defense in
   depth, not the load-bearing fix for this backend: the machine already
   binds nothing at `/run/dagger`, and binds `/run/mill/<id>` — which holds
   only `ws.sock` (`internal/workspace/machine/names.go:22`) — at
   `/run/mill` inside the machine, so `/run/dagger/dg.sock` and
   `/run/mill/mill.sock` already resolve to nothing there today regardless
   of this change. Add a paragraph to `docs/sandbox.md`
   (§Credentials, beside the existing "the model credential never enters
   the machine" bullet) stating this explicitly, so the guarantee is
   asserted in the one place that already inventories what a session inside
   a machine cannot reach, rather than left to be re-derived from the bind
   list.
   Files touched: `internal/workspace/machine/machine.go`, `docs/sandbox.md`.
   Proof: a new case in `internal/workspace/machine/machine_test.go`
   mirroring step 2's, asserting `Environment()` carries the same dead

   `internal/workspace/machine`'s existing bind-mount specs live, e.g.

6. **Add the `mill doctor` probe.**
   A probe that reimplements `DeadSockets` and checks its own output against
   itself cannot fail — the two are the same deterministic function, so
   nothing exercises whether steps 2-3's *wiring* is actually in place. The
   probe instead exercises the real code, and does so without needing
   anything `doctorOptions` does not already carry: the first review of this
   plan found that a throwaway workspace built with `local.Workspace.Create`
   cannot work here, because `Create` requires `spec.Origin`/
   `w.options.Origin` and runs a real `git clone` against it, and a `mill
   doctor` invocation has no project origin or forge credential to give it —
   on an ordinary host `Create` would fail with "no origin to clone" before
   `Environment()` is ever reached, so the probe's own "wiring missing"
   branch would fire on every correctly-configured host.
   `Attach` has no such precondition: it opens whatever checkout already
   sits at `<dir>/checkout`, and does not clone anything. So the probe
   provisions that checkout itself — `os.MkdirTemp(opts.workspaceDir,
   "doctor-isolation-*")` for the run's directory (a real child of the
   host's configured workspace directory, not an unrelated system temp path,
   so a workspace directory that cannot host a socket at all — wrong
   filesystem, no exec permission — is also caught), `os.MkdirAll` the
   `checkout` subdirectory, and `git init --quiet` it — no clone, no origin,
   no credential, just enough of a repository for `Attach`'s own
   `BranchOf`/`checkout -B` to succeed on an unborn HEAD — then calls
   `local.New(local.Options{Root: root, ...}).Attach(ctx,
   workspace.Spec{RunID: "doctor-isolation", NodeRef: "doctor/isolation"})`.
   This is the same `Attach` a resumed run's own workspace goes through, so
   a workspace directory the host cannot use for a real run (permissions,
   `arrangeSigner`'s `ssh-keygen` failing) fails the probe honestly rather
   than being sidestepped.
   The check itself is a small, pure function of the resulting environment
   — `checkSessionEnv(env map[string]string, socket, daggerSocket string)
   doctor.Result`, unexported and called by `SessionSockets` once `Attach`
   succeeds — so the two failure branches the acceptance criterion names
   are tested directly, with a fabricated map, rather than by trying to
   coax the real `git init`-and-`Attach` path into failing in a specific
   way: it fails when `DG_SOCKET`/`MILL_SOCKET` are missing or empty (the
   wiring from step 2 is not present), when either equals `socket`/
   `daggerSocket` (the session's path *is* the production path), or when a
   short dial to either succeeds — on a healthy host the real `socket` is
   live (that is what the `socket` probe already establishes), so a dial
   succeeding on the value `Environment()` handed back means the wiring
   leaked the real address rather than a dead one. `SessionSockets`
   (exported, in `internal/doctor/doctor.go`) is the part that does the
   `git init`/`Attach`/`Environment()`/`Destroy` dance and hands the result
   to `checkSessionEnv` — an `Attach` failure is reported as the probe's own
   failure, with the underlying error attached, rather than left to panic
   the command. The workspace is destroyed before the probe returns either
   way. This is a local-only probe — no worker RPC round-trip, following
   `probeWorkspace`/`probeSpace`'s existing pattern — because a session's
   environment is a fact about this host's configuration and code, not
   about a run in flight.
   Wire it into `internal/cli/doctor.go`: add `"isolation"` to `ProbeNames`
   (`doctor.go:41-44`), a `probeIsolation(opts doctorOptions) probe` calling
   `doctor.SessionSockets(ctx, opts.workspaceDir, opts.socket,
   opts.daggerSocket)`, add it to `runProbes`'s slice (`doctor.go:226-238`)
   — after `probeWorkspace`, since both are workspace-shaped, local,
   always-answerable probes — and a line in the command's `Long` help text
   listing it among the others (the `doctor_internal_test.go:152-157` spec
   already enforces that the help text and `ProbeNames` agree, so this is
   what makes the addition pass or fail loudly rather than silently drift).
   Files touched: `internal/doctor/doctor.go`, `internal/cli/doctor.go`,
   `docs/tools.md` (§doctor: bump "eleven probes" to twelve, add the table
   row and, for consistency with the existing worked example, a
   `pass  isolation ...` line in the sample transcript).
   Proof: new cases in `internal/doctor/doctor_test.go` for `checkSessionEnv`
   directly — a fabricated environment missing `DG_SOCKET`/`MILL_SOCKET`
   reports missing; one where `socket`/`daggerSocket` are given the same
   value the fabricated environment carries reports a live collision (using
   a real `net.Listen("unix", ...)` for the "succeeds" half of the dial
   check); and the passing case — plus one case for `SessionSockets` itself,
   on an ordinary `--workspace-dir`, asserting it passes and that the
   directory it provisioned is gone afterward (`Destroy` ran), which is the
   spec that actually exercises the `git init`/`Attach` path this step adds
   and would fail if that plumbing were wrong even though `checkSessionEnv`
   passed its own unit tests. `internal/cli/doctor_test.go`/
   `doctor_internal_test.go` cover that `isolation` appears in `ProbeNames`,
   in the reported output, and in the `--help` text, in the same position
   in all three (the existing `Expect(reported).To(Equal(cli.ProbeNames))`
   assertion already forces this).

7. **Close the two places mill's own specs already omit a socket, and make
   the shared fixtures force both flags.**

   socket, and named two counterexamples: `internal/cli/run_test.go`'s
   `--gateway` describe block, "refuses to start without the upstream
   credential, before claiming" (around line 253), calls `cli.Run` directly

   check failing before the store is ever dialed; and
   `internal/cli/environment_test.go`'s private `invoke` helper (line 89),
   used by "A unit spec starts no worker whatever the environment names"
   (line ~108), calls `cli.Run` with neither `--socket` nor `--dagger-socket`

   `DG_PROJECT` check firing first. Both pass today only because of

   `environment_test.go`'s second use of `invoke` (line ~123, "A config path

   Fix both concretely: give the `--gateway` test an explicit

Steps are ordered so the tree keeps building and passing after each: 1 adds
an unused pure function, 2-3 wire it into the two workspace backends behind
specs that only add assertions, 4 is spec-only, 5 closes the sidecar's own
copy-list gap, 6 adds a new, independent probe, 7 fixes the two concrete
unguarded specs and hardens the shared fixtures against future ones, and 8
proves the whole chain only once every link exists.

## Risks

- **`internal/workspace/machine`'s exact accessor for the per-run socket
  directory may differ from what step 3 assumes.** The plan reads
  `filepath.Dir(handle.Socket)`, which line 559's `handle.Socket:
  filepath.Join(w.config.socketDir(record.ID), SocketName)` should make
  identical to `w.config.socketDir(record.ID)` directly — but if `open`'s
  shape has moved since this was read, the implementer should use whichever
  accessor already exists rather than add a new one. Mitigated by keeping
  the change symmetric with `local.go`'s `filepath.Dir(handle.Socket)`,
  which is the more defensive of the two (works even if the directory
  layout changes) and needs no new field.
- **A new `doctor` probe changes an exact-match assertion
  (`Expect(reported).To(Equal(cli.ProbeNames))`) and the help-text spec
  together** — missing either the `ProbeNames` entry, the `Long` text line,
  or `docs/tools.md`'s count leaves the build red or the docs stale. `mill
  mcp`'s doctor tool is documented (`docs/tools.md`) to reuse the same
  `runProbes` result, so no separate wiring is expected there, but the
  implementer should grep `ProbeNames` and `runProbes` once more before
  finishing to confirm nothing else enumerates all twelve probes by hand.
- **`SessionSockets` spins up a real `local.Workspace` inside a `doctor`
  invocation** — a `git init`, a `ssh-keygen` through `arrangeSigner`, and a
  socket bind — which is heavier than every other probe (all of which are
  either a cheap RPC or a `statfs`) and could pick up unrelated failures —
  no `git` on `PATH`, permissions on `--workspace-dir`, `ssh-keygen`
  missing — that have nothing to do with socket isolation. Mitigation: catch
  an `Attach` error and report it as the probe's own failure with the
  underlying error attached, rather than letting it panic the command, so a
  doctor run still reports the other eleven probes; and keep the actual
  pass/fail logic (`checkSessionEnv`) a pure function of an environment map,
  so the failure branches AC3 asks for are proven with a fabricated map in
  milliseconds rather than by finding a way to make the real `git
  init`/`Attach` path fail in a specific, reproducible way.
- **The first review of this plan found the "guard two helper functions"
  design incomplete** — any spec built by calling `cli.Run`/
  `root.ExecuteContext` directly, rather than through `mill.run`/`mill.try`/
  `runCLI`, bypasses the guard entirely. Step 7 fixes the two concrete
  instances the review named, but does not add a structural guarantee (a
  lint rule, or a single choke-point every `internal/cli` spec must go
  through) that a *third* future spec cannot repeat the mistake. Accepted
  as the smallest fix that satisfies AC4's stated scenario: building that
  guarantee would mean a new `forbidigo` pattern restricted to
  `internal/cli`'s test files, which is a larger, separately-reviewable
  change this node did not ask for. Mitigation: a reviewer of a future spec
  in this package should grep for `cli.Run(` and `.ExecuteContext(` and
  confirm every call site names both sockets explicitly, the same way this
  review caught the two that didn't.
- **Renaming or repositioning `DG_SOCKET`/`MILL_SOCKET` handling risks
  colliding with a legitimate consumer this plan did not find** — e.g. a
  workflow step that genuinely names `DG_SOCKET` in `env.passthrough` for
  some diagnostic purpose. `denied()` already refuses that today (mill#24),
  so no such step exists in a workflow that currently runs; a grep of
  `workflows/*/workflow.yaml` for `env.passthrough`/`env.set` before step 4
  is cheap insurance. The same grep should cover `env-probe` opting into
  `WORKSPACE_EGRESS_ENVIRONMENT`'s two new names before step 5.
- **The machine-backend live spec (step 3) is the slowest and most
  environment-dependent piece of this plan** — it needs a real machine to
  boot, which the existing `_live_test.go` suite already assumes but which
  may not run in every CI lane. If it cannot run where this change is
  verified, the documentation half of step 3 (`docs/sandbox.md`) and the
  narrower `machine_test.go` unit case still hold, and the live spec should
  be flagged rather than skipped silently.

## Decisions

- **The fix has two production landing points, not one: `Workspace.Environment()`
  and `sidecar/src/session.ts`'s `sessionEnv`.** Neither alone closes AC1 —
  the first gets the dead paths into the sidecar's own process, the second
  is what actually copies them into a session's tools — and the first
  review of this plan is what surfaced that a session's tools do not simply
  inherit the sidecar's process environment. Nothing changes in
  `internal/harness/claude/environment.go`'s deny list: it already does its
  job (strips whatever the mill's own process has), and extending
  `deniedPrefixes` or `FloorNames` would not affect either landing point,
  since `denied()` runs before the floor check and already removes
  `DG_`/`MILL_` names unconditionally.
- **`DG_SOCKET`/`MILL_SOCKET` join `WORKSPACE_EGRESS_ENVIRONMENT`, not a new
  list**, because the property they need — copied past a step's own
  carve-out, in both env modes — is exactly what that list already
  guarantees for the proxy and gateway variables, for the same reason ("a
  step may not choose its own way out").
- **The machine backend gets the same `DeadSockets` merge as the local
  backend, in addition to documenting its existing guarantee**, reading the
  acceptance criterion's "or" as "either is acceptable, but doing both is
  cheap and keeps the two backends' environments shaped the same way,"
  rather than picking one. The live spec in step 3 is what actually
  discharges the criterion; the code change is defense in depth in case a
  future change to the machine's bind list narrows the guarantee.
- **The new probe is named `isolation`**, distinct from the existing
  `socket` probe (which asks whether the service answers on its own
  socket — the opposite question). Placed after `workspace` in report order
  since both describe backend-shaped guarantees about where a run's
  processes stand. It exercises a real, throwaway `local.Workspace` rather
  than recomputing `DeadSockets` and checking it against itself — the first
  review's finding was that the reimplementation could never fail, because
  a pure function compared to its own output is a tautology, not a check —
  so the probe intentionally spends the cost of a real workspace to make a
  wiring regression in step 2 actually detectable.
- **That real workspace is reached through `Attach`, not `Create`, on a
  checkout the probe provisions with `git init`.** The first review also
  found that `Create` needs an origin `doctorOptions` has no way to supply,
  which would have made the "wiring missing" branch fire on every host
  rather than only a broken one. `Attach`'s precondition is just an existing
  checkout directory, so a bare `git init` (no clone, no network, no
  credential) is enough to open one for real. The pass/fail check itself
  (`checkSessionEnv`) is kept a separate, pure function of the resulting
  environment map so the two failure branches AC3 names are still unit-
  tested directly, rather than depending on the real `git init`/`Attach`
  path being coaxed into failing in a specific way.
- **AC4's guard is a `panic`, not a Ginkgo `Fail`,** and lives in the two
  shared helper functions (`mill.run`/`mill.try`, `runCLI`), not as a
  build-tag or environment check inside production code.
  `internal/testsupport`'s dagger fixture needs no change: it never accepts
  a caller-supplied socket that could be empty. The two concrete specs the
  first review found bypassing those helpers are fixed directly rather than
  routed through a new universal choke point — see the matching Risk — since
  building one is a larger change than this node asked for.
- **The Scenario's proof (step 8) is a workspace-level spec, not a full
  Claude Code session.** The mechanism the incident exploited — what
  environment a spawned process receives — is exactly what steps 2, 4 and 5
  already pin down end to end, from the workspace through the harness
  adapter to a session's own Bash environment; re-proving it through a real
  sidecar would cost a credential and materially more suite time for the
  same confidence.
