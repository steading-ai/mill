# Cost by day, and per-step outcome counts beside the totals

## Approach

Two queries, folded in Go, inside the one `Store.Cost` call — not a rewrite
of the existing `UsageSince`-driven rollup into a single merged query.
`UsageSince` gains one column (`recorded_at`) so day-bucketing is a Go-side
grouping over rows already fetched, no new query. The funnel needs its own
query, `StepRunsSince`, windowed on `step_runs.started_at` rather than
`usage.recorded_at`: `usage` rows exist only for skill steps that billed a
model, so a check or gate step (no usage rows, ever) would silently vanish
from `reached`/`died`/`attempts` if the funnel were derived from usage rows
the way the other four sections are. `Store.Cost` therefore issues two SQL
statements — still O(1) round trips regardless of how many runs are in the
window, which is the thing the node's own note ("keep... in one query pass,
as today") and the motivating problem (steading's one-`Inspect`-per-run cost)
both actually care about, not literal single-statement-ness.

Rejected: rewriting `UsageSince` into a single `step_runs LEFT JOIN usage`
query that serves both the token rollup and the funnel. It is the more
"pure" single-statement answer, but it changes the window every existing
section is computed against (`started_at` instead of `recorded_at` for
by_run/by_workflow/by_step/by_model too — a usage row recorded just after its
step_run started but outside a narrow `--since` would move sections), and it
rewrites a working, tested query and its `rollup` type for a benefit ("truly
one SQL statement") nothing in the node asks for. Also rejected: computing
the six counts as SQL aggregates (`FILTER`, `ROW_NUMBER() OVER (PARTITION BY
run_id ...)`) instead of folding rows in Go — every other section in this
file is folded in Go over rows the store already loaded, and nothing about
this window's size (the same order of magnitude as `usage` rows, already
loaded whole) justifies breaking that convention here.

3. **The per-step funnel.**
   `internal/store/queries/step_runs.sql`: new query `StepRunsSince`,
   windowed on `sr.started_at` the same way `UsageSince` is windowed on
   `u.recorded_at` (`since`/`until`/`project` narg), joining `step_runs sr`
   to `runs r` (for `r.status`, `r.id`) and `workflows w` (for the
   `name@version` key), and left-joining `step_runs target ON target.id =
   sr.feedback_from` to resolve the feedback source's `step_name` — done as
   a join, not a second filter, so a `revise`'s target is named correctly
   even when that earlier attempt itself falls outside a narrow window (the
   thing being windowed is the later, feedback-carrying attempt, not the
   attempt it answers). Returns per row: `sr.id`, `sr.run_id`,
   `r.status AS run_status`, `w.name`, `w.version`, `sr.step_name`,
   `sr.attempt`, `sr.status`, `sr.feedback_from`, `target.step_name AS
   feedback_from_step`, `sr.started_at`.
   `internal/store/store.go`:
   - Generalize `workflowKey` to take `(name, version *string)` instead of a
     `UsageSinceRow`, so both `UsageSince` and `StepRunsSince` rows produce
     the identical key — this is what makes a `by_step` key agree with its
     run's `by_workflow` key by construction, not by two separately
     maintained formats.
   - `Store.Cost` calls `StepRunsSince` alongside `UsageSince` (still two
     queries, one `Cost` call) and folds the rows in one pass: per `run_id`,
     track the attempts seen for each `(workflow_key, step_name)` — to
     derive `reached` (>=1 attempt), `passed` (>=1 `CLOSED` attempt),
     `retried` (>1 attempt), `attempts` (count) — and separately track, per
     `run_id`, the single row with the greatest `started_at`; when that
     run's `run_status` is `FAILED` or `ABANDONED`, its `(workflow_key,
     step_name)` gets one `died`. A row with non-empty `feedback_from`
     increments `revises` on `(this row's workflow_key, feedback_from_step)`.
   - `by_step`'s bucket set becomes the *union* of the keys `UsageSince`
     produced (steps with token usage) and the keys `StepRunsSince` produced
     (every step, including checks and gates with none) — a key present in
     only one map still gets a bucket, with zero totals or zero counts on
     whichever side it's missing. This is the change that stops a check
     step from silently having no funnel row at all.
   - `Cost.ByStep` entries now carry `Counts`, everything else in the struct
     unchanged.
   `internal/domain/runs.go`, `internal/server/store_service.go`: no new
   fields needed (since/until/project already threaded through from step 2);
   just confirm `Cost.ByStep[i].Counts` survives the existing
   `cost.ByStep` passthrough (it does — the field rides on `CostBucket`
   itself, added in step 1).
   `internal/cli/read.go`: the STEP section's row loop
   (`runCost`, around line 716) currently emits nothing for a bucket whose
   `GetTotals()` is empty — `for _, source := range sourcesOf(bucket.GetTotals())`
   iterates zero times when there is no usage, which is exactly the
   check/gate-step case (and this step's own funnel-scenario steps, which
   record no usage at all) that the counts exist to surface. Give the STEP
   section its own header (`STEP\tSOURCE\tINPUT\tOUTPUT\tCACHE READ\tCACHE
   WRITE\tREACHED\tPASSED\tDIED\tRETRIED\tREVISES\tATTEMPTS`) and row logic:
   when a bucket has one or more usage sources, print one row per source as
   today, with the bucket's six counts (constant per bucket, not per
   source) repeated on each; when a bucket has none, print exactly one row
   with `-` for SOURCE and `0` for the four token columns, still carrying
   the real counts. RUN/WORKFLOW/MODEL keep today's five-column header and
   per-source-only rows — only STEP buckets carry `Counts`.

   `internal/store/step_runs.sql.gen.go` (regenerated by sqlc),

## Risks

- **Two windows, one request.** `usage.recorded_at` and `step_runs.started_at`
  are different columns bounded by the same `since`/`until` pair. A step
  whose session ran a long time (attempt started before `--since` but billed
  its tokens after) could appear in one section's window and not the
  other's, which is a real, if narrow, way for the day-bucket total and the
  funnel to tell slightly different stories about "the same" window. This is
  inherent to Approach 1 and was named as the reason Approach 2 (a single
  merged query, one window) was rejected — accepted here because the node's
  own acceptance criteria never ask the two to reconcile against each other,
  only that `by_day` sums to `by_model` (both `usage`-window) and the funnel
  numbers match its own scenario (`step_runs`-window). If steading's console
  later needs the two to agree pixel-for-pixel, that is Approach 2's
  rewrite, not a patch on this one.
- **`dayKey`'s UTC boundary is untested against real wall-clock data.** The
  Ginkgo spec can only prove "one day, one row" (no way to backdate
  `usage.recorded_at` through the public write API — confirmed by reading
  `internal/store/queries/usage.sql:4-7`, which has no `recorded_at`
  parameter). Mitigated by giving `dayKey` its own fast, DB-free unit test
  that exercises the boundary directly (step 2) — the multi-day case is
  proven by a pure function test, not by seeding two real days.
- **`docs_test.go` may assert against `mill cost`'s current output shape.**
  Not yet checked (see Files, Uncertain); if it does, step 4's doc rewrite
  and step 2/3's new columns need to keep it passing — a `make test` failure
  here is expected to be self-diagnosing (the test names the mismatched
  line), not a design risk.
- **`StepRunsSince`'s self-join cost.** A window with many step runs joins
  `step_runs` to itself once per row to resolve `feedback_from`. Negligible
  at today's scale (the same order of magnitude as `usage` rows, already
  loaded whole per window) and not worth pre-optimizing; flagged only so a
  reviewer doesn't read the join as accidental.
- **`by_step`'s key format change is a real behavior change wrapped in an
  additive-looking wire diff** (`CostBucket.key` stays `string key = 1`, but
  what it contains changes from a bare step name to `name@version/step`).
  `buf breaking` will not catch this — it isn't a schema break. Named
  explicitly here and in step 1 so the reviewer judges it as the design
  decision it is, per `AGENTS.md`'s instruction to name a contract change
  rather than let a lint pass stand in for review.

## Decisions

- **Two queries folded in Go, not one merged query or SQL-side aggregates**
  — see Approach; the deciding fact is that check/gate steps have no
  `usage` rows and would vanish from the funnel under a usage-row-only
  source, and every other section in this file already folds rows fetched
  once into Go maps, so `StepRunsSince` follows the same shape rather than
  introducing a second computation style.
- **`TimeBucket` has no explicit `NONE` value** — the zero value
  (`TIME_BUCKET_UNSPECIFIED`) already means "no bucketing," matching every
  other enum in `mill.proto`; the work order's "none, day" is read as the
  two observable states, not a mandate for two non-zero enum values.
- **`StepCounts` rides on `CostBucket` as an optional-in-effect field**,
  not a second bucket message and not a rename of `by_step`'s field type —
  the smallest additive shape, and the one the existing `CostBucket` doc
  comment already anticipates ("what the bucket groups by... a step name,
  or a model").
- **`by_step`'s key is `<name>@<short-version>/<step-name>`**, reusing
  `workflowKey`'s existing format for `by_workflow` verbatim rather than
  adding a second field to `CostBucket` for the version — one string, one
  place a consumer parses it, consistent with `by_run`'s own key (a dagger
  node reference, also a single opaque string).
- **`--until` takes the same relative-window syntax as `--since`** (`24h`,
  `7d`, parsed by the existing `parseWindow`), not an absolute timestamp —
  the work order gives no CLI shape for it, and symmetry with `--since` is
  the smallest choice that doesn't ask an operator to learn a second syntax.
- **Day bucket keys are UTC calendar dates.** No precedent for a different
  timezone convention exists anywhere else in the repo (checked: no other
  day-truncation code); UTC is the only default that doesn't depend on
  where the binary happens to run.
- **New Ginkgo specs live in `internal/cli/read_test.go`**, not a new
  `internal/store`-level or `internal/server`-level suite — `Cost` has no
  existing coverage below the CLI layer (checked: no `Describe("Cost"` /
  `Describe("cost"` hit outside `internal/cli`), and the package's own
  stated convention is that these tools are "specified against a real
  service over a real socket... nothing here fakes the store."
- **Funnel scenarios seed a small literal `*millv1.Workflow`**, not
  `workflows/feature`'s real skill files — `internal/store/derive_test.go`'s
  `fiveStepWorkflow()` already establishes that a bare step-name literal is
  sufficient test data at this layer, and it avoids depending on a sibling
  workflow directory's skill content this feature has nothing to do with.
- **The seeded scenario reaches `RUN_STATUS_FAILED` via the `Fail` RPC
  directly**, not by driving `internal/run`'s full retry/breaker loop — the
  RPC is the same one the breaker itself calls, and every other read-tool
  spec in this file already writes ledger rows directly through the
  store's public API rather than running the engine.
