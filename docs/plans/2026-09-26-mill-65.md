# A red default branch files one bug node per repository, kept current and dropped when green

## Approach

Build the probe/reconciler split the work order's Decision section asks for,
as its own small surface inside `internal/run` rather than folded into
`sweep.go` or a new sub-package. The rejected alternative — inlining the
create/comment/drop logic directly into `sweepOne`-style code with no
separate `Reconcile` function — is smaller today but throws away the one
property the work order is explicit about: "the reconciler is the seam a
webhook receiver plugs into." A webhook receiver that arrives later needs to
call the exact same convergence logic with its own findings, not a poll
loop's private helper; splitting later, after callers exist, is strictly
more work than splitting now. `internal/run/healing.go` (the work order's
first-named option) is chosen over a new sub-package because `Sweep`,
`Repository`, and `Forge` are already in scope there and nothing about
healing needs its own package boundary — it is one more file beside
`sweep.go`, not a new subsystem.

Two gaps in the work order's literal deliverable list are resolved here,
both under **Decisions** below rather than left implicit:

1. **`Forge.Checks` cannot supply what acceptance criterion 1 demands.** The
   title format (`main is red at <sha>: <check name>`) and the body
   ("failing checks by name with their URLs") need per-check detail; today's
   `Checks(ctx, sha) (Status, error)` collapses everything to one of three
   values. A second interface method, `FailingChecks`, is added alongside
   `DefaultHead` — not named in deliverable 1, but required to meet
   deliverable 3 and acceptance criterion 1 as written.
2. **"The merged pull request at that sha if the forge can name it"
   (deliverable 3's prose) is cut from this plan's scope.** No acceptance
   criterion tests it, GitHub and GitLab would need materially different new
   lookups to support it, and the work order's own hedge ("if the forge can
   name it") reads as optional. Left as a follow-up rather than a third new
   `Forge` method built for a detail nothing checks.

Every write the reconciler makes goes through a `*skift.Client` **scoped to
the finding's own project** (`Client.Scoped(project)`, the same mechanism
`Runner.repository` already uses to route a claim's writes into the project
it landed in — `internal/run/run.go:581`), never through the runner's own
client and its own (possibly empty) project. This is what makes a
cross-project sweep — one worker healing several repositories, each its own
skift project — file each finding into the right place instead of into
whichever project the unfiltered worker's client happens to default to.

Idempotence (deliverable 2, acceptance criterion 6) comes from reading
current state before writing, not from relying on skift's `request_id` dedup
to swallow a redundant call: for every project in play, `Reconcile` first
reads every currently-open node this reconciler has ever filed there (a
project-wide list by a shared `mill-heal` label — see Decisions), then
diffs that set against the findings passed in, and only calls `ApplyPatch`
for an actual difference. A second `Reconcile` over unchanged findings and
an unchanged set of open nodes issues zero `ApplyPatch` calls. The `mill-`
request ids described in the Notes are kept as a second line of defense
against a crash between the read and the write (matching the ledger's own
"request id makes a retry a no-op" convention, `docs/ledger.md` §"What goes
to skift, and when"), not as the primary mechanism — and, per a finding
against the previous version of this plan, not as the *proof* of
idempotence either: skift accepts a byte-identical replay of a request id
as a no-op, so a reconciler that blindly re-sent the same write under the
same id on every call would also show "no second write" if the ledger
row's own request-id replay were what the test relied on. Step 3's test
proves the stronger claim — that `Reconcile` does not even attempt the
call — by counting `ApplyPatch` RPC attempts at the transport level, not by
reading skift's resulting state.

**Rejected: testing idempotence against a new hand-rolled fake skift
client.** Acceptance criterion 6 names "the fake skift client counting
`ApplyPatch` calls," but no such fake exists anywhere in this codebase today
— `internal/skift`'s own specs (`client_test.go`, `support_test.go`) and
`internal/run`'s DB-labelled specs all exercise a real skift
(`testsupport.Skift`) over its actual RPC surface. Building a parallel fake
implementation of the whole client for one spec would be new test
infrastructure with no other user. Step 3 gets the same call-counting proof
the acceptance criterion asks for by wrapping the *transport* the real
`skift.Client` is built on (`skift.New` takes any `connectrpc.com/connect`
`HTTPClient`, and `testsupport.Skift.HTTPClient()`/`BaseURL()` already
expose what is needed to build one) with a small `http.RoundTripper` that
counts requests whose path names the `ApplyPatch` RPC. This counts real RPC
attempts against a real service, which is what the acceptance criterion is
actually protecting, without a fake that reimplements skift's own
semantics.

## Steps

1. **`forge.Forge` gains `DefaultHead` and `FailingChecks`; both adapters
   implement them; the GitHub probe uses `DefaultHead`.**
   `internal/forge/forge.go`: add `DefaultHead(ctx context.Context) (ref,
   sha string, err error)` and `FailingChecks(ctx context.Context, sha
   string) ([]CheckResult, error)` to the `Forge` interface, plus a
   `CheckResult{Name, URL string}` type. `DefaultHead` returns the
   repository's default branch name and its current head sha (empty sha
   when the branch has no commits, mirroring `BranchHead`'s "not yet is not
   an error" contract). `FailingChecks` returns one entry per check that is
   not green on the given sha — empty when everything is green or there is
   nothing to check — named and linked where the forge gives a URL.
   `internal/forge/github/github.go`: `DefaultHead` composes the existing
   private `repository(ctx)` (for `DefaultBranch`) and `BranchHead`, the
   same two calls `probe.go` already makes in sequence.
   `internal/forge/github/probe.go`: its `repository` + `BranchHead` pair
   (lines ~127-133) is replaced by one call to `c.DefaultHead(ctx)`, kept
   behind the same permission-classification path.
   `checkRuns`'s anonymous run struct gains `Name` and `HTMLURL` (GitHub's
   check-run JSON already carries both); `FailingChecks` calls the same
   check-runs endpoint `Checks` does plus GitHub's per-context commit
   statuses endpoint (`/commits/{sha}/statuses`, distinct from the combined
   `/status` `Checks` reads), and reports every entry not green by name
   (check run `name` / status `context`) and URL (`html_url` /
   `target_url`).
   `internal/forge/gitlab/gitlab.go`: `DefaultHead` composes the existing
   private `projectInfo(ctx)` and `BranchHead`. `FailingChecks` re-reads the
   latest pipeline for the sha (as `Checks` does) and, when it is not
   green, lists that pipeline's failed jobs (`GET
   /projects/:id/pipelines/:id/jobs?scope[]=failed`) for their name and
   `web_url`.
   Every hand-rolled type in this repository asserting `var _ forge.Forge =
   (*T)(nil)` must gain the two new methods to keep compiling:
   `internal/run/support_test.go`'s `fixtureForge`, `internal/workspace/verbs/verbs_test.go`'s
   `catchUpForge`, and `internal/forge/forge_test.go`'s `stubForge` (found

   of this plan). A minimal `DefaultHead` returning a fixed branch/sha and
   `FailingChecks` returning nil are enough for all three's existing specs,
   none of which exercise either method today.
   Test: new cases in `internal/forge/github/github_test.go` and
   `internal/forge/gitlab/gitlab_test.go` — `DefaultHead` returns the
   forge's configured default branch and its head sha; a repository with no
   commits on that branch returns an empty sha and no error (mirroring
   `BranchHead`'s own "not yet" contract); `FailingChecks` on a green sha
   returns empty; on a red sha returns the failing check/job names and URLs
   the fixture server was set up to answer, and omits any that are green.
   `internal/forge/github/probe_test.go` keeps passing unchanged (it
   asserts on `Probe`'s outcome, not on which internal method produced it).
   `go build ./...` (all three fixtures compile) and `go test
   ./internal/forge/... ./internal/run/... ./internal/workspace/...`.

2. **A `skift.Client` capability for a non-gate node: file, drop, comment,
   and list by the healing marker — every write scoped to the finding's own
   project.**
   `internal/skift/patch.go`, beside `CreateGate`/`Gates`:
   - `HealingLabel = "mill-heal"`, a constant every node this package files
     under this feature carries — the shared marker `Findings` (below)
     lists by, analogous to `GateLabel`.
   - `KeyLabel(key string) string` — `"mill-heal-key-" +
     hex(sha256(key))[:12]`, the deterministic, per-finding label a node
     carries alongside `HealingLabel`. Exported because `internal/run`'s
     reconciler needs to derive the same label from a `Finding.Key` to
     match a finding against the node it already filed.
   - `GreenLabel = "mill-heal-green"` — added to a claimed node's labels
     the one time the reconciler comments that main is green on it, so a
     later sweep does not repeat the comment on a node nobody has acted on
     (see step 3).
   - A `Finding` struct (`Title, Body string; Labels []string`) and
     `FileFinding(ctx, requestID string, finding Finding) (*skiftv1.Node,
     error)` — one `create_node` op, no `Parent`, no `blocked_by` edge,
     `Kind: "bug"`, `AssigneeKind: ASSIGNEE_KIND_AGENT`, `Priority:
     PRIORITY_P1` fixed inside the method, labels
     `append([]string{HealingLabel}, finding.Labels...)`.
   - `DropFinding(ctx, requestID, ref, detail string) error` — a
     `drop_node` with `Reason: DROP_REASON_NO_LONGER_RELEVANT`.
   - `CommentFinding(ctx, requestID, ref, body string, addLabel string) error`
     — a comment, and, when `addLabel != ""`, an `update_node` adding that
     label in the same patch (one `ApplyPatch` call with two ops, the same
     one-patch-two-ops shape `CreateGate` already uses for its node+edge
     pair) — this is how the green comment and `GreenLabel` are set
     together, so a crash between them cannot leave one without the other.
     Called with `addLabel: ""` for the plain "new sha" comment, which
     needs no label change.
   - `Findings(ctx context.Context) ([]*skiftv1.Node, error)` — every open
     node in `c.project` carrying `HealingLabel`
     (`NodeFilter{Projects: []string{c.project}, Labels: []string{HealingLabel},
     Status: STATUS_OPEN}`, `View: VIEW_FULL` so `.Claimed`/`.Labels` are
     populated) — no per-key label, no `Parent`, no `AssigneeKind`
     restriction, which is the one respect in which this cannot reuse
     `Gates`. A caller matches a returned node back to a finding's key by
     scanning its labels for the `KeyLabel` prefix.
   Every write here goes through the existing `ApplyPatch`, so
   `refuseGateWrites` (unaffected — none of these ops target a
   user-assigned node) and the empty-lease path both apply unchanged. None
   of these methods take a project parameter: like every other method on
   `Client`, they act on `c.project`, and a caller that needs to act on a
   different project calls them on `c.Scoped(project)` — the reconciler
   (step 3) is exactly such a caller, and this is what closes the routing
   gap the previous version of this plan left open (a bare `FileFinding`
   with no project argument, called once across every project, would have
   filed every finding into the runner's own client's project — empty for
   an unfiltered worker — instead of each repository's own project).
   Test: `internal/skift/finding_test.go` (new, matching
   `client_test.go`/`support_test.go`'s fixture-and-real-skift pattern) —
   `FileFinding` with an empty lease id succeeds against the real service
   and returns a node with the given title/body, kind `bug`, assignee kind
   agent, priority P1, no parent, carrying `HealingLabel` plus the given
   labels; `DropFinding` with an empty lease id succeeds on an
   agent-assigned node (the positive case beside `client_test.go`'s
   existing proof that the same op is *refused* on a user-assigned node);
   `CommentFinding` with a non-empty `addLabel` leaves the node carrying
   that label and the comment, in one patch; `Findings` returns exactly the
   nodes carrying `HealingLabel` in the client's own project, none from
   another project seeded in the same fixture, and reports `Claimed: true`
   once a claim is taken on one. `go test ./internal/skift/...`.

3. **The finding type and the reconciler.**
   New `internal/run/healing.go`: `Finding{Key, Project, Title, Body,
   Labels []string}` (the work order's own shape) and `Reconcile(ctx
   context.Context, base *skift.Client, projects []string, findings
   []Finding) ([]HealAction, error)`. A `HealAction{Key, Ref, Verb string}`
   (`Verb` one of `"filed"`, `"commented"`, `"commented-green"`,
   `"dropped"`; unchanged findings produce no action) is returned so the
   caller (step 5) can turn only the actual writes into ledger findings.
   `Reconcile` takes the **full project list**, not just the projects
   `findings` happens to mention, because a project whose branch has gone
   fully green produces zero findings this call and would otherwise never
   be visited to check whether it has a stale open node to drop — this is
   the fix for a gap in the previous version of this plan, where the only
   read (`FindingsWithLabel` per finding) had nothing to enumerate once a
   finding's label no longer existed anywhere in the call.
   For each project in `projects`: scope a client
   (`skift := base.Scoped(project)`), read `skift.Findings(ctx)` once,
   and index the result by each node's `KeyLabel` (scanning its labels for
   the `mill-heal-key-` prefix skift.KeyLabel produces). Then, for each
   finding in `findings` whose `Project` is this project: compute `label :=
   skift.KeyLabel(finding.Key)`; if no indexed node carries it, call
   `FileFinding` with request id `"mill-heal-create-" + label + "-" +
   shortSHA` (`shortSHA` taken from the finding's own key/body — see
   Decisions for the exact derivation) and record `"filed"`; if one does
   and its body does not already equal `finding.Body`, call
   `CommentFinding` (no label change) with request id `"mill-heal-comment-"
   + node.GetReference() + "-" + shortSHA` and record `"commented"`; if one
   does and its body already matches, no write, no action. Either way, mark
   that indexed node (if any) as seen. After every finding in the project
   is applied, any indexed node **not marked seen** — open under a key this
   call's findings no longer carry, i.e. its branch is no longer red — is
   handled by whether it is claimed: unclaimed calls `DropFinding` with
   request id `"mill-heal-drop-" + node.GetReference()` and records
   `"dropped"`; claimed and not already carrying `GreenLabel` calls
   `CommentFinding` with `addLabel: GreenLabel` and request id
   `"mill-heal-green-" + node.GetReference()`, recording `"commented-green"`;
   claimed and already carrying `GreenLabel` is left alone with no write and
   no action, which is what makes a claimed, healed node's silence
   permanent instead of repeating the comment every sweep. Every request id
   above keys off either the finding's own key+sha (create, where no node
   exists yet to name) or the filed node's own reference (comment, drop,
   green — unique per filed node, so a later red incident on the same
   branch, which files a *different* node under the same key label, mints
   fresh ids and is never refused as a same-key-different-content replay —
   the collision a sha-less, label-only id scheme had in the previous
   version of this plan).
   `Reconcile` takes no interval, no "since last time," and no notion of
   who produced `findings` — it is exactly the seam a webhook receiver
   calls later with its own list, per the Notes.
   Test: `internal/run/healing_test.go` (new, DB-labelled like
   `sweep_test.go`, against a real skift fixture, using a `countingTransport`
   — an `http.RoundTripper` wrapping `testsupport.Skift.HTTPClient()` that
   increments a counter on every request naming the `ApplyPatch` RPC —
   wired into a `skift.Client` built with `skift.New(&http.Client{Transport:
   counting}, testsupportSkift.BaseURL(), project)`) — the three Gherkin
   scenarios directly:
   - A finding reconciled once files exactly one node with `HealingLabel`,
     the finding's `KeyLabel`, kind `bug`, assignee kind agent, priority
     P1, and the counting transport shows exactly one `ApplyPatch`
     attempt. Reconciled again with the identical finding and project list:
     the counting transport's count is unchanged from before the second
     call — the call was never attempted, not merely replayed as a no-op
     (the property the previous version of this plan's node/comment-count
     proof could not distinguish from a blind replay).
   - A finding whose `Body` changes (a moved sha) comments the new body on
     the existing node (one more `ApplyPatch` attempt) and files nothing
     new.
   - A previously-open node whose key is absent from the next `findings`
     list, in a project passed in `projects` with zero current findings, is
     dropped with `no_longer_relevant` when unclaimed; the same setup with
     the node claimed instead comments that main is green and adds
     `GreenLabel` (one `ApplyPatch` attempt); calling `Reconcile` a further
     time with the same claimed, still-green state makes no additional
     attempt (the counting transport's count is unchanged) because
     `GreenLabel` is already there.
   - Two findings in different projects each file into their own project's
     `Findings()` result, and neither project's fixture sees the other's
     node — proof that `Scoped` routes each write correctly.
   `go test ./internal/run/...`.

4. **The red-main probe.**
   `internal/run/healing.go` (or a second file,
   `internal/run/healing_probe.go`, if `healing.go` grows unwieldy —
   confirm at implementation time): `RedMainFindings(ctx context.Context,
   projects []string, projectNamed func(ctx context.Context, slug string)
   (*skiftv1.Project, error), repositories Repositories, warn func(project
   string, err error)) []Finding`. `projectNamed` and `repositories` are
   given as two separate functions rather than a single
   slug-to-`Repository` closure so the signature names exactly the two real
   calls a caller already has to hand — `Skift.ProjectNamed` and
   `Options.Repositories` — matching the pattern `Runner.repositoryOf`
   already uses for the same slug-to-repository resolution
   (`internal/run/run.go:709-720`); the previous version of this plan
   invented a `repository func(ctx, project string) (Repository, error)`
   parameter that named neither real method and did not compile against
   `Runner.repository`'s actual `*skiftv1.Project` parameter.
   For each project slug: `projectNamed(ctx, slug)` then
   `repositories(ctx, project)` to get a `Repository`; a failure at either
   call warns and moves on. Otherwise `repo.Forge.DefaultHead(ctx)`, then
   `repo.Forge.Checks(ctx, sha)`. `Pending` and `Success` yield nothing for
   that project. `Failed` calls `FailingChecks(sha)` and builds one
   `Finding` keyed `"red-main:" + repo.Path + ":" + ref` (repository and
   ref, deliberately excluding the sha — the key identifies "this branch of
   this repository," the sha is what changes inside the same key), titled
   `main is red at <7-char sha>: <first failing check's name>`, with a body
   naming the repository's path, the ref, the full sha, and every failing
   check by name and URL — never the worker's own host or any credential
   (Ivy's rule; the only inputs to the body are the forge's own
   path/ref/sha/check data). A `DefaultHead`/`Checks`/`FailingChecks` error
   for one project calls `warn` and moves to the next project; it never
   produces a `Finding` and never aborts the pass (acceptance criterion:
   "the sweep logs a warning… still completes").
   Test: `internal/run/healing_test.go` gains cases — a project whose fake
   `Repository`/forge reports `Failed` yields one `Finding` with the
   expected key, title format, and body contents (asserted to exclude any
   hostname or token — acceptance criterion 8, checked with a fixture
   `Forge`/worker host that would show up if the code leaked it);
   `Pending`/`Success` yield none; a `projectNamed`, `repositories`, or
   `Checks` error calls `warn` exactly once with that project's slug and
   yields no finding, and a second, healthy project in the same call still
   yields its own finding (one project's failure does not stop the pass).
   `go test ./internal/run/...`.

5. **Wire the probe and the reconciler into `Sweep`.**
   `internal/run/sweep.go`: `Runner.Sweep`'s signature gains a `projects
   []string` parameter (the worker's project filter, `WorkerOptions.Projects`
   — `Sweep` has no other way to reach it today, since it currently reasons
   only about live runs, not a project list). After the existing `for _,
   summary := range res.GetRuns()` loop and before `RecordReconciliation`:
   ```
   findings := RedMainFindings(ctx, projects, r.options.Skift.ProjectNamed, r.options.Repositories, warn)
   actions, err := Reconcile(ctx, r.options.Skift, projects, findings)
   ```
   (`warn` logs through `r.options.Log.Warn`, matching the existing sweep's
   own use of its logger for non-fatal problems, and does not touch
   `report.Findings` — a probe failure is a log line, not a ledger row,
   matching the acceptance criterion's "logs a warning" rather than
   "records a finding"). Every `HealAction` becomes a `machine.Finding`
   appended to `report.Findings`: three new `machine.FindingKind` values
   beside the sweep's existing `FindingStranded` —
   `FindingHealFiled` (verb `"filed"`), `FindingHealCommented` (verbs
   `"commented"` and `"commented-green"`), `FindingHealDropped` (verb
   `"dropped"`) — so `mill history` shows what happened, per deliverable 4.
   `internal/run/worker.go`'s one call site (`w.options.Runner.Sweep(ctx,
   w.driving)`, line 271) becomes `w.options.Runner.Sweep(ctx, w.driving,
   w.options.Projects)`.
   `internal/run/sweep_test.go`'s three existing `Sweep(ctx, ...)` call
   sites gain the new parameter (empty slice where the existing specs do
   not care about healing, so today's stranded-run behavior is provably
   unaffected).
   Test: `internal/run/sweep_test.go` gains cases matching the acceptance
   criteria end to end, using the package's existing DB-backed fixture
   (`f.runner(...)`, a `fixtureForge` configured per step 1) — a project
   with a failed check produces one `FindingHealFiled` on the first sweep
   and nothing on the second with the same state (`skift node list --label
   <key>` shows exactly one node, per the acceptance criterion's own
   phrasing); a moved red sha produces `FindingHealCommented`; the branch
   turning green with the node unclaimed produces `FindingHealDropped`;
   turning green with the node claimed produces `FindingHealCommented`
   (the "main is green" comment) and no `FindingHealDropped` (a claim taken
   on the healing node inside the spec, using the same `Claim` path other
   specs in this package already use); a `Pending` check produces nothing;
   the fixture forge returning an error for one project produces a log

   `internal/cli`'s own log-capture specs work — confirm the pattern at

  repository's `ginkgo ./...`) before calling the node done.
  `internal/skift` and `internal/run`'s DB-labelled specs need `make db-up`
  (or `make test-db`) first, matching what their existing suites already
  require.
- `make lint` (`go vet ./...`, `golangci-lint run ./...`, `buf lint`, `sqlc
  vet`) passes clean — this change touches no `.proto` or `.sql`, so `buf
  lint`/`sqlc vet` are expected to be no-ops, and `golangci-lint` is the one
  that actually exercises the new code.
- The three Gherkin scenarios in the work order map onto step 3's and step
  5's cases one for one; passing is exactly those `It`s going green.
- Every checkbox in the work order's Acceptance criteria maps to a specific
  spec named above: title/label/kind/priority format and "second sweep
  files nothing" → step 5; sha-move comment → step 5; green-and-unclaimed
  drop vs. green-and-claimed comment → step 3 and step 5; pending → step 5;
  forge-unreachable warning → step 5; idempotence via a call-counting
  transport → step 3; `DefaultHead` on the interface and both adapters →
  step 1; no hostname/credential → step 4; `go test ./...`/`golangci-lint
  run` → this section.

## Risks

- **`FailingChecks`'s GitLab implementation needs the failing pipeline's
  job list, a call `Checks` never makes today.** If GitLab's jobs endpoint
  needs a scope or pagination shape not yet confirmed against a live
  instance, step 1's GitLab half may cost more than its GitHub half.
  Mitigated by keeping `FailingChecks` additive and independent per
  adapter — a GitLab-specific snag does not block the GitHub half, `Sweep`,
  or the reconciler, all of which are adapter-agnostic.
- **Dropping "the merged pull request at that sha" from scope (see
  Approach) is a deliberate cut a reviewer may want back.** It is not
  covered by any acceptance criterion, but the work order's prose does ask
  for it. If a reviewer disagrees, it is a small, additive follow-up (one
  more optional field on the probe's output) and does not require
  reworking anything this plan builds.
- **Changing `Sweep`'s signature is a breaking change to every caller.**
  Confirmed to be exactly one production call site (`worker.go:271`) and
  three test call sites (`sweep_test.go`), all listed in Files above and
  all straightforward to update; no other package calls `Runner.Sweep`.
- **`WorkerOptions.Projects` is empty by default** (no `--project` flag
  passed to `mill work`), which means the red-main probe iterates zero
  projects for the common unfiltered worker. This is the work order's own
  literal deliverable ("for each project in `WorkerOptions.Projects`"), not
  a bug this plan introduces, but it means healing does nothing until an
  operator scopes a worker to specific projects. Left as specified rather
  than having the probe fall back to "every project the principal may
  read" on empty, since the work order does not ask for that and it would
  silently probe repositories no worker claim ever touches. Flagged for
  the reviewer under Decisions.
- **`Reconcile` now reads every project in `WorkerOptions.Projects` once per
  sweep, even those with no current finding**, to catch a branch that just
  went green with an open node still on it. For a worker scoped to many
  projects this is one extra `ListNodes` call per project per sweep
  interval (15 minutes by default) — small, but worth naming since the
  previous version of this plan had no such read at all.

## Decisions

- **`FailingChecks` is added to `Forge` alongside `DefaultHead`, though only
  `DefaultHead` is named in deliverable 1.** Acceptance criterion 1's exact
  title format and body content ("the failing checks by name with their
  URLs") cannot be produced from `Checks`'s existing three-value `Status`
  alone; a second method supplying per-check detail is the smallest
  addition that makes the acceptance criteria satisfiable as written.
- **"The merged pull request at that sha" is cut from this plan's scope.**
  No acceptance criterion tests it, the two forges would need materially
  different new lookups to support it, and the work order's own phrasing
  ("if the forge can name it") reads as optional. Left as a follow-up
  rather than a third new `Forge` method built for a detail nothing
  checks.
- **Every reconciler write is issued on a client scoped to the finding's
  own project (`base.Scoped(project)`)**, never on the runner's own client
  and its own project. The work order does not say this explicitly, but
  `ApplyPatch` writes into whatever project the client instance it is
  called on carries, and `Runner.repository`'s own pattern
  (`Skift.Scoped(claimed.Project.GetSlug())`, `internal/run/run.go:581`) is
  the existing precedent for "one client, redirected per project" rather
  than "one client per project held somewhere."
  This is corrected from a previous version of this plan that called a
  single, unscoped `FileFinding` across every project, which would have
  filed every finding into the runner's own (possibly empty) project.
- **A shared `HealingLabel` marks every node this feature files, read
  project-wide by `Findings()`, independent of any one finding's key.**
  Without it, the moment a branch's finding disappears (because it went
  green) there is no label left to search *for* — the previous version of
  this plan's per-finding `FindingsWithLabel` had nothing to enumerate in
  exactly the case (a healed, unclaimed branch) the "drop when green" half
  of the feature exists to handle. `Reconcile` therefore takes the sweep's
  whole project list, not just the projects `findings` mentions, so a
  project with zero current findings is still visited and its stale open
  node still found.
- **Idempotence (acceptance criterion 6) is proven by counting `ApplyPatch`
  RPC attempts at the transport level, against the real skift fixture, not
  by reading skift's resulting node/comment state and not by a new
  hand-rolled fake client.** No fake skift client exists anywhere in this
  codebase; every existing `skift`-touching spec proves its claims against
  a real service. A previous version of this plan proposed reading node
  and comment counts before and after a repeated `Reconcile` call, which a
  reviewer correctly pointed out cannot distinguish "no write attempted"
  from "the same write attempted and skift's own request-id replay made it
  a no-op" — both leave the counts identical. Wrapping the real client's
  HTTP transport with a request counter proves the stronger, correct claim
  without inventing a parallel implementation of skift's semantics.
- **Write request ids are derived from the filed node's own reference for
  every write except the initial create (comment, green-comment, drop),
  and from the finding's key plus its sha for create.** A label-only id
  (used in a previous version of this plan) collides across a
  red-then-green-then-red-again cycle on the same branch: skift refuses a
  replayed request id whose content differs, so a second incident's create
  would replay the first incident's id with a different body and be
  refused, silently filing nothing for the second incident. Once a node
  exists, its own reference is unique to that filing and safe to build a
  request id from for every subsequent write on it, including across a
  later, different-node incident under the same key.
- **`RedMainFindings` takes `Skift.ProjectNamed` and `Options.Repositories`
  as two separate parameters, matching `Runner.repositoryOf`'s existing
  two-call pattern (`internal/run/run.go:709-720`), rather than a single
  `repository(ctx, project string)` closure.** A previous version of this
  plan invented a signature matching neither real method, including a
  `Repository` resolver keyed on a bare project string where the runner's
  actual `Repositories` type takes a `*skiftv1.Project`.
- **`WorkerOptions.Projects` empty means healing probes nothing**, matching
  today's `ClaimNext` semantics being about claim scope, not about healing
  scope. Not widened to "every project the principal may read" on empty,
  since the work order does not ask for that; flagged under Risks for a
  reviewer who wants the wider default instead.
- **Where the work order was silent on how `Sweep` learns the project
  list**: a new parameter on `Sweep` itself (`projects []string`), sourced
  from `WorkerOptions.Projects` at its one call site, rather than adding a
  new field to `Runner`'s own options — `Sweep` already takes the one other
  piece of per-call context it needs (`driving`) as a parameter rather than
  a stored field, so this follows the existing shape rather than inventing
  a second one.
