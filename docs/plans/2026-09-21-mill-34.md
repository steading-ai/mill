# A session that never started is reported as a step that produced nothing

## Approach

Three fixes, one per acceptance criterion, none touching the `ProcessExit`
proto (`EXIT_REASON_REFUSED` already means "the harness declined to start
the session at all").

**Criterion 1** ("never a judgement about the evidence it did not
produce") traces to one mechanism: the sidecar (`sidecar/src/session.ts`)
reports `Status:0` — a clean success — for a resumed session whose very
first SDK message is a bare `"result"`, because `handleMessage`'s
`"result"` case trusts `fromResult(message)` unconditionally, with nothing
upstream distinguishing "the session talked and then finished" from "the
session's first word was the finish." This is the exact mechanism behind
the mill#19 incident: a Status:0 exit and zero session activity, with
`verifyCommit`'s `sha == base` clean-tree branch filling the silence with
"the session made no commit" — technically correct given its inputs,
misleading about the cause.

I considered detecting this in the *runner* by counting wire events per
attempt. Rejected: `internal/harness/fake/fake.go`'s `Script.Events` is
optional and the dominant pattern across `internal/run/*_test.go` (e.g.
`commit_test.go`'s "No commit, no evidence") is a scripted `Terminal` with
no `Events` at all — a legitimately-run turn that simply said nothing on
the wire. A wire-event-count heuristic in Go cannot tell that apart from
the bug. The distinction only exists where the actual SDK message stream
is visible: inside the sidecar.

Inside the sidecar, the naive version of this fix — flagging "turn
activity" by whatever `handleMessage` did not resolve to a result — is
also wrong: `handleMessage`'s outer `switch` returns `undefined` from its
own `default` case for every message type it does not otherwise handle,
including the SDK's `"system"` init messages, and a real session's stream
begins with three of those before the first `"assistant"` message
(`docs/spikes/sdk-sessions.md` §Q5: `["system","system","system",
"assistant",…]`). A flag set on "any unresolved message" would already be
true by the time a genuine bare `"result"` arrived, defeating the fix in
production while still passing a fake-SDK test that does not simulate
those init messages. The signal has to be "a real conversation message
arrived" specifically: `message.type === "assistant"` or `"user"` — the
SDK's actual turn content (text, tool calls, tool results, usage), never
its `"system"` bookkeeping. `handleMessage`'s own `"assistant"` case
documents that a complete `"assistant"` message always follows a turn's
streamed deltas (to carry `tool_use` and `usage`, which are not
streamed), so this signal is present before `"result"` for every real
turn and absent for none.

**Criterion 2** ("`fail_step_run` never records `exit={}`") does not need
a change beyond criterion 1's fix, once the actual paths that reach
`internal/run/revise.go`'s `failStep` are traced. `res.exit` reaching
`failStep` is either: nil (a Go-level early return before the harness ran
at all — `internal/run/execute.go`'s several `return result{}, err`
points), already caught by `failStep`'s existing `exit == nil` guard,
unchanged by this plan; or a real exit the harness reported, which after
this plan's step 1 is always well-formed for a session that never ran
(`Status:-1`, a named `Reason`) and is `Status:0` only for a session that
demonstrably ran (`internal/harness/fake/fake.go`'s `Terminal()` helper,
used throughout `commit_test.go`, deliberately builds this zero value for
"a session that ran and said nothing"). I first tried widening
`failStep`'s guard to also catch the *zero-value* exit
(`Status:0,Signal:0,Reason:UNSPECIFIED`) and rename it never-ran. Rejected
on review: `Status:0` for a step that failed on evidence — the exact
shape of `commit_test.go`'s "No commit, no evidence" — is not unknown, it
is a session that ran and whose evidence did not check out, and relabeling
it never-ran would ship the mirror image of this node's own bug. There is
no code path today that produces a non-nil `ProcessExit` with `Status < 0`
and no `Reason` (every construction — `sidecar/src/exit.ts`'s `neverRan`,
`internal/run/finish.go`'s `neverRan()`, `internal/harness/claude/
adapter.go`'s synthesised refusal, `internal/harness/fake/fake.go`'s
`NeverRan()` helper — sets one), so a defensive check for that shape would
be untested, unreachable code; per this repo's own conventions
(`CLAUDE.md`) it is not added.

**Criterion 3** (a session that ends its turn with subagents still
running is waited for, or the wait is recorded) is the one the work order
itself hedges on — the `simplify` step's "Waiting on the last one — reuse"
is "suspected (but unconfirmed by the ledger)," and `docs/architecture.md`
confirms a subagent (an `Agent` tool call) can still be resolving after
"the top-level session has moved on to other turns," i.e. asynchronously
to the turn that produces the `"result"` message. `sidecar/src/tasks.ts`'s
wait/heartbeat/breaker already covers exactly this shape of problem, but
only for the harness's own background-task system messages
(`task_started`/`task_notification`/`task_updated`), which Bash uses
today; nothing in `docs/architecture.md`, `docs/activity.md`, or
`sidecar/spec/fake_sdk.ts`'s `"subagent"` scenario (which models a
subagent's tool call and result resolving synchronously, inside the same
turn) confirms Agent-tool subagents emit that same message family or can
outlive a turn in a way the sidecar can observe and wait on. Building a
second wait mechanism against an unconfirmed SDK contract risks solving
the wrong problem, so this step does the smallest thing the criterion
actually asks for — "waited for, or the wait is recorded" — by recording:
track top-level `Agent` tool calls still open when `"result"` arrives, and
say so in the terminal record. Separately, `internal/harness/claude/
adapter.go`'s `flight.readLoop` already waits on `s.process.Wait()` (line
377) before the turn is reported finished, so whatever race exists is
already bounded to state that outlives the sidecar's own OS process (an
abandoned in-process async operation, not the process itself still
running) — the plan does not attempt to characterise that further, since
nothing in the codebase confirms it exists.

The stderr half of criterion 1 ("carries the harness's own exit and
stderr") needs no new step: `internal/run/execute.go` (lines 211-216)
already records `terminal.Diagnostics` as a `HarnessStderr` activity
whenever it is non-empty, unconditionally, on every turn regardless of
exit status.

## Risks

- **The `sawTurnActivity` signal still misses some legitimate turn
  shape.** Mitigation: it is keyed on the SDK's own message-type
  discriminant (`"assistant"`/`"user"`), which `handleMessage` already
  treats as the sole source of real turn content (text arrives via
  `"stream_event"` deltas, but every turn's `"assistant"` message that
  follows them is what carries `tool_use` and `usage` — see
  `handleMessage`'s own comment, session.ts ~line 905-909 — so it is
  never absent from a genuine turn). If a turn shape is found that
  reaches `"result"` through neither, the symptom is a legitimate
  session's success reported as never-ran — visible in the ledger, and
  step 1's fake-scenario test (with its leading system messages) is the
  regression gate that would have caught the previous, wrong signal.
- **Step 3 is a partial answer to criterion 3.** It records an open
  subagent; it does not wait for it or prevent a teardown race with the
  next step's `Resume`. `internal/harness/claude/adapter.go`'s
  `flight.readLoop` already waits for the sidecar's own OS process to
  exit before the turn is reported finished, so a race, if real, is
  already bounded to something that outlives that process rather than
  the process itself. If review decides the criterion needs an actual
  wait, this step is undersized and would need to grow once the SDK's
  subagent-background contract is confirmed — which this plan does not
  attempt, having found no evidence of what message, if any, the SDK
  sends when a subagent outlives the turn that started it.
- **Step 2's cause-suppression could hide a real evidence problem.** If
  `execErr` is set for an unrelated reason and `result.exit` happens to
  read as never-ran, `verifyErr` is dropped even where it held real
  information. Mitigation: the condition is narrow
  (`result.exit.GetStatus() < 0`, which only the harness itself sets) and
  `verify()` still runs and still feeds `reviewed()` — only the reported
  failure `cause` changes, not the work performed. `result.exit.
  GetStatus() < 0` is the same predicate the codebase already treats as
  the authoritative "never ran" signal (`harness.ProcessExit.NeverRan()`,
  `internal/cli/read.go`'s `exitText()`), so this reuses an existing
  invariant rather than inventing a new one.

## Decisions

- No proto change: `EXIT_REASON_REFUSED` already means "never started";
  reusing it keeps this a non-contract change.
- No change to `internal/cli/read.go`: `exitText()` already renders
  `Status<0` as `"never-ran:<reason>"`; fixing the underlying `ProcessExit`
  value is sufficient for `mill explain` to say the right thing.
- No change to `internal/run/revise.go`: its existing `exit == nil` guard
  already names the one genuinely-unknown case (an exit never populated
  at all); widening it to also catch the zero-value exit was tried and
  rejected on review because `Status:0` is the legitimate, load-bearing
  representation of "the session ran" throughout the codebase and test
  suite (`commit_test.go`'s evidence-failure cases). Once step 1 lands,
  no code path produces a non-nil, ambiguous `Status<0` exit, so there is
  nothing left for a broader guard to catch that is not already either
  handled (nil) or correct as written (`Status:0`).
- No new step for criterion 1's "carries ... stderr": `execute.go`
  (lines 211-216) already records `terminal.Diagnostics` as a
  `HarnessStderr` activity unconditionally, independent of exit status.
- Criterion 3 is satisfied by recording, not waiting, given the work
  order's own "unconfirmed by the ledger" hedge on the causal chain and
  the absence of a confirmed SDK contract for subagent lifetime beyond a
  turn. This is the smallest option that makes the acceptance criterion's
  own wording ("or the wait is recorded") literally true, and it is
  scoped narrowly enough (`adapter.go:377`'s existing process-exit wait)
  to state honestly what race remains open rather than claim to have
  closed it.
- `verify()` keeps running unconditionally in `walk.go`'s failure path
  (step 2); only the *reported cause* is narrowed, not the evidence work,
  since `reviewed()` findings are also used on other paths.
