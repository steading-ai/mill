# A usage per synthesised assistant message closes turns early and double-counts tokens

## Approach

With `includePartialMessages: true` (always on — `sidecar/src/session.ts`'s `buildOptions` sets it unconditionally), the SDK can emit several `"assistant"` SDK messages for one model response, one per completed content block, sharing `message.id`. `sidecar/src/session.ts`'s `handleMessage` (`case "assistant"`) emits a `usage` activity event for every one of them unconditionally, so one response's cost is recorded once per synthesised message instead of once, and `internal/run/activity.go`'s `assignTurn` (`case *millv1.Activity_Usage`) closes the currently-open turn on every `usage` it sees, so the spurious extra usage also splits a turn that should be one (mill#79: one sentence split into turn 35 and turn 36).

**The correct signal is not on any `assistant` message.** The SDK's own doc comment on `SDKAssistantMessage` (`@anthropic-ai/claude-agent-sdk`'s `sdk.d.ts`) says several consecutive assistant messages can share one `message.id`, and on all of them — not just the non-final ones — `stop_reason` is null and `usage` is not final: the turn's real stop reason and total usage arrive on the *result* message. The recorded live transcript `docs/spikes/mcp/transcripts/mcp-only.jsonl` bears this out directly: all 9 `assistant` messages in it carry `stop_reason: null`, including each response's last one. So `message.message.stop_reason !== null` is not a usable gate on the `assistant` message — it is never true.

The deliverable names a second signal: `message_delta`. This is a raw Anthropic stream event that already reaches the sidecar as a `stream_event` SDK message — `sidecar/src/session.ts`'s `case "stream_event"` already switches on `event.type` (`message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`), and its `default` arm today silently drops `message_delta` (and `message_stop`) without handling them. Its mere arrival, once per model response and immediately before `message_stop`, is the response-ending signal, regardless of how many synthetic `assistant` SDK messages the SDK layers on top of the same response — no new wire event or SDK message type is needed, since `session.ts` already receives this event and only has to stop ignoring it.

**`message_delta` alone is not a full usage record.** Per the checked-in `@anthropic-ai/sdk` types (`BetaMessageDeltaUsage`), its fields are `number | null`, and in the documented raw SSE shape only `output_tokens` is actually populated there (`{"type":"message_delta","delta":{...},"usage":{"output_tokens":12}}`) — input and cache tokens are decided before generation starts and ride `message_start`'s own `message.usage` block instead. This repo already models exactly that split: `internal/gateway/usage.go`'s `observer` seeds a running `Usage` from `message_start`'s `message.usage`, then overlays `message_delta`'s `usage` on top field-by-field (`usageBlock.apply`: "Fields it does not carry on a given event decode as nil and leave the count alone"). The sidecar fix follows the same, already-proven shape: track a running per-scope usage baseline captured at `message_start`, overlay `message_delta`'s fields onto it when `message_delta` arrives, and emit the merged total — not `message_delta`'s fields alone, which would silently zero out input and cache tokens on every emission.

Chosen approach: fix both ends, because they are independent bugs, not one:

1. **Sidecar** (`sidecar/src/session.ts`): stop emitting `usage` from `case "assistant"` entirely, and emit it instead from a new `case "message_delta"` inside `case "stream_event"`, sourced from `message_start`'s usage overlaid with `message_delta`'s. `fromTurn` and `UsageAccumulator` (`sidecar/src/usage.ts`) are unchanged in logic — the fix only moves the call site and adds the overlay — so the cancellation fallback (`accumulated.total()`, used when `result.modelUsage` never arrives on an aborted turn) still sums correctly, now once per response instead of once per synthesised message.
2. **Writer** (`internal/run/activity.go`): `assignTurn` must not close a turn while a text/thinking block it opened is still streaming (`delta: true`, no `final` yet). Add open-block tracking to `activityWriter` so a `usage` arriving mid-block is written into the still-open turn and deferred; the turn closes once that block's own final record arrives (or immediately, as today, if no block is open).

Both fixes are needed: tracing the real event order, a `usage`-bearing event can arrive between two deltas of a still-open text block (the mill#79 shape — a spurious per-message `usage` landed there under the current bug; even after fix 1, the single genuine `message_delta` for one response can itself still race a straggling delta of a block that logically belongs to it, since `content_block_stop` and `message_delta` are two separate events with no ordering guarantee relative to a slow consumer). Fixing only the sidecar's emission count leaves the writer's assumption — "a `usage` means no block is open" — still false in the general case.

**Considered and rejected:** gating emission on `message.message.stop_reason` from the `assistant` SDK message itself. This was the first candidate signal, ruled out because `stop_reason` is null on every one of the SDK's synthesised assistant messages, not just the non-final ones — confirmed by both the SDK's own doc comment and the recorded live transcript — so this gate would suppress every usage event rather than select one per response.

## Steps

1. **Sidecar: move usage emission from the `assistant` message to a `message_start`-seeded, `message_delta`-completed baseline.**
   Files: `sidecar/src/session.ts`, `sidecar/src/usage.ts`.
   - `sidecar/src/usage.ts`: add `mergeTurn(base: TurnTokens, delta: TurnTokens): TurnTokens`, overlaying only `delta`'s non-null/non-undefined fields onto `base` and leaving the rest of `base` alone — the TS mirror of `internal/gateway/usage.go`'s `usageBlock.apply` ("fields it does not carry ... leave the count alone"). Widen `TurnTokens.input_tokens` and `TurnTokens.output_tokens` from `number | undefined` to `number | null | undefined`, matching the two cache fields (already nullable) — `BetaMessageDeltaUsage`'s fields are all `number | null`. `n()` already treats `null` and `undefined` alike at runtime; only the type surface changes.
   - `sidecar/src/session.ts`, `case "assistant"`: delete the `const usage = fromTurn(...)` / `accumulated.add` / `emitEvent({case: "usage", ...})` block entirely; tool_use forwarding is untouched.
   - `sidecar/src/session.ts`, `StreamBlocks`: extend each scope entry (keyed by `parentToolUseId`, alongside its existing block-tracking map) with `model: string` and `usage: TurnTokens`, both defaulted empty. Add `seedResponse(parentToolUseId, model, usage)` (called from `case "stream_event"`'s existing `message_start` handling, sourced from `event.message.model` and `event.message.usage` — the raw `message_start` event always carries both, before any content block starts) and `response(parentToolUseId): { model, usage }` to read them back.
   - `sidecar/src/session.ts`, `case "stream_event"`'s switch: add `case "message_delta": { const { model, usage: base } = blocks.response(message.parent_tool_use_id); const usage = fromTurn(model, mergeTurn(base, event.usage ?? {})); if (Object.keys(usage.byModel).length > 0) { accumulated.add(usage); emitEvent({ case: "usage", value: usage }, parentCallId); } return undefined; }`. Sourcing model from the `message_start`-seeded baseline (rather than the most recently seen `assistant` message) also means a response with no content block yet emitted still has a real model, never `fromTurn("", ...)`.
   Proof: `npx tsc --noEmit` (type-checks the widened field, `mergeTurn`, and the new `event.usage` passthrough); step 3's test.

2. **Fake SDK: make every scenario's usage come from where production usage now comes from, split realistically across `message_start` and `message_delta`, and add the split-response scenario.**
   File: `sidecar/spec/fake_sdk.ts`.
   - `messageStart(id: string, model: string, usage: Partial<TurnTokens>): Record<string, unknown>` gains `model` and `usage` (a real `message_start` always carries both; existing bare `messageStart(id)` call sites get `model`/`usage` filled in from the response's numbers) — returns `{ type: "message_start", message: { id, model, usage } }`.
   - Add `messageDelta(usage: { output_tokens?: number | null }, stopReason: string): Record<string, unknown>` returning `{ type: "message_delta", delta: { stop_reason: stopReason, stop_sequence: null }, usage }`, wrapped at each call site with the existing `streamEvent(...)` helper (so it can still take a `parentToolUseId`). Its `usage` type is deliberately restricted to `output_tokens` only, matching the real SSE shape (`{"usage":{"output_tokens":12}}`) — a builder that could still accept input/cache fields would let a broken "read `message_delta` alone" implementation pass by accident.
   - Every existing scenario that currently relies on `assistantText`/`toolCall`'s own embedded `usage` field to produce a `usage` event — at minimum `trivial`, `hang`, `streamed-text`, `streamed-thinking`, `subagent`, `subagent-open` (a full run of `sidecar_test.go`/`streaming_test.go` after step 1 finds any others) — is wrapped with a leading `streamEvent(messageStart(id, model, {input_tokens, cache_read_input_tokens, cache_creation_input_tokens}))` before the response's content and a trailing `streamEvent(messageDelta({output_tokens}, stopReason))` after it (`"end_turn"` after text, `"tool_use"` after a tool call), the two together carrying exactly that response's numbers. This is mechanical: it stops the fake from asserting a shape — a usage-bearing, non-null-`stop_reason` assistant message — that production never sends, and from asserting a shape — an all-fields-bearing `message_delta` — that production never sends either.
   - New scenario `"straddled-response"`, reproducing the mill#79 shape faithfully: `messageStart` (carrying the model and only the input/cache numbers) → `content_block_start` (text) → `text_delta` → a synthesised `assistant` message for the block so far (`stop_reason: null`, matching real traffic) → another `text_delta` → `content_block_stop` → the block's closing `assistant` message (`stop_reason: null`) → a `tool_use` block's own `assistant` message (`stop_reason: null`) → one `messageDelta` carrying only `output_tokens` and `stop_reason: "tool_use"`.    Proof: exercised by steps 3 and 5.

## Risks

- Step 2 touches every fake-SDK scenario that currently produces usage, which is broad, mechanical churn across one file. Mitigated by running the full `sidecar`/`internal/run` suite after the edit: any scenario missed shows up as a test that now asserts on an empty usage list instead of silently passing.
- Splitting the `Text, Thinking, ToolCall` case in `assignTurn` into per-type handling touches code three existing tests already exercise closely; care is needed to keep `ToolCall`'s existing (unchanged) turn-opening and `callTurn` bookkeeping byte-for-byte identical, only adding new behavior for `Text`/`Thinking`.
- If a response's `message_delta` arrives while a block from a *different, already-finished* response is somehow still marked open (should not happen given the SDK emits `content_block_stop` before starting a new block), the writer would wrongly hold a turn open indefinitely. Mitigated by scoping `openBlocks` per block id exactly as `StreamBlocks` does on the sidecar side, and by step 5's test covering the documented real-world ordering.
- Step 7 (the live gateway test) costs tokens and needs a real subscription credential, so it cannot run in default CI; it is written and correct but its pass/fail is only observed when someone runs it with `MILL_SIDECAR_LIVE=1` and `CLAUDE_CODE_OAUTH_TOKEN` set, the same limitation every other `Label("live")` spec in this repo already has.

## Decisions

- Route usage entirely through the stream (`message_start` + `message_delta`) rather than keeping it on the `assistant` message as a secondary/fallback source: a single source of truth rules out double-counting by construction, instead of adding a de-duplication layer over two sources that would need its own justification.
- Merge `message_start`'s usage with `message_delta`'s rather than trusting either alone: the real SSE shape splits a response's usage across the two events (input/cache decided upfront on `message_start`, output finalized on `message_delta`), exactly as `internal/gateway/usage.go`'s `usageBlock`/`apply` already models for the Go-side gateway observer; reading `message_delta` alone (the earlier draft's design) would silently zero input and cache tokens on every emitted usage event.
- Source the per-response model from the `message_start`-seeded baseline rather than the most recently seen `assistant` message: it is captured once per response, before any content block exists, so there is no window where a `message_delta` could arrive with no model recorded yet and fall back to `fromTurn("", ...)`.
- Split the "asserts one `usage` and one turn" deliverable across two tests (sidecar-level for the `usage` count, `internal/run`-level for turn assignment), because `harness.v1.Event` has no `turn` field — only the Go writer's `mill.v1.Activity` output does.
- Did not change `UsageAccumulator`'s or `fromTurn`'s logic (`sidecar/src/usage.ts`): the bug was entirely in *which event(s)* the call site read from, not in either function's own logic, so the smaller fix is to move the call site, add one merge helper, and widen one type.
- Proved AC3 with an in-process real `internal/gateway.Gateway` and a buffer log sink rather than shelling out to `journalctl`, consistent with how `internal/gateway/live_test.go` already proves the identical `"gateway: usage"` log line without a live systemd unit; the acceptance criterion's `journalctl -u mill.service` is the operator-facing illustration of the same log line, not a literal test requirement.
- Did not attempt to reconstruct `openBlocks`/`usagePending` on `reopenActivityWriter`: `currentTurn`/`turnOpen`/`callTurn` already don't survive a reopen today, so adding partial reconstruction for only the new fields would be an inconsistent, unrequested behavior change.
