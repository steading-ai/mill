# Logs stream over the socket, follow across steps, and page

## Approach

Build the `Logs` RPC and its observer as new, additive infrastructure on top of what mill#13 already delivered (the `Activity` proto, the per-attempt live file, `ActivityPath`/`ReadActivity`/`ReadActivities`/`RenderActivity` in `internal/run/activity.go`), rather than changing how activity is written. Concretely:

- The `Logs` handler lives beside the other `StoreService` handlers in `internal/server/store_service.go` and reads live activity files directly off disk via `internal/run`'s existing helpers — it does not go through `internal/domain`/`internal/store` for activity, matching the work order's own reasoning ("the process serving the record must hold [log-dir]") and the fact that activity bodies are deliberately kept out of the database (`docs/activity.md` §"Deliberately absent").
- The observer is a new small type owned by `internal/server` (not `internal/domain`), because "the store's own handlers" in the work order's language are literally the `StoreService` Connect handlers that already wrap every domain mutation one-for-one (`internal/server/store_service.go`). Those eight handler methods signal it after a successful domain call, so no new dependency from `internal/domain` is needed.
- The one part that crosses the worker/server split — the activity writer in `internal/run` signalling the same observer on every append — is wired at the composition root, `internal/cli/serve.go`, which is the only place that already constructs both `*domain.Service`/`server.Server` and (for `serve --work`) the in-process `run.Runner` in the same call. The writer gets an optional callback (mirroring how `activityWriter` already treats a nil `*activityWriter` as a no-op), so a worker that is not co-located with the server it reports to — `mill work` run standalone against a remote socket — still gets correct results, just later: the observer's fallback timer is exactly the seam the work order names for that case ("the observer is the seam [Postgres LISTEN/NOTIFY] would replace when a worker is a separate process"), not a gap this node has to close.

Rejected: routing the activity writer's append through a new store RPC so every signal source is unified in `internal/domain` (approach 2 in the prior step's note). That would put every event on the ledger's write path, which is exactly what mill#13's file-based design and this node's own deliverable ("serve learns log-dir... because the process serving the record must hold it") were written to avoid. Also rejected: a poll-based `Logs` follow loop with no observer — it cannot satisfy the acceptance criterion that a follower sees `attempt_ended` without the fallback timer elapsing, since a pure poll has no path faster than its own tick.

1. **Proto surface, generated code, permission table, and a compiling stub.**
   Add `Activity`'s companions from `docs/activity.md` §The RPC — `Logs` (server-streaming), `LogsRequest`, `Cursor`, `LogsResponse`, `RunEnd`, `GateRef` — to `proto/mill/v1/store.proto` (the RPC, alongside the other `StoreService` methods) and `proto/mill/v1/mill.proto` (the messages, beside `Activity`). Add `millv1connect.StoreServiceLogsProcedure: interceptor.PermissionRead` to `internal/server/permissions.go`. Run `make generate` to regenerate `gen/mill/v1`. Add a `Logs` method to `internal/server/store_service.go` that returns `connect.NewError(connect.CodeUnimplemented, ...)`, purely so `StoreService` keeps satisfying `millv1connect.StoreServiceHandler` (the existing `var _ millv1connect.StoreServiceHandler = (*StoreService)(nil)` assertion at the top of that file would otherwise fail to compile the moment the interface gains a method).
   **Proof:** `make check-generated` (generated code matches proto), `make check-breaking` (passes: this is an additive RPC, no existing method's wire shape changes), `go build ./...`, `make test` still green. Extend `internal/server/roles_test.go` with "a reader uid can call Logs" against the stub and assert it gets `CodeUnimplemented`, not `CodePermissionDenied` — this nails down acceptance criterion 5's permission half early, before the behavior exists.

2. **The observer, as an inert primitive.**
   New file `internal/server/observer.go`: a type holding one condition (or broadcast channel) per run id behind a mutex, `Signal(runID string)` and `Wait(ctx, runID, fallback time.Duration) <-chan struct{}`-shaped API, and a package-level default fallback interval. No RPC wiring yet. Wire `Signal` calls into the eight existing handler methods in `store_service.go` — `StartStepRun`, `CloseStepRun`, `FailStepRun`, `MarkWaiting`, `Park`, `Done`, `Fail`, `CreateRun` — called after the wrapped `s.svc.*` call succeeds, using the run id already in scope in each method's request/response. `StoreService` gains an `*observer` field; `NewStoreService` takes it as a new parameter (every call site — `internal/cli/serve.go` and the server test fixtures — updated to construct and pass one).
   **Proof:** new `internal/server/observer_test.go` (plain Go or Ginkgo, no database needed — this type touches nothing in `internal/store`): a waiter unblocks immediately when `Signal` is called for its run id and not for another run id; a waiter with no signal unblocks only after the fallback duration, timed with a short fallback (e.g. 50ms) so the spec stays fast. `go build ./...` and `make test` still green with the new field threaded through.

3. **`Logs`, one run, unfollowed.**
   Replace the stub with the real handler for `follow: false`: `step`/`attempt` narrowing over one run using `run.ActivityPath`/`run.ReadActivities` (needs the run's attempt list, which the handler already has via the same domain lookup `Inspect` uses); whole-run reads walk attempts in start order then the live file, with `attempt_started`/`attempt_ended` staying in-band exactly as the record already carries them; `tail` (last N records), `after` (skip through the cursor). `every run` (`id` and `node_ref` both empty) is out of scope for this step — only single-run reads. `serve` gains a `--log-dir` flag reading the same config key `mill work` already reads (check `internal/cli/serve.go` and `internal/cli/run.go` for that key's current name and plumb the same one through), and `NewStoreService`/the `Logs` handler take the resolved directory.
   **Proof:** new `internal/server/logs_test.go`, modeled on `internal/cli/logs_test.go`'s `appendActivity`/`textActivity` fixture helpers (moved or duplicated as needed — check whether they can be shared via `internal/testsupport` instead of duplicated, since both the CLI and the server now need to fabricate activity files). Specs: two attempts' worth of fixture records come back in `seq` order across attempts with boundaries; `step`+`attempt` narrows to one; `tail` returns the last N; `after` skips through a cursor.

4. **`before`/`limit` paging and every-run reads.**
   Add `before`+`limit` (refused when `follow` is set — a request validation error, `CodeInvalidArgument`), and the every-run path: records across all runs' live files at or after `since`, ordered by `(at, step_run_id, seq)`, `tail` counting across runs. Bodies over 64 KiB stay whole here — truncation only applies to a followed stream (§5).
   **Proof:** extend `logs_test.go` with the two paging acceptance criteria verbatim: `before` with `limit` 20 returns the 20 records immediately before the cursor in `seq` order; `after` one before a cut body with `limit` 1 returns it whole (this second one is really proving that an unfollowed single-record fetch never truncates, so write the fixture with a body over 64 KiB and assert the returned body is whole). Add a since-ordered every-run spec with two runs' fixtures interleaved by `at`.

5. **Follow.**
   Wrap the step 3/4 reader: after draining what's on record, `Wait` on the observer (from step 2) for the run id, with the request's step's or (for a whole-run follow) the run's terminal-status check between wakes — reuse the existing `stillRunning`/`Inspect`-style status check already in `internal/cli/logs.go` (which moves into the handler; the CLI stops doing its own polling, see step 6). End conditions exactly as specified: `RunEnd` when the run reaches `done`/`failed`/`abandoned`/`waiting`/`parked` and no `step` was requested; the attempt's own `attempt_ended` and no `RunEnd` when `step` is set; a body over 64 KiB cut with `truncated` set, only on this path. `RunEnd.GateRef` is filled from the last `gate_filed` record already read in this same attempt (the `GateFiled` message already carries `node_id`, `node_ref`, `title` per `docs/activity.md`'s table) — no new skift call needed. `every run` with `follow` never ends; run ends surface as `RunEnd` frames in the stream instead of closing it.
   **Proof:** the work order's own Gherkin scenario as a Ginkgo spec — follow a run on `implement`, close it, start `commit`, assert the stream keeps going and shows both boundaries. A gate/parked spec: a run that files a gate ends a followed stream with `RunEnd{status: waiting, gate: ...}`; a parked run similarly with `status: parked`. The no-fallback-timer criterion: configure a short fallback (as in step 2) that is *longer* than the time the spec takes to close the attempt and signal, and assert the `attempt_ended` frame arrives before that fallback would have fired — e.g. assert delivery within a tight deadline while the fallback is set to something clearly longer, so a regression to poll-only would fail by timing out or arriving late relative to the deadline.

6. **`mill logs` on the stream.**
   Rewrite `internal/cli/logs.go`: drop `run.ActivityPath`/`run.ReadActivities`/direct file access and the 200ms poll loop (`logPoll`, `follow`, `drainActivities`, `stillRunning` all go — their job moves into the server). The command becomes a thin `Logs` RPC client exactly like `internal/cli/read.go`'s other tools (`storeClient(opts.socket).Logs(...)`, `connect.NewRequest`, iterate the `*connect.ServerStreamForClient`). Add flags: `--step`, `--attempt`, `--json`, `-f`/`--follow`, `-n`/`--tail` (default 10, only meaningful with `-f`), `--no-tail`, `--no-pager`, `-e`. Remove `--log-dir` from this command only (`mill work`/`serve` keep their own).

   `run.RenderActivity` is left untouched: its doc comment (`internal/run/activity.go:533-547`) commits it to being byte-identical to the old text log, a promise the existing spec at `internal/cli/logs_test.go:129` pins down and that `docs/activity.md`'s retention section (§Lifecycle, compaction: "the code that renders it already exists") already names as something a later node reuses — changing what it does with `attempt_started`/`attempt_ended` would break both. Instead, `internal/cli/logs.go` gains a small renderer of its own, called for every record alongside `RenderActivity`, that turns `attempt_started` into an open marker naming the step and attempt (`AttemptStarted.step`/the record's own attempt) and `attempt_ended` into a close marker carrying `AttemptEnded.reason` — which `docs/activity.md`'s table already specifies as "written to read alone as the stream's last line" (`verdict: revise, 2 blocking`, `exit status 1`, `gate denied`), so the marker is exactly that reason on its own line, e.g. `-- implement attempt 1 started --` / `-- implement attempt 1 ended: exit status 1 --`. This is what makes "prints implement's end and commit's start" (the Gherkin scenario) and "prints every attempt with its boundaries" (acceptance criterion 1) true of the rendered output, without loosening `RenderActivity`'s contract for anything the byte-identical spec covers.

   Non-follow path: for every record, print the new boundary line when it's a boundary, else `RenderActivity`'s line when non-empty (unchanged: a kind that already rendered "" — a verb, a gate filing mid-stream — still does), piped into `$PAGER` when stdout is a terminal (`LESS=FRX` set when the operator hasn't set `LESS`), honoring `--no-pager`/`-e`; exits 0 at the end of the stream. Follow path: same per-record rendering, plus reading `RunEnd`/stream-break to pick the exit code (0 `done`; 1 `failed`/`abandoned`; 3 `waiting`; 4 `parked`; 2 a broken stream) and print the last line naming why (e.g. `-- run done --`, `-- waiting on gate mill#7 --`). Define these as named constants beside `ExitFenced` in `internal/cli/run.go` or a shared exits file, checked against `2` (doctor) and `75` (`ExitFenced`) for collisions as the work order notes.
   **Proof:** rewrite `internal/cli/logs_test.go` to drive a real (test-fixture) server instead of local files — it already runs in the `testsupport.DBLabel` suite so a real `StoreService` fixture is available the way `roles_test.go`'s does. Cover: acceptance criterion 1 (a "no log directory on this host" scenario — point the CLI's `--socket` at a server whose `--log-dir` differs from anything the test process would default to, and confirm every attempt prints its start and end marker, exit 0); criterion 2 (`-f` prints last 10 lines, then streams across a step change — assert both the outgoing step's end marker and the incoming step's start marker appear — ends with the done line and exit 0, reusing the step 5 server-side scenario end to end); criterion 3 (gate/parked exit codes 3/4); `--json` line shape (raw `Activity` per line, boundaries included, since `--json` is for a script and should not need the marker convention); pager invocation with `--no-pager` exercised directly (CI has no real pager) and a smoke check that `$PAGER`/`LESS` env handling doesn't blow up when unset. Leave the existing `internal/cli/logs_test.go:129` byte-identical spec's expectations on `RenderActivity`'s covered kinds unchanged — it is still true, since that function did not change.

7. **MCP tool and docs.**

## Risks

- **The observer's cross-package wiring turns out awkward at the composition root.** `internal/cli/serve.go` is where `--work`'s in-process worker and the server are both constructed today; if that's not actually true (e.g., `--work` shells out to a separate `mill work` invocation rather than constructing a `run.Runner` in the same process), the plan's step 2/step 6 wiring is wrong and the notify hook has nowhere in-process to attach. **Answer:** confirm this by reading `internal/cli/serve.go` in full at the start of step 2, before writing `observer.go`'s API — if `--work` is a separate process, the notify hook is dropped from the writer entirely for this node (it just relies on the fallback timer always, which still satisfies the RPC contract, only later) and that's recorded as a decision, not discovered mid-implementation.
- **`buf breaking` false-fails or the generated-code diff is noisy** because `store.proto`/`mill.proto` are large, hand-maintained files with heavy comments (`COMMENTS` lint rule is on) — every new message/field needs a doc comment or `make lint` fails on `buf lint`, not just `check-breaking`. **Answer:** copy comments verbatim from `docs/activity.md`'s proto sketch, which is already written in the repo's comment style.
- **Every-run reads (step 4) have no natural place to enumerate "every run with live files"** — there's no index yet (that's rollout item 3). The handler has to either ask `internal/domain` for runs in relevant statuses and then look for their live files, or walk the log-dir. Walking the log-dir does not depguard-violate anything but couples the handler to the on-disk layout more than a domain query would. **Answer:** default to asking domain for the run list bounded by `since`/status the way `Status`'s handler already does, then only touch files for runs it names — decided in step 4, recorded there if it turns out domain has no such "runs touched since" query and one has to be added (that would be new domain surface, worth flagging back rather than improvising).
- **`internal/cli/logs_test.go` currently fabricates activity files directly on disk** (`appendActivity`, `internal/cli/logs_test.go:29`); moving the CLI off local files means this fixture helper needs to write through whatever the *server* under test reads from, which means the CLI spec needs a running fixture server, not just a `cli.RunLogs`-style unit call. This is more test infrastructure than the old spec needed. **Answer:** reuse `internal/server`'s fixture pattern (`roles_test.go`'s `newFixture`) from the CLI test package if it's exported, or build an equivalent — confirm during step 6 rather than assuming it's importable as-is.
- **Test timing flakiness** in the "no fallback timer elapsed" spec (step 5) if the fallback interval and the assertion deadline are too close together on a loaded CI box. **Answer:** use a generous ratio (e.g. fallback at 2s, assert delivery under 200ms) rather than a tight one.

## Decisions

- **Observer lives in `internal/server`, signalled by the `StoreService` Connect handlers**, not in `internal/domain`. The work order says "signalled by the store's own handlers," and the existing codebase's handlers (one-to-one wrappers over `domain.Service` calls) are the more literal reading; it also avoids adding new dependencies to `internal/domain`, which depguard already treats as the narrow, careful boundary.
- **The activity writer's signal to the observer is an optional callback threaded through `run.Options`, not a shared package import between `internal/run` and `internal/server`.** Keeps the existing one-way dependency shape (`internal/run` → `internal/domain`/`millv1connect` client only) and matches `activityWriter`'s existing nil-is-a-no-op pattern.
- **A worker not co-located with its server (standalone `mill work` against a remote socket, if that is in fact a supported shape — see Risks) gets eventual, timer-bound delivery only, not instant push, for this node.** The work order explicitly scopes real-time cross-process signalling ("Postgres `LISTEN/NOTIFY`... when a worker is a separate process") out of this node, so this is taking that at face value rather than building a stopgap.
- **`run.RenderActivity` is not extended to cover `attempt_started`/`attempt_ended`; a separate renderer in `internal/cli/logs.go` handles them instead.** `RenderActivity`'s doc comment commits it to reproducing the old text log byte-for-byte, a contract an existing spec (`internal/cli/logs_test.go:129`) checks and that `docs/activity.md`'s retention section already plans to reuse verbatim for compaction. Boundaries were never in the old log, so making them printable belongs to the new streaming CLI, not to the function that promises fidelity to the old one.
- **`RunEnd.GateRef` is populated from the `gate_filed` activity record already present in the stream being followed, not a fresh call to skift.** `GateFiled` already carries `node_id`, `node_ref`, and `title` (`proto/mill/v1/mill.proto:1102-1111`), so the handler needs no new dependency on `internal/skift` (which today only the CLI's `explain` command reaches, for a similar but not identical purpose).
- **Every-run reads (`id`/`node_ref` empty) are scoped to what step 4 can build without a new domain query**, per the risk above; if `internal/domain` has no existing "runs active since T" style call, the plan takes the smallest one that satisfies `docs/activity.md`'s stated semantics ("rows... ordered by `(at, step_run_id, seq)`... including runs that start later") rather than a general-purpose new query surface, and flags it for review rather than expanding domain's API further than this node needs.
- **`mill#7`'s closure is left to the review/workflow step, not written by this plan** — this checkout step has no established mechanism (or evident credentials) for closing a skift node, and the acceptance criteria don't name it as a testable outcome; the plan surfaces it as a note for whoever reviews or merges this work instead.
