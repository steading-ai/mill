# A migration merged with a number below one already shipped stops mill from starting

## Approach

Three independent fixes, each landing on the smallest surface that already
exists for its shape of problem, rather than one new subsystem:

1. **The merge-time check is a spec, not new merge-gate code.** `internal/run/gate.go`'s
   `checkCaughtUp` (mill#52) already runs every `check`-kind step between
   `commit` and `merge` against the post-catch-up tree and turns a failure
   into a `mergeFinding` routed to `implement` — exactly AC1's "sent back...
   with the next free number named." `mill-quick-fix` and `mill-feature`
   already run `make test` as such a step (the `live-tier` check,
   `workflows/mill-quick-fix/workflow.yaml:116-121`,
   `workflows/mill-feature/workflow.yaml:269-274`). Adding the new spec to
   `internal/store/migrations` rides that machinery for free: no change to
   `gate.go`, no new workflow step. **Rejected: a dedicated new check step**
   inserted into both workflow YAMLs ahead of `live-tier`, for a faster
   fail — real, but not asked for, and it would duplicate logic the spec
   already has to contain; if the cost of discovering this class of failure
   only at the end of the full test run turns out to matter, that is its own
   follow-up. **Rejected: teaching `gate.go` about migrations directly** —
   structurally blocked twice over: `depguard` lets only `internal/domain`
   and `internal/store` import `internal/store/migrations`, and `forbidigo`
   bans `os/exec` everywhere but `internal/workspace` and `_test.go` files,
   so `internal/run` can neither import the package nor shell out to `git`
   itself.

2. **The out-of-order decision lives entirely inside `internal/store/migrations`,
   on the one code path `mill serve` and every test fixture already share.**
   `Migrator.Up` gains a check, before calling goose, for missing migrations
   below the current database version; if every one of them carries
   `-- +mill out-of-order: safe`, it re-runs with `goose.WithAllowOutofOrder`
   enabled (only reachable this way — goose has no per-call flag, only a
   constructor option, so this is a second `*goose.Provider` over the same
   `*sql.DB`); otherwise it returns a sentinel-wrapped error naming the
   migration and the manual command, before anything is applied. **Rejected:
   parsing goose's own error text** ("detected 1 missing (out-of-order)
   migration...") to decide what to do — brittle against a goose upgrade,
   and `Provider.Status`/`GetDBVersion` already expose the same fact as
   structured, public, side-effect-free reads.

3. **`docs/ledger.md` documents both, once their shape is settled** — it is
   downstream of 1 and 2, not an independent decision.

The smallest-possible alternative — fix only 2, skip the merge-time check,
and hand-document the convention — was rejected outright: it leaves the
actual hole (a bad merge landing at all) open and fails AC1/AC4.

## Steps

1. **Make the missing/out-of-order decision inside `Migrator.Up`, gated by a
   per-file annotation, and give `00028` the annotation.**
   `internal/store/migrations/migrations.go`: store the `*sql.DB` on
   `Migrator` (needed to build a second provider); factor provider
   construction into a small helper taking an `allowOutOfOrder bool`; add
   `ErrBlocked` (a sentinel, `errors.New`, matching `ErrNotFound` etc.'s
   style in `internal/domain/domain.go`); add `Versions(fsys fs.FS) (map[string]int64, error)`
   and `VersionOf(name string) (int64, bool)`, refactoring `Wanted()` to use
   the latter rather than duplicating the digit-prefix parse a third time;
   add an unexported `safeVersions(fsys fs.FS) (map[int64]bool, error)`
   scanning each `.sql` file's bytes for a line-anchored
   `-- +mill out-of-order: safe`. Change `Up` to: read `GetDBVersion` and
   `Status`, compute the missing-and-below-current set; if empty, call
   `provider.Up` exactly as today (proves nothing changed on the ordinary
   path); if all missing versions are in `safeVersions`, build the second
   provider with `WithAllowOutofOrder(true)` and call its `Up`; otherwise
   return `fmt.Errorf("%w: migration %d (%s) is missing but the database is
   already past it; apply it by hand: goose -dir internal/store/migrations
   postgres \"$DATABASE_URL\" -allow-missing up", ErrBlocked, version, path)`
   before touching the database. Add an exported `OpenFS(ctx, databaseURL
   string, fsys fs.FS) (*Migrator, error)`, with `Open` calling it with the
   package's own `FS` — the seam the next step's specs need to exercise this
   logic against a small synthetic schema instead of the real 29
   interdependent migrations. Give `00028_step_runs_seq.sql` the annotation
   comment (it adds an identity column, independent of anything `00029`
   touches, so applying it late is genuinely safe).
   Proof: `go build ./...` compiles; the existing "two databases in the same
   cluster" and "no two migrations share a version" specs in
   `migrations_test.go` still pass unmodified (proves the ordinary path is
   untouched).

2. **Prove AC2 and AC3 against a real PostgreSQL, using a small synthetic
   schema, not the real 29 migrations.**
   `internal/store/migrations/migrations_test.go`: two new `db`-labelled
   specs, each building a 3-file `fstest.MapFS` (00001 creates a table,
   00002 adds a column and is marked safe, 00003 adds another column) via
   `OpenFS`. AC2's spec applies 00001 and 00003 to a blank `testsupport`
   database (skipping 00002, mirroring the guest's real 27-then-29 shape),
   then calls `Migrate`/`OpenFS(...).Up` with the full synthetic set and
   asserts: no error, the database ends at version 3, and 00002 is recorded
   applied (`Status` shows it `StateApplied`). AC3's spec is the same
   fixture with 00002's annotation removed, and asserts: `Up` returns an
   error satisfying `errors.Is(err, migrations.ErrBlocked)`, the error names
   `00002` and the `goose ... -allow-missing up` remedy, and — the part that
   proves "no restart loop" at this layer — the database version is
   unchanged and 00003 was not applied (nothing ran before the refusal).
   Proof: `make test-db` (needs the `db` label; `testsupport` starts the
   container) — both new specs pass; re-running the whole package's suite
   confirms nothing above cross-contaminates (each spec takes its own blank
   database per the suite's existing per-spec-clone convention).

3. **Add the ordering check as a pure function, proven without git, then
   wired to the real checkout.**
   New `internal/store/migrations/order.go`: `type Violation struct{ File
   string; Version, TargetHighest int64 }` with an `Error() string` naming
   the file, its number, the target's highest, and "renumber it to at least
   %d" (`TargetHighest+1`); `func CheckOrder(target, ours map[string]int64)
   []Violation` — for every name in `ours` not present in `target`, a
   violation if its version is `<=` the highest value in `target`. Pure,
   no I/O, so it needs no `db` label and no git.
   New `internal/store/migrations/order_test.go`: (a) deterministic specs
   calling `CheckOrder` directly with hand-built maps, covering the node's
   own scenario numbers verbatim (target's highest 29, a new file at 28 →
   one violation naming 30; a new file at 30 → none) and the "no target
   resolvable" shape is out of scope for this half, since `CheckOrder`
   itself takes plain data; (b) one spec that gives the check real teeth,
   reading only what is already local — no fetch of its own, and so no
   credential to have or lack. By the time `live-tier`'s `make test` runs,
   `catchUp` (`internal/run/gate.go:147`) has already run its own
   credentialed `git fetch origin <target>` (`internal/workspace/verbs/verbs.go:343-344`)
   against exactly this checkout, and because the clone that made it was a
   plain `git clone --branch <ref>` with no `--single-branch`
   (`internal/workspace/local/local.go:243-249`,
   `internal/workspace/machine/git.go:20-26`), that fetch runs under the
   default refspec and lands at `refs/remotes/origin/<target>`, not only
   `FETCH_HEAD` — so the spec reads that ref straight off disk. It resolves
   which branch is the target the same way GitHub's own default-branch
   fallback does when a run does not name one (`internal/forge/github/github.go:379-382`)
   by reading the local symref a plain clone already sets,
   `refs/remotes/origin/HEAD` (`git symbolic-ref -q refs/remotes/origin/HEAD`),
   then `git ls-tree -r --name-only <that ref> -- internal/store/migrations`
   — both read-only, local, uncredentialed `os/exec` calls, permitted in
   `_test.go` per `.golangci.yml`'s exclusion. It builds `target` from that
   listing and `ours` from `migrations.Versions(migrations.FS)`, calls
   `CheckOrder`, and asserts no violations against the resolved target's own
   current tree. Absence of `.git` or of the symref is treated exactly like
   `testsupport.requireAvailable` treats a missing fixture
   (`internal/testsupport/skift.go:138-153`): `Skip` with a named reason
   normally, but `Fail` when `MILL_REQUIRE_FIXTURES` is set, since that is
   what the live tier sets precisely so a database (or, here, a target)
   this check needed and didn't get is a failure, not a quiet pass — the
   gap the reviewed attempt left open. This is the spec `live-tier`
   exercises on every run, and — because it runs in the actual workspace
   `checkCaughtUp` executes `make test` against, on the tree catch-up just
   produced, after catch-up's own fetch already refreshed the target ref —
   it is what actually catches a mill#105-shaped collision at merge time.
   Proof: `make test-unit` (no `db` label needed) — both the deterministic
   and the real-repo spec pass on this branch's own tree (which, being
   target-relative and adding nothing lower, is not itself a violation);
   running the same spec with `refs/remotes/origin/HEAD` renamed away (`git
   symbolic-ref -d refs/remotes/origin/HEAD`) demonstrates the `Skip`, and
   the same with `MILL_REQUIRE_FIXTURES=1` set demonstrates the `Fail`.

4. **Give `mill serve` a distinguished, non-restarting exit status.**
   `internal/domain/domain.go`: re-export `ErrMigrationBlocked =
   migrations.ErrBlocked` beside the existing `Err*` block (domain already
   imports the store; nothing else may). `internal/cli/run.go`: add
   `const ExitMigrationBlocked = 78` beside `ExitFenced`, documented the same
   way (`sysexits.h`'s `EX_CONFIG`, since this is "a human must fix the
   deployment," not a transient condition — distinct from `ExitFenced`'s
   `EX_TEMPFAIL`). `internal/cli/root.go`: add a branch to `ExitCode` —
   `errors.Is(err, domain.ErrMigrationBlocked)` → `ExitMigrationBlocked`.
   `contrib/systemd/mill.service`: add `RestartPreventExitStatus=78` beside
   `Restart=on-failure`, with a comment pointing at this incident and this
   exit status.
   Proof: extend `internal/cli/run_test.go`'s existing exit-code table
   (alongside its `ExitFenced` assertion, `:478`) with
   `Expect(cli.ExitCode(domain.ErrMigrationBlocked)).To(Equal(cli.ExitMigrationBlocked))`.
   Add one `db`-labelled spec to `internal/cli/serve_test.go` (alongside its
   existing migrate-related specs, `:65-102`, `:219-234`) that points
   `runServe` at a database seeded the way step 2's AC3 fixture is, and
   asserts the returned error satisfies `errors.Is(..., domain.ErrMigrationBlocked)`
   and the socket was never bound — proving the crash-loop's actual entry
   point is closed, not just the exit-code table.

5. **Document the numbering convention.**
   `docs/ledger.md`: new section (near the `step_runs`/schema material, or
   its own short section after the table descriptions) stating: migration
   numbers are assigned by the branch that adds them, off whatever main
   carried when the branch started; two branches in flight can pick the
   same next number or numbers that land out of order once merged, which
   the merge gate's catch-up now catches (`internal/store/migrations`'s
   ordering spec) before either reaches the forge, telling `implement` the
   next free number; a migration that still lands out of order regardless
   (the check is best-effort — "when it can resolve the target") is safe to
   apply late only when it is annotated `-- +mill out-of-order: safe`, which
   is only for migrations independent of anything numbered between them and
   the version they landed behind (mill#105 — `00028`'s identity column vs.
   `00029`'s trigger change); anything else stops `mill serve` once, by
   design, rather than retrying.
   Proof: none beyond review — documentation, not behavior, matching
   mill#52's own precedent for a docs-only step.

## Risks

- **The real-repo spec (step 3b) depends on `refs/remotes/origin/HEAD` and
  `refs/remotes/origin/<target>` already being on disk** rather than fetching
  either itself. This is true precisely where it has to be: the merge gate's
  own `catchUp` always runs its credentialed fetch of the target
  (`internal/run/gate.go:147`, `internal/workspace/verbs/verbs.go:335-346`)
  before `checkCaughtUp` runs `live-tier`'s `make test`
  (`internal/run/gate.go:161-168`), and the clone every run starts from sets
  the `origin/HEAD` symref the way any non-`--single-branch` clone does. The
  case this can't help is a checkout `go test` runs in that was never
  produced by mill's own clone-then-catch-up sequence — a bare `git clone`
  a developer made by hand with `origin/HEAD` never resolved, say. There the
  spec now `Fail`s instead of silently skipping when `MILL_REQUIRE_FIXTURES`
  is set (matching `testsupport.requireAvailable`'s own convention), and
  simply `Skip`s otherwise; either way the deterministic half (step 3a)
  still proves `CheckOrder` itself on every run everywhere, fixture or not.
- **`Provider.ApplyVersion`'s exact transactional behavior with a synthetic
  `fstest.MapFS`** hasn't been run, only read from goose's source
  (`vendor/github.com/pressly/goose/v3/provider.go:217-230`) and inferred
  from `up.go`'s `findMissingMigrations`. If it turns out to need the
  registered-Go-migration path or behaves differently for a `MapFS` than an
  `embed.FS`, step 2's fixture gets simpler (fewer files) rather than a
  different mechanism — the risk is to the fixture's shape, not the
  approach.
- **Multiple simultaneous violating files.** `CheckOrder` reports each
  violation independently, naming `target's highest + 1` for every one of
  them rather than a sequence — correct for the node's own singular
  scenario (one file, one collision) but would suggest the same number
  twice if a branch added two colliding files at once. Not fixed here:
  out of the node's stated scope, and `implement`, told about both
  violations, renumbers them distinctly on its own the same way `e24714b`
  already did by hand.
- **`ExitMigrationBlocked`'s value (78) is a judgment call**, not named by
  the work order. If review disagrees with `EX_CONFIG` over some other free
  number, it is a one-line change in two files (`run.go`, `mill.service`).

## Decisions

- **The merge-time check is a spec inside `internal/store/migrations`,
  wired into the existing `live-tier`/`checkCaughtUp` path — no new
  workflow step, no new `gate.go` code.** See *Approach*.
- **AC4's "against a real PostgreSQL" is read as applying to AC2 and AC3
  only.** AC1's check is git-and-filesystem logic with nothing for a
  database to prove; its specs (step 3) carry no `db` label.
- **The out-of-order annotation is a line-anchored SQL comment,
  `-- +mill out-of-order: safe`, parsed by this package alone** — not a
  goose extension, not a separate manifest file.
- **`OpenFS` is a new, permanently exported constructor**, not a test-only
  hook removed later: it is the seam that keeps `Migrator.Up`'s decision
  logic tested against a small, legible schema instead of the real one, and
  costs nothing on the `mill serve` path (`Open` just calls it with `FS`).
- **`ExitMigrationBlocked = 78`** (`sysexits.h`'s `EX_CONFIG`), distinct from
  `ExitFenced`'s 75 (`EX_TEMPFAIL`) — this failure is not transient.
- **Only `00028_step_runs_seq.sql` is touched among the existing migration
  files**; no new migration is added by this node.
- **The real-repo spec (step 3b) resolves its target via the local
  `origin/HEAD` symref, not `pr.Target` directly** (which no test process
  has); this reads the same as `pr.Target` whenever a run targets the
  repository's default branch — the ordinary case, and the reviewed
  attempt's own `main`-hardcoding covered only that case too — but not when
  a run explicitly targets some other branch. Left as raised: the review
  marked that gap a note, not blocking, and closing it needs `pr.Target`
  itself in reach of the spec, which is a larger change than this fix.
- **The recovering (AC2) path is proven only at the migrations-package
  tier, not re-proven end-to-end through `runServe`.** The review noted
  this as an improvement, not a blocking gap — AC4 pins the specs' location
  to `internal/store/migrations`, not to `internal/cli` as well — so step 4
  keeps its `serve_test.go` addition to the refusal (AC3) side only.
