# A fenced heartbeat's reason is lost behind the step's context cancellation

## Approach

`Runner.stop` (internal/run/run.go:953-982) is the one place every exit path
of the run loop converges — `couldNotOpen` failures, the walk's own result,
everything — so it is the one place to fix this, rather than chasing the
race at each of the many store/skift calls (`call()`) that can be in flight
when the heartbeat's goroutine cancels the step's shared context.

The fix: in `stop`, widen the condition under which the heartbeat's reason
(`s.beat.err()`) overrides the step's own error, from `err == nil` to
`err == nil || errors.Is(err, context.Canceled)`. Today's code
```go
if beatErr := s.beat.err(); beatErr != nil && err == nil {
    err = beatErr
}
```
drops `beatErr` the instant the cancelled step's own in-flight call returns
anything, which is exactly what happened in the incident: some call left
running past `walk`'s and `step`'s own `ctx.Err()` checkpoints returned a
bare `context.Canceled` rather than the heartbeat's own
`errors.Join(ErrFenced, reclaimErr)`. Overriding is not safe to do
unconditionally, though: when the heartbeat's reason is `errCancelled` or
`errShutdown`, `stopped()` (walk.go:154-169) has already turned it into a
call to `cancelStep`/`shutdownStep`, which itself releases the lease and
returns the deliberate sentinel `errReleased` — a value `stop` must leave
alone, both because it is not an error (the run stayed resumable on
purpose) and because overriding it with the raw `errCancelled`/`errShutdown`
would make `stop` fall past its `errors.Is(err, errReleased)` early return
and re-release an already-released lease, the very warning criterion 3
forbids. The same is true of a `stopped()` call that already resolved to
`ErrFenced` cleanly at one of its checkpoints. Neither `errReleased` nor
`ErrFenced` wraps `context.Canceled` — they are plain sentinels raised
directly — so gating the override on `errors.Is(err, context.Canceled)`
catches exactly the leaked, untranslated case the incident showed and
none of the cases `stopped()` has already handled correctly. Once the
heartbeat's reason wins in that one case, `stop`'s own next check —
`errors.Is(err, ErrFenced) || errors.Is(err, errReleased)` — already skips
the `Skift.Release` call for a fenced reclaim failure (`reclaim`'s failure
is always joined with `ErrFenced` in `heartbeat.go:82`), so criterion 3
falls out of this same change without a second code path.

One approach considered and set aside:

- **Make every `call()` site cancellation-aware** by threading the
  heartbeat into the generic `call[Req, Res]` helper, so a call interrupted
  by the shared context resolves to `s.beat.err()` at the source instead of
  at the one place all paths already meet. Rejected as disproportionate to
  a quick fix: it touches a widely-used generic helper and every call site
  in `walk.go`/`step`, for the same outcome `stop` already gets in four
  lines.

## Steps

1. **Narrow the leak in `stop`'s override without disturbing the paths that
   already resolve correctly.** Edit `internal/run/run.go`: change line 961's
   condition from `beatErr != nil && err == nil` to
   `beatErr != nil && (err == nil || errors.Is(err, context.Canceled))`;
   update the surrounding comment to say why — a raw `context.Canceled`
   surviving to `stop` is never more authoritative than the reason that
   raised it, but `errReleased` and an already-correct `ErrFenced` are
   deliberate outcomes `stopped()` already computed and must pass through
   untouched. No other line in `stop` changes — the existing
   `errors.Is(err, ErrFenced)` early return already then skips the
   `Release` call for the newly-caught case, closing criterion 3 as a
   consequence rather than a separate edit. `context` is already imported
   in `run.go`.

   *Proof:* a new spec in `internal/run/run_test.go`, under the existing
   `Describe("Being fenced out", ...)` block. Reuse the unreclaimable-fence
   setup from "A fenced heartbeat stops the worker" (expire the lease, have
   a second principal take the node via `f.reclaim(ctx)` so the worker's own
   reclaim fails), but additionally wrap the store so a call made *after*
   `execute` has already returned cleanly — `Store.RecordUsage`
   (`internal/run/finish.go:41`) — blocks on a channel the spec controls,
   then returns a bare `context.Canceled` once released, standing in for
   the race: a store write in flight at the moment the heartbeat's
   `cancel()` fires. The spec releases that channel only after confirming
   the fence has happened (`f.leaseOf` no longer matches the first lease).
   Assert `Execute` returns `MatchError(run.ErrFenced)` — not a bare
   `context.Canceled` — and, via the `warnCounter` handler already defined
   in `internal/run/worker_test.go` (same `run_test` package), that
   `"releasing the lease after a failure"` is never logged. This is the
   scenario the work order states verbatim and is the one the current code
   fails today; running it before the fix (mentally, or by reverting the
   one-line change) should reproduce `context canceled` and the WARN.

   The two existing specs that stop a run through `f.cancelRun` (the
   success path at `run_test.go:118` and the reclaim-succeeds path at
   `:194`) must keep passing unchanged: `cancelRun` drives the heartbeat to
   `errCancelled`, which `stopped()` turns into `cancelStep`'s own release
   and `errReleased` — a plain sentinel that does not wrap
   `context.Canceled` — so the narrowed condition never touches it, and
   both `Eventually(done).Should(Receive(BeNil()))` assertions keep holding
   exactly as they do today. Running the full `Describe("Being fenced
   out", ...)` and `Describe("A node driven end to end...")` blocks after
   the change is part of this step's proof, not just the new spec.

2. **Log what `reclaim` attempted and got back, on both paths.** Edit
   `internal/run/heartbeat.go`'s `reclaim` (`:103-117`): log at `Debug` on
   success, naming the node, the run, and the new lease id; log at `Warn` on
   failure, naming the node, the run, and the error `Claim` or `SetLease`
   returned (distinguish the two calls so the message says which one
   refused). This is the piece of the incident that left nothing in the
   journal at all.

   *Proof:* extend both existing "Being fenced out" specs
   (`internal/run/run_test.go:123`, `:155`) with a `warnCounter`-style
   handler (or a second instance of the same type, matched on the new
   messages) asserting exactly one matching record on each spec's path —
   the success spec sees the `Debug` line, the failure spec sees the `Warn`
   line. Ginkgo's `slog` injection already goes through `o.Log` in
   `f.runner(...)`, the same seam `worker_test.go` uses.

3. **Establish, and record, why mill#34's reclaim failed while steading#5's
   succeeded.** No code change is expected here unless step 1's evidence
   (once it exists in production) points at a bug in `skift.Client.Claim`
   or `reclaim` itself. Reading `internal/skift/lease.go:42-79`: `Claim`
   does a bare `Node` read and a `node.GetReady()` check *before* any label
   write; a `NotReadyError` there produces zero skift events — exactly what
   the incident shows (no `update_node`, no `claim_node` for mill#34,
   between the expiry and the failed heartbeat). The leading, and only
   evidence-supported, explanation: skift has some delay before a node
   with an expired lease reappears in the ready set, and mill#34's
   heartbeat (78s after expiry) landed inside that window while steading#5's
   (4m16s after expiry) did not. That is a timing property of skift, not a
   defect in mill's `Claim`/`reclaim` logic, so nothing in this plan changes
   either. This finding, and the reasoning above, go in the PR description
   so the node's fourth criterion is answered by citation rather than left
   silent. A bounded retry inside `reclaim` (try once more after a short
   delay before giving up) would be a reasonable mitigation *if* future
   occurrences (visible now, via step 2's logging) confirm the pattern —
   named here as an explicit non-goal, not folded into this fix.

   *Proof:* not a test — a documentation obligation. The PR description
   states the `NotReadyError`-before-any-write reasoning above, cites
   `internal/skift/lease.go:42-56`, and states plainly that this is
   skift's timing rather than mill's logic, so the reader can check the
   reasoning against the same three lines rather than take it on faith.

## Risks

- **The `RecordUsage`-blocking reproduction is fragile if the store call it targets changes.** If a future change reorders `step`'s post-execute calls so `RecordUsage` is no longer reachable after a clean `execute` return, the new spec would need to target a different call. Mitigation: the spec's comment names the exact invariant it needs (some store write reachable after `execute` returns cleanly, before the loop's own `ctx.Err()` checkpoints re-run), not the specific method, so a maintainer moving the call sees why the spec exists.
- **The condition still has to be gotten exactly right, or it reintroduces the bug from the other side.** Gating on `err == nil` alone (today's code) drops the heartbeat's reason; gating on `beatErr != nil` alone (an earlier draft of this plan) instead clobbers `errReleased` and an already-correct `ErrFenced`, reintroducing the very re-release warning criterion 3 forbids, just from a different path. The `errors.Is(err, context.Canceled)` gate is what keeps both failure modes closed at once; step 1's proof running the full existing "Being fenced out" and cancellation specs alongside the new one is what catches a regression here, not just the new spec in isolation.
- **Criterion 4 may not fully satisfy a reviewer who wants certainty, not a hypothesis.** The evidence ceiling was already reached in the previous step (gather-context): skift recorded nothing for mill#34's failed reclaim, so nothing retroactively distinguishes "skift's readiness lag" from any other pre-write failure in `Claim`. Step 2's logging is what would make the *next* occurrence conclusive; this plan does not block on manufacturing false certainty about the one that already happened.
- **Nothing this plan depends on is missing.** `warnCounter` (worker_test.go:445), the `failing`-style store-wrapper pattern (run_test.go:417), and the `f.expire`/`f.reclaim`/`f.leaseOf` fixture helpers (support_test.go) all already exist and are reused, not invented.

## Decisions

- **Log levels for `reclaim`'s new lines:** `Debug` on success, `Warn` on
  failure. The work order only says "records... that it was attempted and
  what it got back"; `Debug` for the routine (and potentially frequent,
  under a flaky network) success case and `Warn` for the actionable failure
  case matches the level this file and its neighbors already use for
  similar pairs (e.g. `hold`'s `Warn`, `openWorkspace`'s `Debug`).
- **No retry added to `reclaim`.** The work order's fourth criterion asks
  for the cause to be "fixed if it is mill's"; the evidence points at
  skift's own timing, not mill's logic, so no behavioral change is made
  there. Named as a possible follow-up, not attempted here.
- **The override in `stop` is gated on `errors.Is(err, context.Canceled)`
  in addition to `err == nil`,** not unconditional on `beatErr != nil`.
  Taken because `errReleased` and an already-correct `ErrFenced` are
  deliberate outcomes of `stopped()` (the cancel and shutdown paths in
  particular) that an unconditional override would clobber, reintroducing
  a dead-lease release from the other direction. Both sentinels are plain
  errors that never wrap `context.Canceled`, so the gate catches only the
  leaked, untranslated case the incident showed.
