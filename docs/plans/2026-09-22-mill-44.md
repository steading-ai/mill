# A restarted worker claims new nodes before resuming the runs it aborted

## Approach

A restarted worker's own runs — live, `worker_ref` this worker, latest step run `aborted` by that same worker's prior graceful shutdown (`shutdown.go:37-51`, `docs/ledger.md` §Resume) — should be reclaimed by name, ahead of `ClaimNext`'s round-robin, up to concurrency, oldest-abort-first. This is the literal reading of the acceptance criteria and the incident: a graceful `SIGTERM` restart (the reported case) already marks the attempt `aborted` synchronously before the process exits, so at the next start the ledger already knows exactly which runs to prefer and does not need to guess.

Rejected:

- **Order by `run.updated_at` instead of the aborted step run's own `ended_at`.** Cheaper (no `Inspect` call per candidate), but wrong: `AbortOpenStepRuns` (`store.go:1035-1073`) never writes the `runs` row itself, only `step_runs`/`step_tokens`/`events`, so `runs_guard`'s `updated_at` trigger never fires on abort (`internal/store/migrations/00004_runs.sql:79-97`). `updated_at` reflects whatever the run's last unrelated write was (e.g. the claim before the aborted attempt), not when it was aborted — it would satisfy the given scenario (2 candidates, 2 slots, order doesn't matter) but not the acceptance criterion's explicit "in the order they were aborted" once there are more candidates than slots.
- **Also reclaim runs left `running` (not yet `aborted`) by a hard crash.** `docs/architecture.md`'s "Stop." and "The worker crashes mid-step" bullets already describe these as two different paths: a graceful stop marks the attempt `aborted` synchronously; a crash leaves it `running`, and marking it `aborted` is deferred to whichever `ClaimNext` eventually claims the node again (`docs/ledger.md` §Resume, the `run.status in (running, selecting)` branch). Folding the crash case in here means guessing liveness from `worker_ref` alone, which `sweep.go:76-78`'s TTL guard exists precisely because that guess is unsafe without it. The acceptance criteria says "aborted step run," which the crash case is not, yet. Out of scope for this node.
- **Prefer reclaimable runs at every freed slot, not just at start.** Would also close the case of more aborted runs than concurrency, but changes the steady-state hot loop (`claim()`) rather than only what happens before the first `ClaimNext`, which is more than the acceptance criteria (explicitly scoped to worker start) or the incident (a one-time restart race) asks for.
- **Ask skift to prioritize a caller's own prior nodes in `ClaimNext`.** Not implementable here: `skift` is a separate service this repo only holds a generated client for (`gen/skift/v1`); `docs/architecture.md`'s "one binary, two faces... there is no scheduler" is skift's design, not mill's to change.

The mechanism: `Runner.Resumable` (new, `internal/run/reclaim.go`) lists this worker's own candidates from the ledger; `Worker.reclaim` (new, `internal/run/worker.go`) claims each by name via `skift.Client.Claim`, scoped to the candidate's own project (`Client.Scoped`, already used identically by `drive` at `run.go:579` and by `mill run`'s `Execute` at `run.go:547`), and hands it into the same slot/goroutine machinery `claim()`'s tail already uses. Nothing about `Claim`, `Scoped`, or the drive path is new; only the pre-pass that decides which nodes to hand it, and where.

## Steps

1. **`Runner.Resumable`: list this worker's own aborted-but-live runs, oldest first.**
   New `internal/run/reclaim.go`. `Runner.Resumable(ctx context.Context) ([]Resumable, error)`, where `Resumable{RunID, NodeRef string; AbortedAt time.Time}`. Calls `call(ctx, r.options.Store.Status, &millv1.StatusRequest{Statuses: []millv1.RunStatus{millv1.RunStatus_RUN_STATUS_RUNNING, millv1.RunStatus_RUN_STATUS_SELECTING}})` (the same two statuses `docs/ledger.md` §Resume's `run.status in (running, selecting)` branch names — `waiting`/`parked` runs are excluded: their open step run is a gate's own attempt, not an aborted one). For each `RunSummary` whose `run.GetWorkerRef() == r.options.WorkerRef` and `summary.GetLastStepStatus() == millv1.StepRunStatus_STEP_RUN_STATUS_ABORTED`, calls `call(ctx, r.options.Store.Inspect, &millv1.InspectRequest{Id: run.GetId()})` and reuses the existing `latestStepRun(detail, summary.GetLastStep())` helper (`gate.go:738`, same package) to read that attempt's `GetEndedAt()`. Sorts the result by `AbortedAt` ascending. Modeled on `sweep.go:65-78`'s `worker_ref`/`driving` filtering, minus the TTL recency guard — not needed here because this only ever runs once, before any claim, when nothing is yet in flight.
   **Proof:** new `internal/run/reclaim_test.go` (Ginkgo, `Label(testsupport.DBLabel)`, same fixture style as `worker_test.go`/`sweep_test.go`): drive two runs to a step each via the store RPCs directly (no skift claim needed — `StartStepRun`, then `AbortOpenStepRuns` with two different `RequestId`/timestamps a beat apart), assert `Resumable` returns both, oldest-aborted first. A third run aborted under a different `worker_ref` is excluded. A fourth run whose step run is `closed` (not `aborted`) is excluded. A fifth, `waiting` run is excluded.

2. **`Worker.reclaim`: claim those candidates before the first `ClaimNext`.**
   `internal/run/worker.go`: extract the goroutine-spawn boilerplate already at the tail of `claim()` (lines 406-413: `inFlight.Store`, `wg.Add`, the `go func(){...}` with its three deferred cleanups) into `func (w *Worker) spawn(ctx context.Context, wg *sync.WaitGroup, claimed *skift.Claimed)`, and call it from both `claim()`'s tail and the new `reclaim()`. Add `func (w *Worker) reclaim(ctx context.Context, wg *sync.WaitGroup) error`: calls `w.options.Runner.Resumable(ctx)`; for each candidate, in order, stops if `w.stopped()`/`ctx.Err()`; takes a slot with a *non-blocking* `select { case w.slots <- struct{}{}: default: return nil }` (unlike `claim()`'s blocking take — reclaim must stop, not wait, once concurrency's worth is already spoken for, leaving the rest to whatever `ClaimNext` would have done with them anyway); filters out a candidate whose project (`projectOf(c.NodeRef)`, `walk.go:459`, same package) is not in `w.options.Projects` when that list is non-empty (empty means every project, matching `ClaimNext`'s own convention at `worker.go:360`) — giving the slot back unused when skipped; claims via `w.options.Runner.options.Skift.Scoped(projectOf(c.NodeRef)).Claim(ctx, c.NodeRef)`; on a claim error, gives the slot back, logs a warning (`w.options.Log.Warn`), and continues to the next candidate rather than failing the whole pass (a node that became unready between listing and claiming — e.g. someone else already has it — is not this worker's problem to stop over); on success, handles the same "claim landed as the worker stopped" case `claim()` already handles (worker.go:375-383) by releasing and returning rather than driving; otherwise prints `w.printf("resumed %s, aborted at %s\n", claimed.Node.GetReference(), c.AbortedAt.Format(time.RFC3339))` (the journal line the acceptance criteria asks for — the "claimed" counterpart already exists, unchanged, in `drive`'s own `r.printf("claimed %s under lease %s\n", ...)` at `run.go:581`, which still fires for both origins at the per-attempt level) and calls `w.spawn(ctx, wg, claimed)`. Wire into `Worker.Run` (`worker.go:197-208`): after `w.start(ctx)`, before `w.claim(ctx, &wg)`, call `w.reclaim(ctx, &wg)` — sharing the same `wg` so `Run`'s existing `wg.Wait()` still waits for reclaimed runs too. A `reclaim` that fails to list (the store not answering) stops the worker the same way a sweep or reconcile failure does; a single candidate's claim failing does not.
   **Proof:** extend `internal/run/worker_test.go` with the acceptance criteria's own scenario: a worker of concurrency 2, two runs already `running` with an `aborted` step and `worker_ref` this worker's own (built via the fixture driving a run partway then aborting it exactly as `shutdownStep` does, per step 1's fixture pattern), plus a third, unrelated ready node. Start the worker: assert (via `mill status`-equivalent store reads, or the worker's captured `Out`) that its first two drives are the two resumable runs and the third node is not claimed until a slot frees — matching the work order's scenario line for line. A second spec: three resumable candidates, concurrency 1 — the earliest-aborted one is claimed first, the other two are left for the ordinary loop (proving the ordering, not just the "both fit" case the plain scenario alone would let slide). A third: a candidate outside `w.options.Projects` is left unclaimed by `reclaim` and picked up by the ordinary `ClaimNext` path instead (proving the projects filter). Confirm the full existing `worker_test.go`/`run_test.go` suite still passes unchanged after the `spawn` extraction (a pure refactor — its proof is the untouched suite, not a new spec).

3. **Docs, and confirming `mill status` needs no change.**
   `docs/architecture.md`'s "Stop." bullet (line 276) gains one clause: on the next start, a resumable run left this way is reclaimed before any new node is claimed, in abort order, up to concurrency (mill#44) — placed right after "Resume is the crash path," since this is what makes that true in practice rather than in theory. `docs/ledger.md` §Resume gains a short paragraph after the algorithm box (around line 313, beside the three "properties fall out" bullets) naming the same thing, and pointing at `Runner.Resumable`/`Worker.reclaim`. Confirm `internal/cli/read_internal_test.go`/`read_test.go`'s existing `renderStatus` specs already exercise a `leases > 1` row; add one if every existing case is `leases == 1` only.

## Risks

- **`skift.Client.Claim`'s project scoping, for a worker with no single pinned project.** `claimLabelled` (`lease.go:83-107`) filters `ClaimNext` by `Filter.Projects: []string{c.project}` — if `c.project` were empty (a multi-/all-project worker's base client, `internal/cli/work.go:262-266`), that could filter to nothing. Mitigated by construction, not by testing skift's tolerance for an empty entry: `reclaim` always calls `Scoped(projectOf(c.NodeRef))` before `Claim`, so the client used is never unpinned regardless of the worker's own base configuration. The existing test fixture (`internal/run/support_test.go`) runs a single skift project throughout, so this mitigation is argued from the code (`Scoped`'s implementation is a pure struct copy, `client.go:107-111`, nothing project-specific to get wrong) rather than exercised end to end across two live skift projects in this plan; flagged rather than silently assumed correct.
- **A candidate goes unready between `Resumable`'s listing and `reclaim`'s claim** (someone else took it, or it closed). Handled as a soft failure per candidate — logged, slot returned, loop continues — not a reason to fail the whole start.
- **`reclaim`'s non-blocking slot take races the concurrency count in a way `claim()`'s blocking take does not.** Read carefully: at the point `reclaim` runs, nothing is yet in flight (it is strictly before `claim()`'s loop begins), so `w.slots` starts empty and the `select`/`default` only ever declines once `reclaim` itself has filled every slot — not because of any run started elsewhere. No race with `claim()`, since the two never run concurrently (`reclaim` finishes, `wg`/`slots` state settled, before `w.claim` is called in `Run`).
- **The store call in `Resumable` failing mid-list.** Same failure mode `sweep`/`reconcile` already have at start; treated the same way — stop the worker rather than start claiming with a ledger it could not fully read.

## Decisions

- Reclaim covers only runs whose latest step run is already `aborted` (the graceful-shutdown case), not ones merely `running` under this `worker_ref` (the crash case) — the acceptance criteria's own wording, and the existing docs already treat these as two separate paths.
- Reclaim runs once, before the first `ClaimNext`, not at every freed slot afterward — matches "on start, before its first `ClaimNext`" literally; a worker with more aborted runs than concurrency leaves the remainder to the ordinary loop, same as today, accepted as this node's scope rather than solved here.
- Reclaim is filtered by the worker's configured `Projects` (empty = every project, matching `ClaimNext`), not by `Labels` — a run this worker was already driving necessarily satisfied the label filter when first claimed, and nothing in `RunSummary` carries a node's current labels to recheck cheaply; rechecking would need an extra `Skift.Node` read per candidate for a condition that essentially never changes on a live node.
- The "journal" the acceptance criteria names is the worker's own `printf`/`slog` output (the same channel `sweep`'s findings already use, `worker.go:252`), not a new persisted table — nothing in the codebase suggests a separate journal concept.
- `mill status`'s "resumed vs fresh" half of acceptance criterion 3 is read as already satisfied by the existing `LEASES` column; no new field or rendering branch is added for it.
