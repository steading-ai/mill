# The live specs skip, naming the host half, on a host with sudo but no sandbox

## Approach

Add one new method to the `driver.Driver` interface, `SandboxReady(ctx context.Context, root, machines string) (reason string, err error)`, that checks — in the order the acceptance criteria names — `systemd-nspawn` and `machinectl` on PATH, the `mill-machine@` template unit and its helper, then `root` on btrfs with a `machines` subvolume. `reason` is empty when the host is ready and otherwise names the first thing missing. `root` and `machines` are arguments, not constants read internally, precisely so the method is testable: a spec passes a temp directory, a real caller passes `driver.DefaultRoot`/`driver.DefaultMachines`. Implement it once in `systemd.go` (the real driver, which already shells everything through `workspace.Spawner.Exec` — this method keeps that invariant for the PATH and unit checks, using direct `os.Stat`/`syscall.Statfs`-style checks for the helper file and the subvolume, following `Statfs`'s own existing precedent for "not a command" host facts) and script it in `fake.go` for unit-tier coverage, exactly like every other `Driver` method (`Container` is the closest precedent: one host command, one string result).

Every live spec that needs the host — `internal/workspace/machine`'s two, `internal/workspace/machine/cache`'s two, `internal/workspace/machine/image`'s one — already constructs a `driver.NewSystemd(...)` and already has a `BeforeAll`/`BeforeEach` chain of `Skip()`s (`MILL_SANDBOX_HOST` unset, `InsideMachine()`, `sudo -n` refused). They call `SandboxReady` directly on that same driver value, passing the file's own `liveRoot`/`liveMachines` constants (already aliases of `driver.DefaultRoot`/`driver.DefaultMachines` in `machine_test`; added where missing in `image`/`cache`), and `Skip()` with its reason — no new package or wrapper needed. `mill doctor`'s `probeWorkspace` (`internal/cli/doctor.go`), which already holds a `driver.Driver` and already checks `Statfs`/btrfs for `workspace.KindMachine`, calls the same method — but only when `machine.InsideMachine(ctx, host)` is false, mirroring how `resolveSandboxRoot`/`machine.Check` already treat "running inside a machine" as its own case with none of the host-only facts available — and folds a non-empty reason into its existing fail path. The spec and the operator-facing probe read off exactly the same fact, from exactly one implementation, and neither one misreads a healthy nested worker as broken.

**Rejected: duplicate the checks inline in each of the 5 `Describe` blocks.** Cheapest edit, but leaves `mill doctor` as an unavoidable third, independently-drifting copy of the same logic — directly against AC #4 ("reports the same facts"), and against five slightly different skip messages for the same underlying condition.

**Rejected: a plain function in `internal/workspace/machine` or `internal/testsupport` that shells out itself, instead of a `Driver` method.** `internal/testsupport` is out because its non-test files (`activity.go`, `dagger.go`) already import `ginkgo`/`gomega`, and no production file in the repo imports `internal/testsupport` today — adding one from `internal/cli/doctor.go` would pull test frameworks into the shipped binary, which is presumably why nothing does that yet. A plain function in `internal/workspace/machine` that calls `exec.LookPath`/`exec.Command` directly would also make `probeWorkspace`'s existing `Label("unit")` specs (`internal/cli/doctor_internal_test.go`), which script a `FakeDriver` and must stay hermetic, depend on whatever binaries happen to be on the machine running `go test` — a `Driver` method is the only shape that is both fakeable for the unit tier and real for the live tier, which is exactly what the interface exists for.

**Rejected: check PATH tools via `exec.LookPath` even inside the real driver's implementation, bypassing `workspace.Spawner`.** Lint permits it (`.golangci.yml` excludes `internal/workspace/` from the `os/exec` forbid rule), but `systemd.go`'s own package doc states the real driver "shells out through `workspace.Spawner.Exec` and nothing else" as a stronger, self-imposed invariant than lint enforces. Keeping every command-shaped check on that one path means a reviewer never has to reason about two different execution routes inside the same driver, and it is also what makes the PATH checks stubbable at all: `Commands` fields are the only thing `newHost()`-style fixtures can point at a temp directory.

Revised from the last attempt: the previous draft gave `SandboxReady` no parameters and had it read `driver.DefaultRoot`/`driver.DefaultMachines` and a bare `systemd-nspawn` off the real PATH internally. That made the method's own happy path — and every check after the PATH probe — impossible to write as a hermetic `Label("unit")` spec, and would have had the new check silently read this host's real `/var/lib/mill` inside `go test` regardless of what a spec stubbed. Fixed by (a) adding `Commands.Nspawn` (a stubbable field, following the exact pattern every other `Commands` field already uses — empty resolves to the bare name `systemd-nspawn` on PATH in `withDefaults()`, same as `Systemctl`/`Machinectl`/`DetectVirt`) and (b) taking `root`/`machines` as arguments instead of reading constants internally. `SandboxReady` still never runs `systemd-nspawn` itself — the probe is a presence check only (`--version`, discarded), exactly as `Container` runs `systemd-detect-virt --container` only to read a fact, never to act.

## Risks

- **The one thing this plan cannot fully test here: `SandboxReady`'s "everything present" path.** Every PATH/unit/helper check is exercised both missing and present (stubbed), but the two filesystem checks can only be proven missing/absent and "present but not btrfs" in this environment — the actual "root is on btrfs with a `machines` subvolume, reason empty" branch is the same fact `probeWorkspace`'s pre-existing `Statfs`/`Btrfs()` check already reports correctly on `core` today (it is unchanged by this plan), so the narrower new risk is just `SandboxReady` reaching that reused call correctly, not reimplementing it. Mitigation: `SandboxReady` calls `d.Statfs`/`Btrfs()` rather than duplicating the syscall, so this risk is confined to the four checks ahead of it (PATH tools, unit, helper) and their present-branches, all four of which the unit spec exercises stubbed-present in Step 1. Watch `MILL_SANDBOX_HOST=1 make test` on the next real run on `core`, mill#47's own AC #3, rather than assuming a green run here proves it.
- **`systemctl list-unit-files mill-machine@.service --no-legend` may not be the right invocation.** I validated `systemctl cat mill-machine@.service` works unprivileged on this host and correctly reports absence ("No files found"); `list-unit-files` is the more standard way to ask "does this unit exist" without needing the file's contents, but its exact output shape for a template unit that is genuinely installed has not been observed anywhere in this environment (there is none to observe). The implementer should re-verify the chosen subcommand's output shape against `systemd 259` docs or a stub before trusting it, and the new `systemd_test.go` spec must stub realistic output for both the present and absent cases.
- **Reordering `real = driver.NewSystemd(...)` ahead of the existing guard checks in `live_test.go`/`nested_live_test.go`.** `NewSystemd` only builds a struct (no I/O), so this should be inert, but it's a change to code around three `Skip()`s that other in-flight work could also be touching — worth a careful diff read rather than assuming it's mechanical.
- **`probeWorkspace` gaining a `ctx` parameter** touches a function with 5 existing call sites in tests plus 1 production call site; missing one is a compile error, not a silent bug, so this is low-risk but not zero-effort.

## Decisions

- **`SandboxReady` takes `root` and `machines` as explicit parameters instead of reading `driver.DefaultRoot`/`driver.DefaultMachines` internally.** The previous version of this plan had it read the constants directly; the reviewer correctly flagged that as untestable, since nothing in `Commands` or the method signature let a spec redirect those paths to a temp directory. Parameterizing fixes both the testability gap and, as a direct consequence, means `mill doctor --sandbox-root X` and the probe report against the same root the operator configured, not a hardcoded default.
- **`Commands.Nspawn` is a new stubbable field, not a bare `exec.LookPath("systemd-nspawn")` inside `SandboxReady`.** Follows the same reasoning as the "Rejected" alternatives in Approach: everything the real driver checks stays on one execution path (`workspace.Spawner.Exec`) so it is stubbable the same way every other `Commands` field already is, and `newHost()`-style fixtures don't need a second mechanism for this one check.
- **`probeWorkspace` skips `SandboxReady` entirely when `machine.InsideMachine(ctx, host)` is true, rather than calling it and treating its reason as informational.** The reviewer's second blocking finding was that folding the reason in unconditionally would fail a healthy nested worker's probe, since the host-only facts (template unit, helper, `machinectl`, `systemd-nspawn`) are absent there by design — `resolveSandboxRoot` already resolves `opts.sandboxRoot` to `machine.NestedRoot` before this probe runs for exactly that reason. Skipping the call (rather than calling it and ignoring a "missing" reason) also means a nested worker's probe never depends on `SandboxReady`'s behavior for facts that don't apply to it, matching how the live specs `Skip` on `InsideMachine()` before ever reaching `SandboxReady` themselves.
- **`probeWorkspace` passes `driver.DefaultMachines` for `machines`, not a new `doctorOptions`/CLI field.** `machine.Config.Machines` is configurable at the driver-configuration level, but `doctorOptions` has no corresponding flag today, and adding one is CLI plumbing this node's acceptance criteria doesn't ask for. Noted as a reviewer note (not blocking) rather than fixed, to keep this revision scoped to the two blocking findings; a future node can add `--machines` if an operator ever needs to point the probe somewhere nonstandard.
- **Podman is checked only by the image spec, not folded into `SandboxReady`.** The acceptance criteria's own phrasing sets it apart — "and (for the image spec) podman" — and the other four specs never touch podman; baking it into the shared method would make them skip for a reason that has nothing to do with what they actually need, and would make `mill doctor`'s workspace probe fail on a host that can run every other machine operation but hasn't built a derived image yet.
- **One new `Driver` interface method, not a plain function in `internal/workspace/machine` or `internal/testsupport`.** Settled in Approach; recorded here because the previous step's note left this open as the main unknown, and the deciding fact is that `internal/testsupport`'s non-test files already import `ginkgo`/`gomega` and are never imported by production code today — using it from `doctor.go` would be a new, undesirable dependency direction.
- **The helper and `machines`-subvolume checks use direct filesystem calls (`os.Stat`), not the existing `Exists(ctx, path)` Driver method.** `Exists` runs `sudo -n test -e <path>` when `Sudo` is set, which would conflate "the helper file is present" with "sudo works" — two facts the acceptance criteria and the existing specs already treat as separate and ordered (AC #2: "`sudo -n` succeeding is necessary... never sufficient"). `Statfs`'s own implementation already bypasses the spawner for a direct syscall when the fact isn't really "a command," which is the precedent taken here.
- **`SandboxReady`'s reason strings are not fixed in this plan.** The acceptance criteria requires a message "naming the first missing thing," in `HostOnlySkip`'s style, but doesn't mandate exact wording, and this host cannot exercise every "present" branch to sanity-check a full message catalogue against reality. Left to the implementation step, with the constraint that each message name what's missing and point at the relevant `docs/sandbox.md` section, matching `HostOnlySkip`'s existing shape.
- **Not addressed (reviewer note, not blocking): whether the image and cache specs should run a narrower check than the full `SandboxReady` list.** The image spec's own file comment says it never touches `/var/lib/machines`, and the cache specs only need a writable btrfs root, not a booted machine — so on a hypothetical host with `nspawn`/`machinectl`/the template unit missing but podman and btrfs present, this plan's `SandboxReady` would skip both anyway, more conservatively than strictly necessary. Left as-is because splitting the check into composable pieces is a real design change, not a fix to either blocking finding, and the work order's own AC #1 lists the full set as what "each live spec checks... for what it actually needs" without carving out image/cache as exceptions. Worth revisiting if a future host actually has that split of tools present.
