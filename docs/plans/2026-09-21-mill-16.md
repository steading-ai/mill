# Closed attempts are sealed into frames with an index and a twin

## Approach

Build seal as new, additive infrastructure layered on what `mill#13`/`mill#14` already delivered — the `Activity` proto, the live file (`internal/run/activity.go`), and the `Logs` RPC reading live files directly (`internal/server/logs.go`) — rather than reworking either. Concretely:

- The frame and twin are files the **worker** writes, on the same host and under the same `--log-dir` it already writes the live file to (`docs/activity.md`'s "one backend-specific step" language and `internal/server/logs.go`'s existing local-disk reads both assume `mill serve` and `mill work` share a filesystem on one host, which is the deployment shape node `mill#14` already built against). Sealing therefore lives in `internal/run`, beside `activityWriter`.
- `internal/run` never talks to Postgres directly — `Options.Store` is a `millv1connect.StoreServiceClient` (`internal/run/run.go:145`), and only `internal/domain`/`internal/store` may import the store package (depguard). The index rows a seal produces therefore cross the wire as a new unary RPC, `SealAttempt`, on `StoreService` — the worker computes the frame, the twin, and the index rows locally, and hands the (bodyless, small) index rows to the server to insert. This mirrors `RecordUsage`/`RecordWorkspace`: a worker-side fact, reported once, inserted by the server behind the existing store boundary.
- Recovery's read side needs no new RPC: `Inspect` (`proto/mill/v1/store.proto:946`) already returns every attempt's `StepRun.status` for a run, and it is already a `StoreServiceClient` method — the same client `internal/run` already holds. Recovery walks `--log-dir` for live files, and for each asks `Inspect` whether that attempt is over.
- `Logs`'s every-run read (`internal/server/logs.go:102` `readEveryRunActivities`) re-reads every attempt file of every run from scratch on every wake — a `mill#14` review finding (noted, not required to fix, in that node's review). This node's index table is the fix the finding named ("a since/cursor-aware read... would bound it"), so step 8 below replaces that function's shape as part of delivering `since`, not as separate cleanup.
- The one genuinely new primitive is pulling the harness's transcript out of a workspace for the twin: today `workspace.Workspace.Read`/`Write` (`internal/workspace/workspace.go:588,590`) are confined to the checkout, and nothing reaches a session's `HOME`. This plan adds a narrow interface for that (step 6) implemented first for the `local` backend (a plain local tar — `HOME` is already host-reachable) and separately for `machine` (step 10 — `HOME` is inside a VM and needs the driver's own reach-in mechanism), so the harder, less-familiar piece is isolated and does not block or muddy the mechanical seal work.

Rejected, from the prior step's note:

1. **Local-only twin, machine backend left as follow-up.** Fails two of the six acceptance criteria outright (the machine directory never gets a `.twin.tar.zst`, and `docs/activity.md`'s own "Changes, by component" table names the machine capture as in-scope). Only worth it if the machine-backend hook were a much larger yak-shave than everything else combined — worth checking before ruling out, and step 10 below is written to surface that early rather than at the end, by trying the driver's existing exec/copy mechanism first instead of inventing a new one.
2. **One combined step that does seal, recovery, the index, and both backends' twins together.** Same total work as what follows, but nothing is independently provable until nearly the end — exactly what "a plan whose middle is broken cannot be reviewed, resumed, or abandoned halfway" warns against. Splitting into the ten steps below keeps the tree buildable and testable after each one.

## Steps

1. **Proto surface: the `activity` index row and the `SealAttempt` RPC.**

Add to `proto/mill/v1/store.proto`: `rpc SealAttempt(SealAttemptRequest) returns (SealAttemptResponse)`, request carrying `step_run_id` and `repeated ActivityIndexRow records`, response empty. Add the stub to `internal/server/store_service.go` (`CodeUnimplemented`, matching `mill#14`'s step 1 pattern so `var _ millv1connect.StoreServiceHandler` keeps compiling) and `SealAttemptProcedure` to `internal/server/permissions.go` — a worker-only write, so the same permission the other step-run mutation RPCs (`CloseStepRun` et al.) use, not `PermissionRead`.
   **Proof:** `make generate && make check-generated`; `make check-breaking` (additive, expect a clean pass); `go build ./...`; `make test` stays green. Extend `internal/server/roles_test.go` with a case asserting a worker-scoped token can call `SealAttempt` and gets `CodeUnimplemented`, not `CodePermissionDenied`.

   **Proof:** `make db-migrate` applies cleanly; `make db-reset` (down then up) round-trips. `sqlc vet` passes once step 3's queries reference the table.

3. **sqlc queries and the `Store` wrapper.**
   New `internal/store/queries/activity.sql`: `InsertActivityIndex` (`:many`, multi-row `INSERT ... VALUES` built from `unnest($1::text[], $2::bigint[], ...)` so one round trip inserts a whole attempt's rows — matching the existing multi-row pattern sqlc already generates for `AbortOpenStepRuns`/`SupersedeStepRuns`'s `:many` shape, adapted for insert), `CountActivityForStepRun` (`:one`, used by the acceptance-criteria proof and nowhere else in prod code), `ListActivityForStepRun` (`:many`, ordered by `seq`, for `Logs` reading a closed attempt), `ListActivitySince` (`:many`, ordered by `(at, step_run_id, seq)`, for every-run reads). `internal/store/store.go` gains `Store.SealAttempt(ctx, stepRunID string, rows []*millv1.ActivityIndexRow) error` and `Store.ActivityForStepRun`/`Store.ActivitySince` read wrappers, converting to/from the generated row types the way `convert.go` already does for `sessions`/`usage`. No lease-fencing: `activity` is not one of Invariant 9's fenced tables (a sealed attempt's own lease is already gone), so this is a plain transaction, not `fence()`.

4. **`SealAttempt` handler.**
   Replace the step 1 stub in `internal/server/store_service.go` with a real handler calling `s.store.SealAttempt`.
   **Proof:** extend `internal/server/store_service_test.go`: calling `SealAttempt` with fabricated rows, then reading them back via a direct store call, matches; a second call for the same `step_run_id` with different rows (simulating a retried seal after a partial failure) either replaces or duplicates predictably — pick one (see Decisions) and assert it.

5. **The seal algorithm, local backend only, no recovery trigger yet.**
   New `internal/run/seal.go`: `sealAttempt(dir, runID, step string, attempt int64, sessionID string, store millv1connect.StoreServiceClient, twin workspace.TwinSource) error` (`twin` may be nil — an attempt with no session, e.g. a gate or check step where `sr.GetSessionId()` is empty, writes no twin at all, and neither does one whose `sessionID` is empty). Steps inside: read the live file via the existing `decodeActivities`/`ReadActivities` path (`internal/run/activity.go:520,673`); coalesce — group consecutive `Text`/`Thinking` records sharing `source`+`turn`+`block_id`, but never merge across a `Final:true` record, which always closes its group. On today's code this is a no-op that changes nothing: `activityFromEvent` (`internal/run/execute.go:277-299`) always emits `Text` with `Final:true` and an empty `block_id`, so every group is exactly one record, and grouping-then-closing-on-Final reproduces the live file's records unchanged rather than discarding any of them. Once a future node gives the harness real streaming (non-empty `block_id`, `Final:false` mid-stream), a group's coalesced text is the **concatenation of every record's own text in `seq` order**, not just the last one kept alone — each mid-stream record holds only its own disjoint released fragment (`redact.DeltaHoldback.Add`, `internal/workspace/redact/redact.go:285-301`, returns `release`, the newly-freed slice, not the running total; only the final call's return plus every prior release together reconstruct the whole block). The group's `at` is its first record's `at`, `ended_at` its last's. Then: renumber `seq` contiguously over the surviving (post-coalescing) records (see Decisions — the live file's `seq` is not preserved past coalescing); zstd-encode the coalesced records, length-prefixed exactly as the live file already is, at level 3 via `github.com/klauspost/compress/zstd` (promote from indirect to direct in `go.mod`), to `<step>.<attempt>.activity.zst`; decompress what was just written and compare record-for-record against what was read, refusing to proceed on mismatch; build one `ActivityIndexRow` per surviving record, `offset` = that record's byte position in the *uncompressed* frame; call `store.SealAttempt`; if `twin` is non-nil, capture it (step 6) to `<step>.<attempt>.twin.tar.zst`; only once every prior step has succeeded, remove the live `.activity` file. Any error before the last step leaves the live file exactly as `docs/activity.md`'s "a partial seal leaves the live file" requires — no partial `.zst`/`.twin.tar.zst` renamed into place either (write to a `.tmp` suffix, `os.Rename` at the end, so a crash mid-write never leaves a half-written frame that looks sealed).
   **Proof:** new `internal/run/seal_test.go`: a live file shaped like today's real output — several complete (`Final:true`, empty-`block_id`) `Text` records among other kinds — seals to a frame with the same record count and the same text each record held, proving coalescing-as-no-op loses nothing; a second, synthetic case (two `Final:false` records sharing a `block_id` followed by one `Final:true`) coalesces to one record whose text is the **concatenation** of all three, not just the last, proving the merge case is correct too. `CountActivityForStepRun` (via a `testsupport.DBLabel` fixture, since this needs a real store) matches the frame's record count after `SealAttempt`; killing the process (simulated: return an error from a fake `workspace.TwinSource` mid-seal) leaves the live file and no `.zst`. This is acceptance criterion 3 end to end and half of criterion 1 (the local-backend half).

6. **The twin source interface and the local backend's implementation, without the `sessions` table.**
   The plan's original design keyed twin capture on `sessions.adapter_ref`, but no code writes that table: `Store.PutSession` (`internal/store/store.go:1544`) has no caller anywhere in the tree and its own comment records that the proto names no RPC for it ("the worker node that drives sessions will need one") — that RPC is not part of this node's deliverables, so `adapter_ref` is always empty and a lookup against it would always miss. Fix: derive the transcript path the same way the harness itself does, from data `internal/run` already has locally, no store round trip needed. Per `docs/spikes/sdk-sessions.md` (§Q1, confirmed against SDK 0.3.263/CLI 2.1.263), Claude Code writes each session's transcript to `$HOME/.claude/projects/<cwd-slug>/<session-id>.jsonl`, `cwd-slug` being `cwd` with `/` and `.` each replaced by `-`, and subagent transcripts land in the same `<cwd-slug>` directory under their own session ids. `internal/run` already knows both halves without asking the store: the session id is `sr.GetSessionId()` (already read at `internal/run/execute.go:130,249`), and for the local backend the cwd is the workspace's own checkout — `internal/workspace/local.Options.Root` plus the run id (`internal/workspace/local/local.go:74-76`, `checkoutDir = "checkout"` at line 37), the same convention this very checkout sits under. `HOME` itself is not per-run for the local backend: it is floor-inherited from the worker process's own environment (`internal/workspace/exec.go`'s `FloorNames` doc), so every local-backend session on one worker shares the one real `$HOME`, distinguished only by `cwd-slug`.
   New interface in `internal/workspace/workspace.go`: `TwinSource interface { CaptureTwin(ctx context.Context, sessionID string) (io.Reader, error) }` — deliberately not on the main `Workspace` interface, so a backend or call site with nothing to offer (a check step's workspace, or recovery with no live workspace open) is simply not asked, matching `ActivitySink`'s existing optional-interface pattern (`internal/run/execute.go:396`, `if sink, ok := s.workspace.(workspace.ActivitySink); ok`). `internal/workspace/local` gets a free function, `local.CaptureTwin(ctx, root, runID, sessionID string) (io.Reader, error)`, doing the slug computation and tar (not compress — `seal.go` applies the outer `.zst`) of `$HOME/.claude/projects/<slug>/` — every `.jsonl` under that directory, not only the one named by `sessionID`, since a subagent's own session id is not known in advance and this is the smallest rule that satisfies "including subagent transcripts." `local.Workspace` implements `TwinSource` by calling this function with its own already-known root and run id; recovery (step 8) calls the same free function directly, needing no live workspace.
   **Proof:** `internal/workspace/local/local_test.go` gains a spec: given a fabricated `$HOME/.claude/projects/<slug>/…jsonl` (main session plus one differently-named subagent file) computed from a known `root`+`runID`, `CaptureTwin` returns a tar containing both, byte-identical to the source files. A second spec pins the slug computation itself against the one example `docs/spikes/sdk-sessions.md` records (`/home/ivy/src/github.com/ivy/mill` → `-home-ivy-src-github-com-ivy-mill`), flagged in Risks as resting on observed, not documented, CLI behavior. `internal/run/seal_test.go` (step 5) is extended to use the real `local.CaptureTwin` instead of a fake for one spec, closing the local half of acceptance criterion 1 for real (`.twin.tar.zst` present, opaque, not decoded).

7. **Wire seal into the attempt-end path.**
   `internal/run/execute.go`'s `endActivity` (the single choke point already shared by `gate.go:376`, `revise.go:51`, `select.go:244,270`, `walk.go:323`) calls `sealAttempt` after `s.activity.End(...)` succeeds and before clearing `s.activity`/detaching the sink, passing `s.workspace` (already in scope, and already a `workspace.TwinSource` per step 6 for the local backend) as `twin`, and `sr.GetSessionId()`/`s.run.GetId()`/the step/attempt already available. A seal failure is logged, not fatal to the step's own outcome — the attempt already closed or failed on its own evidence; an unsealed live file is exactly recovery's job (step 8), not a reason to fail work that already succeeded. `abortActivity` (the no-outcome-recorded path, `select.go:214`, `walk.go:242,259`) does **not** seal — those attempts are not yet "over" per the ledger (`AbortOpenStepRuns` marks them later, on a future resume), matching `docs/activity.md`'s "the ledger says what it should have."
   **Proof:** extend `internal/run`'s existing attempt-lifecycle specs (`feature_test.go`/`run_test.go`'s fixtures already exercise closed/failed/gate-denied attempts end to end) to assert a `.activity.zst` and no `.activity` exist after a normal run completes a step, using the real DB fixture. `RenderedLog`/`ReadActivities`-based specs elsewhere in the suite that assume a live `.activity` file survives a closed attempt need updating to read the frame instead — audit `internal/run/*_test.go` for `ActivityPath`/`ReadActivities` used against a *closed* attempt and adjust (open question flagged in Risks: how many specs this touches is unknown until this step is under way).

8. **Recovery: seal orphaned live files before the first claim.**
   New `internal/run/recover.go`: `func (r *Runner) SealOrphans(ctx context.Context) error` — lists `<dir>/*/​*.activity` under `r.options.LogDir`, parses `(runID, step, attempt)` back out of each path (inverse of `ActivityPath`, `internal/run/activity.go:51`), groups by `runID`, calls `store.Inspect` once per run, and for each file whose matching `StepRunDetail.step_run` is not `running` (closed/failed/aborted/superseded — i.e., the ledger says the attempt is over) calls the step 5 `sealAttempt`, passing that `StepRun`'s own `session_id` and, for the local backend, `local.CaptureTwin` (step 6) built from the runner's configured `Root` and the parsed `runID` — no live workspace needed, since that function only ever reads `$HOME` and a deterministic path. A file whose run `Inspect` can't find (deleted run, wrong host) or whose status is still `running` is left alone. A machine-backed orphan whose VM was already destroyed before recovery ran captures no twin — the same accepted crash-window gap step 11 names, not a new one. Wire into `internal/run/worker.go`'s `start()` (`worker.go:180`), one call per `w.options.Runners[0]` — or, if `LogDir` and `Store` are confirmed to vary per `Runner` during this step (unverified — `WorkerOptions.Runners` is one per project; whether they share one `mill work` process's `--log-dir`/socket or each carries its own is not yet confirmed by this plan), once per runner — placed right after `w.sweep(ctx)` and before `Startup.Reconcile`, since sealing local files needs neither dagger nor the host reconciliation pass.
   **Proof:** new `internal/run/recover_test.go`: a live file for a step run the fixture DB already marked `closed` gets sealed by `SealOrphans`; one for a `running` step run is untouched. A `worker_test.go` spec (that package already fabricates a `Worker`) asserts `start()` calls it before the first `claim` — e.g. a live file present before `Run` is called is a frame after `start()` returns, before any node is claimed. This is acceptance criterion 2.

9. **`Logs` reads frames and the index for closed attempts.**

11. **The machine backend's twin capture.**
    Implement `workspace.TwinSource` on `internal/workspace/machine/machine.go`'s `Workspace`. First check whether the machine driver already exposes a generic "pull a path out of the machine" primitive (whatever the sidecar/verb-exec path already crosses this boundary with — unconfirmed by this plan, first thing to check in this step) before adding a new one; if one exists, this step is a thin adapter reading `sessions.adapter_ref`'s config dir the same way step 6's local implementation does, over that primitive, into the same tar shape. ## Risks

- **The `$HOME/.claude/projects/<cwd-slug>` path and its `/`→`-`, `.`→`-` slug rule are observed CLI behavior (`docs/spikes/sdk-sessions.md`), not a documented contract.** A future Claude Code CLI upgrade could change the encoding and silently break twin capture (an empty or missing tar, not a loud failure). Answer: step 6's proof pins the one example the spike doc already recorded as a regression test, and `CaptureTwin` reading zero files is treated as "no twin," logged, and does not fail the seal — matching how a missing session already behaves — so an encoding drift degrades gracefully rather than blocking every attempt from sealing.
- **Coalescing deltas changes `seq` (Decisions below), and any existing spec or downstream reader that assumes a sealed attempt's `seq` values match what the live file had will break.** Answer: this is the audit called out in step 7 — grep every test asserting on `seq` against a *closed* attempt's records before assuming it's cosmetic.
- **`WorkerOptions.Runners` may or may not share one `LogDir`/`Store` per worker process** (step 8 depends on this). Answer: read `internal/run/worker.go` and `internal/cli/work.go` in full at the start of step 8, before writing `SealOrphans`'s call site — if runners differ, seal once per runner rather than once for `Runners[0]`, and record that as a decision rather than a surprise.
- **The machine backend may have no existing "pull a file out of the VM" primitive** (step 11's stated first check). If none exists and building one is materially bigger than the rest of this plan combined, that is grounds to split step 11 into its own follow-on node rather than force it into this one — flagged here so a reviewer sees the possibility rather than discovering it mid-implementation.
- **A `SealAttempt` RPC retried after a partial failure could double-insert index rows** if the worker's own call succeeded server-side but the response was lost (network blip between two local processes, unlikely but not impossible). Answer: make the insert idempotent — `ON CONFLICT (step_run_id, seq) DO NOTHING` — so a retried seal (the worker doesn't know whether its first call landed) is safe; recorded in Decisions.
- **The "before `Destroy`" ordering for the machine twin has one uncovered crash window** (step 11): a worker that dies before sealing its last attempt, followed by a restart or sweep that destroys the workspace before any worker recovers it. Accepted as out of scope for this node (see Decisions) rather than silently unhandled — a future node (or a widening of `activity-retention`) is the place to close it if it matters in practice.

## Decisions

- **Seal renumbers `seq` contiguously over the coalesced records in the frame**, rather than preserving the live file's original `seq` with gaps. The live file's `seq` was only ever a per-attempt ordering key; the frame and the index are the durable form, and `docs/activity.md`'s own language ("the frame holds turns and the index has one row per block") reads as the post-coalescing count being the one that matters. The smallest option that satisfies "one row per block."
- **`SealAttempt`'s insert is idempotent (`ON CONFLICT (step_run_id, seq) DO NOTHING`)**, so a seal retried after an ambiguous failure (frame written, response lost) never double-counts. The work order is silent on retry behavior; this is the smallest safe default given seal is explicitly retriable ("a partial seal leaves the live file, which is the signal to try again").
- **Recovery calls `Inspect` once per run found on disk**, not a new bulk "every step run's status" RPC, since the expected number of orphaned live files at any one worker start is small (one crash's worth, not a backlog) and `Inspect` already exists and is already reachable from `internal/run`'s client type.
- **The machine backend's uncovered crash window (twin lost if `Destroy` is reached before seal ever ran) is accepted, not fixed, in this node.** Closing it fully would mean either blocking every `Destroy` call on a synchronous seal attempt regardless of which worker is doing the destroying (a bigger change to `docs/ledger.md`'s resume/sweep algorithms than this node's scope) or accepting data loss in an already-rare double-failure case (worker crash *and* no recovery ever runs before someone tears the workspace down). The work order's acceptance criteria do not test this path, and `docs/activity.md`'s notes on the twin ("nothing decodes it") suggest it is already treated as best-effort archival rather than a correctness-critical copy.
- **`mill logs` with no run prefixes lines with the run's display key (`node_ref`), not its internal id** — matching every other CLI-facing identifier in this codebase (`mill#16`, not a ULID), and requiring the server to carry `node_ref` (or the CLI to resolve it via a lookup) alongside each `Activity`'s `step_run_id` in the every-run stream. Exact mechanism (server includes it in `LogsResponse`, vs. CLI resolves via a side `Inspect`/`Status` call per run) left to step 10's implementer to choose the smaller of the two once the RPC's existing shape is back in view — recorded here as the requirement, not the wire change, so the proto surface for it isn't guessed at in step 1 before it's needed.
