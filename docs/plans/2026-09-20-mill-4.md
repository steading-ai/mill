# mill doctor from a client host probes the worker, not the client's files

## Approach

Three independent findings, three independent fixes, landed under one node
because they share a command.

**sidecar / signing / forge.** `mill serve --work` is, today, the only
process that ever holds the sidecar entrypoint, the signing key and the
forge credential — `docs/architecture.md` §"One binary, two faces" is
explicit that `work` is a *client* of `serve`'s store, never the reverse,
and that the Connect boundary between them exists precisely so a worker on
another host is "a configuration change," not a redesign. `StoreService`
itself says of its own scope that it "holds no rule of its own" beyond
mapping the ledger — it is not the place to grow sidecar-spawning or
forge-crediting logic. So the fix is a **second, separate Connect service**
(`WorkerService`, one RPC: `Probe`) that `mill serve --work` mounts only
when it actually is running a worker in this process, backed by the exact
settings `--work` already parsed for real runs. `mill doctor` calls it first
for these three probes and falls back to today's local probing when the
socket doesn't answer it (older server, or a bare `mill serve` with no
`--work` — the RPC is simply not mounted there). This satisfies the
deliverable's stronger clause ("passes forge and sidecar") wherever a worker
answers the socket, and its fallback clause everywhere else, without
inventing a way for the store to reach across processes it has no channel
to.

*Rejected:* folding the three probes into `StoreService`/`domain.Service`
directly — it would work for the MVP's one-process topology but bakes
worker-only capabilities into the ledger's API, which is exactly the
coupling the existing Connect boundary is there to avoid, and it would need
undoing the moment a second worker exists. Also rejected: detect-and-point
only (report "run this on the worker" and stop) — smaller, but it only
reaches the AC's weaker "or" clause and leaves the Mac exactly where stead
found it: doctor still can't go green from the client when a worker is one
hop away and perfectly reachable.

**gateway.** The header gap is real but not mill's to close by
hand-rolling values: `anthropic-beta` and `user-agent` are chosen by the
Claude Agent SDK inside the sidecar process at request time, not by
anything mill's own code sets — `internal/harness/claude` carries no such
constant today (checked; `ENABLE_TOOL_SEARCH` from the spike's decision
paragraph is not yet implemented anywhere in this tree). Hardcoding a
guessed header set would be a second, unmaintained copy of an external
detail that drifts silently with every CLI upgrade — worse than the gap it
claims to close. The chosen fix is the deliverable's second clause: write
down, next to the probe's request, exactly why full parity isn't
attainable, and make sure the probe sends every header mill *does* control today (there are
none beyond the three it already sends) rather than a plausible-looking
guess. `docs/tools.md` gets the same limitation stated for a reader.

*Rejected:* routing the probe through a real sidecar session so its request
is byte-identical to a real one — it would give true fidelity but turns a
"cheap, no-billing" health check into a full harness round trip, and the
finding is about headers, not about the sidecar being unreachable (that is
already `sidecar`'s job).

**signing.** Add an optional `forge.ContentReader` interface, mirroring the
existing optional `forge.Prober` (`internal/forge/forge.go` — `Prober` is
implemented today only by GitHub; GitLab has neither `Prober` nor will it
get `ContentReader` in this change, for the same reason `probeForge`
already degrades gracefully for forges without `Prober`). `probeSigning`
tries the existing checkout-based `trustedBy` first, and when nothing there
trusts the key it asks the forge — GitHub's Contents API for one file, no
clone, no workspace/git involvement — before failing. A forge with neither
capability fails exactly as today, naming that plainly.

*Rejected:* an ephemeral shallow clone through the workspace — it reuses a
real run's exact path, but pulls `doctor` into git/workspace machinery it
has never needed for a health check, for one file's contents.

## Steps

1. **Extract the three worker-local probe bodies into a new package,
   `internal/doctor`.** `probeSidecar`, `probeSigning`/`trustedBy`, and
   `probeForge`'s bodies move out of `package cli` into plain functions
   there (no cobra, no `doctorOptions` — small config structs instead), so
   both `internal/cli` and the new server handler can call the same logic.
   `internal/cli/doctor.go` keeps its `probe{Name,OK,Reason,Warning}` shape
   and thin wrappers that call into `internal/doctor` and adapt the result.
   **Proof:** pure refactor, no behavior change — `doctor_test.go` and
   `doctor_internal_test.go` pass unmodified.

2. **`forge.ContentReader` and GitHub's implementation.** Add the interface
   next to `Prober` in `internal/forge/forge.go`: `ReadFile(ctx, path)
   (string, error)`, `ErrNoSuchFile` for a 404. Implement it in
   `internal/forge/github` against the Contents API (base64-decoded body).
   **Proof:** new unit spec in `internal/forge/github` — reads an existing
   file, a 404 path, and a permission-denied path, against a fake HTTP
   server the way `probe_test.go` already fakes GitHub's API.

3. **`internal/doctor`'s signing probe consults the repository when no
   checkout trusts the key.** `trustedBy`'s existing scan runs first;
   finding nothing, and given a project and a forge that implements
   `ContentReader`, it reads `allowed_signers`/`.allowed_signers` off the
   project's default branch and checks the same way. No checkout, no
   `ContentReader`, or the file not there: fails exactly as today, naming
   which of those it was.
   **Proof:** new specs — passes on a key with no checkout when a fake
   `ContentReader` returns a file naming it; still fails when the fake
   returns 404, and when the forge is a fake with no `ContentReader` at
   all (GitLab's shape today).

4. **`WorkerService`: proto, server handler, conditional mount.** Add
   `service WorkerService { rpc Probe(ProbeRequest) returns (ProbeResponse); }`
   to `proto/mill/v1/store.proto` (same `mill.v1` package as `StoreService`,
   same generated file set) with `ProbeResponse` carrying the same
   `{name, ok, reason, warning}` triples doctor already prints, for
   `sidecar`, `signing`, and `forge`. `make generate`. New
   `internal/server/worker_service.go` implements the generated handler by
   calling `internal/doctor`, built from the settings `--work` already
   parses (`workOptions`/`runOptions`: sidecar entrypoint, env mode,
   workspace dir, identity, name, forge, project). `internal/server/server.go`'s
   `New` gains an optional second handler parameter (nil when there is no
   worker in this process); `runServe` passes it only inside the existing
   `if opts.work` branch. `internal/server/permissions.go` gets a second
   requirement — `PermissionRead`, the same tier `Health`/`WhoAmI` sit at —
   for `WorkerServiceProbeProcedure`.
   **Proof:** new spec in `internal/server` — a mux built with a worker
   handler answers `Probe`; a mux built without one (bare `serve`) 404s /
   `CodeUnimplemented`s on the same path. `internal/cli/serve_test.go`
   extended: `serve --work` mounts it, plain `serve` does not.

5. **`mill doctor` asks the socket first, falls back to local.**
   `probeSidecar`, `probeSigning`, `probeForge` in `internal/cli/doctor.go`
   call `WorkerService.Probe` over the already-resolved `--socket`; a
   `CodeUnimplemented`/`CodeNotFound` answer (no worker behind this socket)
   falls back to exactly today's local probing unchanged; any other RPC
   answer is the worker's own pass/fail, reported verbatim. This also
   covers the case where `doctor` runs on the worker's own host directly —
   it gets the same RPC answer a remote client would, which is the more
   authoritative one since it reads `--work`'s actual config rather than
   `doctor`'s own possibly-drifted flags.
   **Proof:** `doctor_test.go` gains cases: against a `serve --work`
   fixture with no local sidecar/signing/forge files at all, `sidecar` and
   `forge` pass (RPC-answered) and `signing` passes when the fixture's
   fake forge trusts the key with no checkout; against a fixture serving
   only `StoreService` (today's shape), all three probes behave exactly as
   the existing specs already assert — regression coverage, not new
   behavior.

6. **Gateway probe: document the header gap.** Comment in
   `internal/gateway/probe.go` beside the three headers it sets, stating
   plainly that `anthropic-beta`/`user-agent` are the CLI/SDK's own choice
   at request time and not a value mill holds, so the probe cannot mirror
   them; if a future mill-set env toggle changes what the CLI sends (the
   spike's `ENABLE_TOOL_SEARCH`, not yet implemented), this is where it
   would be threaded through. No behavior change.
   **Proof:** existing `gateway_test.go`/`doctor_test.go` gateway specs
   pass unchanged — this step is a comment and a docs line, verified by
   `make lint` (godot/comment linters) and no diff to test expectations.

7. **`docs/tools.md` §doctor.** Update the probe table for `sidecar`,
   `signing`, `forge` to say each is answered by the worker behind the
   socket when one is there, and locally otherwise; add the gateway header
   limitation as a line under that probe; update the worked `$ mill doctor`
   example if any line's wording changed.
   **Proof:** `doctor_internal_test.go`'s "probe names match usage and
   docs/tools.md §doctor" spec still passes; a human diff reads true
   against the code from steps 1–6.

8. **Whole-tree gate.** `make lint && make test`, plus `make lint-contract`
   for the report the proto change owes (not a gate, but the change must be
   named explicitly in the result per `AGENTS.md`).

## Risks

- **Proto change lands without being flagged.** `make lint-contract` only
  reports; the implementer's final message must name the new
  `WorkerService`/`ProbeRequest`/`ProbeResponse` explicitly, since nothing
  else will (`AGENTS.md`). Mitigation: it is called out as its own step (8)
  precisely so it isn't forgotten in a summary about doctor's UX.
- **`internal/doctor` importing `internal/harness/claude`,
  `internal/forge`, `internal/workspace/signing` from both `internal/cli`
  and `internal/server` creates a cycle.** Checked: neither `internal/cli`
  nor `internal/server` is imported by any of those three packages today,
  and `internal/server` currently imports none of them — so a new shared
  leaf package sits underneath both without issue. If `make lint`'s
  `depguard`/build disagrees, the fallback is to keep the server-side probe
  bodies as an unexported duplicate in `internal/server` rather than force
  a shared package — smaller, at the cost of the two copies drifting, which
  would need its own follow-up.
- **`server.New`'s signature change breaks an existing caller.** Only one
  call site was found (`internal/cli/serve.go`); `server_test.go` and
  `serve_test.go` are the specs that would catch a missed one.
- **GitHub's Contents API rate limit or a private-repo permission gap makes
  the new signing fallback flaky in real use**, distinct from the fake-server
  unit specs. Out of scope to fully harden here — `docs/tools.md`'s new line
  should say the fallback needs the same read permission `forge` already
  probes for (`Contents`, per `internal/forge/github/probe.go`'s
  `Permissions` table), so a failure there is diagnosable the same way a
  forge-probe failure already is.
- **The gateway fix is "just a comment."** A reviewer expecting code may
  read this as under-delivering against the deliverable's first clause
  ("the request carries the headers a session's request carries"). The plan
  takes the deliverable's own second clause ("or the reason it differs is
  written beside it") deliberately, because the alternative is fabricating
  values mill does not own — this is flagged here rather than discovered
  in review.

## Decisions

- **`WorkerService` lives in `proto/mill/v1/store.proto`, package `mill.v1`,
  not a new proto file.** The work order left the mechanism open ("a
  `Doctor` or `Probe` RPC the service answers"); one file keeps today's
  generated-code layout (`gen/mill/v1/...`) unchanged in shape, only larger.
- **The RPC answers for *this* process's worker only**, matching the MVP's
  one-worker-per-store topology (`docs/architecture.md` §"One binary, two
  faces"). It does not attempt to address a specific worker among several —
  that question doesn't exist until multi-worker does, and is out of scope.
- **GitLab gets no `ContentReader` in this change**, matching that it has
  no `Prober` either today; `probeSigning`'s repository fallback simply
  doesn't fire for a GitLab project, and fails naming that as plainly as
  `probeForge` already does for GitLab's missing `Prober`.
- **The gateway probe's header gap is closed by documentation, not by a
  synthesized header set.** No mill-owned header/env toggle exists today to
  thread through (`ENABLE_TOOL_SEARCH` is unimplemented); inventing values
  the CLI/SDK actually owns would be a maintenance liability disguised as a
  fix.
- **RPC failure semantics: `CodeUnimplemented`/`CodeNotFound` means "no
  worker here, probe locally"; any other error is the worker's own
  answer.** This is the smallest rule that distinguishes "old/bare server"
  from "worker says no" without a new sentinel field on the wire.
