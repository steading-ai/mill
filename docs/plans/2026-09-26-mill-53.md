# A re-pushed workflow version does not become the one runs select

## Approach

`store.PutWorkflow` (`internal/store/store.go:1808-1858`) is idempotent by
content hash: pushing a version already stored finds the existing row and
returns it untouched, reporting `unchanged`. Selection
(`GetNewestWorkflow`) and listing (`ListWorkflows`,
`internal/store/queries/workflows.sql:16-26`) both order candidates by
`created_at DESC, id DESC`, so whichever version was *first created* most
recently keeps winning — re-pushing an older version to make it authoritative
again does nothing, because nothing about that row changes.

The fix adds a second, genuinely mutable timestamp — `pushed_at` — that
selection and listing order on, while `created_at` keeps its existing,
documented meaning ("when this version was stored", `proto/mill/v1/mill.proto:745`)
untouched. `PutWorkflow`'s found-branch now touches `pushed_at` to `now()`
instead of leaving the row alone; the not-found branch inserts a new row,
whose `pushed_at` defaults to `now()` the same way `created_at` already does.

**Rejected: bump `created_at` itself on re-push, with no new column.** This
is the smallest possible diff — no migration, no index change, the existing
`ORDER BY created_at DESC` already does the right thing once the value moves.
It was rejected because it contradicts two things already on record: the
migration's own comment ("Never updated. A new definition with the same name
and scope is a new row...") and the proto field's doc comment ("When this
version was stored"). It would also make the fact this node's own acceptance
criteria state — "the last push wins, not the first creation" — impossible to
observe, since after a re-push there would be no way to tell a row's true
first-stored time from its latest push time; `list`'s `CREATED` column and
`show --view full`'s `stored` line would silently start meaning something
they do not say they mean. A new column keeps both facts visible and keeps
`created_at`'s contract exactly as documented.

**Rejected: a monotonic sequence counter instead of a timestamp.** Ties
between `pushed_at DESC` and the `id DESC` tiebreak are a real, if unlikely,
edge case (`id` is a ULID fixed at a row's original creation, so once a row
is touched its `id` no longer tracks its `pushed_at`; a value pushed at
exactly the same instant as a distinct row's creation could tiebreak toward
the newer *row* rather than the newer *push*). A `bigserial` counter bumped on
every `PutWorkflow` call, found or created, would remove the tie entirely.
Rejected for this fix's scope: `pushed_at` already has the same shape as
every other ordering column this schema uses (`workflows_name_scope_created_at_idx`,
`runs_ended_at_idx`), the tie window is microseconds and pushes are
operator-paced (seconds apart at the fastest, including in the spec this node
adds), and introducing a new column *kind* alongside the existing
`<timestamp>, id` convention would be a bigger, less consistent change than
the bug being fixed. Noted under Risks rather than solved.

## Steps

1. **Migration: add `pushed_at`, repoint the index, and grant the
   application role permission to touch it.**
   New `internal/store/migrations/00025_workflows_pushed_at.sql`:
   `ALTER TABLE workflows ADD COLUMN pushed_at timestamptz NOT NULL DEFAULT
   now();` then `UPDATE workflows SET pushed_at = created_at;` (backfills
   existing rows to their true creation time rather than the migration's own
   apply time — with the `id DESC` tiebreak already in place, this
   reproduces today's `created_at`-based ordering exactly for every row that
   has never been re-pushed, so the migration itself changes no run's
   selected workflow). Then `DROP INDEX workflows_name_scope_created_at_idx;`
   and `CREATE INDEX workflows_name_scope_pushed_at_idx ON workflows (name,
   scope, project, pushed_at DESC, id DESC);`, matching the comment already
   above the old index ("Resolving a name to its newest version in a scope").
   Finally, `GRANT UPDATE (pushed_at) ON workflows TO mill_app;` — a
   column-level grant, not a table-wide one:
   `internal/store/migrations/00012_grants.sql:18` gives `mill_app` (the role
   the service actually runs as) only `SELECT, INSERT` on `workflows`, and
   that migration has already shipped, so it is not edited here. Without this
   grant, `TouchWorkflow`'s `UPDATE` (step 2) would fail with "permission
   denied for table workflows" under real privileges the moment a directory
   already stored gets pushed again — the exact case this node exists to fix
   — even though every other step of this plan would look correct. The grant
   is scoped to the one column that is now genuinely mutable, so `definition`,
   `version`, `id`, `name`, `scope`, `project`, `source`, and `created_at`
   stay ungrantable to `mill_app` for `UPDATE`, keeping every other part of
   "a workflow row is never edited" exactly as true as it is today.
   `+goose Down` reverses all three in the opposite order: revokes the
   column grant, drops the new index, recreates the old one, drops the
   column.
   Files: `internal/store/migrations/00025_workflows_pushed_at.sql` (new).
   Test: `internal/store/migrations/migrations_test.go`'s existing up/down

## Risks

- **Timestamp ties between a touched row's `pushed_at` and a distinct row's
  `created_at`-derived `pushed_at` could tiebreak toward the wrong row via
  `id DESC`**, since a touched row's `id` (a ULID) still reflects its
  original creation, not its latest push. Accepted rather than solved with a
  sequence column (see Approach's second rejection): the window is
  microseconds and this schema's other ordering columns all use the same
  `<timestamp>, id` shape; if this ever proves live in practice, the fix is
  a `bigserial` push counter, additive and not a redesign of this change.
- **The migration backfills `pushed_at = created_at` for every existing row
  before repointing the index.** On a table with a very large number of
  workflow versions this is an `O(n)` rewrite; `workflows` holds one row per
  pushed version of a handful of named workflows per project, not a
  high-volume table, so this is not expected to be a real cost, but it is
  worth confirming row counts on a production-like database before running
  the migration there, since the plan does not have that number in hand.
- **`sqlc generate`'s exact output filenames for the new/changed queries in
  `workflows.sql`** are stated provisionally above (`db.gen.go` per
  `sqlc.yaml`'s `output_db_file_name`) and should be confirmed once
  regeneration is actually run, not assumed from the config alone.
- **Whether `internal/domain.Service.GetWorkflow` or some other layer between
  it and `internal/run`'s workflow selection does any caching or its own
  ordering** that this fix would not reach. Read at gather-context time:
  `internal/domain/workflows.go`'s `GetWorkflow` is a direct passthrough to
  `store.GetWorkflow` with no caching; nothing else sits between `store` and
  `internal/run`'s selection today. If implementation finds otherwise, that
  is new information changing this plan's step 3 test, not a reason to skip
  proving it at the store layer.

## Decisions

- **A new `pushed_at` column, not a repurposed `created_at`.** Chosen over
  the smaller diff of just bumping `created_at` because the work order's own
  acceptance language ("the last push wins, not the first creation")
  describes two facts that need to stay distinguishable, and the existing
  migration comment and proto doc comment already commit `created_at` to
  meaning first-stored time.
- **`created` stays `false` when a push only touches `pushed_at`.** The CLI's
  `stored`/`unchanged` reporting (`internal/cli/workflow.go`'s `stateOf`) is
  about whether a new version was created, which a touch does not change;
  re-pushing an unchanged directory still prints `unchanged`, now truthfully
  paired with the version actually becoming selectable again.
- **No new `mill workflow` verb to retire or unpin a version.** The work
  order names this gap but its acceptance criteria do not ask for a retire
  command — they ask that re-pushing make a version win again, which this
  plan delivers without one. Adding a retire verb is out of scope for this
  fix.
- **The new grant is column-level (`GRANT UPDATE (pushed_at) ON workflows TO
  mill_app`), not table-wide.** `internal/store/migrations/00012_grants.sql:18`
  deliberately grants `workflows` only `SELECT, INSERT` today, grouped with
  `evidence`, `events`, and `skills` — the append-only tables. A table-wide
  `UPDATE` grant would let the service role rewrite `definition`, `version`,
  or `source` on an existing row if a future bug tried to, which is exactly
  what the missing grant protects against today (Invariant-6-style: refused
  by the server's own privileges, not just by careful code). Scoping the
  grant to `pushed_at` gets `TouchWorkflow` working without opening that
  door.
- **The acceptance spec is written at the `internal/store` layer, calling
  `store.PutWorkflow`/`GetWorkflow`/`ListWorkflows` directly**, not through
  the CLI or a full run. `store.GetWorkflow` is the one place resolution
  logic lives (confirmed by reading `internal/domain/workflows.go`), so this
  is the layer closest to the actual bug and matches the existing sibling
  spec's own level in `store_test.go`.
