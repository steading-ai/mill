# The merge gate merges before it reads the head's checks

## Approach

Move the forge's status read from *after* the merge to *before* it, by
calling the run's own `r.verify` — the same `evidence.Verify(EVIDENCE_KIND_STATUS,
...)` path that already exists, with its existing bounded-pending and
`statusPolicy` semantics — from inside `mergeRetrying`, immediately before
every call it makes to `f.Merge`, not just the first. A check that succeeds
is carried forward (through a new field on `result`) so the generic
post-execute verification `walk.go` runs for every step is *skipped* for a
merge gate that already merged; a check that fails (including a bounded
pending wait timing out) becomes a `mergeFinding`, exactly the shape
`catchUpCheckError` (mill#52) already established, so `f.Merge` is never
called for that head and the run revises from `implement`; a check that is
still pending propagates as the same `*evidence.PendingError` the step
machinery already knows how to wait on and retry.

The first version of this plan placed the check once, before entering
`mergeRetrying`, and treated "the pull request was already merged when
`approve` looked" as needing no further attention. Review found both
insufficient: `mergeRetrying`'s own conflict handling can run a second
`catchUp` — a push that moves the head — and then retry `f.Merge` on that new
head with no check of its own (gate.go:161–165), and an attempt that finds
the pull request already merged (a worker that died between `f.Merge`
succeeding and the step closing on it, then resumed) skipped the check
entirely and still let the generic post-execute path re-read the forge and
turn a red result into a revise of an already-merged, already-closed branch
— precisely what the second acceptance criterion forbids. This version fixes
both: the check runs immediately before *every* `f.Merge` call, including
one after a conflict-triggered `catchUp`, and an attempt that finds the pull
request already merged builds its closing evidence from that fact directly,
without asking the forge again at all.

This was chosen over two alternatives (see the prior *Think* note for the
fuller comparison):

- **Add a checks read to `approve()` but leave the post-merge `r.verify()`
  call in `walk.go` untouched.** Satisfies the acceptance criterion about not
  merging a red head, but leaves a second, independent read of the same fact
  after the merge — exactly the shape of race this bug already is, just
  narrowed. Rejected: it does not satisfy "whatever the checks said
  afterwards" (AC2) as anything more than a probabilistic improvement.
- **Make the merge gate close itself directly, mirroring `resumeGate`'s
  direct-`closeStep` path, bypassing the generic `execute → verify → close`
  pipeline entirely.** The most symmetric fix, but it would require
  duplicating or reshaping the post-execute bookkeeping that pipeline already
  does unconditionally for every step kind (token revoke, usage recording,
  activity recording — `walk.go`'s `step()`, lines ~288–331) inside `runGate`
  instead. Rejected as more invasive than the problem requires: the chosen
  approach gets the same end state (no second forge read) by skipping only
  the one call that must not happen twice, leaving everything else generic.

## Steps

1. **Plumbing: let a step's evidence be handed in pre-computed, and let a
   step's own error carry a pending verdict.**
   Files: `internal/run/execute.go`, `internal/run/walk.go`.
   Add a `verified *evidence.Evidence` field to `result` (`execute.go`), with
   a doc comment restricted to its one caller: a gate step's approve already
   verified its own evidence — or established the merge as a fact no
   evidence read can unmake — before acting on it, and the generic
   post-execute verification must not ask the forge again. In `walk.go`'s
   `step()`, where `verified, verifyErr := r.verify(ctx, s, step, sr, detail,
   result)` is called: if `result.verified != nil`, use it directly and skip
   the call; otherwise call `r.verify` exactly as today. Widen the pending
   case correctly: build `cause := errors.Join(execErr, verifyErr)` once,
   test `evidence.Pending(cause)` for the branch condition, and use the same
   `cause` (not the bare `verifyErr`) for the `errors.As(cause, &pending)`
   inside the branch body that reads `pending.RetryAfter` — a pre-merge
   pending status now arrives as `execErr` from `execute()`, and a version of
   this widening that only changed the `case` condition would pass the
   branch test and then dereference a nil `*evidence.PendingError` reading
   `RetryAfter`.
   This step changes no observable behaviour by itself — nothing yet sets
   `result.verified` or returns a pending `execErr`.
   **Proof:** `make test` passes with no new or changed specs — the existing
   `internal/run` suite (in particular every `gate_test.go` spec) is green
   unchanged, showing the refactor is behaviour-preserving before the
   following steps give it something to do.

2. **Read the forge's checks immediately before every merge attempt, not
   after any of them.**
   Files: `internal/run/gate.go`.
   Add a `checksFailedError` (a `mergeFinding`, the same shape as the
   existing `catchUpCheckError`/`catchUpOverlapError`, gate.go:175–236),
   wrapping the `evidence.NotVerifiedError` a failed or timed-out-pending
   check produces; its `finding()` names what the forge reported and says
   nothing was merged. Add a small helper, `checkBeforeMerge(ctx, s, step,
   sr, detail, sha)`, that calls `r.verify(ctx, s, step, sr, detail,
   result{claim: sha})` and classifies the result: nil error → return the
   `evidence.Evidence` to use; `evidence.Pending(err)` → return the
   `*evidence.PendingError` unchanged; anything else → return a
   `checksFailedError`. Restructure `mergeRetrying` (currently
   gate.go:151–173) to call `checkBeforeMerge` on `pr.HeadSHA` once before
   its loop's first `f.Merge` call, and again on the (possibly new)
   `pr.HeadSHA` immediately after the `Conflict` branch's own `catchUp`
   (gate.go:161–165) and before it retries `f.Merge` — this is what "after
   any catch-up push" means literally: the outer catch-up `approve` already
   runs, and this inner one, both push before their next merge attempt.
   `mergeRetrying` returns the `*evidence.Evidence` of whichever check
   preceded the `f.Merge` call that actually succeeded, alongside the merged
   `forge.PullRequest`. Thread `sr` and `detail` into `approve` (both already
   available in `runGate`, which calls it) so they reach `mergeRetrying`;
   `approve` returns `(string, *evidence.Evidence, error)`, and `runGate`
   sets `out.verified` from the second value on success.
   A bare pending-mergeability refusal (no conflict, gate.go's existing
   `mergeRetryBudget` sleep-and-retry path) does not re-run the check: the
   head has not moved, so nothing new to ask the forge about — only a
   conflict's own `catchUp` re-triggers it.
   **Proof:** in `internal/run/gate_test.go`, alongside the existing
   `Describe("The merge gate absorbs the forge's own transients", ...)` and
   `Describe("Catching up with a moved target before merging", ...)` blocks:
   - `f.forge.checksAt = forge.Failed` before `Execute`: assert
     `f.forge.mergeCalls() == 0`, the `merge` step run is `FAILED`,
     `after(detail, "merge") == "implement"`, and the revised prompt names
     the forge's verdict — the node's own Gherkin scenario ("A red head does
     not merge"), closing AC1 and AC3 together.
   - the same shape with `checksAt = forge.Pending` and a workflow variant
     overriding `Status: &millv1.StatusPolicy{Interval, Timeout}` to a few
     milliseconds (mirroring how `f.variant` already mutates a step's field
     elsewhere in this file), so the bounded wait expires quickly: assert
     `mergeCalls() == 0` and the step ends as a finding once the bound is
     spent — proving "pending waits (bounded)" rather than merging early or
     hanging.
   - extending the existing "absorbs a conflict refusal by catching up again
     and merges once it clears" spec (gate_test.go:432–443): give
     `fixtureForge` a `checksQueue []forge.Status` (a sibling of its existing
     `refuseQueue`, consumed one status per `Checks` call and falling back to
     `checksAt` once exhausted — see step 4) set to `[]forge.Status{forge.Success,
     forge.Failed}`, so the first check (before the conflict) passes and the
     second (on the head the conflict's own catch-up produced) fails: assert
     the run never calls `Merge` a second time successfully (`mergeCalls()`
     stops at the refused attempt), the step fails and revises, and the
     finding names the new head — direct proof that a catch-up triggered
     *inside* the retry loop is checked too, closing the gap review found in
     the first version of this plan.

3. **An attempt that finds the pull request already merged does not ask the
   forge again.**
   Files: `internal/run/gate.go`.
   In `approve`, the `if !pr.Merged() { ... }` branch is where `catchUp` and
   `mergeRetrying` (and now the check) run; the `else` — the pull request was
   already merged when this attempt looked, which only happens when an
   earlier life of this same attempt (or an earlier attempt) already merged
   it and did not reach `closeStep` before the worker stopped — currently
   falls straight through to `f.MergeCommit` with no evidence at all, which
   is exactly what let the post-execute `r.verify()` in `walk.go` re-read a
   possibly-since-changed status and revise a branch whose pull request is
   already closed (the finding this step exists to fix). Build the STATUS
   evidence for this branch directly from the fact of the confirmed merge —
   `Kind: EVIDENCE_KIND_STATUS`, a `Status: "success"` value, `VerifiedBy`
   naming this routine rather than a check, `VerifiedAt` from `r.options.Now`
   — without calling `Forge.Checks` at all: the merge already happened, is
   irreversible, and per the second acceptance criterion nothing the forge
   says now is allowed to matter. Set this as the `*evidence.Evidence`
   `approve` returns alongside `pr.HeadSHA`.
   **Proof:** a new spec seeding `f.forge.merged = true` and
   `f.forge.pr.State = "merged"` before `Execute` (simulating an attempt that
   finds the merge already done, without needing to simulate a literal
   process crash), with `f.forge.checksAt = forge.Failed` — the case that,
   before this step, would still have revised: assert the run completes
   `RUN_STATUS_DONE`, not a revise, and `f.forge.mergeCalls() == 0` — direct
   proof for "once `MergeCommit` returns, the step closes on the merge,
   whatever the checks said afterwards" in the resume path specifically,
   which the first version of this plan missed.

4. **Prove a successful merge never reads the forge's checks after it has
   happened.**
   Files: `internal/run/support_test.go`, `internal/run/gate_test.go`.
   Add a `checksCalls()` counter to `fixtureForge`, mirroring the existing
   `mergeCalls()` (support_test.go:457–464): increment a counter in `Checks`,
   guarded by the same mutex, and expose it the same way. Add the
   `checksQueue []forge.Status` field step 2's third spec needs: `Checks`
   consumes one entry per call when the queue is non-empty, falling back to
   the existing `checksAt` (or `forge.Success` when that too is unset)
   otherwise — the same consumption pattern `refuseQueue` already
   establishes for `Merge`.
   **Proof:** extend the plain auto-approved-merge case already exercised by
   this file's `Describe("A predicate that holds", ...)` (or the "merges
   after catching up on a target that moved with no overlap" spec,
   gate_test.go:335) with `Expect(f.forge.checksCalls()).To(Equal(1))` once
   `f.runOf(ctx).GetStatus()` is `RUN_STATUS_DONE` — the concrete,
   falsifiable form of AC2 for the ordinary, no-retry path: the forge is
   asked about the head's checks exactly once, before the merge, and never
   again once it has happened. (A conflict-retry path legitimately calls
   `Checks` more than once — once per head it actually considers merging —
   which step 2's own spec already covers; the invariant this step proves is
   narrower and deliberately so: the head that ends up in `main` is never
   asked about twice.)

## Risks

- **The widened `Pending` branch in `walk.go` (step 1) could accidentally
  catch a pending verdict from some other evidence kind that was never meant
  to reach it via `execErr`.** Today only `verifyStatus` ever produces a
  `*evidence.PendingError`, and after this change the only caller that can
  put one on `execErr` is `mergeRetrying`'s new pre-merge check — but the
  branch itself doesn't distinguish the source. Mitigation: keep the check
  narrow (`errors.As` against the concrete `*evidence.PendingError` type, not
  a broader predicate) so it only ever fires for an actual pending-status
  error, from wherever it originates — which is the correct behaviour either
  way.
- **`checkBeforeMerge` being called from two places inside `mergeRetrying`
  (before the loop, and inside the `Conflict` branch) risks the two call
  sites drifting apart if one is edited without the other.** Mitigation: both
  go through the one helper function rather than duplicating the
  `r.verify`-plus-switch logic inline at each site, so there is exactly one
  place that decides what a check's outcome means.
- **`checksFailedError` needs to read cleanly as the step's failure message
  and the revise prompt both.** `catchUpCheckError`/`catchUpOverlapError`
  already establish the pattern of a distinct `Error()` (for logs) and
  `finding()` (for the implementer's next prompt); the new type follows the
  same split, so this is a known shape, not a new one.
- **On the failing path, `approve` returns no claim, so `walk.go`'s
  post-execute `r.verify()` still runs with an empty claim and joins a
  spurious "no commit was recorded to read checks for" refusal into the
  recorded failure cause.** The specs' assertions still hold — the finding
  the implementer sees comes from `res.feedback`, which `checksFailedError`
  sets directly — so this does not affect correctness of any acceptance
  criterion; left as-is rather than adding a further bypass for a failure
  path whose recorded-but-unused secondary reason is cosmetic, not wrong.
- **Podman/testcontainers must be available in the environment the proof
  runs in** (`make test` exercises the `db`-labelled specs this change's
  tests live under) — AGENTS.md names podman as the only assumed system
  package, so this is expected to already be true rather than a new
  dependency this plan introduces.

## Decisions

- **Reuse `r.verify`/`evidence.Verify(EVIDENCE_KIND_STATUS, ...)` for every
  pre-merge check rather than a second, hand-rolled call to
  `forge.Forge.Checks`.** The work order is silent on this; the default
  taken is to keep exactly one implementation of "what does `status`
  evidence mean and how long does a pending one wait," matching the
  workflow's configured `status.interval`/`status.timeout` rather than
  introducing a second, possibly-diverging bounded-wait implementation.
- **A conflict-triggered re-catch-up inside `mergeRetrying` gets its own
  check; a bare pending-mergeability retry (the head unchanged) does not.**
  The work order says the check runs "after any catch-up push" — a
  mergeability-pending refusal pushes nothing, so nothing new exists to ask
  the forge about; a conflict's own catch-up does push, and review confirmed
  this path was the gap in the first version of this plan.
- **An attempt that finds the pull request already merged builds its closing
  evidence from that fact, without calling the forge at all**, rather than
  calling it and discarding an unfavourable answer. The work order's second
  acceptance criterion is explicit that nothing the forge says after a merge
  may matter; not asking at all is the version of that with no room for a
  discarded answer to leak into a log line or a metric and be misread later.
- **`docs/domain-model.md` gets a one-line correction, not a rewrite.** The
  work order names no documentation deliverable, but the sentence it would
  otherwise leave incorrect ("approving it is what performs the merge",
  silent on when the forge is read) is the exact behaviour this change
  corrects; per AGENTS.md, a work order is the only reason to touch a design
  document, and this one gives reason enough for the one line describing the
  ordering this task changes — nothing else in that section is touched.
