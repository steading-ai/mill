# ListRuns: ended runs by filter and window, in keyset pages

## Approach

Add `ListRuns` as a new RPC that reuses the existing `Status`/`Inspect` derivation path (`internal/store/store.go`'s `summarize()`) rather than a batched or SQL-window-function alternative. Concretely:

- `last_step`/`last_step_status` cost nothing new to compute: `summarize()` already calls `latestState`, which runs `LatestStepRuns` (`DISTINCT ON (step_name) ... ORDER BY step_name, attempt DESC`) and hands back one `StepRun` per step name. Because attempts within one step are strictly time-ordered, the run-wide latest-started attempt is always one of these rows — so `last_step`/`last_step_status` is a max-by-`started_at` pass over data already in memory, not a new query.
- `rounds` needs `count(*) FROM step_runs WHERE run_id = $1 AND feedback_from IS NOT NULL` across *every* attempt, which `LatestStepRuns` does not carry (a step revised twice folds down to one row). This becomes one new one-row count query, in the exact shape of the existing `CountRunLeases` query, called from `summarize()` alongside it.
- `ListRuns` itself gets its own paged, filtered query and calls the same `summarize()` per row that `Status` and `Inspect` already use, accepting the same per-row (N+1) query cost they do.

Two alternatives were considered and rejected:

- **Batch the per-row derivations** (fetch the page's run rows once, then batch every side query with `WHERE run_id = ANY($ids)`, zip in Go). Rejected because it would give `RunSummary`'s new fields a second, parallel derivation path from `Status`/`Inspect`'s, which is exactly the kind of drift `docs/ledger.md` warns `current_step` off of by never storing it. Nothing in the work order or `docs/roadmap.md`'s M0 framing says this RPC is hit at a frequency where per-row queries matter yet; `docs/ledger.md` itself argues against building pagination/partitioning machinery ahead of a demonstrated need ("one operator running tens of runs a day does not justify the machinery"). If `ListRuns` at `limit=200` is ever shown to be slow, batching is a follow-up that does not change the RPC contract.
- **Push `rounds`/`last_step` into the main listing query as window functions.** Rejected because `current_step` still requires the decoded workflow definition (a Go-side JSONB decode), so `summarize()`'s Go path can't be retired either way — this would just add a second SQL-side derivation for two of the three new fields while leaving the third in Go, which is more moving parts for no simplification.

One ambiguity in the work order is resolved here rather than left implicit: a request whose `statuses` mixes terminal and non-terminal values, or is entirely non-terminal, cannot be ordered by `ended_at` (null on a live run). Decision: if every requested status is terminal (or the filter is empty, defaulting to all three terminal states), order and page by `(ended_at DESC, id DESC)`; if *any* requested status is non-terminal, order and page by `(updated_at DESC, id DESC)` instead, matching the work order's own note ("`ListRuns` with a non-terminal status in `statuses` orders those by `updated_at`"). This is implemented as two separate, single-purpose sqlc queries (`ListRunsByEnded`, `ListRunsByUpdated`) chosen in Go by inspecting the requested statuses, rather than one query with a `CASE`-driven `ORDER BY` and a dynamic tuple comparison — simpler to read and to prove correct, in keeping with the rest of `queries/runs.sql`.

## Risks

- **The cursor's tuple comparison (`(ended_at, id) < ($1, $2)`) needs both columns non-null for every row it's compared against.** `ended_at` is null on a live run, which is exactly why `ListRunsByUpdated` exists as a separate query keyed on `updated_at` (never null) instead of trying to make one query handle both orderings. If a future caller manages to request `ListRunsByEnded` while somehow including non-terminal statuses (a bug in the Go-side routing, not the SQL), the tuple comparison would silently drop rows with a null `ended_at` rather than error — worth a defensive spec (mixed statuses always route to `ListRunsByUpdated`) rather than trusting the routing logic by inspection alone.
- **`--since`'s existing meaning on `readOptions` may not transfer cleanly to `status --ended`.** `mill cost --since` almost certainly means "usage recorded at or after now-minus-duration" (an open-ended lower bound with no upper bound), while `status --ended --since 7d` needs `ended_after = now - 7d` specifically. If `cost`'s flag parsing already produces exactly a lower-bound `time.Time`, sharing `parseWindow` is fine; if `cost` bakes in cost-specific defaulting, `status` needs its own flag variable rather than overloading the shared one. Resolve by reading `runCost`'s use of `opts.since` (`internal/cli/read.go` around line 681-729) before writing `runStatus`'s version, in step 8, not by guessing here.
- **No existing test helper ends a run at a chosen `ended_at`, or drives a revise.** Both are needed for the acceptance criteria's exact scenarios (window boundary, tie-breaking, the failed-after-revise fixture) and don't exist in `helpers_test.go` today. This is flagged now so it isn't a surprise mid-implementation; it is ordinary test-fixture work, not a missing dependency that blocks the plan.
- **`RunSummary`'s new fields must not change `Status`'s or `Inspect`'s existing wire output for callers that don't look at them.** Since `summarize()` is shared, adding fields to its return value is additive by construction as long as no existing field's derivation is touched — the plan does not modify `CurrentStep`, `CurrentAttempt`, `Totals`, `Leases`, or `Workspace`.
- **`make lint-contract` is a report, not a gate** (per `AGENTS.md`/`proto/README.md`) — a genuinely breaking mistake would still commit. The plan's own discipline (additive field numbers, no renumbering, new RPC rather than changing `Status`) is what keeps it breaking-free; this is called out explicitly in the final report as `AGENTS.md` requires for any proto change.

## Decisions

- **Mixed or all-non-terminal `statuses` order and page by `updated_at`; all-terminal (including the empty/default case) order and page by `ended_at`.** Implemented as two separate sqlc queries chosen in Go, not one dynamic query, per *Approach*.
- **The cursor is an opaque base64 string, not a structured proto message** (unlike `Logs`'s caller-constructed `Cursor{step_run_id, seq}`): it encodes whichever sort column was used (`ended_at` or `updated_at`, RFC3339Nano) and the row's `id`, and is only ever replayed, never built by a caller. `ListRunsRequest.cursor` and `ListRunsResponse.next_cursor` are both `string`.
- **`view` is a plain `string` field on `ListRunsRequest`** (`"refs"`, `"summary"`, `"full"`, parsed the same way the CLI's existing `parseViewName` already does), not a new proto enum — there is no precedent for a view enum elsewhere in the contract, and the CLI's own vocabulary is already exactly these three strings. `refs` skips `summarize()`'s side queries entirely (returning only the `Run`); `summary` and `full` are identical for `RunSummary`, since — unlike `Inspect`'s `StepRunDetail`, which has heartbeats/environments to expand — `RunSummary` has nothing further `full` could add. This is called out in the proto comment so it isn't mistaken for an oversight later.
- **"limit above 200 is clamped, and the response says so"** is satisfied by adding `bool limit_clamped = 4` to `ListRunsResponse`, rather than overloading the `findings` field (typed specifically as `UndecodableWorkflow`, which clamping is not) or inventing a generic finding type the work order didn't ask for.
- **`ListRunsRequest` field list**: `repeated RunStatus statuses = 1; string project = 2; string node_ref = 3; string worker_ref = 4; string workflow_id = 5; google.protobuf.Timestamp ended_after = 6; google.protobuf.Timestamp ended_before = 7; int32 limit = 8; string cursor = 9; string view = 10;` — order follows the work order's own listing.
- **`ListRunsResponse` field list**: `repeated RunSummary runs = 1; string next_cursor = 2; repeated UndecodableWorkflow findings = 3; bool limit_clamped = 4;`.
- **No MCP tool for `ListRuns`.** `mill status` is already exposed over `mill mcp` (`internal/cli/mcp_tools.go`); the work order names only the RPC, the proto, and the `mill status` CLI surface as deliverables, not an MCP tool. Adding one would be a dependency the work order didn't name (`AGENTS.md`'s change-hygiene rule); left out, and easy to add later without touching this plan's shape.
- **The internal sqlc query already named `ListRuns`** (backing `Store.Status`, `internal/store/queries/runs.sql`) keeps its name. The two new queries are named `ListRunsByEnded`/`ListRunsByUpdated` to avoid a duplicate `Queries.ListRuns` method, even though the new proto RPC is also called `ListRuns` — the RPC name and the sqlc query name are different namespaces (`Store`/`StoreService` methods vs. sqlc `Queries` methods) and this collision is the only place that actually matters.
