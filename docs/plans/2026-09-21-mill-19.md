# MCP servers a session gets, global from the host and named by a workflow

## Approach

Split the work along the boundary the codebase already draws between mill and
the harness: **mill (Go) owns what MCP servers exist and are reachable this
run; the sidecar owns interpreting a step's own `mcp` and `tools.deny`
against that catalog.** Concretely:

- The worker's config file gets `mcp-servers` (command/args/env/global), and
  a workflow definition gets `mcp-servers` (the same shape, no `global`).
  Both are mill-side data — deployment configuration and workflow grammar —
  never read for their content by the loader beyond shape-checking, exactly
  like every other config key and every other part of a workflow document
  that is not a step's `harness` table.
- At run start, mill merges the host's servers (each carrying `global`) with
  the run's workflow's servers (`global: false`) into one per-run catalog and
  hands it to the adapter on `harness.Session`, which puts it on the wire as
  a new field on `Start`/`Resume`, sibling to `Workspace` — the same pattern
  `Workspace` already uses to hand a session "the entire environment" it is
  given, extended by one more piece of environment.
- `mcp: [names]` stays exactly where `tools`, `env`, and every other
  harness-specific knob already lives: inside the step's `harness.claude`
  options document, read and validated by nobody but the sidecar
  (`sidecar/src/options.ts`). The sidecar resolves the mounted set — every
  `global` server, plus every name the step's `mcp` lists, `PolicyError` on a
  name neither map defined — and reuses the exact mechanism `tools.deny`
  already has (`disallowedTools`) for the opt-out, since `sdk.d.ts` documents
  that a `mcp__server__*` spec there removes a whole server's tools.
- The per-run `<workspace-dir>/<run>/browser` directory is a new sibling to
  the existing `checkout`/`signing` directories the local and machine
  backends already keep beside a run's checkout (`internal/workspace/local/local.go`
  `checkoutDir`, `signingDir`; `internal/workspace/machine/machine.go`
  `SigningDir`) — the same "beside the checkout, never in it" rule, one more
  name.

**Rejected: sidecar resolves everything, host and workflow maps both cross
the wire raw** (approach 3 of the prior note). It costs the same proto
surface as the chosen approach, but `mill workflow push`'s collision check
still needs a separate read of the host's names at push time, so nothing is
saved — the merge logic just ends up duplicated on both sides of the pipe
instead of owned once, in Go, where `push` already runs.

**Rejected: put the catalog inside the options `Struct`** rather than as its
own proto field. It would avoid a proto change, but it means host
configuration would arrive at the sidecar disguised as if the step's own
document had asked for it, which breaks the documented rule that "nothing on
this side of the wire reads a key of [the options document]" — a reviewer of
`sidecar/src/options.ts` a year from now would have no way to tell a
step-authored key from an injected one.

**Rejected: teach the SDK a real per-server `cwd`.** It has none
(`McpStdioServerConfig` in `sdk.d.ts` is `command`/`args`/`env`/`timeout`/
`alwaysLoad` only) and is not ours to add. The plan wraps `command` in a
shell that `cd`s first instead (Decisions, below).

## Steps

1. **Proto: carry a per-run MCP server catalog to the sidecar.**
   `proto/harness/v1/harness.proto` gets a new message
   `McpServer { string command = 1; repeated string args = 2; map<string,
   string> env = 3; bool global = 4; }` and two new fields on both `Start`
   and `Resume`: `map<string, McpServer> mcp_servers = 10;` and
   `string mcp_dir = 11;` (the `browser` directory, absolute path, empty
   when the workspace has none). Regenerate with `buf generate` so
   `gen/harness/v1/harness.pb.go` and `sidecar/gen/harness/v1/harness_pb.ts`
   pick up the new types.
   **Proof:** `buf generate` runs clean; `go build ./...` and the sidecar's
   `tsc --noEmit` (or its build script) both succeed with the new generated
   types referenced nowhere yet.

2. **Worker config: `mcp-servers`.** `internal/cli/config.go`'s `Config`
   gets `McpServers map[string]McpServerConfig \`yaml:"mcp-servers"\`` where
   `McpServerConfig` is `{ Command string; Args []string; Env
   map[string]string; Global bool }`, following the file-only-key precedent
   of `nested_repos`/`skift_checkout` (no flag, since a map has no natural
   flag spelling).
   **Proof:** a config test decodes a fixture `config.yaml` with a
   `mcp-servers` block and asserts the struct; an unknown key beside it is
   still ignored as documented, unchanged.

3. **Workflow grammar: `mcp-servers` at the workflow level.**
   `proto/mill/v1/mill.proto`'s `Workflow` message gets a new message
   `McpServer { string command = 1; repeated string args = 2; map<string,
   string> env = 3; }` (no `global` — a workflow's servers are never
   host-global) and a field `map<string, McpServer> mcp_servers = N;` (next
   free number on `Workflow`). `internal/workflow/definition.go`'s
   `document` gets `McpServers map[string]mcpServerYAML
   \`yaml:"mcp-servers,omitempty"\`` beside `Steps`, with `toProto`/its
   inverse filling `millv1.Workflow.McpServers`. The loader does not
   validate names against anything at load time — collision with a host
   name is a push-time question (step 10), not a load-time one, matching
   the loader's existing rule of reading a document's own shape and nothing
   about the world it will run in.
   **Proof:** `internal/workflow/load_test.go` gets a case that round-trips
   a `workflow.yaml` carrying `mcp-servers` through `Load`/`toProto` and
   back via the existing pull path, unchanged in content.

4. **Go harness types and the adapter's wire-up.**
   `internal/harness/harness.go`'s `Session` gets `McpServers
   map[string]McpServer` and `McpDir string`, with a new `McpServer{Command
   string; Args []string; Env map[string]string; Global bool}` type beside
   `Workspace`. `internal/harness/claude/adapter.go`'s `wireStart`/
   `wireResume` (or wherever `Start`/`Resume` messages are assembled from a
   `Session`) fill the new proto fields from these.
   **Proof:** `internal/harness/claude/adapter_test.go` gets a case
   asserting a `Session` carrying one `McpServer` and an `McpDir` produces a
   `Start`/`Resume` message with `mcp_servers`/`mcp_dir` set accordingly —
   the same shape of test the file already has for `Workspace`.

5. **The per-run `browser` directory.** `internal/workspace/local/local.go`
   gets a `browserDir = "browser"` constant beside `checkoutDir`/
   `signingDir`, created alongside the checkout when a run's workspace is
   created, and exposed on whatever handle `internal/run/execute.go` already
   reads `Socket`/`Root` from (a new field or method, e.g. `BrowserDir`).
   `internal/workspace/machine/machine.go` gets the matching directory for
   the machine backend. `internal/run/execute.go` reads it into
   `Session.McpDir` beside where `Cwd: sessionCwd` is already set.
   **Proof:** a workspace spec (local and machine) asserts the directory
   exists after `Create`, sits beside the checkout (not inside it, so a
   `git status` inside the checkout never reports it — mirroring the
   existing signing-directory assertion), and is gone after `Destroy`.

6. **Run engine: merge the host and workflow catalogs.** Wherever
   `internal/run/execute.go` (or its caller, whichever already holds both
   the worker's `Config` and the run's loaded workflow definition) builds
   the `harness.Session`, merge `config.McpServers` (as given, `Global`
   already set from config) with the workflow's `McpServers` (forced
   `Global: false`) into `Session.McpServers`. Because `mill workflow push`
   (step 10) already refuses a name collision before a colliding workflow
   can be stored, the merge does not need to arbitrate a collision it should
   never see; take the workflow's entry over the host's on the same name
   defensively (Decisions).
   **Proof:** an `internal/run` spec starts a run whose workflow declares
   one server and whose config declares another (different names) and
   asserts both reach the built `Session`.

7. **Sidecar options: `mcp` in the harness options document.**
   `sidecar/src/options.ts` adds `mcp?: string[]` to `HarnessOptions` and a
   `case "mcp": options.mcp = stringsAt(key, value); break;` in
   `parseOptions`, following `tools`/`env`'s exact shape.
   **Proof:** the existing options spec gets cases for `mcp: ["x"]`
   accepted, and `mcp: "x"` (wrong type) refused with a `PolicyError` naming
   the key — the same pattern every other key in that file already has a
   case for.

8. **Sidecar: mount, allow, and wrap cwd.** `sidecar/src/session.ts`'s
   `Turn` gets `mcpServers: Record<string, {command, args, env, global}>`
   and `mcpDir: string`, filled in `turnOf` from the new proto fields.
   `buildOptions` computes the mounted set — every `global` entry, plus
   every name `declared.mcp` lists (`PolicyError` naming a name in neither
   map) — builds `options.mcpServers[name]` by substituting the literal
   token `${MCP_DIR}` in each server's configured `args` and `env` values
   with `turn.mcpDir`, and wrapping `command` so the spawned process's
   working directory is `turn.mcpDir` (Decisions: the SDK has no per-server
   `cwd`, so this is a shell wrapper). `mcp__<name>__*` is appended to
   `allowed` for every mounted server, the same list `TASK_TOOLS` already
   joins. The comment at `session.ts` line 353 ("No MCP server is
   registered…") is rewritten to describe this. `turn.mcpDir === ""` mounts
   nothing (no workspace directory to point servers at) — this only arises
   if step 5/6 wiring is incomplete, so it is a defensive empty case, not a
   feature.
   **Proof:** a `session.ts` unit spec: a turn with one `global` server and
   a step with no options mounts it and adds `mcp__x__*` to
   `allowedTools`; a turn whose step names `mcp: ["nope"]` throws
   `PolicyError` naming `nope`; a turn whose step sets
   `tools.deny: ["mcp__x__*"]` still builds `options.mcpServers.x` (it is
   spawned) but `disallowedTools` contains the deny spec, matching how a
   built-in tool is already denied without being un-mounted.

9. **Fake stdio MCP server + real proof of mount, deny, and cleanup.** The
   sidecar has no TypeScript test runner (`sidecar/package.json` declares
   only `build`/`typecheck`); every non-live sidecar behavior is asserted
   from Go, via `sidecar_test.go`'s Ginkgo specs driving the compiled
   `dist/spec/fake_main.js`, whose fake `QueryFn` (`sidecar/spec/fake_sdk.ts`)
   today only records the `Options` it was handed and plays back a scripted
   transcript — it does not act on `options.mcpServers`. Two additions,
   picking the mechanism the review asked for:
   - **Deterministic.** Add a fixture stdio server
     (`sidecar/spec/fixtures/fake-mcp-server.mjs`, answering `initialize`,
     `tools/list` with one tool, and one `tools/call`, per the node's Notes)
     and a new `MILL_FAKE_SCENARIO` (e.g. `"mcp-mount"`) in `fake_sdk.ts`
     that actually spawns each `options.mcpServers` entry as a child
     process, speaks the fixture's stdio protocol to it (`initialize`,
     `tools/list`), applies `options.allowedTools`/`disallowedTools` glob
     matching to the discovered `mcp__<name>__*` names the way the real SDK
     is documented to (Risks, wildcard item), and emits its init/system
     message with whatever survives. A `sidecar_test.go` case, using the
     existing `startRequest`/`settings()` pattern (`sidecar_test.go:118`),
     asserts the init message's tool list contains `mcp__fake__*` when
     nothing denies it, and does not when the step sets
     `tools.deny: ["mcp__fake__*"]`. The same scenario records the
     fixture's own PID to a file (matching the existing `PID_VAR`
     convention) and forwards a scripted `tools/call` to it, letting the Go
     spec assert a `tool_call`/`tool_result` pair on `s.events()` and, once
     `run` returns, that the recorded PID is no longer alive — proving "the
     server process is gone when the step ends" without a real SDK.
   - **Live.** Add one spec to `sidecar/live_test.go`
     (`Label("live")`, `Serial`, gated on `MILL_SIDECAR_LIVE` like its
     neighbors) that starts a real session with the same fixture mounted
     through actual `options.mcpServers`, asserting against the real SDK's
     own init message and the fixture's process exit — the part "no fake
     can assert" (`live_test.go`'s own stated rationale), covering whatever
     the deterministic fake's approximation of SDK tool-filtering might get
     wrong.
   Also confirms, as a read-only check rather than a code change
   (`handleMessage` already emits `tool_call`/`tool_result` for any
   `tool_use`/`tool_result` block regardless of name), the deliverable that
   the activity record and log treat an MCP call as any `tool_call`/
   `tool_result`.
   **Proof:** `go test ./sidecar/...` covers the new deterministic case in
   `sidecar_test.go`; `MILL_SIDECAR_LIVE=1` against the same suite (per
   `live_test.go`'s own gating) covers the live case. Together they close
   all three acceptance criteria the prior plan attempt left unprovable: the
   init message's tool list with and without `tools.deny`, and the process
   being gone when the step ends.

10. **`mill workflow push` refuses a colliding server name.**

    **Proof:** an `internal/server` (or `internal/cli/workflow_test.go`,
    whichever already drives `push` against a live store in a spec) case
    pushes a workflow whose `mcp-servers` names a server the fixture
    worker's config also names, and asserts the push is refused and stores
    nothing; a non-colliding push still succeeds unchanged.

    **Proof:** `internal/doctor`'s spec gets a case pointing a fixture host

## Risks

- **The wildcard `mcp__<name>__*` may not be honored by the top-level
  `Options.allowedTools`/`disallowedTools`** the way it is documented for
  `AgentDefinition.disallowedTools` (`sdk.d.ts`). If step 9's fake-server
  spec shows it is not, `buildOptions` must enumerate the mounted server's
  actual tool names (calling `tools/list` before the session starts, the
  same thing the doctor probe already has to do) rather than writing a
  glob — a materially bigger change to `buildOptions`, from "compile a
  static list" to "probe, then compile." Caught early by step 9 running
  before steps 10–12 are relied on.
- **The shell-wrap for `cwd` may not survive every server's argument
  shape** (spaces, globs, a command that is itself a shell one-liner).
  Mitigate by keeping the wrapper minimal (`sh -c 'cd "$1" && shift &&
  exec "$@"' sh <dir> <command> <args...>`, using `exec "$@"` so no
  further shell re-parsing happens) and covering it with the fake server,
  whose own args can include a space to catch a quoting mistake early.
  If the real Playwright server (stead's to provide) turns out to need its
  cwd for reasons this wrapper does not satisfy, that surfaces in stead's
  integration, not here — but the wrapper should be unit-tested against a
  fixture that actually checks `process.cwd()` inside the child, not just
  that the child started.
- **`mill workflow push`'s collision check assumes the RPC handler
  (`serve`) has the same `mcp-servers` config as the worker (`work`) that
  will run it.** True for every deployment this repo documents (`serve
  --work` in one process), but a `serve` fronting more than one `work`
  process with different configs would need per-worker collision data this
  plan does not model. Flagged as a Decision below rather than solved,
  since nothing in the repo today describes that topology.
- **The exact probe-registration shape in `internal/doctor` was not
  confirmed** during gather-context/think (only that the package exists);
  step 11 directs the implementer to read the existing pattern first
  rather than guessing one, so a mismatch here is a research gap to close
  at implementation time, not a design risk.
- **Regenerating proto touches two languages at once** (`gen/harness/v1`
  and `sidecar/gen/harness/v1`); a `buf generate` run that only regenerates
  one side (stale `pnpm install`/toolchain) would produce a Go/TS mismatch
  that only surfaces as a runtime decode failure. Mitigate by running the
  regen and both build steps (step 1's proof) before touching any code
  that depends on the new fields.

## Decisions

- **The wire shape is a Go-resolved catalog, not raw host/workflow maps.**
  The work order names the deliverables but not the wire; taking the
  smallest option consistent with the existing "sidecar only reads its own
  options document" rule (§Approach).
- **`${MCP_DIR}` is a literal substitution token** the mill replaces in a
  configured server's `args`/`env` values with the run's absolute
  `<workspace-dir>/<run>/browser` path, rather than mill hardcoding a
  `--output-dir` flag onto every server. The work order's wording ("Its
  working directory and `--output-dir` are `<workspace-dir>/<run>/browser`
  for every server") reads as a property every mounted server should have,
  but `--output-dir` is Playwright's own flag, not a generic MCP one; a
  substitution token lets a host's own `mcp-servers.playwright.args`
  declare `["--output-dir", "${MCP_DIR}"]` itself, keeping mill's mechanism
  generic. Actual process `cwd` is still forced to the same directory
  unconditionally, satisfying "working directory" for every server whether
  or not its args use the token.
- **A denied but mounted server is still spawned, only its tools are
  removed from the model's context** — matching how `tools.deny` already
  behaves for built-ins (`disallowedTools` removes from context; the SDK's
  own process, not ours, decides whether to still connect). Not spawning a
  denied server at all would save a process but adds a second code path
  (skip-mount vs. mount-then-deny) for a case the work order does not
  distinguish; the smaller option is one path.
- **On a same-name collision between a run's merged host and workflow
  catalogs at run time** (which `mill workflow push`'s check should prevent
  from ever being stored), the workflow's entry wins over the host's. This
  should be unreachable in practice; it is a defensive default, not a
  designed behavior, and is worth a comment saying so where it is written.
- **`mill workflow push`'s collision check reads the config of the `serve`
  process handling the RPC**, on the assumption (true of every deployment
  this repo documents) that `serve --work` is one process with one config.
  Recorded as a risk above rather than generalized to multiple workers,
  since nothing in the repo today needs that generalization.
- **The fake stdio MCP server fixture lives under `sidecar/spec/fixtures/`**
  rather than reusing `spikes/mcp/`'s scripts — the spike's server is a
  three-tool filesystem/exec stand-in for the *workspace socket* mount
  (a different node, mill#11), not a minimal `initialize`/`tools/list`/one
  `tools/call` fixture for this node's plain stdio servers. Building a new,
  smaller one avoids coupling this node's tests to a spike script that may
  change or be removed independently.
