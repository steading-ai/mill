# A revise verdict is evidence: Inspect returns a failed review attempt's findings

## Approach

Extend the existing evidence path so a revise verdict is written to the
`evidence` table on the step run it failed, instead of being discarded after
`attachVerdict`'s markdown artifact. `Inspect` already reads evidence
unconditionally (`internal/store/store.go` `Inspect`, ~line 2371-2390 —
`q.GetEvidence` runs regardless of the step's status), so once the row
exists, `mill inspect --view full` and `internal/cli/read.go`'s
`verdictValue`/`evidenceValue` render it with no further change — both are
already status-agnostic.

This requires four things to move together, in this order, because each is
the other's precondition:

1. `internal/evidence.verifyVerdict` must populate `.Value` for a revise
   decision (today it leaves it nil and only the `NotVerifiedError` carries
   the decision).
2. Domain-layer validation must accept a revise verdict on the *record but
   don't close* path, while still rejecting it on `CloseStepRun` — so the
   approve-only rule in `internal/domain/evidence.go`'s
   `EVIDENCE_KIND_VERDICT` case needs to split into a structural-only check
   (kind matches value, value present) reused by both paths, and a
   closing-specific check (decision must be approve) used only by
   `CloseStepRun`.
3. The evidence has to travel from `walk.go` (where `verify()` already
   produces it) through `revise.go`'s `failStep`, into
   `Service.FailStepRun` → `Store.FailStepRun` → a `FailStepRunRequest`
   proto field, because today nothing between those layers carries it.
4. The DB will reject the insert regardless of the Go-level plumbing: the
   deferred constraint trigger `evidence_closes_step_run`
   (`internal/store/migrations/00006_evidence.sql`) currently raises unless
   the target step run's status is `closed` at commit. This needs a new
   migration that narrowly admits `kind = 'verdict' AND status = 'failed'`
   in addition to the existing `status = 'closed'` case — narrow, not a
   blanket relaxation, so every other evidence kind (commit, exit,
   structured, url, status, artifact, gate) still can only land on a closed
   row.

`internal/run/breaker.go`'s in-memory `s.findings`/`roundsOf` reading and the
walk's supersede/on_failure/retry logic are untouched — this plan only adds a
row to the ledger describing what already happened; it changes nothing about
what a revise *does* to the run.

## Steps

1. **`verifyVerdict` sets `.Value` for a revise, not just for approve.**
   `internal/evidence/evidence.go`, `verifyVerdict()` (~line 512-571): in the
   `decision == "revise"` branch, build the same
   `&millv1.Evidence{Value: &millv1.Evidence_Verdict{Verdict: verdict}}`
   the approve branch already builds, assign it to the returned `Evidence.Value`,
   and keep returning the `NotVerifiedError` alongside it (the step still
   does not close — only the evidence shape changes). `Verify()` (~line
   296-311) already fills in `Kind`/`VerifiedBy`/`VerifiedAt` on any non-nil
   `.Value`, so no change is needed there.
   Files: `internal/evidence/evidence.go`.
   Test that proves it: `internal/evidence/evidence_test.go`, the existing
   spec at ~line 333-348 ("refuses a revise that blocks, and keeps the
   findings for the revise prompt") currently asserts
   `Expect(result.Value).To(BeNil())` — update this assertion to instead
   assert `result.Value` is non-nil, `result.Value.GetKind() ==
   EVIDENCE_KIND_VERDICT`, and `result.Value.GetVerdict().GetDecision() ==
   VERDICT_DECISION_REVISE`, while leaving the surrounding
   `MatchError(ContainSubstring("1 blocking finding"))` and
   `result.Verdict.GetFindings()` assertions as they are. This is a
   deliberate behavior change to a pinned test, not a regression.

2. **Split `ValidateEvidence`'s verdict rule into structural vs. closing.**
   `internal/domain/evidence.go`: in `validateValue()` (~line 79-127), the
   `EVIDENCE_KIND_VERDICT` case currently both confirms the value is a
   verdict (structural) and rejects non-approve decisions (closing-specific)
   in one place. Split this: `validateValue` keeps only the structural
   check (kind is verdict, value's oneof matches). Add a small unexported
   helper, e.g. `verdictCloses(evidence *millv1.Evidence) error`, called
   only from `ValidateEvidence`'s existing top-level path used by
   `CloseStepRun` — not from a new path used by `FailStepRun`. Add a new
   exported entry point, e.g. `ValidateFailureEvidence(evidence
   *millv1.Evidence) error`, that runs the structural checks only (kind set,
   value present, kind matches value — reusing whatever `validateValue`
   factors out) and explicitly does not call `verdictCloses` or
   `checkDeclaredKind`. `checkDeclaredKind` (~line 137-158) is not reused
   here: the run loop only ever attaches verdict evidence to a step already
   declared verdict-kind, by construction, so a workflow-lookup kind check
   adds no safety on this path and would need a second, needless DB round
   trip.
   Files: `internal/domain/evidence.go`.
   Test that proves it: extend `internal/domain/evidence_test.go` (or
   wherever `ValidateEvidence`'s existing table/spec lives — confirm exact
   file when writing) with a case asserting `ValidateFailureEvidence` accepts
   a revise-decision verdict evidence value that `ValidateEvidence` still
   rejects, and that `ValidateFailureEvidence` still rejects a
   structurally-broken value (kind/value mismatch), matching
   `ValidateEvidence`'s existing structural-failure cases.

3. **Thread evidence through `Service.FailStepRun` / `Store.FailStepRun`.**

   `internal/store/store.go`: `Store.FailStepRun` (~line 1010-1056) gains the

   Files: `internal/domain/steps.go`, `internal/store/store.go`.
   Test that proves it: `internal/store/store_test.go` gains a case

## Risks

- **DB trigger is the load-bearing piece and the easiest to get subtly
  wrong.** If the narrowed predicate in `00026` is written loosely (e.g.
  matching on step status alone, forgetting the `kind = 'verdict'` guard),
  every evidence kind could be inserted against a failed row, silently
  widening the ledger's meaning beyond what this node asks for. Mitigated
  by step 6's explicit "commit-on-non-closed still fails" and
  "verdict-on-running still fails" invariant cases, which fail loudly if the
  guard is too broad.
- **Migration reversibility**: getting `00026`'s Down wrong (e.g. `DROP
  FUNCTION` instead of restoring the original body) would break `00006`'s
  own future Down if migrations are ever rolled back past both. Mitigated
  by writing Down as a `CREATE OR REPLACE` restoring the exact original
  body, not a drop.
- **Double-setting `StepRunId` on the evidence value**: both `revise.go`
  (step 5) and `Store.FailStepRun` (step 3) touch `value.StepRunId`;
  redundant-but-harmless if both set it to the same id, but worth deciding
  explicitly which layer owns it when writing, to avoid confusion reading
  the diff later (leaning: store layer only, matching `CloseStepRun`'s
  existing precedent where the domain/run layers pass the evidence through
  unmodified and the store sets the id right before insert).
- **`ValidateEvidence` vs `ValidateFailureEvidence` naming/shape drift**:
  if the structural checks the two functions share are duplicated instead
  of factored into one helper, a future change to the verdict shape could
  fix one path and silently miss the other. Mitigated by extracting a
  shared unexported structural-check helper in step 2 rather than
  copy-pasting.
- **Blast radius of the `FailStepRun` signature changes** is bounded and
  already enumerated: 5 direct Go call sites in `internal/store` tests plus
  1 production call site in `internal/domain/steps.go`; RPC-based test call
  sites (`internal/cli/read_test.go`, `internal/cli/tools_support_test.go`,
  `internal/run/support_test.go`) use named-field proto struct literals and
  are unaffected by the new optional proto field.
- **Existing pinned test must change, not just gain new tests**:
  `internal/evidence/evidence_test.go`'s `Expect(result.Value).To(BeNil())`
  encodes the pre-fix behavior; if step 1 lands without step-1's paired test
  edit, CI fails on an existing spec rather than the new one, which is the
  intended signal that the fix and its test travel together.
- **Scope discipline**: `internal/run/breaker.go`'s in-memory
  `s.findings`/`roundsOf` reading (mill#77's concern) and the
  supersede/on_failure/retry decision logic in `walk.go` must not change —
  this plan only adds an evidence row describing a revise that already
  happened; verified in Think/Plan that `predicate.go`'s gate auto-evaluator
  (the one existing consumer that implicitly assumes "evidence ⇒ closed")
  is safe unchanged, since it only evaluates after a step has structurally
  closed.

## Decisions

- **Approach chosen: extend the existing `evidence` table/proto path**
  (write a real evidence row on failure), over alternatives considered and
  rejected in the Think step (e.g. relying solely on `attachVerdict`'s
  markdown artifact, or inventing a parallel non-evidence read path for
  `Inspect`) — the proto and store already have the shapes; the gap is
  narrow and DB-enforced, not architectural.
- **Validation split over a boolean parameter**: `ValidateFailureEvidence`
  is a new, separate exported function rather than `ValidateEvidence(e,
  closing bool)` — keeps `CloseStepRun`'s call site unchanged and makes the
  two call sites' intent readable without inspecting a flag's meaning.
- **`checkDeclaredKind` not reused for the failure path**: the run loop only
  ever attaches verdict evidence to a step already declared verdict-kind by
  construction (it comes from `verify()`'s own parse of that step's
  session output), so a second workflow-lookup check on the failure path
  would be redundant, not defensive.
- **Migration scoped to `kind = 'verdict'` only**, not a blanket
  "any evidence on a failed row" relaxation — every other evidence kind
  (commit, exit, structured, url, status, artifact, gate) still only closes,
  per the work order's explicit framing that this is about verdicts
  specifically, and per Invariant 5's original intent that evidence marks
  closure except where this node carves out one named exception.
- **`docs/domain-model.md` and `docs/ledger.md` left unedited** despite
  becoming stale ("evidence... closes a step" / "one row per closed step
  run") — only `docs/architecture.md` is named in the work order's
  deliverables; expanding scope to other docs is left as a follow-up
  observation, not silently absorbed into this plan.
- **`internal/run/predicate.go` and `internal/cli/read.go` require no
  changes** — confirmed in Gather Context/Think: `Inspect` is already
  status-agnostic about evidence, the CLI's `verdictValue`/`evidenceValue`
  already render a revise decision with its findings, and the gate
  auto-evaluator's "evidence ⇒ closed" assumption is safe because it only
  runs after a step has structurally closed.
