# A drain waits on parked, cancelled and stale runs that no worker holds

## Approach

Two mechanisms exist today, and they are not equally broken.

`Worker.inFlight` (`internal/run/worker.go`) — what `mill drain [--wait]` and
`WorkerService.Probe` report — is already precise: it is a process-local
`sync.Map` populated only on a successful `skift` claim (`spawn`, `reclaim`)
and emptied the instant the goroutine driving that node returns (park's
`errReleased`, a drain's boundary release, a close). It never contains a run
this process does not itself hold, so a parked, cancelled, or another
worker's stale run can never sit in it. This was confirmed by reading
`spawn`, `reclaim`, `State`, `breaker.go`'s `park`, and `walk.go`'s
mill#70 boundary release — not inferred from the doc comments alone.

The actual counting bug lives outside this checkout. `stead`'s follower is
`/usr/local/bin/stead-guest` (`stead-guest.service`, `ExecStart=... guest
follow`), and its stripped symbol table names `ai/cli/internal/follow.millDrain`,
`.statusInFlight`, `.parseInFlight`, `.InFlight`, `.Follower.tickDraining` —
and no `Probe`/`WorkerService` symbol anywhere. It derives "in flight" by
running `mill status` and parsing rows, not by polling `Probe`. That code is
in the `steading` repo, which has no source checkout on this machine (only
the built RPM), so it cannot be changed from here.

Given that split, the approach is: **(1)** add the test coverage the
acceptance criteria ask for, against the mechanism that is actually already
correct (`Worker`/`Probe`/`mill drain --wait`) — this is real, provable
work, not a formality, since nothing currently pins this behaviour; **(2)**
give `mill status` an operator- and follower-consumable "held" distinction,
computed from ledger columns the store already has, so a human reading
`mill status` — and a future fix to the follower — can tell a run this
process is actively driving apart from a parked, cancelled, or orphaned one,
without guessing at lease liveness the ledger cannot judge (`store.go`'s own
`claimableStatuses` comment: "Whether a lease has expired is skift's
judgement, not the ledger's"). This second part cannot close the loop by
itself — a run whose worker died with its lease neither aborted nor yet
expired in skift's eyes is indistinguishable from a genuinely running one
using ledger columns alone, and that gap is deliberately left to skift
rather than papered over with a local TTL guess (see *Decisions*).

**Rejected: teaching `Store.Status` a local TTL/staleness heuristic**
(comparing `updated_at` against a guessed lease TTL, mirroring `sweep.go`'s
own staleness check) to fully close the "stale" case in `mill status` too.
Rejected because the codebase has already drawn this line once
(`claimableStatuses`'s comment) and drawing it differently here would silently
contradict that precedent, plus it would require either duplicating skift's
TTL as a second source of truth or querying skift per row from a read path
that today only touches the ledger — too large for a quick fix, and it still
would not be as precise as `Worker.inFlight` already is for free.

**Rejected: fixing this only by asking `steading` to switch the follower to
`Probe`.** Correct in spirit (`Probe` needs no heuristic and already handles
all three cases, including "stale", since it never claims a lease it does
not hold), and worth recommending, but not implementable from this
checkout — no `steading` source exists here, only its compiled binary. Left
as a follow-up recommendation, not a step, so this plan does not claim
credit for a change it cannot make.

**Rejected: the smallest thing (tests only, no `mill status` change).**
Would satisfy acceptance criteria 1/2/4 to the letter but leave deliverable 2
("mill status… say separately how many parked or unowned runs exist")
completely unaddressed, and leaves an operator staring at `mill status`
with the exact same misreading the follower has. Cheap, but it does not
touch the part of the problem that is actually reachable from this repo.

## Steps

1. **Lock in `Worker`/`Probe`/`mill drain --wait`'s existing precision with tests.**
   `internal/run/worker_test.go` (or a new `internal/run/drain_test.go` beside
   it, matching the file-per-concern pattern `reclaim_test.go` already uses):
   add a `parkedRun` fixture helper mirroring `reclaim_test.go`'s existing
   `abortedRun`/`drainedRun` (`CreateRun` → `SetLease` → `StartStepRun` →
   `Park`, leaving `status: parked`, `lease_id` cleared, a `gate_node_id`
   set). Reuse `abortedRun` as-is for the "cancelled" shape the work order
   describes (`status: running`, last attempt aborted, no current claim) —
   it already produces exactly that row.
   - Scenario for acceptance criterion 1: start a worker with one real
     in-flight step (a fake harness held open, the same pattern
     `worker_test.go`'s existing specs already use), seed several
     `parkedRun`/`abortedRun` rows under other node refs the worker is not
     driving, call `Drain()`, let the held session close, and assert
     `State()` reaches `WORKER_STATE_IDLE` at that boundary — well inside
     the spec's own patience, never at a drain timeout — and that
     `InFlight()` never named the seeded rows at any point polled.
   - Scenario for acceptance criterion 2: seed only `parkedRun` rows (no
     live claim at all), call `Drain()`, and assert `State()` reports
     `WORKER_STATE_IDLE` immediately (no polling loop needed to observe it).
   - **Proof:** `make test-db` (Ginkgo, `Label(testsupport.DBLabel)`) passes
     both new specs; if writing them surfaces an actual bug in `worker.go`/
     `walk.go` (contrary to the read above), fix it here and note the
     surprise — do not let the test bend to match a bug.

2. **Add `RunSummary.held` to the contract.** `proto/mill/v1/mill.proto`:
   add `bool held = 10;` to `message RunSummary` (next free field number
   after `rounds = 9`), documented as computed, not stored, and naming
   exactly what it does and does not detect (see the doc comment drafted in
   *Files* below — it is the honest version of this plan's *Decisions*
   section, in the contract itself). Run `make generate` to regenerate
   `gen/mill/v1/*.go` and `gen/mill/v1/millv1connect/*.go`.
   - **Proof:** `make check-generated` reports nothing stale; `go build
     ./...` succeeds with the new field's generated accessors present.

3. **Compute `held` in the store.** `internal/store/store.go`'s
   `summarize()`: derive `held` from data already loaded there —
   `state.Run.GetStatus()` in (`SELECTING`, `RUNNING`), `state.Run.GetLeaseId() != ""`,
   and `lastStepStatus != STEP_RUN_STATUS_ABORTED` (the same predicate
   `Runner.Resumable`, in `internal/run/reclaim.go`, already uses to
   recognize this exact "aborted, no worker" shape — reuse the concept, not
   the code, since `Resumable` is scoped to one `worker_ref` and `held` is
   not). Set it on the `RunSummary` literal alongside the existing fields.
   - Store-level tests (new cases in `internal/store/store_test.go` or a
     sibling file, following the existing `l.store.Park(...)`-direct style
     used in `store_test.go`/`rerun_test.go`): a plain running run →
     `held == true`; a parked run (`Store.Park`) → `held == false`; a run
     with an aborted last attempt and no lease (mirroring `abortedRun`'s
     shape at the store layer) → `held == false`; a drain-released run
     (`ReleaseLease`, lease cleared, status still `running`) → `held ==
     false`.
   - **Proof:** `make test-db` (the `internal/store` Ginkgo suite) passes,
     including the four new cases.

4. **Surface the split in `mill status`.** `internal/cli/read.go`'s
   `runStatus`: after `renderStatus` prints the table, print one summary
   line counting `held` vs. not, across the listed rows — e.g. `3 held, 2
   parked or unowned`. Keep the existing table columns and every existing
   view (`refs`/`summary`/`full`) untouched: the acceptance criterion asks
   for a count an operator can read at a glance, not a new column that
   would ripple through every positional-cell assertion the current
   `read_internal_test.go` specs make (see *Decisions*).
   - Extend `internal/cli/read_internal_test.go` with a case built the same
     way `inspectOf`/`machineWorkspace` already compose fixtures by hand:
     a `RunSummary` slice mixing `held: true` and `held: false` rows,
     asserting the summary line's counts.
   - **Proof:** `make test-unit` (the `Label("unit")` suite `read_internal_test.go`
     lives in) passes the new case.

5. **Document it.** `docs/tools.md`'s `mill status` section: add the new
   summary line to the sample output block and one sentence explaining
   `held` (a run this process, or the one it queried through, can confirm
   is actually being driven right now — and the one case it still cannot
   rule out: a lease a dead worker never released and skift has not yet
   expired, which is why a real drain still needs `mill drain --wait`, not
   `mill status`, for a guaranteed answer). No code; proof is a careful
   read against step 4's actual output.

## Risks

- **`held`'s predicate still misses the "dead worker, unexpired lease"
  case**, by design (see *Approach*). Risk: someone reads `mill status`'s
  "N held" and trusts it as a complete drain-readiness signal, the same
  mistake the follower currently makes. Mitigation: the proto doc comment
  and `docs/tools.md` say explicitly what this does not detect, and point
  at `mill drain --wait` as the mechanism with no such gap.
- **This does not close the work order's own acceptance criterion 3 or its
  evidenced production symptom**, since the fix that would (the follower
  switching off `parseInFlight`/`statusInFlight` to `Probe`, or at least to
  the new `held` field) lives in a repo not present here. Mitigation: say so
  in the *Proof* section rather than claim completion; the follow-up is
  visible to whoever reads this node next, phrased as a recommendation, not
  invented code in a repo this session cannot see or test.
- **Step 1's tests might already pass with zero production change**, which
  could look like busywork. It is not: nothing currently pins this
  behaviour, and the work order's own acceptance criteria ask for exactly
  these tests. If they somehow fail, that is the more urgent finding and
  changes this plan's priority — fix `internal/run` first, `mill status`
  second.
- **`buf generate` / `sqlc` tooling availability.** `make generate` depends
  on `buf` (and its plugins) being on `PATH`; if the sandbox this runs in
  lacks it, step 2 cannot regenerate and the plan should say so rather than
  hand-write generated code.

## Decisions

- **No table column for `held`; a summary line only.** The work order asks
  `mill status` to "say separately how many parked or unowned runs exist" —
  a count, not necessarily a per-row marker. Adding a column would touch
  every view (`refs`/`summary`/`full`) and the existing positional-cell
  assertions in `read_internal_test.go` (e.g. `cells[len(cells)-6:]`),
  which is more blast radius than this deliverable needs. The `held` field
  is still on the wire for any future per-row consumer (a `--view full`
  addition, or the follower reading structured output directly).
- **`held`'s predicate is ledger-only, no skift call, no local TTL guess.**
  Matches `store.go`'s own precedent that lease liveness is "skift's
  judgement, not the ledger's." Accepted cost: the "dead worker, unexpired
  lease" case is not distinguishable by `mill status`, only by `mill drain
  --wait`. Documented rather than hidden.
- **The follower (`steading`/`stead-guest`) is out of scope for this node's
  code**, since its source is not checked out on this machine (verified by
  grepping the installed binary's symbol table for `follow.*` and finding
  no `Probe`/`WorkerService` reference at all). This plan produces the
  signal a follower-side fix would consume and says so; it does not invent
  or guess at `steading` source to patch blind.
- **`internal/run/reclaim_test.go`'s `abortedRun` is reused as-is for the
  "cancelled" test shape**, rather than adding a new `Cancel`-RPC-driven
  fixture, since the row it produces (`status: running`, aborted last
  attempt, current claim absent) is structurally identical to what the work
  order's evidence describes for a cancelled run. Named explicitly so a
  reviewer can see the two are being treated as one case on purpose.
