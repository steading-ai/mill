# The built mill, sidecar and workflows are published to GHCR on every push to main

## Approach

Build both architectures sequentially on one `ubuntu-latest` job, push each
as an ephemeral per-arch tag with `docker buildx build --push`, then combine
them into the real tags with `docker buildx imagetools create`. This is the
standard, most-documented path for "multi-arch manifest to a registry with
`GITHUB_TOKEN`" and needs no QEMU: the Containerfile only `COPY`s pre-built
artifacts, so nothing in the image build executes target-architecture code.

Rejected:

- **A single `docker buildx build --platform linux/amd64,linux/arm64`
  invocation.** This needs both architectures' staged trees present in the
  build context at once. The existing `package-%` Makefile target
  deliberately reuses one `dist/stage` directory serially across
  architectures (its own comment: "share one staging tree, so they are
  built one after the other"), and duplicating that into two directories
  just to satisfy one buildx call is more moving parts than the problem
  needs.
- **A two-job matrix that pushes each architecture by digest and combines
  them in a follow-up job (Docker's own documented multi-platform
  recipe).** More robust against tag clutter, but doubles the CI wiring
  (matrix job, artifact upload/download of digests, a combining job) for a
  private repo whose Actions minutes are explicitly called out as metered.
  The single-job, sequential-build-then-`imagetools create` version reaches
  the same published result with one job and no artifact transfer; the
  cost is two harmless, ephemeral `:<sha>-amd64` / `:<sha>-arm64` tags left
  in the package's tag list alongside the real ones.
- **`podman build` + `podman manifest create/add/push` for the whole
  pipeline**, matching the podman-only tooling `images/base/Containerfile`
  and the Makefile use elsewhere. Rejected because GHCR multi-arch manifest
  pushes from GitHub Actions are a far less trodden path with podman than
  with `docker buildx`, which is preinstalled on `ubuntu-latest` runners
  specifically for this job; AGENTS.md's podman assumption is scoped to
  local dev and testcontainers, not a CI policy, and the published image is
  identical either way — the acceptance scenario itself verifies the
  result with `podman run`, not with whatever built it.
- **Bundling a Node runtime (distroless base) so the image can run
  `mill serve` directly.** The deliverable frames the image as a
  distribution of files ("consumers copy the binary out... or run it, as
  they choose"), and the only acceptance test that runs the container
  (`podman run ... mill version`) never touches the sidecar. `mill version`
  needs nothing beyond the static binary, so `scratch` is enough; the
  sidecar's own JS runtime is the consumer's concern, same as any
  `node_modules` tree shipped as files.
- **Running `make package-<arch>` in CI as-is and discarding the `.rpm`.**
  Works, but needs `nfpm` on the runner for an artifact the workflow throws
  away, and buries "what the container actually needs" inside a target
  that also does unrelated packaging work. Extracting the staging half of
  `package-%` into its own `stage-%` target is a small, faithful reading of
  "build the same staged tree the package target stages" and removes the
  unnecessary `nfpm` dependency from the publish workflow entirely.

## Steps

1. **Split `package-%` into `stage-%` (the cross-compile + sidecar staging)
   and `package-%` (which now just depends on `stage-%` and runs `nfpm`).**
   `Makefile`: move every line of the current `package-%` recipe up to and
   including the `claude-agent-sdk-linux-*-musl` cleanup into a new
   `stage-%: sidecar-build` target, unchanged in content — same `$(STAGE)`
   path, same commands. `package-%` becomes `package-%: stage-%` followed
   by the `mkdir -p $(DESTDIR)` and `nfpm package` lines only. No output
   path changes, so `packaging/nfpm.yaml`'s `src: dist/stage/...` entries
   need no edit.
   **Proof:** `make package` still passes `package_test.go` unchanged (it
   only asserts on the produced `.rpm`s' contents, not on intermediate
   targets) — `make test-unit` covers it (Ordered `Describe("The package")`,
   `Label("unit", "slow")`). Additionally, `make stage-amd64` run alone
   leaves `dist/stage/mill` and `dist/stage/sidecar/dist/main.js` in place
   with no `.rpm` produced in `dist/`.

2. **Add `packaging/Containerfile`, and a Ginkgo spec that builds and
   inspects it.** `scratch` base; `ARG REVISION` and
   `LABEL org.opencontainers.image.revision=${REVISION}` (plus
   `image.source` pointing at the repository, matching the pattern
   `packaging/nfpm.yaml`'s `homepage:` already sets); `ENV PATH=/usr/local/bin`
   so `mill` resolves as a bare command the way the acceptance scenario
   invokes it; `COPY dist/stage/mill /usr/local/bin/mill`,
   `COPY dist/stage/sidecar /usr/local/libexec/mill/sidecar`,
   `COPY workflows /usr/local/share/mill/workflows`. No `ENTRYPOINT`/`CMD` —
   the acceptance scenario runs `podman run --rm <image> mill version` as a
   full command, which only works if nothing already occupies the entry
   point.

   Add `containerfile_test.go`, mirroring `package_test.go`'s
   build-once-inspect-many shape (`Describe("The container image",
   Label("unit", "slow"), Ordered, ...)`, `BeforeAll` builds once, every
   `It` reads the result): `dir := checkout()`, `makeTarget(dir,
   "stage-amd64")`, then `podman build -f packaging/Containerfile
   --build-arg REVISION=<a test SHA> -t mill-ci-test <dir>`. `scratch` has
   no shell, no `cat`, no `ls`, so the specs cannot `podman run` an
   inspection command inside it — they inspect from outside instead:
   - `podman run --rm mill-ci-test mill version` (this *is* a real exec of
     the image's one binary, not a shell command, so it works on `scratch`)
     — its output matches `make -s version` run in the same checkout,
     proving the version stamped in the image is the one the build was
     for.
   - `podman create --name <id> mill-ci-test` (creates, does not start —
     nothing executes inside the image) then `podman export <id> | tar -tf
     -` lists the flattened filesystem; asserts it contains
     `usr/local/bin/mill`, `usr/local/libexec/mill/sidecar/dist/main.js`
     and `usr/local/share/mill/workflows/feature/workflow.yaml`, then
     `podman rm <id>` in `DeferCleanup`. Proves the three deliverable paths
     without executing anything inside a shell-less image.

   **Proof:** `make test-unit` (or `ginkgo -focus "The container image"`)
   — both `It`s above pass. Locally, the same two commands run by hand
   after `make stage-amd64 && podman build -f packaging/Containerfile
   --build-arg REVISION=$(git rev-parse HEAD) -t mill-ci-test .` reproduce
   what the spec checks.

3. **Add `.github/workflows/publish.yml`, and a Ginkgo spec that reads it
   as data.** Trigger `on: push: branches: [main]` only (no `pull_request`,
   satisfying that acceptance criterion by construction). `permissions:
   contents: read, packages: write`. Steps: `actions/checkout@v4` with
   `fetch-depth: 0` (the `VERSION` computation in `Makefile` needs the
   `v*` tags reachable, or every image reports `0.0.0+dev.0.<sha>` instead
   of the real series); `jdx/mise-action` (or equivalent) to install the
   pinned toolchain from `mise.toml`; `actions/cache` for `~/go/pkg/mod` +
   the Go build cache keyed on `go.sum`, and for the pnpm store keyed on
   `sidecar/pnpm-lock.yaml`, per the work order's note on metered minutes;
   `docker/setup-buildx-action`; `docker/login-action` against `ghcr.io`
   with `${{ github.actor }}` / `${{ secrets.GITHUB_TOKEN }}`; a loop over
   `amd64` and `arm64` that runs `make stage-$arch` then `docker buildx
   build --platform linux/$arch --build-arg REVISION=${{ github.sha }}
   --file packaging/Containerfile --tag
   ghcr.io/steading-ai/mill:${{ github.sha }}-$arch --push .`; a final
   `docker buildx imagetools create --tag ghcr.io/steading-ai/mill:${{
   github.sha }} --tag ghcr.io/steading-ai/mill:main
   ghcr.io/steading-ai/mill:${{ github.sha }}-amd64
   ghcr.io/steading-ai/mill:${{ github.sha }}-arm64` to publish the two
   real tags as one multi-arch manifest list.

   Add `publish_test.go`, `Label("unit")` (no build, no podman — reads
   committed text, so it runs in every `make test`/`make test-unit`
   invocation, fast): parses `.github/workflows/publish.yml` with
   `gopkg.in/yaml.v3` (already a dependency — `internal/cli/config.go`,
   `internal/workflow/definition.go`) into a generic `map[string]any` and
   asserts:
   - the trigger has a `push` key naming `branches: [main]` and has no
     `pull_request` key at all (the "runs nothing on pull requests"
     criterion, checked structurally rather than by reading the YAML by
     eye).
   - `permissions` is exactly `{contents: read, packages: write}` — no
     other key.
   - the raw file text matches `ghcr\.io/steading-ai/mill:\$\{\{\s*github\.sha\s*\}\}` and
     `ghcr\.io/steading-ai/mill:main` (the tag scheme criterion) and
     `--file packaging/Containerfile` (wires to step 2's file).
   - the raw file text's only `secrets\.[A-Z_]+` match is
     `secrets.GITHUB_TOKEN` — "no other secret" as a regression-proof
     assertion, not just a claim in prose.

   **Proof:** `make test-unit` — `publish_test.go`'s spec passes; a
   deliberate edit (e.g. adding `pull_request:` to the trigger, or a second
   secret) fails it, which is the point: the criteria now live in `make
   test`, not only in this plan. Full end-to-end verification (criterion 1
   and the Gherkin scenario's actual pull from `ghcr.io`) still only
   happens on the first real push to `main` after merge — see Risks.

4. **Add `docs/publishing.md`.** Records: the image name
   (`ghcr.io/steading-ai/mill`), the tag scheme (`:<sha>`, the full commit
   SHA, immutable; `:main`, moved on every push to `main`), what the image
   carries and at which paths (mirroring step 2's `COPY` lines), how a
   consumer gets the files out (`podman create` + `podman cp`, or `oras`,
   quoting the work order's own phrasing since that's the two ways
   named), and the one manual step a person takes once: in the package's
   GitHub settings, "Manage Actions access" → add the consuming repository
   with the Read role — a settings page, not an API, per the work order's
   note, so it is recorded here as a runbook line rather than automated.
   **Proof:** the file exists and states those four facts; nothing in
   `docs_test.go` scopes over arbitrary `docs/` files (it only checks
   `docs/adrs/`, `docs/sandbox*.md`, and
   `docs/retrospectives/o2.md` — confirmed by reading `docs_test.go`), so
   this step needs no spec change, only a human-legible read-through against
   the deliverable's list.

| `.github/workflows/publish.yml` | New. The repository's first workflow: builds both architectures via `make stage-<arch>` + `docker buildx`, pushes `:<sha>` and `:main` as one multi-arch manifest, `push`-to-`main` triggered only. |

## Proof

- `make test-unit` — runs all four new/changed specs (`package_test.go` unchanged, `containerfile_test.go`, `publish_test.go`) alongside the existing suite; passing means every acceptance criterion that can be checked without an actual GHCR push is enforced in code, not just asserted in this plan.
- `make check` — the existing full gate (`lint`, `lint-contract`, `test`) still passes, proving the `Makefile` split and the two new spec files don't break anything else the build depends on.
- Locally, outside Ginkgo: `make stage-amd64 && podman build -f packaging/Containerfile --build-arg REVISION=$(git rev-parse HEAD) -t mill-ci-test . && podman run --rm mill-ci-test mill version` prints `mill version <the string `make -s version` prints>` — the same assertion `containerfile_test.go` makes, runnable by a reviewer without reading Go.
- A manual read of `.github/workflows/publish.yml` confirming the trigger, `permissions`, and tag scheme match `publish_test.go`'s assertions — the spec is the enforcement; the read is a sanity check that the spec's regex/keys actually match what was intended.

## Risks

- **The workflow cannot be run end-to-end in this session** — no network path to `ghcr.io`, no real `main` push to trigger it. Criterion 1 ("a push to `main` produces both tags") and the Gherkin scenario ("steading's check workflow ... pulls that tag") are only fully provable after merge, on the first real push. Mitigation: `containerfile_test.go` and `publish_test.go` cover everything that doesn't require GHCR itself — the image builds correctly, carries the right paths and version, and the workflow file's trigger/permissions/tags are structurally correct — and the YAML is kept small and copied from well-documented, standard actions (`docker/setup-buildx-action`, `docker/login-action`, `buildx imagetools create`) specifically to minimize what can go wrong only in CI. If the first real run fails, the likely culprits are narrow: `fetch-depth: 0` not actually giving `git describe` the tag it needs, or a repository setting that blocks package creation from Actions — outside this plan's control.
- **The Actions-access grant is a manual, external step** (GHCR package settings, not the workflow). The node itself says this is expected — "the node is done when the image is published, and the grant is a person's step recorded in the docs." `docs/publishing.md` records what to do; it cannot verify it was done, and neither can this plan.
- **`docker buildx` introduces a tool family the rest of the repository doesn't use** (podman elsewhere). Contained entirely inside the one new workflow file; nothing else in the repo depends on Docker being present, so this doesn't constrain local development.
- **The two ephemeral per-arch tags (`:<sha>-amd64`, `:<sha>-arm64`) persist in the package's tag list** as a side effect of the `imagetools create` approach (see Approach's rejected two-job alternative). They're harmless — never referenced by `docs/publishing.md` or by consumers — but a reviewer who wants a clean tag list could ask for the digest-based two-job variant instead; noted here rather than silently decided.
- **`containerfile_test.go` needs `podman` on whatever host runs `make test`** — already true of the rest of the suite (`AGENTS.md`, the Makefile header: "the only system package assumed is podman"), so this adds no new host dependency, only a new use of an existing one.

## Decisions

- **Single job, sequential per-arch `buildx build --push` to temp tags, then `imagetools create`** for the multi-arch manifest, over a two-job digest-artifact pipeline or a combined `--platform amd64,arm64` build. Smallest wiring that still uses the standard tool for the job; see Approach.
- **`docker buildx`/`docker/login-action`, not `podman`, builds and pushes the image.** The published artifact is identical either way; buildx is the better-trodden path for GHCR multi-arch manifests from Actions. See Approach.
- **`scratch`, no bundled Node runtime.** The image is a file carrier; the one test that runs it needs only the static binary. See Approach.
- **No `ENTRYPOINT`/`CMD`** in `packaging/Containerfile`, so `podman run <image> mill version` works exactly as the Gherkin scenario writes it, with `mill` resolved via `ENV PATH=/usr/local/bin`.
- **`docs/publishing.md` as a new, standalone file**, not a section added to `docs/tools.md` or `docs/runbook.md` — neither covers packaging or CI today, and this deliverable's scope (image name, tags, one grant step) doesn't fit either document's existing shape.
- **No `:latest` tag** — only `:<sha>` and `:main`, exactly what the work order asks for.
- **Image inspection in `containerfile_test.go` uses `podman create` + `podman export | tar -tf -`, never `podman run <image> <shell command>`** — `scratch` carries no shell or coreutils, so any inspection command other than the image's own `mill` binary would fail with `exec: not found` regardless of whether the `COPY`s were correct; listing the exported filesystem from outside the container is the only way to check file placement without adding a shell to the image just to test it.
