# Three review retries are spent in thirty seconds on one 529 outage

## Approach

Detect the outage from the SDK's own terminal verdict on the turn, not from
prose. Every turn ends in exactly one `SDKResultMessage`; when its outcome
was an API error, the CLI marks it `is_error: true` and — specifically for
that shape, not for the other `is_error` cases (max turns, execution errors,
budget, structured-output retries, none of which carry this field) — sets
`api_error_status: number | null`: the upstream HTTP status (529, 503, ...)
when it got one, `null` when it never got a response at all (an unreachable
upstream). That field's presence *is* the typed signal that "the turn ended
because every request to the model's upstream was refused" — which is
exactly AC1's condition, read off the one message the SDK already produces
to say how a turn ended, not off the words in it. `sidecar/src/exit.ts`
classifies on it directly: `is_error` true, `api_error_status` present, and
either `null` or `>= 500` (529/503/... — a 4xx such as a 429 rate limit is
a different problem, see Decisions) sets a new `ExitReason` —
`EXIT_REASON_UPSTREAM_REFUSED` — on the terminal `ProcessExit`, alongside
the real exit status (this session *ran*; status stays whatever Claude Code
exited with). On the Go side, `internal/run` recognizes that reason before
it ever calls `verify()`, so the verdict evidence is never consulted — the
attempt is not "malformed output," it is an outage. It waits with a backoff
that grows per consecutive refusal, does not spend the step's `retries` on
the wait, and folds every consecutive refusal into a single park-gate entry
if the outage outlasts the wait.

Two alternatives were considered and rejected:

- **Regex/keyword matching on the session's final message** (e.g. looking
  for "529" or "Overloaded" in `FinalMessage`). This is exactly what the
  acceptance criteria warns against: prose is not a contract, it is not
  localized, and Anthropic can reword it without notice. It would also still
  have to run inside (or instead of) `verifyVerdict`, keeping the
  classification entangled with evidence-checking rather than replacing it.
- **Buffer the mid-turn `api_retry` system message** (`type: 'system',
  subtype: 'api_retry'`, which the SDK emits each time it retries a
  transient error internally, carrying a typed `error` class). This was the
  first design tried here, but it classifies on the *last retry seen this
  turn*, not on how the turn actually ended: a turn that survived a 529 and
  then failed for an unrelated reason (or, in a long tool-using turn, one
  that retried early and went on to answer normally) would be
  misclassified unless the plan also proved that message was adjacent to
  the end. The terminal result's own `is_error`/`api_error_status` already
  says, without that extra proof, that the turn's outcome specifically *was*
  an unresolved API error — it is the more precise and materially simpler
  signal, and it removes the need to touch `session.ts` at all (only
  `exit.ts`, where every other exit classification already lives).

Within `internal/run`, the accounting is done by scanning the ledger's
trailing run of same-step attempts for `Exit.Reason ==
EXIT_REASON_UPSTREAM_REFUSED`, not by holding a consecutive-refusal counter
in the worker's memory — consistent with invariant 10 (nothing is carried in
the worker's head; a worker can be replaced mid-run without losing where it
was).

## Steps

1. **Add the wire reason.** `proto/harness/v1/harness.proto`: add
   `EXIT_REASON_UPSTREAM_REFUSED = 6` to the `ExitReason` enum, documented as
   "the session ran but every request the harness sent was refused by the
   model's upstream (529, 503, unreachable) until it gave up; the status is
   the session's own, this reason is why a fresh attempt is not evidence of
   a bad answer." Regenerate. Proof: `make generate && make check-generated`
   shows no diff (codegen is deterministic); `go build ./...` succeeds.

2. **Map it on the Go side.** `internal/harness/harness.go`: add
   `ReasonUpstream ExitReason = "upstream"` next to the other `Reason*`
   constants, and an entry in the `reasons` map
   (`harnessv1.ExitReason_EXIT_REASON_UPSTREAM_REFUSED: ReasonUpstream`).
   Proof: extend the existing round-trip test for `ReasonFrom`/`.Proto()`
   (wherever `internal/harness`'s enum table test lives) with the new value;
   `go test ./internal/harness/...`.

3. **Classify in the sidecar's exit mapping.** `sidecar/src/exit.ts`: add
   `api_error_status?: number | null` to the `SdkOutcome` interface (the SDK
   already puts it on the result message `fromResult` receives; only the
   type here needs widening), add an `upstreamRefused(status: number):
   ProcessExit` constructor alongside `ran`/`stalled`, and change
   `fromResult` so that when `result.is_error` is `true` **and**
   `api_error_status` is present on the message (`null` or a number — its
   presence, not the terminal-`is_error`-alone case, is what marks this a
   turn that ended on an API error rather than on a max-turns/execution/
   budget error) and that value is `null` or `>= 500`, it returns
   `upstreamRefused(1)` instead of falling through to `ran(1)`. No change to
   `session.ts`: this is a terminal-result classification, not a mid-turn
   one, so no new message needs to be captured. Proof: this repo has no
   TypeScript test runner (`sidecar/package.json` has only `build` and
   `typecheck`); the seam that exercises `exit.ts` end to end is the fake
   SDK driving the real sidecar, in `sidecar/spec/fake_sdk.ts` +
   `sidecar/sidecar_suite_test.go` (`package sidecar_test`, Go). Add a new
   scenario (e.g. `"upstream-refused"`) to `fake_sdk.ts`'s scenario switch
   that yields a result shaped like the incident (`is_error: true,
   api_error_status: 529`), a second for `api_error_status: null` (the
   unreachable-upstream case), and a third reusing the existing `"failed"`
   scenario's shape (`is_error: true`, no `api_error_status`, an
   `error_during_execution` subtype) to prove that one is *not*
   reclassified; add matching cases to `sidecar_suite_test.go` asserting the
   resulting `Terminal.Exit.Reason`. `pnpm --dir sidecar exec tsc --noEmit`
   for the type change, `go test ./sidecar/...` for the scenarios.

4. **Backoff policy and ledger streak scan, as pure functions.** New
   `internal/run/upstream.go`, all exported because step 7 needs them from
   `internal/cli` too (both packages must compute the same wait from the
   same ledger data — one definition, not two that can drift):
   - `UpstreamWait(consecutive int64) time.Duration` — 15s, doubling per
     consecutive refusal, capped at 5m (see Decisions).
   - `UpstreamStreak(detail *millv1.InspectResponse, step string) (count
     int64, since time.Time)` — scans `detail.GetSteps()` for this step's
     *trailing* run of attempts whose `StepRun.GetExit().GetReason() ==
     EXIT_REASON_UPSTREAM_REFUSED`, mirroring the scan `attemptsAt` already
     does in `internal/run/run.go`; `since` is the start time of the oldest
     attempt in that trailing run, `count` its length.
   - `UpstreamGiveUp(since time.Time, now time.Time) bool` — true once
     `now.Sub(since)` exceeds 30 minutes (see Decisions).
   No sleeping in this file; it is pure over its inputs. Proof: new
   `internal/run/upstream_test.go` — table tests for the backoff sequence
   (15s, 30s, 60s, ... capped at 5m), for `UpstreamStreak` against a
   constructed `InspectResponse` with a mixed history (some refused, some
   not, confirming only the *trailing* run counts and an intervening
   success/other-failure resets it), and for the give-up boundary. `go test
   ./internal/run/...`.

5. **Intercept before verification.** `internal/run/walk.go`'s `step()`:
   right after `execute()` returns and before the existing unconditional
   call to `r.verify()`, check
   `res.exit.GetReason() == harnessv1.ExitReason_EXIT_REASON_UPSTREAM_REFUSED`.
   If so, call a new `r.upstreamRefusal(ctx, s, step, sr, detail, res)` in
   `upstream.go` instead of `verify()`/`reviewed()`/`failStep()`, and skip
   straight to that function's outcome. This is the literal reading of AC1:
   the verdict evidence is never consulted for this attempt. Proof: a
   walk-level test (alongside the existing mill#34-style tests in
   `internal/run`) constructing a `result` whose exit carries the new
   reason, asserting `verify()`/`evidence.Verify` is never reached (e.g. by
   a fake evidence source that panics if called, or a spy).

6. **The wait-then-retry / give-up decision.** `internal/run/upstream.go`,
   `upstreamRefusal`:
   - Computes `count, since := UpstreamStreak(detail, step.GetName())`,
     folding in the attempt that just finished.
   - Always calls `endActivity` with a reason string built for this attempt,
     e.g. `"upstream refusal 2 (opus): 529, waiting 30s"` — this is what
     `mill logs` (`internal/cli/logs.go:436`) and `internal/run/retention.go`
     already render for free via the existing generic `AttemptEnded.reason`
     path. Persists the attempt's `ProcessExit` (status +
     `EXIT_REASON_UPSTREAM_REFUSED`) the same way any other failed attempt's
     exit is persisted today, which is what step 8's `attemptsAt` change
     keys off, and what step 7 reads back for `mill explain`.
   - If `UpstreamGiveUp(since, now)`: calls `s.record(step.GetName(), ...)`
     **once**, with a single synthetic finding describing the whole streak
     ("upstream outage: N consecutive refusals over Xm; last: 529
     Overloaded") — not per-attempt — then parks via the existing `r.park`
     path (reusing `internal/run/breaker.go` unchanged; it already renders
     whatever is in `s.findings[step]`, so one call means one round in the
     gate).
   - Otherwise: sleeps `UpstreamWait(count)`, respecting `ctx.Done()`
     (mirrors the existing `select { <-ctx.Done(); <-time.After(...) }`
     pattern `walk.go` already uses for `evidence.Pending`'s wait), then
     returns an outcome that causes the same step to be attempted again —
     *not* a revise, *not* a park.
   Proof: table-driven test in `internal/run/upstream_test.go` (or a
   `_test.go` alongside `walk_test.go`) using a short-circuited/injectable
   clock and a zero or near-zero backoff (or by making `UpstreamWait`
   injectable) so the test does not really sleep; asserts one `endActivity`
   per attempt, `s.record` called exactly once across a 4-attempt streak
   that exceeds the give-up threshold, and that a streak ending in a normal
   (non-refused) attempt never reaches `park`.

7. **Surface the wait in `mill explain`.** Today `explain()`
   (`internal/cli/read.go:700-735`) builds its `Explanation` from the
   ledger summary plus `exitText(latest.GetStepRun().GetExit())`
   (`read.go:1259-1276`, which — unchanged — will already print
   `"1:upstream-refused"` for the `Exit` line via its generic reason
   rendering), and `waitingOn` (`read.go:738-754`) has no case for this: a
   run sitting in the wait between refused attempts is `RUN_STATUS_RUNNING`
   with the latest attempt not `"running"`, so it falls through to the
   generic "a worker to claim the node and resume at step X" — which is
   true but hides that the reason it hasn't resumed yet is a wait the
   runner itself imposed, not an idle node. `mill explain` never reads
   `AttemptEnded.reason` (only `mill logs` and the retention sweep do), so
   the per-attempt sentence from step 6 does not reach it on its own; this
   step is what step 6 was wrong to claim was unnecessary. Change
   `waitingOn` to take the latest `StepRunDetail` (it currently only takes
   `*Explanation` and `*millv1.Run`) and, when that attempt's
   `Exit.GetReason() == EXIT_REASON_UPSTREAM_REFUSED`, compute
   `count, since := run.UpstreamStreak(detail, step)` and `next :=
   latest.GetStepRun().GetEndedAt().AsTime().Add(run.UpstreamWait(count))`
   — reusing step 4's exported functions rather than re-deriving the wait,
   so `explain` and the runner can never disagree about it — and return
   `fmt.Sprintf("an upstream outage to clear; step %s retries at %s
   (refusal %d)", step, next.Format(time.RFC3339), count)`. Once the outage
   outlasts the cap the run is `RUN_STATUS_PARKED` and the existing parked
   branch already applies, unchanged. Proof: extend (or add)
   `internal/cli`'s test for `explain`/`waitingOn` with a case whose
   `InspectResponse` has a latest attempt exited
   `1:EXIT_REASON_UPSTREAM_REFUSED`, asserting the printed `waiting` line
   names the outage and a retry time rather than "a worker to claim the
   node...". `go test ./internal/cli/...` (the case lives in
   `explain_test.go`, alongside the package's other `explain`/`waitingOn`
   coverage).

8. **Exempt refused attempts from `retries`.** `internal/run/run.go`'s
   `attemptsAt`: extend the discount condition (currently: attempts with
   `StepRunStatus_STEP_RUN_STATUS_ABORTED` don't count) to also discount any
   attempt whose `sr.GetExit().GetReason() ==
   millv1... EXIT_REASON_UPSTREAM_REFUSED`-equivalent on the mill-side wire
   type, regardless of its `StepRunStatus`. Proof: extend `attemptsAt`'s
   existing test table (`internal/run/run_test.go` or wherever it's
   covered) with a case mixing ordinary failed attempts and upstream-refused
   attempts, asserting only the former count toward `retries`.

9. **End-to-end shape.** Add (or extend) an `internal/run` integration-style
   test that runs a step through: refused, refused, refused (waits
   shrink/omitted via an injectable clock), then a normal pass — asserting
   the step closes on its own evidence with zero park gates and `retries`
   untouched. Add a second case where the outage outlasts the 30-minute
   cap — asserting exactly one park gate, with one round in it. Proof: `go
   test ./internal/run/...`.

## Risks

- **The `api_error_status` cutoff might be incomplete or wrong.** Only
  `is_error: true` results carrying `api_error_status` that is `null` or
  `>= 500` are treated as upstream refusal (see Decisions); if a real outage
  surfaces as some other shape the SDK produces (a thrown error before any
  result, for instance — `fromError`'s path is untouched by this plan), the
  classification misses it and the bug reappears for that shape. Mitigation:
  the sidecar change is small and isolated in `exit.ts`'s `fromResult`, so
  the condition is easy to widen later without touching the Go or proto
  side; a thrown-before-result connection failure is flagged as out of
  scope for this pass rather than silently assumed away, since the incident
  this plan fixes was a result message, not a throw.
- **Codegen determinism.** If `buf generate` output differs between local
  and CI toolchain versions, `make check-generated` fails after step 1.
  Mitigation: run `make check-generated` as the very first proof step,
  before writing any Go/TS code that depends on the new enum value.
  `buf --version` (1.72.0) was confirmed present in this environment before
  writing this plan.
- **Docs may describe the retry/malformed model as exhaustive.**
  `docs/domain-model.md`, `docs/ledger.md`, and `docs/activity.md` are
  referenced by comments throughout the touched code but were not read in
  full during Think/Plan; if any of them state or imply that "no output ⇒
  malformed ⇒ same-step retry" is the complete picture, they will be wrong
  after this change and should be corrected in the same PR. Flagged rather
  than resolved here, to keep this plan's research proportional to a
  contained bug fix.
- **Test slowness/flakiness around the wait.** `upstreamRefusal`'s
  wait-then-retry path must not really sleep in tests. Mitigation: keep
  `upstreamWait` a pure function of `count` and make the sleep call sit
  behind a small seam (an injected `after func(time.Duration) <-chan
  time.Time` or a clock interface) the way `walk.go` already isolates
  `evidence.Pending`'s wait — confirmed no existing test in
  `internal/run/*_test.go` currently exercises that wait path directly
  (`RetryAfter`/`time.After`/`DefaultStatusInterval` don't appear in any
  `_test.go` there), so this seam does not yet exist and must be introduced
  as part of step 6, not assumed.
  If `walk.go`'s own `time.After` wait is similarly untested today, that is
  a pre-existing gap, not one this plan needs to close beyond its own new
  code.
- **Scope creep at the interception point.** Branching in `walk.go`'s
  `step()` before `verify()` touches a function that already has several
  special cases (mill#34's `status < 0` suppression among them). Mitigation:
  keep the new branch to a single early check-and-call, with all the actual
  policy in `upstream.go`, so `walk.go`'s diff stays small and reviewable
  against the existing mill#34 precedent.

## Decisions

- **Backoff:** 15s base, doubling per consecutive refusal (15s, 30s, 60s,
  2m, 4m, capped at 5m). Not specified by the work order; chosen to start
  well under the observed 30-second, three-attempt burst while capping at a
  duration a human polling the run would also tolerate.
- **Give-up threshold:** 30 minutes of continuous refusal from the first
  refused attempt in the trailing streak, single elapsed-time cap (no
  separate attempt-count cap). Matches AC3's "outlasted a wait a human would
  also have given up on" without inventing a second, redundant bound.
- **Only `api_error_status` values of `null` or `>= 500` count as upstream
  refusal; a 4xx (a 429 rate limit, a 401, a 400) does not.** A rate limit
  is not upstream capacity failing — it is this workflow asking for more
  than its own quota — and an auth or bad-request error is not a capacity
  problem at all; treating either as a wait-and-retry outage would mask a
  real configuration or usage problem behind a backoff loop. `null` (no
  status at all, because no response came back) and `>= 500` match the work
  order's own examples: 529, 503, and an unreachable upstream.
- **Interception happens before `verify()`, not inside it.** Satisfies AC1
  literally ("does not consult the verdict evidence at all") rather than
  having `verify()` run and then discarding its result.
- **Attempts are fully exempted from `step.Retries`, not given a larger
  separate bound.** AC3 offers both as acceptable; full exemption is the
  smaller change (one discount condition in `attemptsAt`, already
  precedented by the `ABORTED` case) and avoids inventing a new
  configuration surface (a second retries-like field) that the work order
  never asked for.
- **Streak accounting is derived from the ledger on each check, not held in
  worker memory.** Required by invariant 10; also means a worker restart
  mid-outage resumes the correct wait/give-up state for free.
- **The exit status is preserved as whatever the session actually exited
  with; only `Reason` changes.** Consistent with `ProcessExit`'s existing
  convention that `reason` is required when status is -1 but not restricted
  to that case — the session here did run, so a synthesized -1 would be
  inaccurate.
