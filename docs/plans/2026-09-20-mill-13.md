# The activity record replaces the step log

## Approach

Build the `Activity` writer, proto, body-redaction and rendering exactly as
`docs/activity.md` §The activity through §Redaction specify, with one
deliberate narrowing: true incremental streaming ("as it is produced") for
`check_started`/`check_output`/`check`, but for `verb_started`/`verb_output`/
`verb` the output is one whole-buffer `Output` record per stream, emitted
from the buffer `Host.Run` already holds when the command exits, not chunked
live as it runs.

Three approaches were weighed (recorded in full in the prior Think step):
the smallest thing that satisfies every acceptance criterion literally
(drain-then-emit for both check and verb output, no live visibility for
either); doc-literal true streaming for both check and verb output; and this
split. The all-at-once approach was rejected because it contradicts
`docs/activity.md`'s own stated reason for giving check and verb the
start/output/end shape at all — "a suite that runs for twenty [minutes is]
visible while they run... rather than a blank until the exit" — for the one
case (checks) where that reason has real teeth and an acceptance criterion
("check's output is in the file as `check_output` records... in the order
produced") that a drain-then-split-into-chunks implementation would satisfy
only by coincidence, not by construction. Live, chunked streaming was
rejected for verbs specifically: `verbs.Host.Run` (`internal/workspace/verbs/
verbs.go:66-118`) runs sub-second git commands with no existing incremental
IO path, and no acceptance criterion or scenario in this node exercises live
verb output mid-command — building an incremental reader now spends the
node's budget on an architecture change with no observable benefit and no
test that would catch its absence. But the deliverable still names
`verb_output` as one of the three verb kinds, and `Host.Run` already has the
whole of stdout and stderr in memory (`io.ReadAll`, verbs.go:96-105) the
moment the command returns, before `Ended` is called — so emitting one
`Output` record per non-empty stream there costs nothing beyond the record
itself. Verbs get `verb_started`, one `verb_output` per stream, and `verb`;
what is narrowed is liveness, not the kind.

This narrowing is called out explicitly in the final report as a scope
decision, since `docs/activity.md`'s own §Rollout summary assigns "streamed
check and verb output" and "the attempt cap" to a later node (node 4, "Full
fidelity"), while this node's own Deliverables and Acceptance criteria
require both (a `truncated`-past-ceiling criterion, a check-output-ordering
criterion) unambiguously. That is an inconsistency inside the design
document, not a reading of it — per `AGENTS.md`, this node's Acceptance
criteria are the contract, and both the cap and check streaming are built
here; verb output's liveness is the one place a narrower reading was taken,
on the grounds above.

The write path is centralized but its lifetime is the attempt's, not
`execute()`'s. A first pass of this plan opened and closed one
`activityWriter` inside `execute()` itself; a reviewer correctly rejected
that, because an attempt's outcome — `status`, `evidence_kind`, and a reason
that "reads alone" — is only known after `execute()` returns, once `verify`
and `closeStep`/`failStep` (`internal/run/walk.go:278`, `:295`, `:320`,
`internal/run/revise.go:35`) have run, and because a gate step that files
its gate returns `errReleased` and deliberately leaves the attempt open
(`internal/run/gate.go:96-110`) — there is no ending to record at
`execute()`'s return in that case at all. The writer is instead opened once
the attempt's step run exists — right after `StartStepRun`, before
`execute()` is called — and held on `state` (`s.activity`) for as long as
the attempt is open; `execute()` and everything under it (`runSkill`,
`runCheck`, `check.Sink`, `verbs.Sink`) read `s.activity` off the state they
already carry rather than opening or closing anything themselves.
`attempt_ended` is written, and the writer closed, at the point the attempt
is actually decided: inside `closeStep`, inside `failStep`, and at the
`evidence.Pending` branch's abort (`internal/run/walk.go:294-317`). A path
that leaves the attempt open on purpose — `errReleased`/`errAborted` other
than a gate's, or the run stopping — closes the writer's file handle with no
`attempt_ended`, since the attempt has not ended; `errAnswered` closes
nothing at all, because the very next pass of the same process's loop takes
the resume branch that finishes this same attempt (see Steps 4-5 for the
three call sites this touches: `walk.go`'s `step`, `select.go`'s `assess`,
and `gate.go`'s `resumeGate`/`denyGate`, none of which may skip it — the
second rejected-and-fixed finding was exactly that `assess` bypasses
`execute()` and had no writer at all under the first draft).

`internal/check` and `internal/workspace/verbs` never import `internal/run`
(which already imports both, so the reverse would cycle); each package
instead declares its own small `Sink` interface for what it needs to report,
and the attempt's writer is passed in as that interface — the same shape
`workspace.Execer` and `forge.Git` already use for a lower package to accept
a capability without owning it. Verb wiring follows the existing optional-
interface convention (`workspace.CacheCandidate`, `workspace.StepBoundary`,
and `execute.go`'s own `inMachineSession` type assertion at line 119) rather
than adding a required method to the core `Workspace` interface: an
`ActivitySink` optional interface, implemented by both backends the same way
they already implement `Redact` by forwarding into a long-lived field on the
backend's own struct (`w.redactor` today; `w.verbSink` alongside it).

Turn assignment and redaction-over-bodies are both unit-testable independent
of real harness events, which matters because `harness.v1.Event` carries no
`parent_call_id` yet (deferred to `activity-fidelity`) — the writer's
`Record` method takes an already-built `*millv1.Activity` with `parent_call_id`
set by the caller when known, so the subagent-turn-inheritance acceptance
criterion is proven by calling `Record` directly with a hand-built record,
not by threading a real subagent event through the harness adapter that does
not exist yet.

2. **Redaction grows a body walker, a line chunker and a delta hold-back,
   beside the existing line writer.** `internal/workspace/redact/redact.go`:
   add (a) a generic walk over a proto message's string fields (including
   recursing into a `google.protobuf.Struct`/`Value`, for `arguments` and
   the options document) that applies `Redactor.String` to each — this
   replaces hand-listing fields per kind, since the set of string-bearing
   fields is already fully described by the message's own shape and a
   reflection walk means a future body never needs a matching addition
   here; (b) a `Chunker` keyed by stream name (`stdout`/`stderr`, or a
   verb/check's own arbitrary stream key) that takes bytes as they arrive,
   holds back everything after the last `\n` (today's rule, restated for a
   caller that wants discrete chunks back instead of an `io.Writer`), and
   flushes the remainder on an explicit `Close`; (c) a delta hold-back
   keyed by block id that holds back the last `L−1` bytes of a block's
   accumulated text, `L` the longest currently-registered value
   (`Redactor.Values()` already exposes lengths), releasing them on the
   next delta or on `final`. All three read the same underlying
   `Redactor`, so a value registered mid-attempt is honored by whichever
   path is in use.
   *Proof*: new specs in `internal/workspace/redact` — a value split across
   two `Chunker.Write` calls is absent from the flushed chunk and present
   in whichever later chunk completes it (mirrors the acceptance criterion's
   "one split across two check output reads"); a value split across two
   delta writes never appears in an intermediate delta, only once enough
   bytes have accumulated (mirrors "one split across two text deltas"); the
   struct/options-document walk redacts a value nested inside a
   `google.protobuf.Struct` field. `make test-unit` green; nothing else in
   the tree calls these yet, so this step changes no behavior.

3. **The writer itself, tested in isolation.** Replace
   `internal/run/logs.go` with `internal/run/activity.go`: an
   `activityWriter` type wrapping one attempt's open file, with `Record`
   (assigns `seq`, `at` from `options.Now`, applies the turn rule below,
   redacts the body via step 2's walker/chunker/hold-back as the body kind
   requires, marshals length-prefixed — a 4-byte big-endian length header
   followed by the marshaled `Activity` — and appends), `Close` (flushes
   and closes the file, writing nothing), and `End(status, evidenceKind,
   reason)` (a convenience that `Record`s `AttemptEnded` and then closes).
   Two constructors: `newActivityWriter` creates `<step>.<attempt>.activity`
   fresh and starts `seq` at 0 (so the first `Record` call, whatever kind
   it is, becomes `seq` 1); `reopenActivityWriter` opens an existing file
   for append and primes `seq` by decoding the file once to find its
   highest existing `seq` — needed by step 5's gate resume, the one place
   an attempt's writer is reconstructed in a process that did not open it.
   A nil `*activityWriter` (an empty `LogDir`, today's "write nothing"
   case, `internal/run/logs.go:41-43`) makes every method a no-op, so a
   spec that leaves `Options.LogDir` unset keeps writing no file, exactly
   as today. Turn state lives on the writer: a `currentTurn int64`, an
   `open bool` (a turn opens at the first `text`/`thinking`/`tool_call`
   after a `prompt` or after the previous turn's `usage` closes it), and a
   `callTurn map[string]int64` recording which turn each `tool_call`'s
   `call_id` opened in, so a later `tool_result` or a nested
   `parent_call_id` record looks up its turn instead of taking whatever is
   currently open. Records with no session (check, verb, gate, mill kinds)
   are written with `turn` 0 unconditionally — they never pass through the
   turn-opening path. `ActivityPath` replaces `StepLogPath`
   (`<step>.<attempt>.activity`).
   *Proof*: new `internal/run/activity_test.go`, unit-level (no DB label):
   open a writer against a temp file, `Record` a hand-built sequence of
   `Activity` bodies directly (bypassing `harness.v1.Event` entirely, per
   the Approach section's note on why parent_call_id can't come from a real

   turn; a record built with `parent_call_id` set to an open call's id

   doing; a `usage` closes the turn so the next `text` opens a new one; a
   record with `Source` check/workspace/mill and no call context gets turn
   0; a nil writer's methods all no-op without touching the filesystem;
   `reopenActivityWriter` against a file `Close`d after three records

   `decodeActivities(io.Reader) ([]*millv1.Activity, error)` helper (the

## Risks

- **The turn-assignment rule is exercised only by hand-built records, not by
  a real subagent event, because `harness.v1.Event` has no `parent_call_id`
  yet.** This is expected and matches the doc's own note that "the writer
  handles them when they come and ignores their absence" — but it means a
  reviewer can't see the rule proven end-to-end in this node. Mitigation:
  step 3's unit tests are explicit about testing `Record` directly with a
  `parent_call_id` set, and the plan says so up front rather than silently
  narrowing the test to something that looks end-to-end but isn't.
- **The writer's open/close now lives at three call sites instead of one**
  (`walk.go`'s `step`, `select.go`'s `assess`, `gate.go`'s `resumeGate`/
  `denyGate`), because a reviewer correctly rejected centralizing it in
  `execute()`: an attempt's ending is not known until after `execute()`
  returns, and a gate step that files its gate does not end there at all.
  Three call sites triplicate the open/close bookkeeping, and a mistake in
  any one of them either leaks a writer (a file left open, no `attempt_ended`
  ever written, discovered when a later read hangs or a fixture's
  temp-dir cleanup fails on an open handle) or asserts an end that has not
  happened (a `closeStep` call and an `End` call that disagree about
  whether the attempt is really closing). Mitigation: step 4 lands before
  steps 5-9 add content to the writer, its own proof runs the full
  existing skill-path and a new assessment-path suite before anything else
  is layered on, and step 5's gate proof is specifically about the one
  place a writer is reconstructed rather than owned end-to-end by a single
  call site (`reopenActivityWriter`) — the seam most likely to leak or
  double-close.
- **`reopenActivityWriter` (step 5) is new surface with no precedent in the
  codebase**: it decodes an existing file once to recover the last `seq`,
  which only has to be right the one time a gate is resumed by a process
  that did not file it. A bug here either restarts `seq` at 0 (a second
  record 1 in a file that already has one, silently invalid per the
  lifecycle invariant) or reads past the last complete record into a
  partial write. Mitigation: it reuses the one length-prefixed decoder
  step 3 builds to read a file back for its own round-trip test (step 8's
  CLI decode loop calls the same function rather than a third
  implementation), and step 5's proof exercises it specifically across two
  `Runner` instances, not just two calls in the
  same process, which is the case that would hide a bug that only shows up
  across a real process boundary.
- **The check-streaming tee (step 6) changes a concurrency-sensitive path**:
  `Run` already drains stdout/stderr on two goroutines specifically to
  avoid a filled pipe deadlocking the child. Feeding a chunker from each
  goroutine must not introduce a new lock a slow sink could hold across a
  read. Mitigation: the chunker/writer's own locking (already required for
  `seq` assignment across concurrent producers) is the only shared state;
  each goroutine's tee call is a short, non-blocking append.
- **The optional `ActivitySink` interface on the workspace (step 7) could be
  missed by a workspace implementation the plan didn't enumerate** — a test
  fake, or a future backend. Checked during planning: `logs_test.go`'s
  existing fixture calls `f.workspace.Redact(...)` directly, meaning the
  fixture already exercises a real backend (`local`) rather than a
  hand-rolled fake, so no separate fake needs the new method for the
  specs this plan adds. If another test fixture exists that implements
  `workspace.Workspace` directly, it simply won't satisfy the optional
  interface and verb records silently won't be written for it — acceptable,
  since the interface is optional by design (same as `CacheCandidate` today).
- **`docs/activity.md`'s self-contradiction (§Rollout vs. this node's own
  Deliverables) could be read the other way by a reviewer**, expecting caps
  and check-streaming deferred to node 4 as the rollout paragraph says.
  Mitigation: named explicitly in this plan's Approach section and repeated
  in the final report, rather than resolved silently in either direction.

## Decisions

- **Wire framing**: a 4-byte big-endian length prefix followed by the
  marshaled `Activity`. The doc says only "length-prefixed"; this is the
  smallest scheme that supports both append-only writes and an incremental
  reader that can tell "a complete record" from "still being written."
- **The attempt ceiling is a field on the writer, not a hard-coded
  constant**, defaulting to 64 MB (`docs/activity.md`'s number) but
  overridable, so step 9's test exercises the truncation path without
  allocating 64 MB of fixture data. The work order gives the default; it is
  silent on whether it's configurable, and a testable knob costs nothing in
  production behavior.
- **Verb output is whole-buffer, not live-streamed** (Approach section
  above) — the one place this plan takes a narrower reading of "as it is
  produced" than check gets, for the reasons given there; the kind itself
  (`verb_output`) is still produced, once per non-empty stream.
- **The activity writer is owned by the attempt, not by `execute()`**: held
  on `state` and opened/closed at the three places an attempt actually
  begins and ends (`walk.go`'s `step`, `select.go`'s `assess`,
  `gate.go`'s `resumeGate`/`denyGate`/`fileGate`), per the Approach
  section. This is a correction from this plan's first draft, made in
  response to review, not a reading of an ambiguous work order — the
  node's own acceptance criterion ("the first record is `attempt_started`
  ... the last is `attempt_ended`") is unsatisfiable otherwise for a gate
  step or for any step whose outcome depends on `verify`.
- **`attempt_started` is recorded at the writer's open site — right after
  `StartStepRun`, in `walk.go`'s `step` and `select.go`'s `assess` — not
  deferred into `runSkill` once harness and session are resolved.** This is
  also a correction made in response to review: a commit-evidence step's
  `execute()` branch calls `commitAlreadyMade` before `runSkill`, and for a
  step whose base is behind the branch head that runs a real `git log`
  through `verbs.Host.Run` before a session is ever started, so an
  `AttemptStarted` written from inside `runSkill` would lose `seq` 1 to
  `verb_started`. Every fact `AttemptStarted` needs — `step`, `sr`,
  `harnessFor(step)`, `step.GetSession()` — is a property of the step
  definition and the step run the mill already has in hand before
  `execute` is ever called, so there is no reason it has to wait.
- **A gate step that files its gate closes its writer's file handle but
  writes no `attempt_ended`**, and a gate answered in the same process
  leaves the writer open on `state` rather than closing and reopening it,
  since the very next loop iteration finishes the same attempt. The doc is
  silent on what an open attempt's file looks like mid-wait; the smallest
  answer consistent with the lifecycle invariant ("`attempt_ended` is
  last") is that the file simply has no last record yet, the same as a
  worker crashing mid-attempt today.
- **`reopenActivityWriter` decodes the whole existing file once to recover
  the last `seq`**, rather than the writer persisting a separate seq
  counter anywhere else (a sidecar file, a ledger column). The file is the
  only record of the attempt's activity so far, it is already small enough
  to read whole for `mill logs`, and a second place to keep the same
  number is a second place for it to disagree with the file.
- **`forge.pr` and `forge.checks` verbs (`internal/workspace/verbs/
  verbs.go:476,503`) are not wired to the sink in this node.** They reach
  the forge client rather than `Host.Run`, so `Sink.Started`/`Output`/
  `Ended` calls would need a second wiring point this plan does not add;
  raised as a note rather than a blocking finding, and left as a named gap
  for a later node rather than expanded scope here.
- **A short trailing read during `mill logs --follow` is treated as "not
  written yet," not corruption**; outside `--follow` it is where the file
  ends. The doc's Recovery/Seal machinery that would resolve a genuinely
  truncated crash-time record is explicitly a later node's job
  (`docs/activity.md` §Lifecycle, step 5), so this node's reader has to
  pick some default for a file that ends mid-record and this is the
  smallest one consistent with `--follow`'s existing retry loop.
- **`usage` and `heartbeat` bodies reuse `harness.v1.Usage`/`Heartbeat`
  directly** in the `Activity` oneof rather than mill.v1 growing parallel
  copies, since `mill.proto` already imports `harness/v1/harness.proto` and
  the doc's kinds table describes their shape identically to the existing
  harness messages.
- **The redaction body walker uses proto reflection over string fields**
  rather than a hand-maintained list per message kind. The doc enumerates
  the fields as a description of *what* must be covered, not a mandate on
  *how*; a reflective walk covers the same set today and covers a future
  body's string field without a matching change here, which is less
  fragile than a list that has to be kept in sync by hand.
