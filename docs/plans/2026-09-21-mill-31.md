# A host that sleeps longer than the lease TTL fences every live run

## Approach

A fenced heartbeat tries to win the node back before it gives up: `s.dagger.Claim(ctx, s.node.GetReference())`
(the same per-project client and the same primitive `mill run` already uses for a named node), and on success
`store.SetLease` to move the ledger's lease forward, then let the step already in flight keep running. Only when
`Claim` reports the node is not ready (someone else holds it) does the heartbeat fence and abort as it does today.

Both primitives already exist and already do the right thing for this case — `dagger.Client.Claim` refuses
cleanly when another holder has the node, and `store.SetLease` already treats a `running` status as one a new
claim may take over (`store.go:63-83`, ADR-006's documented exception to write-fencing) — so no proto, store, or
dagger-client change is needed. The only new orchestration is in `internal/run/heartbeat.go`.

The one real hazard is `state.lease`: today it is a plain `string` set once at claim and read from roughly three
dozen call sites in the run-loop goroutine, never written after construction. Making the heartbeat goroutine swap
it introduces a second writer. This is not just a data race in the Go-memory-model sense (the project's `test`,
`test-unit`, and `test-db` Makefile targets run plain `ginkgo`, no `-race`, so nothing would catch a torn read) —
it is a functional bug: if the run-loop goroutine issues a write with the pre-swap lease *after* `SetLease` has
already moved the ledger's `lease_id` forward, that write is fenced by the store, which is exactly the outcome
this fix exists to prevent. So `state.lease` becomes an `atomic.Pointer[string]` behind two methods, and every
existing `s.lease` read becomes `s.leaseID()`.

**Rejected**: leaving `s.lease` as a bare field and swapping it without synchronization (the "smallest thing that
could work") — it would likely pass on developer machines and even in CI (no race detector), but leaves the
stale-read hazard above latent under exactly the scenario the incident describes: a long-running step with
mid-flight writes. **Rejected**: deferring the swap to the run-loop goroutine via a channel/mailbox instead of
letting the heartbeat goroutine write `state.lease` directly — I looked for a single chokepoint every
lease-carrying write already passes through and found none (store writes go through a generic `call()` helper,
but dagger writes like `s.dagger.Hold`/`Release`/`ReportUsage`/`Complete` are inline); a channel-based hand-off
would still need a drain check at every one of the same call sites, for no benefit over a lock-free accessor.
**Rejected** (as an addition, not an alternative): the proposal's second idea — a heartbeat that notices wall
time jumped past expiry and renews immediately rather than waiting for the next tick. It is not in the Acceptance
criteria, and the existing tick is already driven by the runtime timer's monotonic deadline, which is already in
the past by the time a frozen process resumes, so the next tick already fires as soon as the goroutine is
scheduled — there is no evidence a proactive check buys a materially smaller window here. Left out of this plan.

## Steps

1. **Make `state.lease` safe to swap from another goroutine, with no behaviour change.**
   `internal/run/run.go`: change the `state` struct's `lease string` field to `leaseID atomic.Pointer[string]`
   (or equivalent lock-free holder), add `func (s *state) leaseID() string` and
   `func (s *state) setLease(id string)`, and set it in `drive()` where `lease: claimed.Lease.GetId()` is
   constructed today. Mechanically rename every other `s.lease` read (in `walk.go`, `preparatory.go`,
   `sandbox.go`, `verify.go`, `shutdown.go`, `notify.go`, `select.go`, `gate.go`, `breaker.go`, `cancel.go`,
   `revise.go`, `finish.go`, and the remaining reads in `run.go` itself) to `s.leaseID()`. No call site's
   argument order or logic changes — this is a pure rename plus the type swap underneath it.
   **Proof**: this step changes no behaviour, so the existing suite is the regression test —
   `make lint && make test-unit` passes unchanged, and `make test-db` (needs the `db`-labelled fixtures) passes
   unchanged, in particular the current "Holding the lease" and "Being fenced out" specs in
   `internal/run/run_test.go`.

2. **Teach the heartbeat to reclaim before it fences.**
   `internal/run/heartbeat.go`: in `beat`, when `r.options.Dagger.Heartbeat` fails with `isFenced(err)`, call a
   new `r.reclaim(ctx, s)` instead of returning immediately. `reclaim` calls `s.dagger.Claim(ctx,
   s.node.GetReference())`; on success it calls `store.SetLease` (via the existing `call()` helper, the same
   shape `openRun` already uses at `run.go:772-776`, but without the `AbortOpenStepRuns` that precedes it there —
   the step is alive, not dead, so nothing about it is aborted) with the freshly claimed lease id, then
   `s.setLease(newLeaseID)` and returns nil, letting `beat` fall through to its existing `cancel_requested` check
   unchanged. If `Claim` fails (node held elsewhere) or `SetLease` fails, `reclaim` returns that error and `beat`
   fences exactly as it does today (`errors.Join(ErrFenced, err)`).
   **Proof**: two new specs under `internal/run/run_test.go`'s "Being fenced out" describe block, both driven
   through the existing real-dagger (`testsupport`, `db`-labelled) fixture and its `f.expire`/`f.reclaim`/
   `f.leaseOf` helpers, extended with one more helper (see Files) to read the ledger's own events:
   - *Self-heal*: `f.expire` the running node's lease and do **not** call `f.reclaim` (nobody else takes it).
     Assert the run still completes (`Execute` returns nil, or the spec's steps keep progressing past the point
     they'd have been aborted at), the node ends up on a lease this same worker holds, and the ledger recorded
     exactly one new `set_lease` event for the run and no `abort_step_runs`/failed-step event.
   - *Still fenced*: unchanged existing spec (`f.expire` followed by `f.reclaim` from a second principal) keeps
     asserting `run.ErrFenced`, the session cancelled, and no evidence written for the in-flight step — this
     proves step 2 didn't change the already-covered path.
   `make test-db` (label `db`) passes, including both specs.

## Risks

- **`SetLease` races with something else mutating run status between the dagger `Claim` and the store call.**
  `SetLease` already re-locks the run row and checks `claimable(state)` itself (`store.go:282-309`); a genuine
  conflict (e.g. the run was concurrently cancelled into a non-claimable status) surfaces as an error `reclaim`
  passes up, and `beat` fences as it does today. No new failure mode, just a narrower window for an existing one.
- **The mechanical rename touches many files and could miss a call site**, leaving a stale plain-`string` read
  that no longer compiles once the field's type changes — `go build`/`make lint` catches this immediately since
  the field type change makes every un-updated reference a compile error, not a silent bug.
- **The self-heal spec is timing-sensitive** (it has to expire the lease while a step is genuinely in flight,
  the same way the existing fenced-out spec already does with `Eventually` on `f.harness.Calls()`); reusing that
  spec's proven wait pattern keeps this from being flaky on its own terms rather than inventing a new one.
- **Acceptance criteria names a "fake dagger"; this plan uses the real one.** `internal/dagger` and `internal/run`
  have no fake/mock dagger seam today (checked: `Client` is concrete, not an interface, and the only precedent
  for this exact scenario — `internal/run/run_test.go`'s existing "Being fenced out" spec — already runs against
  a real `dg serve` via `internal/testsupport`). Building a hand-rolled fake Connect service would contradict
  AGENTS.md's "follow the patterns already in the tree" and add a second, divergent way to test fencing. Flagging
  this as a deliberate deviation from the work order's wording rather than silently reinterpreting it.

## Decisions

- **Lock-free accessor over a mutex**: `atomic.Pointer[string]` for `state.lease`, since writes are rare (at
  most once per sleep-and-resume) and reads are frequent; a mutex would work equally correctly but adds
  lock/unlock pairs to the hot path for no benefit.
- **`s.run`'s in-memory `LeaseId` is not refreshed after `SetLease`.** Checked every read of a run's lease id in
  the package; nothing on the live-loop path reads `s.run.GetLeaseId()` after `openRun` (only `restart.go`, on a
  different, already-ended run's object, and tests). Leaving it stale in memory costs nothing today; a future
  reader that needs it can call `runByNode` for a fresh copy, the same way the loop already does elsewhere.
- **The proactive "wall clock jumped past expiry" renewal is out of scope for this change.** It is listed as
  "also worth doing," not in Acceptance, and the reactive self-heal in step 2 already satisfies both Acceptance
  bullets on its own.
- **The required spec runs against the real dagger fixture (`testsupport`, `db` label), not a new fake.** See
  Risks above.
