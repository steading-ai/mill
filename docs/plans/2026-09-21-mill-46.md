# A deployed workflow change never reaches a run until someone pushes it

## Approach

`mill serve` pushes every workflow directory under a new `workflows-root`
config key at its own startup, before it binds its socket or reports ready,
using the exact same load-validate-store recipe `mill workflow push`
already runs by hand (`internal/cli/workflow.go`'s `runWorkflowPush`,
`workflow.Load`, `PutSkill`/`PutWorkflow`). The push is a direct in-process
call through `*domain.Service` — the same object `runServe` already opens —
not a round trip over the socket, so a refusal happens before the process
ever reports itself ready. Because `PutWorkflow`/`PutSkill` are already
idempotent by content hash, "push again when the digest changes" needs no
new watcher: re-running the same idempotent push at every start already
satisfies it.

This is scoped to `serve` (bare or `--work`), not to a standalone `mill
work` process, because `docs/architecture.md` says workflows are `serve`'s
own ("`serve` owns workflows, runs, the ledger, and step tokens") and
because no standalone worker deployment exists today — `contrib/systemd/`
ships only `mill.service` (`serve --work`). The acceptance criterion's
"`mill serve` (or the worker)" is satisfied by the one process that is
ever actually deployed. A later node can extend this to a genuinely
separate worker process if that topology is ever deployed; building it now
would be speculative.

Two things the work order asks for turn out to already be true or free
once the push exists:

- `mill workflow list` already prints only the newest version of each name
  by default — that already *is* "which version is current for
  selection." Criterion 4's list-side ask needs no code change, only the
  docs sentence it also asks for.
- The workflow version is already a deterministic content hash
  (`internal/store/store.go`'s `canonicalWorkflow` + `contentHash`,
  computed over the fully-loaded definition, skill digests included). That
  hash has no dependency on anything store-internal — it is pure
  `proto.Message` manipulation — so it can be shared with `internal/cli`
  instead of duplicated, giving `mill doctor`'s new probe a genuinely
  read-only way to compare "what pushing this directory would produce"
  against "what the store holds," with no write as a side effect of a
  diagnostic command.

**Rejected: derive the root from the existing `workflow-dir` flag
(no new config key).** `workflow-dir` names one workflow's directory, for
an unrelated purpose (resolving a check step's script paths for the
machine mount). Inferring "the root is its parent" is implicit,
undocumented, and wrong the moment a deployment's `workflow-dir` is not a
sibling of the other workflows it runs — exactly the kind of silent
mismatch this node exists to remove. A separate, explicit `workflows-root`
key costs one more line in the config file and is honest about what it
does.

**Rejected: push over the worker's own RPC client after the socket is
listening, and cover standalone `mill work` too.** Symmetric with the
literal "serve (or the worker)" wording, but it pushes the loud-failure
point *after* the socket binds (a refusal would have to be un-bound or
reported some other way once already serving), and it builds for a
worker-elsewhere topology nothing deploys. In-process, before `Listen`, is
strictly better for the one topology that exists.

**Rejected: let `mill doctor`'s new probe call `PutWorkflow` itself and
report its `created` flag.** That would make a diagnostic command mutate
stored state as a side effect, and — worse — it would auto-fix drift
before ever reporting it, defeating the point of a probe that is supposed
to say whether `serve`'s own push kept up. Comparing a locally computed
hash against what `ListWorkflows` already reports is read-only and cannot
hide the case it exists to catch (`serve` pushed successfully at its last
start, but the directory changed again since without a restart).

## Steps

1. **Share the version hash between `internal/store` and `internal/cli`.**
   Move `canonicalWorkflow` and `contentHash`
   (`internal/store/store.go:1829-1853`) into a new
   `internal/workflow/version.go`, exported as `workflow.ContentHash(proto.Message) (string, error)`
   and `workflow.Version(w *millv1.Workflow) (string, error)` (canonicalize,
   then hash). Update `Store.PutWorkflow` (`store.go:1777`) and the
   digest-fallback branch of `Store.PutSkill` (`store.go:1858-1871`) to call
   the exported functions instead of the private ones. No behaviour change.
   **Proof:** `internal/store`'s existing `PutWorkflow`/`PutSkill` specs
   (db-labelled) pass unchanged — same version and digest values as before,
   because the algorithm is untouched, only relocated. Add one small spec in
   a new `internal/workflow/version_internal_test.go`: two `workflow.Load`
   calls on identical content produce the same `Version`, and mutating one
   byte of one skill body changes it — pins the "one changed byte, new
   version" guarantee `docs/tools.md` already documents, now against the
   shared implementation.

2. **Add the `workflows-root` config key.** `internal/cli/config.go`: new
   `Config.WorkflowsRoot string `yaml:"workflows-root"`` field and a
   `{"workflows-root", "workflows-root"}` entry in `configKeys`
   (`config.go:~306`, beside `workflow-dir`). `internal/cli/work.go`: new
   `workflowsRoot string` field on `runOptions`, a `--workflows-root` flag
   in `bindWorkFlags` (`work.go:71-100`, beside `--workflow-dir`), and an
   entry in both `stringTargets` and `stringValues` (`work.go:164-190`) so
   `applyConfig` fills it from the file the same way it fills
   `workflow-dir`. Default empty, meaning push-on-start is a no-op —
   matches every other setting's "a missing file is not an error."
   **Proof:** `internal/cli/config_keys_internal_test.go`'s existing specs
   (`The config-key table`) pass once `docs/tools.md`'s `§Configuration`
   table (`docs/tools.md:993-1010` area) gets a `workflows-root` row —
   these specs already fail the build if the table, the struct, and the
   bound flags disagree, so getting the row content exactly right is
   mechanically checked, not a judgement call.

3. **Push every workflow directory under the root at `serve` startup.**
   New `internal/cli/workflows_root.go`: `pushWorkflowsRoot(ctx
   context.Context, svc *domain.Service, root string, hostMcpServers
   map[string]struct{}, log *slog.Logger) error`. Empty `root` returns nil.
   Otherwise `os.ReadDir(root)`, skip entries that are not directories or
   carry no `workflow.yaml`, and for every remaining subdirectory:
   `workflow.Load(dir)`, `svc.PutSkill` for each returned skill,
   `svc.PutWorkflow(ctx, definition, hostMcpServers)` — with
   `definition.Source = &millv1.Source{Kind: millv1.SourceKind_SOURCE_KIND_REPO, Path: <abs dir>, PushedBy: "mill serve"}`
   set before the call, reusing the existing-but-unused `SOURCE_KIND_REPO`
   enum value ("the definition was seeded from files in a repo" — no proto
   change). Any error from `Load`/`PutSkill`/`PutWorkflow` is wrapped
   naming the root, the subdirectory, and (already, from `Load`/`toProto`'s
   own errors) the step, and returned rather than logged-and-continued.
   Log one line per push at info level, `stored`/`unchanged`, matching
   `mill workflow push`'s own wording (`stateOf` in `workflow.go`).
   Wire it into `internal/cli/serve.go`'s `runServe`, called with
   `opts.worker.run.workflowsRoot` right after `svc, err :=
   domain.Open(...)` (`serve.go:139-143`) and before `srv.Listen()`
   (`serve.go:175-187`) — using `mcpServerNames(opts.worker.run.mcpServers)`
   when `opts.work`, else `nil`, the same conditional `storeOpts` already
   uses (`serve.go:166-173`). A non-nil error returns from `runServe`
   immediately, so the process exits non-zero before migrating... no —
   before binding the socket (migrations already ran by this point, which
   is fine: the schema itself is not workflow-specific and migrating first
   is the existing, documented order).
   **Proof:** new specs in `internal/cli/serve_test.go` (db-labelled,
   following the file's existing pattern of driving `runServe` through
   `cli.NewRootCommand`/`root.ExecuteContext`):
   - given `--workflows-root <dir>` naming two valid workflow directories,
     `serve` reports ready and `ListWorkflows` (over the bound socket)
     returns both, at the versions `workflow.Load` on those directories
     computes;
   - starting `serve` again against the same directories reports ready and
     changes nothing (`PutWorkflow`'s `created` stays false — assert via a
     second `ListWorkflows` returning the identical version, or by
     asserting no new row after a second start);
   - given a `workflows-root` where one subdirectory's `workflow.yaml` is
     malformed (e.g. an unknown field, or a step missing `evidence`),
     `root.ExecuteContext` returns a non-nil error naming that workflow's
     directory and the step, the socket is never bound (no file at the
     socket path), and nothing was pushed (`ListWorkflows` against a
     *second*, working `serve` pointed at the same database shows the
     other, valid workflow was not stored either — the whole root fails
     together, not partially, since `runServe` returns before `Listen`).

4. **`mill doctor` reports drift per workflow.** `internal/cli/doctor.go`:
   add `"workflows"` to `ProbeNames` (`doctor.go:41-44`), add
   `workflowsRoot string` to `doctorOptions` and a `--workflows-root` flag
   (mirroring `--sidecar`'s pattora at `doctor.go:~135`, filled from the
   config file the same way `doctor` already fills `sidecar`/`forge`/etc. —
   check how those are read into `doctorOptions` today, likely
   `applyDoctorConfig` or similar, and follow it), and a new
   `probeWorkflows(ctx, opts) []probe`: if `opts.workflowsRoot == ""`,
   return `[]probe{pass("workflows", "no workflows-root configured")}` (the
   `mcp` probe's "none configured" precedent). Otherwise, for each
   subdirectory of the root carrying a `workflow.yaml`: `workflow.Load`,
   `workflow.Version(definition)`, then `storeClient(opts.socket).GetWorkflow(...)`
   for that name/scope/project's newest stored version; `pass` naming the
   workflow and the matching short digest when equal, `fail` naming the
   workflow, the stored digest, and the disk digest when not, `fail`
   naming the workflow and "not stored" when `GetWorkflow` finds nothing.
   Wire `probeWorkflows` into `runProbes` (`doctor.go:227-243`), appended
   like `probeMcp`'s multi-line result.
   **Proof:** new specs in `internal/cli/doctor_test.go`/`doctor_internal_test.go`:
   a `workflows-root` whose directories match what a preceding push stored
   reports every line `pass`; one whose disk content differs from what is
   stored (write, then mutate the file without pushing again) reports
   `fail` naming the workflow and both digests; an empty/unset
   `workflows-root` reports the single "not configured" `pass` line and
   does not change the command's exit code. Also extend
   `internal/cli/docs_test.go`'s coverage implicitly: `doctor` is not in
   its `undocumented` map, so the existing "every flag a described command
   declares is named in the text" spec already fails until
   `docs/tools.md`'s `## doctor` section names `--workflows-root`.

5. **Docs.** `docs/tools.md`:
   - `## doctor` (`docs/tools.md:480-524`): "Twelve probes" → "Thirteen
     probes", add a `workflows` row to the probe table, add a
     `workflows` line to the example transcript.
   - `## workflow list` (`docs/tools.md:448-459`): one sentence — a run
     selects from what is stored, not from any directory on disk; the
     newest version this command prints for a name is the one a run
     without an explicit `--workflow` version pin would follow.
   - `§Configuration` (`docs/tools.md:935-1010`): the `workflows-root` row
     (mechanically required by step 2's proof already) plus a sentence
     explaining what it does — every directory under it with a
     `workflow.yaml` is pushed at every `serve` start.
   **Proof:** `make test` (the `docs_test.go` and
   `config_keys_internal_test.go` specs named in steps 2 and 4 above) plus
   a manual read-through: the scenario in the work order — a merged
   `workflows/feature/workflow.yaml` change reaching a run with no manual
   push — is now true end to end and the docs say so.

## Risks

- **`internal/store` importing `internal/workflow` turns out to have a
  hidden cycle or a depguard objection.** Checked: `internal/workflow`
  imports only `internal/evidence`, `gen/mill/v1`, and stdlib/yaml/proto —
  nothing that reaches back to `internal/store`, and depguard's
  `store-only-from-domain` rule restricts who may import *store*, not what
  store may import. Low risk; `go build ./...` after step 1 confirms it
  immediately if wrong.
- **A directory under the root that is not a workflow at all** (a stray
  file, a `skills/`-only leftover, a `.git`) **is mistaken for one.**
  Mitigated by requiring a `workflow.yaml` to be present before attempting
  `workflow.Load`; anything else is silently skipped, matching how
  `packaging/nfpm.yaml` installs the whole `workflows/` tree (which
  currently has no non-workflow entries, but a future one should not break
  startup).
- **A large or slow-to-`stat` root delays every `serve` start.** The
  existing `workflows/` tree has five directories; this is not a
  perf-sensitive path at that scale, and nothing in the acceptance
  criteria asks for concurrency. Left sequential.
- **Criterion 3 ("mill doctor reports... whether the stored version
  matches the directory on disk") could be read as wanting this run
  *remotely* — a Mac's `doctor` checking a Linux worker's disk — the way
  `sidecar`/`signing`/`forge` are delegated through `WorkerService.Probe`.**
  Decided against (see Approach) because it would need a proto change
  criterion 3 does not ask for and the other local-only probes
  (`workspace`, `space`, `mcp`) are the closer precedent for a
  filesystem-and-RPC check like this one. If a reviewer disagrees, the
  fix is confined to step 4 and does not touch steps 1-3 or 5.
- **The exact `docs/tools.md` `§Configuration` table row text has to match
  `configKeyTable`'s rendering byte for byte**, per
  `config_keys_internal_test.go`'s existing spec. Not a design risk, but an
  easy way for the implementer to lose time — run `make test-unit` after
  step 2 alone, before moving on, and let the failure's diff supply the
  exact text.
- **`doctorOptions`'s existing config-reading path for flags like
  `--sidecar` needs to be found and matched exactly** (the plan says
  "mirror it" rather than naming the line, because it was not read closely
  enough in this pass to cite). If it turns out doctor does not read the
  config file for any of its flags today and instead takes everything
  from explicit flags, `--workflows-root` should follow that pattern
  instead — the implementer should read `newDoctorCommand`'s flag
  bindings and any config-application call near it before writing step 4,
  and adjust to match whatever precedent is actually there rather than
  what this plan guessed.

## Decisions

- **Scope:** push-on-start lives in `serve` (bare or `--work`), not in a
  standalone `mill work` process. The work order's "(or the worker)" is
  read as acknowledging a future split, not requiring it now, since no
  standalone worker is deployed.
- **New config key, not a repurposed one:** `workflows-root` is separate
  from `workflow-dir`, because the two name different things (a root of
  many workflows vs. one workflow's script-resolution path) and conflating
  them would recreate a silent-mismatch risk of the same shape this node
  removes.
- **In-process push, not over the socket:** `pushWorkflowsRoot` calls
  `*domain.Service` directly, before `Listen()`, so a refused definition
  fails the start before anything is reachable — the most literal reading
  of criterion 2's "fails the start loudly... rather than leaving the
  previous version silently in service."
- **"Digest changes" is satisfied by re-running the idempotent push at
  every start**, not a live filesystem watcher within one running
  process. Nothing in the acceptance criteria or scenario describes
  runtime watching, and `PutWorkflow`/`PutSkill` are already idempotent by
  content hash, so this is the smallest mechanism that satisfies the
  literal text.
- **`mill workflow list` gets no code change**, only the docs sentence
  criterion 4 also asks for — it already shows only the newest (=current)
  version per name by default, which is what "current for selection"
  means.
- **`SOURCE_KIND_REPO`, already defined in the proto and unused, is what
  push-on-start stamps on what it stores** — no proto/contract change.
- **`mill doctor`'s new probe runs locally against the process's own
  `workflows-root` and the store's RPC, not delegated to a remote worker**
  — see Risks for the alternative considered and rejected.
- **`packaging/config.yaml` is updated** to set `workflows-root` alongside
  `workflow-dir` so a package install gets the self-healing behaviour by
  default, and its now-stale "push by hand" comment is corrected. Wiring
  homestead's Ansible role to the same effect (`docs/retrospectives/o2.md`
  "Next run" item 5) is out of scope — that role is not in this
  repository, and this node's job is to make the mill binary itself no
  longer depend on that role remembering to run.
