# A clean tree after a revise closes commit, and the plan file has an owner

## Approach

Centralize the `commit`-evidence judgment in `verifyCommit`
(`internal/evidence/evidence.go`) and reduce `observe()`
(`internal/run/execute.go`) to a dumb fact-gatherer that always hands the
branch head to the verifier, whether or not it moved. Today `observe()`
short-circuits with a hard error the instant the head equals the attempt's
`base_commit`, so `verifyCommit` never gets a chance to judge that case at
all — which is why a revise that changes nothing has no way to close. That
short-circuit is the actual defect; `verifyCommit`'s own doc comment already
reads as if it owns the whole decision ("every clause is load-bearing"), and
the acceptance criteria pin the new test cases to
`ginkgo --focus 'verifyCommit' ./internal/evidence/...`, which only makes
sense if the deciding logic lives there.

Two alternatives considered and rejected:

- **Do the clean-tree/earliest-base check inside `observe()` instead**, and
  leave `verifyCommit`'s unconditional refusal alone. Rejected: it duplicates
  git-fact-gathering across two packages, contradicts the evidence package's
  stated design ("verifiers reach the world through seams on `Step` and not
  through the session"), and can't satisfy the acceptance criterion that
  pins these four cases to `internal/evidence`'s own suite.
- **A separate, retroactive closing path** invoked from `failStep`/`park`
  that synthesizes commit evidence outside the normal `observe` →
  `r.verify` → `evidence.Verify` pipeline. Rejected: every other evidence
  kind closes through that one pipeline; a second path would be a second,
  inconsistent notion of "what closes a `commit` step" for no benefit over
  fixing the one pipeline that already exists.

The new fact `verifyCommit` needs — the base of the step's *earliest*
attempt in this generation, from before any revise — is already computed by
an existing helper, `firstBase` (`internal/run/verify.go:406-415`), used
today for `reviewBrief`. `r.verify` already receives the `detail` that
function needs, so wiring it in is one line. A restart (`mill rerun`)
creates a brand-new run row per generation (`internal/run/restart.go`,
`Store.CreateRun` with the next generation), so `Inspect`/`ListStepRuns` for
the *current* run id never spans a prior generation — `firstBase` is already
correctly scoped without any extra filtering.

The other three deliverables have no real design space — they are what the
work order specifies, applied directly. The one sequencing choice: land the
loader change (checks default to `retries: 0`) *before* setting an explicit
`retries: 0` on the four `clean-tree` steps, because today the loader cannot
tell "omitted" from "explicitly zero" (`step.GetRetries() == 0` triggers the
default either way) — writing `retries: 0` into YAML before the loader
change would silently keep defaulting to 3 with no compile-time signal.

## Steps

1. **`verifyCommit` learns to close on an unmoved head.**
   `internal/evidence/evidence.go`: add `EarliestBase string` to `Step`
   (doc comment: the base of the step's earliest attempt this generation,
   before any revise; empty behaves as if this were the earliest attempt).
   Restructure the `sha == base` branch of `verifyCommit`:
   - `git status --porcelain` through the existing `Git` seam; non-empty
     output refuses with exactly `"the branch head is still %s: the session
     made no commit"` (`sha` in place of `%s`) — the very sentence
     `observe()` refuses with today, moved verbatim rather than
     reworded, since it is the only occurrence of that phrase in the tree
     and the acceptance criterion quotes it exactly.
   - `earliest := step.EarliestBase`, falling back to `base` when empty.
     `sha == earliest` refuses with today's exact wording ("%s is the head
     the step started at: the session made no commit") — the plain
     first-attempt case is unchanged.
   - `sha` must descend from `earliest` (`merge-base --is-ancestor`); a
     failure here refuses naming `earliest` as "the earliest base of this
     step" (distinct wording from the existing "does not descend from
     %s, the head the step started at" used in the moved-head path, so a
     failed step's message always names the right base).
   - `verifyCommitter(ctx, step, sha)`, unchanged, still runs.
   - Success returns `Evidence{Value: commit=sha}`, naming the unmoved head.
   Update `verifyCommit`'s doc comment (lines 321-338) to describe the
   exception. Update `docs/domain-model.md` §Evidence's `commit` row and
   `docs/ledger.md`'s `base_commit` paragraph to state the rule as it now
   stands: a `commit` step may also close on a head that has not moved this
   attempt, when the tree is clean and that head already descends from the
   step's first base in this generation.
   Also rename the file's top-level container, `Describe("The commit
   verifier", ...)` (line 23), to `Describe("The commit verifier
   (verifyCommit)", ...)`. Ginkgo's `--focus` matches against a spec's full
   text — every enclosing `Describe`/`Context`/`It` description joined
   together — not against Go identifiers, and today nothing in this file's
   text contains the string "verifyCommit"; `--focus 'verifyCommit'` would
   therefore select zero specs and the acceptance criterion's command would
   pass vacuously. Putting the word in the outer container's own text makes
   every spec under it — the existing ones and the new ones alike — match,
   so one small rename is enough to cover all four cases the criterion
   names without touching each spec's own description.
   *Proof*: new/updated specs in `internal/evidence/evidence_test.go`
   under the renamed "The commit verifier (verifyCommit)" container — a
   clean tree with `EarliestBase` behind `Base` closes on `base`; a dirty
   tree with the same setup refuses with the exact moved-verbatim sentence
   above; `EarliestBase` unset (or equal to `Base`) still refuses exactly
   as today (existing spec "refuses the head the step started at" needs no
   wording change, only to now live under the renamed container); a
   foreign committer is still refused in the unmoved-head case. `ginkgo
   --focus 'verifyCommit' ./internal/evidence/...` now actually selects
   the whole "commit verifier" suite, old and new specs both, and passes;
   `go test ./internal/evidence/...` green too. This step alone changes no
   run-time behavior yet — nothing calls `evidence.Verify` with a real
   unmoved head until step 2 — so the tree stays fully working and the
   existing suite is the only thing that has to pass.

## Risks

- **The new `verifyCommit` clauses could accidentally widen what closes a
  `commit` step beyond the unmoved-head case.** Mitigation: the new logic
  only runs inside the existing `sha == base` branch — every other path
  through the function (a real new commit, on-branch check, ancestry from
  `base`) is untouched. The clean-tree check specifically is what stops a
  session that edited a file without committing from closing the step, per
  the work order's own warning not to relax it to "no staged changes" —
  the plan checks *working-tree* status (`git status --porcelain`), not
  just the index.
- **Reusing `firstBase` might not be scoped the way "this generation"
  requires**, if a restart somehow shared step-run rows across
  generations. Checked during planning: `Restart` creates a new run row
  per generation via `Store.CreateRun`, and `Inspect`/`ListStepRuns` scope
  to one run id, so a prior generation's rows are never visible to the
  current one. No change needed to `firstBase` itself.
- **Simulating a full revise round-trip in `commit_test.go`'s new spec
  (script `implement`, fail `clean-tree`, resume `commit`) could be
  fragile** if the fixture's turn-scripting doesn't cleanly support
  scripting five-plus steps end to end. Mitigation: the existing fixture
  already supports this shape (`f.script(f.quickFixScripts()...)` runs a
  full `quick-fix` pass in "The commit that was made is the evidence"); the
  new spec adds one extra forced `clean-tree` failure and one extra no-op
  `commit` turn to that same shape rather than inventing new fixture
  machinery. If it proves awkward, the fallback is a narrower spec that
  calls `evidence.Verify` directly with a hand-built `Step{EarliestBase:
  ..., Base: ..., Claim: ...}` (already covered by step 1's unit tests) and
  a thinner run-level spec that only asserts `r.verify`'s wiring passes the
  right `EarliestBase` through, without exercising a real revise.
- **A `check` step somewhere outside the four workflows this node touches
  might rely on the old implicit `retries: 3` default.** Checked during
  planning: grepped all four target workflows' `gate` steps (the other
  kind that shares the default-fill branch) and found every one sets
  `retries` explicitly already; `check` steps outside `clean-tree` (e.g.
  `live-tier` in `mill-quick-fix`) also already set `retries` explicitly.
  If another workflow file exists elsewhere in the repo with a `check` step
  that omits `retries` and genuinely wants 3, `go build`/the workflow
  loader's tests won't catch a *behavioral* regression (only a load
  failure would), so a final `grep -rn "kind: check" -A6 workflows/` with
  no `retries:` line found in the six lines after would be worth running
  once during implementation to be sure.

## Decisions

- **`EarliestBase` empty behaves as "same as `Base`"** rather than being
  refused outright as a malformed `Step`, so the existing evidence-package
  unit tests that never set it keep passing unchanged, and a real run's
  first-ever attempt at `commit` (where there is no earlier row) gets the
  same refusal it gets today. The work order is silent on this default;
  this is the smallest option that satisfies both the new behavior and
  backward compatibility.
- **Dirty-tree refusal message** in the unmoved-head branch reuses
  `observe`'s exact current string, `"the branch head is still %s: the
  session made no commit"`, verbatim rather than inventing new wording.
  The acceptance criterion for this case quotes that sentence exactly, and
  it is the only place in the tree the phrase exists — once step 2 deletes
  it from `observe`, `verifyCommit` is the only place left that can still
  produce it, so the wording has to move, not just the intent.
- **Gate steps keep the skill-like default of 3** when they omit `retries`;
  only `check` steps change. The work order's deliverable 4 text only
  contrasts skill against check, and no real workflow currently depends on
  a gate's implicit default (verified by grep), so this is the narrowest
  reading of "a check whose definition omits `retries` gets 0."
- **The four `clean-tree` comments are rewritten individually** rather than
  factored into a shared comment block, matching the existing convention
  in these files where each step's rationale is self-contained.
