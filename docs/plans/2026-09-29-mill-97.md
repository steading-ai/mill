# A step's prompt carries the node's unresolved comments beside its body

## Approach

`workflow.Node` and `workflow.Input` (`internal/workflow/workflow.go:12-37`) are
plain structs with no skift dependency; `internal/run/execute.go`'s
`(*Runner).prompt` (`execute.go:812-835`) is the one place that maps
`*skiftv1.*` wire types into them, and `internal/workflow/prompt_test.go`
leans on the plain-struct boundary to build `Node`/`Input` values with no
skift import at all. This plan keeps that boundary: `workflow.Node` gains a
plain `Comments []Comment` field, `internal/workflow/prompt.go`'s `Prompt`
renders it, and all skift-specific work — fetching, filtering to unresolved,
mapping `*skiftv1.Comment` into `workflow.Comment` — stays in
`internal/run`, the same split `Input` already has.

Two things the work order names as content of each comment aren't actually
fields on `skiftv1.Comment` (checked against the vendored
`vendor/github.com/steading-ai/skift/gen/skift/v1/skift.pb.go`, which has
only `Id, NodeId, Author, Body, InReplyTo, ResolvedAt, ResolvedBy,
Revisions`):

- **"principal and kind"**: there is no kind field, and no `"kind:id"`
  convention to reuse — checking that premise against the code shows it is
  wrong. Skift stores a comment's author as a bare principal id
  (`Author: a.actor.PrincipalID`, skift `internal/domain/comment.go:226`;
  the proto field's own doc says only "Id of the principal that wrote the
  comment"). The same is already true of the existing `Node.Author` and
  `Input.Author`: `execute.go` sets `Node.Author` from
  `s.node.GetAssignee()`, and skift's `Node` message keeps `assignee` (the
  bare id) and `assignee_kind` (the enum) as two separate fields, never
  concatenated — `prompt_test.go:25`'s `"user:ivy"` is an illustrative
  fixture literal, not a shape skift produces anywhere. Checked whether
  mill's client can resolve an id to a kind some other way: neither
  `GraphServiceClient` (`ApplyPatch, GetNode, GetInputs, ListNodes,
  Explain, Search, CreateProject, GetProject, ListProjects, ArchiveProject,
  UpdateProject, HoldProject, UnholdProject`) nor `WorkServiceClient`
  (`Ready, ClaimNext, Heartbeat, Release, ReportUsage`) exposes a principal
  lookup — there is no RPC mill's client can call to attach a kind to an
  id today. `Comment.Author` therefore carries the bare id, exactly as
  `Node.Author`/`Input.Author` already do: no regression, and no worse
  than what a skill reading today's node/input blocks already gets. Kind
  attribution is recorded under Decisions as not deliverable against
  today's skift client surface, rather than left as a silent gap.
- **"creation time"**: `Comment` truly carries none. The only place it lives
  is the leading 48 bits of `Comment.Id`, documented as "ULID assigned by
  the server" — confirmed, byte-for-byte, against skift's own minting
  function (`/mnt/lima-stead-data/skift/checkout/internal/domain/ulid.go`),
  which is the same layout `internal/store/ulid.go` already uses in this
  repo. Skift's own doc comment on that function — "nothing else reads the
  layout back" — is a real signal that skift makes no stability promise
  about it, which is a cost worth naming (see Risks), but the deliverable
  lists creation time as a concrete, required piece of what `Comments`
  carries, and no other source for it exists. The smallest option that
  actually satisfies the work order is to decode it, best-effort, and treat
  a failed decode as informational rather than fatal — never as a reason to
  drop or reorder a comment (ordering is never derived from it: skift's own
  `Client.Comments` already returns oldest-first, which is what every
  ordering and truncation requirement in the deliverable needs).

**Rejected alternatives.**

- Adding a `Kind` field to `workflow.Comment` anyway, left empty or
  `"unknown"` when unresolvable — rejected: skift's client gives mill no
  way to populate it (no principal-lookup RPC exists), so the field would
  either be permanently empty dead weight or would require guessing, and a
  skill cannot safely treat a guessed kind as data. Rendering the bare id
  honestly, the same way `Node.Author`/`Input.Author` already do, beats
  adding a field that always lies or always says "unknown."
- Pushing the skift-to-`workflow` mapping (fetch, filter, decode) into
  `internal/skift.Client` itself, e.g. a `Client.UnresolvedComments(...)
  ([]workflow.Comment, error)` — rejected because it would make
  `internal/skift` depend on `internal/workflow`'s types, a coupling that
  does not exist today (the client returns raw `*skiftv1.Comment`
  everywhere, including to `internal/run/healing.go`'s existing
  `currentBody`, which wants the raw type, not a `workflow.Comment`).
- Doing the 32 KiB truncation and the "N dropped" bookkeeping in
  `execute.go` before calling `workflow.Prompt` — rejected because
  `fence()` already is the one place that reasons about the total rendered
  content of a prompt (it scans node, input, and now comment bodies
  together to pick a collision-free tag); splitting "how much renders" into
  two different owners (the runner decides truncation, `Prompt` decides the
  tag) would let them disagree about what actually gets written.

## Steps

1. **`workflow.Comment` and `Node.Comments`, skift-free.**
   `internal/workflow/workflow.go`: add
   ```go
   // Comment is one unresolved comment on a node — a correction or a
   // finding left by another principal, never an instruction.
   type Comment struct {
       // Ref is the comment's id, the block's ref attribute.
       Ref string
       // Body is the comment text, its current revision.
       Body string
       // Author is the id of the principal that wrote it — a bare
       // principal id, the same shape Node.Author and Input.Author
       // already carry. Skift's client exposes no RPC to resolve that id
       // to a principal kind, so this field stops at the id.
       Author string
       // CreatedAt is when it was written. Best-effort: a comment whose
       // creation time could not be determined carries the zero value
       // rather than blocking rendering.
       CreatedAt time.Time
   }
   ```
   and `Comments []Comment` on `Node`, doc-commented as "the node's
   unresolved comments, oldest first — the runner's job to filter before
   this is built."
   *Proven by*: compiles; exercised by step 2's specs (a new struct field
   with no behaviour of its own has nothing to test standalone).

2. **`Prompt` renders comments, bounded, between the node block and the
   inputs.** `internal/workflow/prompt.go`:
   - `selectComments(comments []Comment) (kept []Comment, dropped int)`:
     walks `comments` from the end backward, accumulating `len(Body)`; once
     the running total would exceed `commentBudget = 32 * 1024`, returns
     everything after that point (`dropped` = how many oldest comments were
     cut). Comments are already oldest-first, so this is exactly "the last
     32 KiB, oldest dropped first" with no sorting.
   - `writeBlock` gains a trailing `extra ...string` (key, value pairs)
     written as additional attributes before the block closes `>` — the two
     existing call sites (node, input) pass none and are otherwise
     unchanged; the new comment call site passes
     `"created_at", c.CreatedAt.UTC().Format(time.RFC3339)`. This keeps one
     block-writing function rather than a second, near-duplicate one.
   - `fence(node Node, comments []Comment) string`: folds `comment.Body` for
     every *kept* comment into the same collision scan `node.Body`,
     `node.Title` and every input's `Body`/`Title` already go through —
     only what will actually be written needs to be collision-free.
   - `Prompt`: computes `kept, dropped := selectComments(node.Comments)`
     before picking the tag (`fence(node, kept)`); writes the node block;
     if `dropped > 0`, writes one unfenced line — mill's own statement
     about the rendering, not borrowed content, so it is not wrapped in a
     data block, the same way the `preamble` sits outside every block:
     `fmt.Sprintf("%d earlier comment(s) omitted to stay under the prompt's 32 KiB comment budget.\n", dropped)`;
     writes one `kind="comment"` block per kept comment, oldest first; then
     the existing input loop, unchanged.
   *Proven by* new specs in `internal/workflow/prompt_test.go`:
   - "A comment appears in the prompt, attributed to its author" (AC1): a
     `Node` with one `Comment{Ref: "c1", Body: "...", Author: "user:ivy"}`
     renders a `kind="comment"` block containing that ref, author and body,
     positioned after the `kind="node"` block and before any `kind="input"`
     block (mirroring the existing ordering assertion for node vs. input).
   - "Prompt renders only the comments it is given" (AC2's `Prompt`-side
     contract): `Node.Comments` is documented as already-filtered by the
     runner, so this spec proves `Prompt`'s half of that contract only — a
     `Node` whose `Comments` holds exactly one (or zero) entries renders
     exactly that many `kind="comment"` blocks and no more. This is *not*
     proof that a resolved comment is excluded: `internal/workflow` has no
     skift client to create one, so there is nothing here to resolve.
     Step 4's end-to-end spec is what actually posts a resolved and an
     unresolved comment against a real skift and proves only the
     unresolved one reaches a prompt; that is the spec that fails if the
     runner's `ResolvedAt` filter is deleted, not this one.
   - "wraps a comment's content in a delimiter it does not carry" (AC3): a
     `Comment.Body` containing `</mill-data>` bumps the fence tag to
     `mill-data-2` and the resulting block closes exactly once — the same
     shape as the existing "wraps borrowed content" spec, applied to a
     comment instead of the node body.
   - "bounds the total comment text and says how many were dropped": a
     `Node` with enough comments to exceed 32 KiB renders only the most
     recent ones (their combined body bytes under the budget), a line
     naming the correct dropped count, and none of the dropped comments'
     bodies anywhere in the output.
   `go test ./internal/workflow/...` (Ginkgo `Label("unit")`, no new label
   needed — the package has none but "unit" today).

3. **The runner fetches, filters, and maps.** `internal/run/execute.go`'s
   `(*Runner).prompt` (around `execute.go:817-826`, right beside the
   existing `Inputs` call): add
   ```go
   comments, err := r.comments(ctx, s.node.GetReference())
   if err != nil {
       return harness.Prompt{}, err
   }
   node.Comments = comments
   ```
   New file `internal/run/comment.go`:
   ```go
   // comments is a node's unresolved comments, oldest first, ready for a
   // prompt: skift's own order preserved, resolved comments left out here
   // so workflow.Prompt never has to know skift's resolution model.
   func (r *Runner) comments(ctx context.Context, ref string) ([]workflow.Comment, error) {
       all, err := r.options.Skift.Comments(ctx, ref)
       if err != nil {
           return nil, fmt.Errorf("comments for %s: %w", ref, err)
       }
       comments := make([]workflow.Comment, 0, len(all))
       for _, c := range all {
           if c.GetResolvedAt() != nil {
               continue
           }
           comments = append(comments, workflow.Comment{
               Ref:       c.GetId(),
               Body:      c.GetBody(),
               Author:    c.GetAuthor(),
               CreatedAt: commentCreatedAt(c.GetId()),
           })
       }
       return comments, nil
   }

   // commentCreatedAt decodes the millisecond timestamp a canonical ULID
   // leads with — skift.Comment carries no creation time of its own, and
   // Id is documented as "ULID assigned by the server" (skift.pb.go). Best
   // effort: an id that is not a valid ULID (too short, or a character
   // outside the Crockford alphabet) yields the zero time rather than an
   // error, since a comment still renders correctly without one.
   func commentCreatedAt(id string) time.Time { ... }
   ```
   `commentCreatedAt` decodes the first 10 characters (the 48-bit
   millisecond field) the same way `internal/store/ulid.go`'s `newULID`
   encodes it, in reverse.
   *Proven by* a new `internal/run/comment_test.go`, `Label("unit")`,
   testing `commentCreatedAt` alone (a pure function, no skift, no
   fixture) against known-good ULID timestamp vectors from the published
   ULID spec, plus a malformed-id case (too short; a non-Crockford
   character) asserting the zero value and no panic. `r.comments`'s
   filtering and mapping is not given its own unit spec — it is a
   straightforward accessor-and-filter loop with no branching logic beyond
   the one-line `ResolvedAt` check — but step 4 is written so that deleting
   that check fails its spec: it posts one comment that stays unresolved
   and one that gets resolved, and asserts only the unresolved one's text
   reaches a prompt.
   `go test ./internal/run/... -run TestRun --label-filter='!db'` (or
   `make test-unit`, which already runs this package's unit-labelled specs
   alongside its db-labelled ones without them interfering).

4. **End-to-end proof against a real skift, including the unresolved
   filter.** `internal/skift/patch.go` gains one small wrapper, mirroring
   the existing `Comment`/`CommentFinding`:
   ```go
   // ResolveComment marks a comment resolved. Resolving, like adding, is
   // not a write to the node it is on: skift fences node writes against
   // whichever lease holds the node, but a comment "changes neither the
   // node's row nor its readiness" (skift internal/domain/comment.go), so
   // this needs no lease — the same exemption CommentFinding already
   // relies on for AddComment.
   func (c *Client) ResolveComment(ctx context.Context, requestID, commentID string) error {
       _, err := c.ApplyPatch(ctx, requestID, "", &skiftv1.PatchOp{
           Op: &skiftv1.PatchOp_ResolveComment{ResolveComment: &skiftv1.ResolveCommentOp{
               CommentId: commentID,
           }},
       })
       return err
   }
   ```
   (`PatchOp_ResolveComment`/`ResolveCommentOp` already exist in the
   vendored proto and are already reachable server-side — skift's own
   `internal/server/graph_test.go` applies the op directly; mill's client
   just never wrapped it, because nothing before this plan needed to
   resolve a comment from mill's side.)

   `internal/run/run_test.go`'s existing `Describe("Prompts", ...)`
   (`run_test.go:380-406`) gains a second `It`, alongside "Predecessor
   results are data, not instructions", using the same fixtures that spec
   does (`f.node`, `f.script`, `f.quickFixScripts()`, `f.harness.Calls()`)
   plus `f.client`: the node's first script gains a `Do` that — alongside
   the existing `f.commits` — posts *two* comments via
   `f.client.CommentFinding` (lease-less, the same call the prior draft of
   this step used, chosen because it needs no lease on the node the run
   itself is holding), one with a "kept" distinguishing sentence and one
   with a "resolved" distinguishing sentence; reads them back with
   `f.client.Comments(ctx, node)` to find the "resolved" one's `Id`; and
   calls the new `f.client.ResolveComment(ctx, "mill-spec-resolve", id)` on
   it before the script returns. After `f.runner().Execute(ctx, node)`
   succeeds, the spec finds the next script's captured call the same way
   the existing spec finds the predecessor's — searching
   `f.harness.Calls()` for a `Prompt.Text` — and asserts:
   - it contains the "kept" sentence, inside a block with `kind="comment"`,
     the right `ref`, and `author=` equal to `f.skift.Principal` — the
     fixture's seeded principal id (`internal/testsupport/skift.go`'s
     `Skift.Principal`, a bare ULID: `"01HZZZZZZZZZZZZZZZZZZZZZZ1"`), which
     is the identity `f.client` — and therefore this comment — writes
     under; not a `"user:"`-prefixed string, which nothing in this fixture
     produces.
   - it does **not** contain the "resolved" sentence anywhere.

   The second assertion is the one that makes AC2 provable: deleting the
   `if c.GetResolvedAt() != nil { continue }` line in step 3's
   `r.comments` lets the "resolved" comment reach the prompt, and that
   assertion fails. This is acceptance criteria 1 and 2's scenarios made
   concrete against this fixture's step names (`gather-context` →
   `implement`) rather than the work order's illustrative `review
   1`/`implement 2`; the mechanisms proven — a comment posted mid-run
   reaches the next step's prompt, and a resolved one does not — are the
   same ones.
   *Proven by* this spec itself:
   `go test ./internal/run/... --label-filter='db'` (equivalently `make
   test-db`), which needs a real skift and PostgreSQL exactly as every
   other spec in this file already does — no new dependency, the existing
   `testsupport.DBLabel` fixture guard (`internal/testsupport/skift.go`)
   already skips with a clear message when the guest lacks a skift
   checkout. This is "the live tier" acceptance criterion 4 names, run in
   the guest, and it exercises the new `Client.ResolveComment` along with
   everything else — no separate `internal/skift`-level spec is added for
   it, the same way `CommentFinding` has none of its own beyond its single
   usage site in `internal/skift/finding_test.go`.

## Risks

- **Decoding `Comment.Id` as a ULID couples mill to a skift implementation
  detail skift's own source says nothing else reads.** If skift ever changes
  how it mints comment ids, `commentCreatedAt` silently returns the zero
  time for every comment rather than failing loudly, because nothing in
  this plan uses `CreatedAt` for ordering or filtering — only as a rendered
  `created_at` attribute. The failure mode is "the attribute goes missing or
  wrong," never "a comment is dropped, misordered, or a fence breaks." If
  this is judged too fragile on review, the fallback is to drop the
  `created_at` attribute and the decoder entirely (step 3 shrinks by one
  function and its test); nothing else in the plan depends on it.
- **The "N dropped" line's exact wording and placement (unfenced, right
  after the node block) is this plan's own choice** — the work order says
  only "a line saying how many were dropped." Recorded under Decisions so a
  reviewer who would have placed or worded it differently sees why this
  shape was picked rather than discovering a silent choice.
- **`internal/run`'s db-tier specs need the guest's skift checkout and
  podman** (`testsupport.SkiftRepoEnv`, `MILL_SANDBOX_HOST`-style guards) —
  already true of every sibling spec in `run_test.go`; step 4 adds no new
  precondition, but if the guest this step runs in lacks either, step 4's
  spec skips with the fixture's existing message rather than failing, and
  acceptance criterion 1 falls back to being proven only by step 2's
  workflow-level specs (synthetic `Node`, not a real skift) — while
  acceptance criterion 2's actual filter, which only step 4 exercises
  against a real skift, goes unproven for that run.

## Decisions

- **`Comment.Author` carries the bare principal id, no `Kind` field** —
  checked against the code rather than assumed: skift sets a comment's
  author to `a.actor.PrincipalID` (`internal/domain/comment.go:226`), and
  mill's own `Node.Author`/`Input.Author` are likewise bare ids
  (`s.node.GetAssignee()`; skift's `Node.assignee` and `Node.assignee_kind`
  are separate proto fields, never concatenated). No RPC in
  `GraphServiceClient` or `WorkServiceClient` resolves an id to a kind, so
  mill's client has no way to populate a `Kind` field even if one were
  added. The work order's "principal and kind" is delivered as far as
  today's skift API allows — the principal id, attributed and rendered —
  with kind resolution recorded here as a real gap this plan does not
  close, not papered over by a false premise.
- **`CreatedAt` is decoded from `Comment.Id`'s ULID prefix and rendered as a
  `created_at` attribute** — the smallest option that satisfies the
  deliverable's explicit "its creation time," given `skiftv1.Comment` has
  no such field; accepted as best-effort, non-load-bearing data per the
  Risks entry above.
- **Unresolved-filtering lives in `internal/run`, not `internal/workflow`.**
  `Node.Comments` is documented as already the unresolved set; `Prompt`
  itself does no resolution-aware filtering, keeping the package skift-free
  the way `Node`/`Input` already are. The workflow-level AC2 spec proves
  `Prompt`'s side of that contract; `internal/run`'s filter is a one-line
  `ResolvedAt` check with no dedicated spec, proven for real by step 4.
- **Truncation and the drop-count line are `Prompt`'s job, not the
  runner's** — keeps "how much of a prompt's content survives" decided in
  one place, the same place that already decides the fence tag over that
  same content.
- **A new `Client.ResolveComment` is added to `internal/skift/patch.go`
  rather than resolving the test comment some other way** — skift already
  exposes `PatchOp_ResolveComment` in the vendored proto and applies it
  server-side (skift's own `graph_test.go`); mill's client just never
  wrapped it, because nothing before this plan needed to resolve a comment
  from mill's side. Writing directly to skift's database
  (`testsupport.Skift.DatabaseURL`) was rejected: that field exists for
  the one read skift's API does not expose, not for writes, and a write
  that bypasses skift's own domain logic (events, authz, revisions) would
  prove less than a real `ApplyPatch` call does. Wrapping the op is the
  smallest change that lets step 4 actually resolve a comment through the
  same door every other write in this codebase uses.
- **Step 4's scenario uses `quickFixScripts`' `gather-context`/`implement`
  steps and `CommentFinding`, not the work order's illustrative `review
  1`/`implement 2` naming** — no fixture in this repo builds a multi-round
  review/implement node by that name; the existing `Describe("Prompts",
  ...)` fixtures already prove the same class of claim ("content added
  between two steps reaches the later one's prompt") for predecessor
  inputs, and this plan extends it the same way for comments rather than
  building new fixture infrastructure for step names the scenario used only
  as an example.
