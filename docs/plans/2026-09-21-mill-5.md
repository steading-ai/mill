# A run driven from a client host, and a worker that says what it holds

## Approach

The previous version of this plan was wrong on two points a reviewer caught,
both because it treated a client-local config read as if it already answered
a question only the worker's own process can answer:

- `mill status`/`mill doctor`'s existing `claims from:` line is fed by
  `LoadConfig(opts.config)` — the *invoking* host's own file
  (`internal/cli/read.go:189-193`, `internal/cli/doctor.go:174-211`) — never
  the worker's. On a client reaching a worker over a forwarded socket, with
  no local config file, it prints `every project` regardless of what the
  worker actually claims. Nothing today carries the worker's filter over the
  socket (`proto/mill/v1/worker.proto` has only `Probe`, which answers
  sidecar/signing/forge, not the claim filter).
- The `mill run` host-mismatch deliverable was dropped as "an undecided
  design." It is not: the work order's own wording — "either refuses ...
  or asks that worker to run the node" — sanctions either branch, and
  refusal is the cheap one. Leaving it unbuilt was wrong.

Both gaps need the same thing: a way for a client to ask, cheaply, "what
does the worker behind this socket claim from, and what host is it on."
`WorkerService.Probe` already exists for a similar purpose but is the wrong
vehicle to reuse for this — it is expensive by design (it spawns the
harness sidecar and does a live forge credential check on every call,
`internal/server/worker_service.go:51-92`, `internal/doctor/doctor.go`'s
`Sidecar`/`Forge`), which `mill doctor` pays once per manual invocation but
`mill status` and `mill run` cannot pay on every call without changing their
cost and side effects. So this plan adds a second, deliberately cheap
`WorkerService` RPC — `Claims`, echoing the exact phrase the CLI already
prints — that returns only fields the worker's process already holds in
memory: the projects and labels it claims from, and its OS hostname. No
sidecar spawn, no network call, no side effect.

`status`, `doctor` and `run` all call this new RPC through one shared
helper. `status` and `doctor` use it to build the `claims from:` line,
falling back to the local config file only when no worker answers at all —
a bare `serve`, an old server, or `run`'s own default socket, matching the
existing `workerProbe` fallback convention (`internal/cli/doctor.go:344-360`)
but, unlike `workerProbe`, treating *any* failure to reach the worker
(including a real RPC error) the same as "no worker answered": the local
fallback is a legitimate answer to the same question here ("what would a
worker with this configuration claim from"), unlike `workerProbe`'s
sidecar/signing/forge probes, whose local fallback would silently answer a
*different* question. `run` uses the same RPC before it claims anything: if
a worker answers with a hostname that is not this process's own
(`os.Hostname()`), it refuses, naming that host; no worker answering (a bare
`serve`, or none at all — `run` needs no worker mounted to execute) is not a
mismatch, and `run` proceeds exactly as it does today.

Rejected: the `--remote` design (a store-carried "claim on behalf of"
request) — the work order itself only asks for one of the two, refusal is
the smaller change, and nothing in the acceptance criteria or the
deliverable's wording requires the other branch too. Also rejected:
stuffing `projects`/`labels`/`host` onto the existing `ProbeResponse` —
correct on the wire but wrong on cost, since every caller of `status` or
`run` would then pay `Probe`'s sidecar-spawn and forge-credential cost on
every invocation merely to read three cheap fields.

## Steps

1. **Add `WorkerService.Claims` to the proto contract.**
   `proto/mill/v1/worker.proto`: add `rpc Claims(ClaimsRequest) returns
   (ClaimsResponse)` beside `Probe`, with `ClaimsRequest {}` and
   `ClaimsResponse { string host = 1; repeated string projects = 2;
   repeated string labels = 3; }`, each field commented with why it's cheap
   (no probe, no side effect — the worker's own already-resolved
   configuration). Regenerate with `make generate` (`buf generate` +
   `buf generate --template buf.gen.ts.yaml`), which regenerates
   `gen/mill/v1` and `gen/mill/v1/millv1connect` (Go) and the sidecar's
   TypeScript contract.
   *Proof:* `go build ./...` compiles against the regenerated
   `millv1connect.WorkerServiceHandler`, which now requires a `Claims`
   method — this alone forces every existing implementer to be updated
   (step 2), so a missed implementer fails the build rather than silently
   answering `Unimplemented` for a method it was supposed to have.

2. **Implement `Claims` on `WorkerService` and thread `Host`/`Projects`/`Labels`
   into its config.**
   `internal/server/worker_service.go`: add `Host`, `Projects []string`,
   `Labels []string` to `WorkerServiceConfig`; add
   `func (s *WorkerService) Claims(ctx, *connect.Request[millv1.ClaimsRequest])
   (*connect.Response[millv1.ClaimsResponse], error)` returning them
   directly — no probing, no context deadline needed beyond the request's
   own.
   `internal/cli/serve.go` (~line 168-176, the existing
   `server.NewWorkerService(server.WorkerServiceConfig{...})` literal built
   only `if opts.work`): add `Projects: opts.worker.run.projects, Labels:
   opts.worker.run.labels`, and `Host:` resolved once via `os.Hostname()`
   (empty string on error — the client-side check below already treats an
   empty host as "can't tell, don't refuse").
   `internal/server/permissions.go`: add
   `millv1connect.WorkerServiceClaimsProcedure: interceptor.PermissionRead`
   to the read-verbs block beside `WorkerServiceProbeProcedure` (line 33).
   Without this, `Claims` is an RPC "absent from this table" and defaults
   to `PermissionWrite` — reachable only by the service's own uid
   (`permissions.go:18-21,44-51`) — which on the exact deployment AC1
   targets (a client whose uid holds `reader`/`operator`, not the
   service's) makes every call `CodePermissionDenied`
   (`interceptor.go:122-123`). Because `workerClaims` (step 3) treats any
   error as "no worker answered" and falls back to the local config file,
   an unclassified `Claims` would silently reproduce the exact defect this
   plan exists to fix, with nothing failing loudly to say so.
   *Proof:* `internal/server/worker_service_test.go` — new spec
   `"answers Claims from this process's own configuration"`: build the
   handler with `WorkerServiceConfig{Host: "mill-worker.example", Projects:
   []string{"mill"}, Labels: []string{"quick"}}` (mirroring the existing
   `httptest.NewServer(workerMux(...))` pattern at line 24), call `Claims`,
   assert the three fields round-trip exactly. A second spec confirms
   `Claims` is `CodeUnimplemented` on `workerMux(nil)`, mirroring the
   existing Probe spec at line 41.
   `internal/server/permissions_test.go`: add
   `Entry("WorkerService.Claims", millv1connect.WorkerServiceClaimsProcedure)`
   to the `"the read verbs need only read"` table (line 28) — this is the
   test that actually catches a regression to the default `PermissionWrite`,
   which none of step 2's own specs would (they call the handler directly,
   never through the interceptor a `reader`/`operator` uid is subject to).

3. **Add the shared cheap-lookup helper.**
   `internal/cli/doctor.go`, beside `workerProbe` (~line 350): add
   `func workerClaims(ctx context.Context, socket string)
   *millv1.ClaimsResponse` — calls `workerClient(socket).Claims(...)` with
   `doctor.ProbeTimeout`, and returns `nil` on *any* problem (Unimplemented,
   NotFound, dial failure, timeout — deliberately not returning an error,
   unlike `workerProbe`; see Decisions). Doc comment states the asymmetry
   with `workerProbe` and why.
   *Proof:* covered transitively by steps 4-6's specs; no standalone unit
   test for a function with one branch and no exported error path worth
   pinning alone.

4. **Make `status`'s and `doctor`'s `claims from:` line worker-authoritative.**
   `internal/cli/config.go`: extend `claimsFrom(projects []string) string`
   to `claimsFrom(projects, labels []string) string`, appending `, label
   <a>, <b>` only when `labels` is non-empty (empty labels changes nothing,
   so every existing `"...: every project"` / `"...: mill"` assertion still
   holds when the label list is empty).
   `internal/cli/read.go:193`: before printing, call
   `workerClaims(cmd.Context(), opts.socket)`; when non-nil, use its
   `Projects`/`Labels`; else fall back to `config.Projects`/`config.Labels`
   exactly as before.
   `internal/cli/doctor.go:211`: the same substitution, reusing the
   `worker, workerErr := workerProbe(...)` call already made at line 239 is
   *not* an option (wrong RPC, wrong cost profile already paid or not); add
   a second, independent `workerClaims(ctx, opts.socket)` call beside it —
   doctor already makes several RPC round trips (`Health`, `Ready`,
   `GetWorkflow` per workflow directory), so one more cheap one is
   consistent with its existing shape.
   *Proof:* extend the existing `"prints what the worker claims from,
   reading the same configuration a worker would"` specs in
   `internal/cli/read_test.go` (~line 91) and `internal/cli/doctor_test.go`
   (~line 109) with a third `By` block: start a `serve --work` process
   (the pattern in `internal/cli/serve_test.go`'s
   `"answers WorkerService.Probe..."` spec, ~line 151) configured with
   `--project mill --label quick`, then run `status`/`doctor` against
   *that* socket with a *local* `--config` naming a **different** project —
   e.g. `project: [not-this-one]` — and assert the printed line names
   `mill` and `quick`, not `not-this-one`. This is the literal reproduction
   of the reviewer's finding, and it only passes once the line is
   worker-sourced.

5. **Refuse `mill run` when the worker behind the socket is elsewhere.**
   `internal/cli/run.go`, in `execute` (line 394), before `newRunner` is
   built: call a new pure function `refusalForHost(claims
   *millv1.ClaimsResponse, localHost string) error` — nil when `claims` is
   nil, `claims.GetHost()` is empty, or it equals `localHost`; otherwise an
   error naming both hosts and telling the caller to run there instead
   (`"mill run: the worker behind %s runs on %s, not %s; run mill run there,
   or drive %s through mill work"`). `execute` itself calls
   `os.Hostname()` (ignoring an error the same way — can't tell, don't
   refuse) and `workerClaims(cmd.Context(), opts.socket)`, and returns
   `refusalForHost`'s result if non-nil before doing anything else.
   *Proof:*
   - `internal/cli/run_internal_test.go` (new or existing internal test
     file — check first): table test of `refusalForHost` alone — nil
     claims, empty host, matching host, mismatched host — no socket, no
     process, pure function.
   - `internal/cli/run_test.go`: a new spec proving the unaffected case —
     `serve --work` and `mill run` against the same socket, both in the
     same test process (so their `os.Hostname()` is necessarily identical,
     the shape every existing `run` test already has, just now with a
     worker mounted too) — a real run still executes to completion. This
     is the regression proof that the refusal check does not break the
     documented, intended "operator on the worker's own host runs `mill
     run` directly" case.
   No test exercises a genuine cross-host mismatch end-to-end — reaching a
   real second hostname from this suite would need a container or a second
   machine, out of proportion here — but `refusalForHost`'s table test
   pins the exact decision the end-to-end case depends on, and step 2's
   `WorkerServiceConfig.Host` plumbing is independently proven.

6. **Update `docs/tools.md`.**
   - The `"run" is not among them` paragraph (line 15-18): add one sentence
     — `mill run` now refuses, naming the worker's host, when the socket it
     is given belongs to a worker elsewhere; it needs no worker mounted at
     all to run locally.
   - §status's `claims from` paragraph and example (lines 81-90): change
     "`project` in the configuration file... read for this line alone" to
     say the line asks the worker behind the socket first — its own
     `project`/`label` filter — and falls back to the configuration file
     only when no worker answers; add a one-line example showing a `label`
     entry.
   - §doctor's equivalent paragraph and example (lines 516-524): the same
     correction.
   - `proto/mill/v1/worker.proto`'s top-of-file service comment: extend
     "`mill doctor` calls it first for the three probes..." to also name
     `Claims` and what calls it (`status`, `doctor`, `run`).
   *Proof:* read-through; prose must not contradict the exact strings
   asserted in steps 4-5's tests.

Each step leaves `go build ./...` green; steps 1+2 land together (a
half-applied proto-without-implementation does not compile, since
`millv1connect.WorkerServiceHandler` gains a required method), and every
step after keeps the full existing suite passing before adding its own
spec.

## Risks

- **`make generate` needs `buf` and the node toolchain for the TypeScript
  half** (`buf.gen.ts.yaml`, per the `Makefile`'s `generate` target). If
  either is missing in the execution environment, generation fails loudly
  before any Go code is written by hand — the fallback is to hand-write the
  new generated Go types matching `protoc-gen-go`/`protoc-gen-connect-go`'s
  existing output shape for `ProbeRequest`/`ProbeResponse` as a template,
  and skip the TypeScript regeneration only if nothing in `sidecar/` reads
  `WorkerService` types (check `sidecar/src` for an import before assuming
  this is safe to skip).
- **`workerClaims` swallowing every error, including genuine ones, is a
  real behavior choice, not an oversight** — a socket that is reachable but
  answering garbage looks identical to "no worker" and silently falls back
  to the local file. Mitigated by `doctor`'s own `socket`/`schema` probes
  already surfacing a dead or misbehaving socket loudly elsewhere in the
  same output, so the claims line's silence is never the only signal.
- **Comparing hostnames, not the configured `--identity`, for the run
  refusal** — a deployment could theoretically run two identically-named
  hosts (containers sharing a hostname) and evade the check, or rename a
  single host and trip it needlessly. Accepted: `os.Hostname()` is the
  literal "host" the deliverable's wording asks to be named, and identity
  is a signing label already documented as configurable independent of
  where the process runs, so comparing it would produce false positives
  for legitimate same-host deployments that set a custom `--identity`.
- **No live cross-host integration test** (noted in step 5) — the risk is
  that `refusalForHost`'s wiring into `execute` has a bug the table test of
  the pure function can't catch (e.g., the hostname or claims call never
  actually reached). Mitigated by the same-host regression spec in step 5,
  which fails loudly if the new call panics, blocks, or misfires against a
  real running worker, even though it can't prove the mismatch branch
  end-to-end.

## Decisions

- **`Claims` is a new RPC, not new fields on `Probe`.** `Probe` is
  documented and implemented as expensive by nature (sidecar spawn, forge
  credential check); adding cheap fields to it would force every caller
  needing only those fields to pay for the expensive ones too. A second RPC
  keeps the cost of `status`/`run` calling it on every invocation at zero
  meaningful overhead.
- **`workerClaims` never returns an error; `workerProbe` still does.** The
  local-config fallback for "what does this worker claim from" is a
  coherent answer to the same question regardless of why the worker didn't
  answer; `workerProbe`'s local fallbacks (sidecar/signing/forge on *this*
  host) answer a different question than the remote worker's, which is why
  it preserves and surfaces real errors. Documented at the point of
  asymmetry so a future reader doesn't "fix" it into matching `workerProbe`.
- **Refusal, not `--remote`.** Per the work order's own wording sanctioning
  either, and per the reviewer's direction that refusal is the cheap one.
  `--remote`'s store-carried "claim on behalf of" request is left for a
  future node if anyone wants it.
- **Host comparison via `os.Hostname()`, not `--identity`.** See Risks.
- **A refusal is fatal, not a warning** — `mill run` stops before claiming
  anything (no lease taken, nothing partially started), matching the
  deliverable's "refuses" wording exactly rather than a soft warning a
  script could miss.
